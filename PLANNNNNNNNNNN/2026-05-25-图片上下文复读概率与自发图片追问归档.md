# 图片上下文复读、图片概率异常与 Bot 自发图片追问待审核方案

## 状态（2026-05-25）

- Phase 1 / 2 / 3 / 4 / 6 已落地。
- Phase 5 已按"结构信号 + 分层 prompt + 窄守卫"重写并落地（见下方 5.x 子节）；移除了原方案里的 `认错/技术发展/游戏截图` 等关键词正则路径。

## 背景

2026-05-24 现场出现三类相关问题：

1. Bot 对连续图片和纠错追问持续围绕同一个对象说话，例如反复沿用“某角色拿剑、红披风、很帅”的句式。严格说不是重复发送同一句，而是话题黏连和表达模板坍缩。
2. Bot 自己发送图片后，后续用户用“？”追问时，Bot 没有把自己刚发的图片当作可识别对象，只按旧文本和人格猜测回复，导致出戏。
3. 纯图片消息的回复概率看起来过高，尤其白名单群里图片几乎被当成“可直接识图回复”的入口，和普通随机回复日志显示的 candidate / cooldown / skip 状态不一致。
4. 重复回复守卫触发后，会抽取一批很早期的硬编码攻击/梗式兜底句，例如“求求你别发了”这类 OOC 文案。它本来是重复失败后的最后兜底，但在图片概率异常和语义黏连时会被更频繁触发，直接出戏。
5. 短句承接会错接旧图片主题。现场用户在讨论“游戏截图基本就别想了 / 等着技术发展吧”，Bot 却把几分钟前三轮车广告图重新捞回来，说成“广告本身就已经很技术”，说明 active scene 把旧媒体背景错当成当前发言对象。

本方案只描述本地代码修复计划，不包含部署、重启或推送授权。

## 现场证据摘要

### 1. 图片分析缓存被人格回复污染

线上 `image-history` 中，部分图片的 `analysis` 不是客观描述，而是最终聊天式回复，例如：

- 带人格口癖、称呼和提问。
- 引用前文纠错后的对象继续夸。
- 个别记录带有 `</think>` 残片。

这说明图片历史缓存已经不是“图片事实索引”，而变成了“上一轮聊天回复索引”。后续 `read_image_history`、active scene、conversation 占位替换都会把这些污染内容继续注入 prompt。

关键代码点：

- [chat.js](../packages/koishi-plugin-dongxuelian-ai/lib/chat.js) 当前会在 `wasVisionRequest` 成功后，把最终自然回复 `finalReply` 写入 `image-store.markAnalyzed()`。
- [image-analyzer.js](../packages/koishi-plugin-dongxuelian-ai/lib/image-analyzer.js) 后台分析要求“50字以内描述”，但缺少输出净化，模型仍可能返回人格式回复或 thinking 残片。
- [image-store.js](../packages/koishi-plugin-dongxuelian-ai/lib/image-store.js) 会把 `analysis` 回填到 conversation，占位符从 `[图片]` 变成 `[图片]: xxx`，污染随即进入普通聊天历史。

### 2. Active scene 对旧媒体话题过度保温

[group-scene-index.js](../packages/koishi-plugin-dongxuelian-ai/lib/group-scene-index.js) 里 `mediaLinked` 会让 10 分钟内带图片的旧片段更容易留在 active scene。连续图片、短句、纠错混在一起时，模型容易把新图和旧图放进同一个现场，尤其当前消息只有 `[图片]` 或“这是谁/？”这类短句时。

现象是：用户已经发了新图，模型仍继续承接上一张图的角色或描述。

### 3. 图片消息绕过了普通随机回复门控

[index.js](../packages/koishi-plugin-dongxuelian-ai/lib/index.js) 中非点名、非私聊时，如果消息有图片/文件/嵌入，会进入一个独立分支：

- 前面 `isRandomCandidate` 因 `shouldSkipForRandomReply` 可能为 false。
- 日志里 `reply-timing` 显示 `decision=silent`、`blockers=content_skipped_for_random`。
- 但后面图片分支又单独执行 `shouldTriggerRandom(getRandomTriggerRate(channelKey))`，命中后直接 `prepareVisionRequest()` 并进入聊天。

因此图片概率没有统一走同一个随机决策结果。白名单群如果主动回复概率被设为 100%，纯图片会非常容易触发回复；即使日志显示普通随机没触发，也可能被图片分支再次抽中。

### 4. Bot 自己发送的图片没有进入图片锚点系统

[reply.js](../packages/koishi-plugin-dongxuelian-ai/lib/reply.js) 里文本气泡会调用 `saveSharedChannelTurn()` 记录 assistant 文本。但 `[图:xxx]` 触发的贴图/图片发送只做发送和冷却，没有：

- 写入 `image-history`。
- 写入 `channelSharedCache` 的 assistant image anchor。
- 保存发送得到的图片消息 ID 与本地图片文件的映射。
- 支持后续用户引用、追问“？”、“这个图”等。

所以用户问 bot 刚发的图时，系统没有可靠图片对象，只能靠附近文字猜。

### 5. 重复回复兜底仍保留旧硬编码梗句

[constants.js](../packages/koishi-plugin-dongxuelian-ai/lib/constants.js) 里 `REPEATED_FALLBACK_REPLIES` 保存了一组早期硬编码句子，其中包含明显不符合当前人格和场景的攻击/梗式文案。[reply-guard.js](../packages/koishi-plugin-dongxuelian-ai/lib/reply-guard.js) 的 `pickRepeatedFallbackReply()` 会在模型重试后仍被判定重复或命中禁词时，从这组句子里挑一条发出。

现场表现是：用户只发了一张图片，Bot 立刻回复旧梗兜底。严格看这不是识图回复，而是“图片触发概率异常 -> 聊天/守卫链路进入重复失败兜底 -> 硬编码旧文案外泄”。

这类文案的问题：

- 不依赖当前人格、上下文和语气设置。
- 无法解释自己为什么这么说，也不能承接图片内容。
- 一旦随机图片回复过频或模型输出重复，就会把内部兜底当成群聊自然回复发出去。
- 属于“硬编码替代模型表达”的旧设计，和当前 agent 目标冲突。

### 6. 短句承接把旧图片背景当成当前话题

现场片段：

- Bot 先把游戏截图/角色图认错。
- 用户点名说“又认错人了”。
- 另一位用户说“游戏截图基本就别想了”。
- 用户接着说“等着技术发展吧”。
- Bot 回复“这广告本身就已经很技术了呀”，并继续描述更早那张三轮车广告图。

这说明当前热窗口没有正确区分“正在讨论识图能力/游戏截图识别”与“旧图片事实背景”。[group-scene-index.js](../packages/koishi-plugin-dongxuelian-ai/lib/group-scene-index.js) 当前在短句时会触发 `fallbackNeeded`，active 太少就回捞最近 8 条；同时 `mediaLinked` 会让旧图片内容在 10 分钟内更容易进入 active scene。短句本身语义弱，模型看到旧广告图分析后，就把“技术发展”错接成“广告技术”。

这个问题和图片分析污染是叠加关系：

- 如果旧图片 `analysis` 是聊天式回复，模型更容易把它当成可继续聊的话题。
- 如果短句没有明确引用链，旧媒体背景不应该自动升级成当前对象。
- 用户刚刚在纠正识图错误时，系统应该降低旧图事实权重，而不是继续让模型自由捞旧图。

## 修复目标

1. 图片历史里的 `analysis` 必须是客观、短、去人格化、去 thinking 的图片事实描述。
2. 当前图片回复和后台图片索引分离：自然聊天回复不能直接作为图片分析缓存。
3. 新图优先级高于旧图；短句追问必须优先锚定最近相关图片，而不是旧媒体话题。
4. 图片消息回复概率只走一套统一门控，日志与实际行为一致。
5. Bot 自己发送的图片也能被记录、追问和引用，但不泄露本地真实路径。
6. 删除旧硬编码重复兜底文案；重复/禁词/泄漏场景应该优先重试、人格化动态兜底或静默，不再发送固定梗句。
7. 短句承接必须优先接当前对话行为和最近显式纠错，不得把旧图片背景自动当成当前话题对象。
8. `analysis` 为空不等于图片从上下文消失：图片锚点、发送者、时间、消息 ID、当前/旧背景分层必须保留，避免群友后续追问时割裂。

## 方案

### Phase 1：拆分“图片事实分析”和“自然聊天回复”

新增或扩展图片分析净化函数：

- `sanitizeImageAnalysis(text)`：
  - 移除 thinking 残片、内部格式、`呀吼` 等强人格口癖。
  - 移除“指挥官觉得怎么样”“要不要一起讨论”等互动尾巴。
  - 长度限制 120 字以内。
  - 如果命中“我看不到图/无法识别/请重发”，不写入 `analysis`。
- `looksLikePersonaImageReply(text)`：
  - 检测明显自然聊天回复，不允许作为图片事实缓存。

调整 [chat.js](../packages/koishi-plugin-dongxuelian-ai/lib/chat.js)：

- 不再把 `finalReply` 直接写入 `markAnalyzed()`。
- 当前图片如果已经通过视觉模型读到内容，应写入单独的 `visionFactSummary`，而不是最终回复。
- 如果当前路径暂时拿不到事实摘要，就不写 `analysis`，但必须保存图片锚点和状态，不允许把图片从公共上下文里抹掉。
- 对话上下文里仍保留轻量占位，例如 `[图片: 待分析/看不清/分析不可用]`，并带安全锚点信息；只有客观事实摘要缺席，锚点本身不能缺席。

调整 [image-analyzer.js](../packages/koishi-plugin-dongxuelian-ai/lib/image-analyzer.js)：

- 后台分析结果必须经过 `sanitizeImageAnalysis()` 后才 `markAnalyzed()`。
- prompt 改为更硬的事实抽取：“只描述图中可见内容，不要称呼用户，不要续聊，不要评价好不好玩，不要输出角色扮演语气。”

### Phase 2：重建图片锚点选择规则

扩展 `image-store` entry：

- `sourceRole`: `user | assistant`
- `messageId`
- `conversationKey`
- `userId`
- `sentByBot`
- `analysisStatus`: `pending | analyzed | failed | unavailable`
- `analysisKind`: `objective`

调整 active scene：

- 当前消息含图片时，active note 明确写入“当前消息包含新图片，优先看当前图，不要复用旧图描述”。
- 当前消息是短句但上一两轮是“认错/纠错/能力边界讨论”时，active note 应明确当前话题是“识图是否可靠/刚才是否认错”，旧图片只作为背景证据，不可直接续聊旧图内容。
- 短句如“这是谁/这是什么/？”时，优先选择最近一条可追问图片锚点：
  - 当前消息图片。
  - 被引用图片。
  - 最近 2 分钟内同一用户或 bot 自己发送的图片。
  - 再退到群内最近图片。
- 旧图片 analysis 只作为候选事实，不作为当前图事实。
- 图片锚点与图片事实摘要分离：
  - 锚点负责回答“刚才/这张/你发的图”到底指向哪条消息。
  - `analysis` 只负责回答“图里客观看到了什么”。
  - `analysis` 缺失时，模型可以知道“有一张图”，但不能假装知道图里内容。
- 对 `fallbackNeeded` 回捞的旧条目加分层标签：
  - `current_turn`: 当前消息和被引用链。
  - `hot_context`: 近几轮真实承接话题。
  - `old_background`: 为理解关系保留，不得主动当作回复对象。
- 当短句没有引用词、没有“这张/上面/刚才那个图”等媒体指示时，旧图片 `analysis` 只能作为背景，不允许模型把它作为当前主语。
- 如果短句包含“技术发展/现在识别不了/游戏截图别想了/又认错”这类纠错或能力边界语义，应优先回答能力边界，不要跳回图片内容。

### Phase 3：统一图片回复概率门控

修复 [index.js](../packages/koishi-plugin-dongxuelian-ai/lib/index.js) 的图片分支：

- 图片、文件、嵌入消息不再二次抽 `shouldTriggerRandom(getRandomTriggerRate(channelKey))`。
- 统一产生一个 `mediaReplyDecision`：
  - 点名/私聊/引用 bot：明确交互，允许识图。
  - 非点名群聊图片：必须走随机候选逻辑，且 respect cooldown、mute、白名单、概率、延迟和 stale 检查。
  - `shouldSkipForRandomReply` 只表示不适合普通文本随机，不应该导致后续日志和行为分裂。
- 日志补充：
  - `mediaCandidate`
  - `mediaTriggered`
  - `mediaReason`
  - `mediaBlockedBy`

同时修正随机冷却：

- 当前图片分支回复成功后，也必须更新 `lastRandomReplyTs`。
- 图片回复被 stale 跳过时，不应继续启动另一条并行 chat。

### Phase 4：记录 Bot 自己发送的图片

在 [reply.js](../packages/koishi-plugin-dongxuelian-ai/lib/reply.js) 的贴图发送成功后：

- 从 `sendStickerImage()` 返回消息 ID 或发送成功元数据。
- 新增 `storeAssistantImageAnchor()`：
  - 写入 `image-history`，`sourceRole='assistant'`，`sentByBot=true`。
  - 保存安全文件名或内部 sticker key，不保存真实本地路径。
  - 写入 `channelSharedCache`：`[图片: bot发送的表情/图片]`。
- 若平台拿不到 messageId，生成安全临时 id：`assistant-image-<timestamp>-<hash>`。

后续用户追问“？”、“这啥”、“这个表情”、“你发的图”时：

- active scene 能看到 bot 自己上一条图片锚点。
- 如果图片文件仍在本地 sticker 目录，可通过安全内部路径读取分析。
- 如果只是 QQ 返回的 file URL，则走现有 `callGetImage` 或缓存。

### Phase 5：分层注入 + 旧背景媒体粘连守卫

原 Phase 5 设计依赖关键词正则识别"识图能力讨论/复读/技术发展"等场景，违反 free-routing-primary 原则（功能实现以自由路由为主，禁止靠硬编码关键词保证主路径），且无法兼容多样化的真实表达。

替换为**结构信号 + 分层 prompt + 窄守卫**三层设计，不引入任何关键词正则：

#### 5.1 结构化分层（[group-scene-index.js](../packages/koishi-plugin-dongxuelian-ai/lib/group-scene-index.js) `classifySceneItemsForActive`）

把 active scene 里的条目按结构信号分到三层，仅依赖 `messageId` / `replyToId` / `ts` / `userId` / `role`，不读文本：

- `current_turn`：当前消息、被引用消息、被引用消息沿 reply chain 上溯 ≤3 跳的条目，以及 90 秒内同一用户或 bot 自己发的消息。
- `hot_context`：3 分钟热窗口内、不在 current_turn 的剩余条目。
- `old_background`：3-10 分钟内的剩余条目，仅作背景。

> 注意：`mediaLinked` 行为**保留**——10 分钟内的旧媒体仍会进入 active 列表作为锚点。删除它会导致"旧媒体不可追问"的退化。问题不是媒体被拉进来，而是模型不懂得分层。

#### 5.2 分层 prompt 注入（`buildActiveGroupSceneNote`）

active scene note 输出三段标签：

```
--- 当前焦点 current_turn ---
... 这一轮直接相关的消息（含焦点媒体）
--- 近期热议 hot_context ---
... 3 分钟内其它消息
--- 旧背景 old_background（仅供理解关系，不要主动续聊） ---
... 3-10 分钟内的旧消息（含旧媒体）
```

并在前置说明里按结构条件追加提示：

- 只有 `current_turn` 含媒体时才出现 `[当前焦点媒体]` 提示，可作为回答主语。
- 只有 `old_background` / `hot_context` 含媒体且 `current_turn` 不含媒体时才出现 `[旧背景媒体] 仅作环境理解` 提示。
- 若旧背景媒体里有 assistant 自发图（`role==='assistant' && hasSceneMedia`），追加"如果群友正在讨论这些识图是否准确，请如实承认能力边界或重新识图，不要回到旧识图结论里继续夸/继续描述"。
- 短句承接 + 旧背景有图但无当前焦点媒体时，追加"宁可不接或自然澄清，不要凭旧描述续聊"。

整段提示由结构判定（媒体所在层、role、是否短句、是否引用链命中），**不靠 `认错/技术发展/游戏截图` 这类关键词正则**。

#### 5.3 旧背景媒体粘连窄守卫（[reply-guard.js](../packages/koishi-plugin-dongxuelian-ai/lib/reply-guard.js) `detectOldMediaTopicSticking`）

只在以下结构条件**全部成立**时触发一次重试：

1. `current_turn` 不含媒体（这一轮没有新图）。
2. `hot_context + old_background` 含媒体（旧媒体存在）。
3. 用户当前消息**没有媒体指代词**（`这张/这图/图里/图片/上面/刚才/刚刚/那个/这个/表情/文件/语音/转发`）—— 这些是结构性的语言指代信号而非话题关键词，等同于"用户没指向旧媒体"的判定。
4. 回复文本提取出的中文 token（≥3 字）/英数 token（≥4 字）里，存在至少 1 个 token **同时**：在旧媒体条目内容里出现 + 不在 current_turn 内容里出现。

满足时执行：

- 第一次：插一条系统提示 `buildOldMediaStickingRetryPrompt()`，让模型重写。提示明确"本轮没有当前焦点媒体，用户也没有指代旧媒体；想表达情绪不要把旧图对象拉回来；看不清就老实说看不清"。
- 重试一次失败：**放行原回复**，不进 `pickRepeatedFallbackReply`。理由：（a）守卫是"宁可错放不要错杀"，（b）静态兜底句反而更出戏。

调用点：[chat.js](../packages/koishi-plugin-dongxuelian-ai/lib/chat.js) 重试循环内，在 `shouldRetryRepeatedReply` 通过后、break 前。一次会话最多用一次，避免与已有 repeat retry 互相打架。

#### 5.4 不再保留的旧机制

- 删除 `buildActiveGroupSceneNote` 里的 `visionCorrectionFocus` 关键词正则（`认错|看错|识别|游戏截图|截图|看不出来|别想了|技术发展|复读|同一句|同一件事`）。
- 不引入"topic fingerprint / 角色名抽取"等会塌缩为关键词词典的方案。
- 不引入"focus = vision_correction | image_followup | ambient_chat"枚举（同样塌缩为关键词分类）。

#### 5.5 例子

时间线：T0 三轮车广告图 → T1 游戏角色截图 → T2 用户A："又认错人了" → T3 用户B："游戏截图基本就别想了" → T4 用户C："等着技术发展吧"。

- T4 时刻，`current_turn` = [T2/T3/T4 三句话]（90 秒内）；`hot_context` = [T1 游戏图]；`old_background` = [T0 广告图]。
- `current_turn` 不含媒体，`old_background` 有媒体（广告图），用户 C 的消息无媒体指代词。
- 若模型回复"这广告本身就已经很技术了"，token 里命中"广告"——`广告` 在 T0 的 `analysis` 里出现、不在 current_turn 文本里——守卫触发，重试一次。
- 重试后模型大概率改写为"识图这块确实还不太行 / 这种类型可能识不太出"等，与当前焦点对齐。
- 重试仍失败也只是发原回复，不会发"求求你别发了"这类静态梗句。

#### 5.6 验证标准

- 单测：构造 current_turn 空 + old_background 含媒体 + 回复包含旧媒体词，断言守卫返回 true；任一条件不成立时返回 false。
- 场景测：复现 T0-T4 时间线，断言重试至少触发一次；重试失败时不进 `REPEATED_FALLBACK_REPLIES`。

### Phase 6：移除旧硬编码重复兜底回复

调整 [constants.js](../packages/koishi-plugin-dongxuelian-ai/lib/constants.js) 与 [reply-guard.js](../packages/koishi-plugin-dongxuelian-ai/lib/reply-guard.js)：

- 删除或停用 `REPEATED_FALLBACK_REPLIES` 里所有固定攻击/梗式句子。
- `pickRepeatedFallbackReply()` 不再直接从固定句池抽取自然语言回复。
- 重复守卫的处理顺序改为：
  - 第一次：带 `buildRepeatRetryPrompt()` 让模型换角度重写。
  - 第二次：调用 `generatePersonaFallbackReply()`，基于当前人格、用户输入和失败原因生成短回复。
  - 仍失败：优先返回空串或极短中性句，例如“不接这句了。”，并按随机/点名场景决定是否发送。
- 对随机主动回复尤其严格：如果随机回复连续重复、泄漏内部格式、命中禁词或只剩兜底，不发送比硬发更合适。
- 对点名/私聊保留最小可见反馈，但必须由当前人格模板生成，不能再使用固定旧梗。

需要同步检查：

- `chat.js` 中 `pickRepeatedFallbackReply(session)` 的调用点，区分随机主动、普通点名、反击模式和禁词重试失败。
- `ABUSIVE_FALLBACK_REPLIES`、`JAILBREAK_FALLBACK_REPLIES` 是否也存在类似 OOC 固定句；本轮重点是重复兜底，但实现时可以先标注后续清理项。
- 测试里不要断言固定兜底原句，只断言“不泄漏旧硬编码句池、不重复、不输出内部格式”。

## 测试计划

### 场景测试

1. **当前图不写人格回复进 image-history**
   - 输入：用户发图片，模型自然回复“呀吼～这图好可爱，要不要一起聊？”
   - 断言：`image-history.analysis` 不包含称呼、续聊问题、人格口癖。

2. **连续新图不复用旧图描述**
   - 输入：图 A 分析为角色拿剑；随后图 B 分析为建筑/广告。
   - 断言：图 B 回复不包含图 A 的角色、拿剑、红披风等关键词。

3. **用户纠错后不继续同一句式**
   - 输入：Bot 误认图片，用户纠正，再发新图或追问“复读几遍了”。
   - 断言：回复承认黏连并停止继续夸同一对象。

4. **非点名纯图片按统一概率**
   - 设置白名单群概率 0。
   - 输入：纯图片。
   - 断言：不调用模型、不发送回复。
   - 设置白名单群概率 1。
   - 输入：纯图片。
   - 断言：只触发一次，冷却期内第二张不触发。

5. **Bot 自己发图后用户追问**
   - 输入：Bot 回复文本并发送贴图，用户发“？”并点名。
   - 断言：active scene 包含 assistant image anchor，回复围绕刚发图片，不按旧文字猜。

6. **图片 stale 检查**
   - 输入：触发图片识别后，期间有新消息推进 channel version。
   - 断言：旧图片回复不补发。

7. **旧硬编码重复兜底不再外泄**
   - 输入：构造模型连续返回重复回复，触发 `shouldRetryRepeatedReply()` 多次失败。
   - 断言：不会发送 `REPEATED_FALLBACK_REPLIES` 里的旧句子；随机主动场景允许静默；点名/私聊只返回人格化动态兜底或极短中性反馈。

8. **短句不把旧图片错接成当前话题**
   - 输入：图 A 是广告，随后图 B 是游戏截图；Bot 认错图 B，用户说“又认错人了”，另一人说“游戏截图基本就别想了”，用户说“等着技术发展吧”。
   - 断言：回复围绕识图能力或刚才认错，不包含图 A 的广告、三轮车、服务等关键词。

## 风险与边界

- 不把真实本地图片路径写入可提交文件或长期索引。
- 不在日志/计划中复述真实服务器地址。
- 自发图片只保存安全 key、文件名 hash、messageId、分析状态，不保存 `file://` 原路径。
- 图片分析失败时宁可不写缓存，也不要把聊天回复当事实。
- 但不能因为不写 `analysis` 就丢失公共图片感知；缺事实摘要时仍要留下可追问锚点和状态，让后续明确追问可以重新分析或说明看不清。
- 随机图片回复改门控后，白名单群体感会变安静，需要通过配置确认期望概率。
- 重复守卫不应该靠固定梗句“看起来有反应”；随机主动回复在守卫失败时可以选择不发，避免把兜底文案当自然聊天。
- 降低旧媒体权重不能让真正的“刚才那张图/这个图/上面那个”追问失效，所以必须依赖引用链、显式指示词、时间窗和发送者关系，而不是简单禁止读取旧图。

## 建议执行顺序

1. 先修图片 analysis 污染，防止继续扩大错误缓存。
2. 再修图片概率统一门控，减少无意义识图触发。
3. 接着补 bot 自发图片锚点，解决“？”追问。
4. 同步删除旧硬编码重复兜底，避免修概率前后继续 OOC。
5. 补 active scene 分层和短句错接守卫，避免“技术发展”跳回旧广告。
6. 最后补 topic sticky guard，兜住连续场景的同对象同句式问题。
