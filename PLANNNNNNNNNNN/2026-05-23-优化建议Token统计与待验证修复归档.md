### L1-1 Agent 文件材料转述坏路会裸发内部文件包裹

真实性：真实存在，可本地隔离复现。

证据：
- `file-analyzer.js` 会把解析后的文件正文包装为内部工具材料：`[用户上传文件: ...]\n---文件内容开始---\n...\n---文件内容结束---`。
- 硬编码“读文件”路径已经会用 `summarizeFileContentForChat()` 转成自然摘要，但 Agent 结果转述路径依赖 `chat(..., { isAgentResult: true })` 的输出守卫。
- 当前 `reply-guard.js` 的 `hasInternalContextLeak()` 只识别 `<user>`、`昵称：`、`发言：`、`[群聊刷到]` 等内部上下文标记，没有识别文件工具包裹。
- 隔离复现：给 `chat()` 的 Agent 转述模式传入文件工具材料，并 mock 转述模型首轮直接返回同一段 `[用户上传文件: plan.txt] ---文件内容开始--- line A line B ---文件内容结束---`；最终 `chat()` 返回该包裹文本，模型调用次数为 1，没有触发重试或人格兜底。

影响：
- 用户追问文件内容时，如果 Agent/模型没有自然总结而是照抄工具结果，QQ 里会出现内部工具包裹，观感像调试输出。
- 这绕过了上一轮“硬编码读文件不直发工具包裹”的修复，只发生在 Agent 结果转述坏路，因此普通 happy path 测试不一定能发现。
- 文件内容本身可能较长，裸包裹还可能和回复分段、上下文保存叠加，让后续聊天记录里混入内部工具格式。

建议修复：
- 把文件工具包裹视为内部上下文泄漏：`hasInternalContextLeak()` 应识别 `[用户上传文件:`、`---文件内容开始---`、`---文件内容结束---`。
- Agent 转述首轮出现该包裹时，按现有人格化纠偏链路重试；重试仍失败时走当前人格兜底，不直接发送包裹。
- 补 scenario：Agent 结果转述模式中，模型首轮照抄文件工具包裹，断言会二次调用模型，最终回复不包含 `[用户上传文件:` 或 `---文件内容开始---`，并能发送自然摘要。

验证方式：
- 修复前隔离复现返回文件包裹且 `calls=1`；修复后应触发重试，返回自然文本。
- 跑文件场景和 chat 场景，确认普通“读文件”兜底、文件追问 happy path 仍通过。

修复状态：已修复。

修复实现：
- `reply-guard.js` 的 `hasInternalContextLeak()` 已把 `[用户上传文件:`、`---文件内容开始---`、`---文件内容结束---` 纳入内部上下文泄漏判定。
- `chat.test.js` 新增 `Agent retell file wrapper leak retries` 场景，模拟 Agent 转述首轮照抄文件工具包裹，断言会重试并最终发送自然摘要，不泄漏包裹标记。

验证结果：
- 修复前隔离复现：`reply` 为文件包裹、`calls=1`、`leaks=true`。
- 修复后隔离复现：`reply="clean file summary"`、`calls=2`、`leaks=false`。
- `npm run check`：通过，语法检查 173 个生产 JS 文件。
- `npm run test:quick`：通过，`passed: 2082, failed: 0, skipped: 1`。
- `npm run test:scenario -- --grep "Agent retell file wrapper"`：实际运行完整 scenario，通过，`passed: 753, failed: 0, skipped: 2`。

### L4-1 单插件 AI 部署脚本会覆盖运行 data 里的可编辑 `ai-skills`

真实性：真实存在，可用服务器 Linux 最小复现确认。

修复状态（本轮）：代码已修，本地验证通过，待部署与线上验证。`deploy-package.sh --copy-ai-skills` 已改为只创建目录并复制缺失文件，不再覆盖已有运行 data；本地 quick/full 测试已断言部署 helper 不再覆盖运行 `ai-skills`，但当前 Windows 环境没有 `bash`，shell 语法仍需在 Linux/Git Bash/服务器环境补验。

证据：
- `scripts/ai.sh` 调用 `deploy-package.sh` 时带 `--copy-ai-skills`。
- `scripts/deploy-package.sh` 在该模式下执行 `cp -R "$SRC/data/ai-skills/." "$APP_DIR/data/ai-skills/"`。
- 在服务器 Linux 上最小复现：先创建运行 data 文件内容 `USER_EDIT`，包内模板同名文件内容 `PACKAGE`，执行同样 `cp -R source/. target/` 后，目标文件内容变成 `PACKAGE`。说明已有运行 data 文件会被覆盖。
- 项目运行时 `ensureRuntimeSkillSeeds()` 的设计是 `copyMissingTree()`，只补缺失文件，不覆盖已有文件；这说明“运行 data 可被用户/Dashboard 编辑”的边界本来存在。部署脚本的全量覆盖与这个边界不一致。

影响：
- Dashboard 或人工修改过的人格、mode、lore、Agent docs 可能在维护者执行 `scripts/ai.sh` 时被包内模板覆盖。
- 这会带来两类相反问题：一方面像 `terra-lore` 这种运行 data 缺 frontmatter 的旧文件需要安全迁移；另一方面部署脚本当前做法过猛，会把用户定制正文、voice_style、lore 说明等一起覆盖。
- 如果用户之后通过 Dashboard 微调人格口吻，再执行单插件 AI 部署，可能出现“人格突然变回模板/口吻漂移/自定义内容丢失”，这类现象容易被误判成人格串台。

建议修复：
- `deploy-package.sh --copy-ai-skills` 不应覆盖已有运行 data 文件；应改成只复制缺失文件，行为与 `ensureRuntimeSkillSeeds()` 一致。
- 对确实需要迁移的结构化元数据，单独做受控迁移。例如 `terra-lore` 只在运行 data 无 frontmatter、包内同名模板有 frontmatter 时，把 frontmatter 头部补到现有正文前，并在写入前备份。
- 若维护者确实想强制重置资源，应使用显式参数，例如 `--overwrite-ai-skills`，并在执行前输出将被覆盖的文件清单，不能让普通 `ai.sh` 默认覆盖。

验证方式：
- Linux 最小复现：已有目标文件执行普通 `--copy-ai-skills` 后仍保持 `USER_EDIT`；缺失文件会从包内模板复制。
- `terra-lore` 迁移场景：缺 frontmatter 的运行 data 文件被补 frontmatter，正文保留；已有 frontmatter 的运行 data 文件不被覆盖。
- `npm run test:quick` 中部署脚本断言从“ai deploy copies ai-skills”调整为“只补缺、不覆盖可编辑 ai-skills”，并新增部署脚本文本或临时目录行为测试。

已排除的疑点：
- 不是所有运行 data 与包内模板差异都应自动修。运行 data 是可编辑资源，差异可能来自 Dashboard/用户定制；只有缺 frontmatter 这类结构诊断错误才应做有条件迁移。
- 当前同类 frontmatter 漏迁移只发现 `lore/SKILL.terra-lore.md`；其他 `ai-skills` 文件在“是否有 frontmatter、name/type 是否匹配”维度未发现同类问题。

### L6-1 `epub` 和旧 `.doc` 被允许但解析结果会变成二进制乱码或底层错误

真实性：真实存在，可本地临时 DATA_DIR 最小复现。

修复状态（本轮）：代码已修，本地验证通过，待部署与线上验证。`file-safety` 已把旧 `.doc` 和 `.epub` 改为 `unsupported_type` 跳过，`file-analyzer` 不再尝试用 docx/text 路径解析它们；`.docx/.xlsx/pdf` 等仍保留支持。本地 `npm run test:quick` 与 `npm test` 已覆盖 unsupported 断言。

证据：
- `file-safety.js` 的 `BINARY_DOC_EXTENSIONS` 允许 `epub`、`doc`、`ppt`、`pptx` 等扩展名。
- `file-analyzer.js` 的 `parseFile()` 对 `epub` 直接调用 `parseText(filePath)`；但常见 EPUB 本质是 zip 容器。最小复现写入一个 `PK...` zip 头后，`analyzeFileNow()` 返回：
  `[用户上传文件: sample.epub] ---文件内容开始--- PK... ---文件内容结束---`
- `file-analyzer.js` 对 `doc` 和 `docx` 都调用 `parseDocx()`，实际使用 `mammoth.extractRawText()`；旧 `.doc` 并不是 docx zip/XML 格式。最小复现写入旧 OLE doc 头后，分析结果被标记为：
  `[文件解析失败: Can't find end of central directory ...]`
- 当前 `analyze_file` 如果看到 `entry.analyzed && entry.analysis` 会直接返回该 analysis。虽然最终 QQ 可见回复还有转述层，但工具材料已经含有二进制乱码或底层库错误，模型可能自然复述成很差的回复。

影响：
- 用户发 EPUB 后问“读一下文件”，bot 可能把 zip 二进制头当作文件正文总结，表现为看不懂文件或乱说。
- 用户发旧 `.doc` 后，工具结果里会出现底层 JSZip 错误，不是自然的“不支持旧 Word 文档/请转成 docx”。
- 这和当前“支持纯文本/PDF/DOCX/XLSX”的实际能力不一致；允许列表比解析能力宽，导致错误进入 Agent 工具材料。

建议修复：
- 安全层与解析层对齐：如果暂不实现 EPUB/旧 DOC 深度解析，就不要把 `epub` 和旧 `doc` 当作可分析正文文件；可以在 `checkFile()` 中把它们标为不支持，或在 `parseFile()` 中返回明确自然的不支持说明。
- 对 `ppt/pptx` 当前已经返回“暂不支持内容提取”，可保留为明确降级；但应考虑是否把状态标记为“无法提取内容”而不是“已分析正文”，避免 Agent 误以为拿到了内容。
- 错误写回前做用户态清洗：不要把 JSZip/mammoth/pdf-parse 等底层异常原文写入 `analysis`；统一改成自然说明，例如“这个文件格式暂时没提取出正文，建议转成 docx/pdf/txt 后再发”。

验证方式：
- 临时 DATA_DIR 写入伪 EPUB zip 头，调用 `analyzeFileNow()` 后不应出现 `PK` 二进制头和 `[用户上传文件:]` 正文包裹。
- 临时 DATA_DIR 写入旧 `.doc` OLE 头，调用 `analyzeFileNow()` 后不应出现 `Can't find end of central directory` 等底层错误。
- 回归 `npm run test:scenario -- --grep file`，确保文本/PDF/DOCX/XLSX happy path、硬编码读文件兜底和文件追问仍通过。

本轮验证结果：
- `npm run test:scenario -- --grep file`：通过，实际运行完整 scenario，`passed: 764, failed: 0, skipped: 2`。
- `npm run test:scenario -- --grep voice`：通过，实际运行完整 scenario，`passed: 764, failed: 0, skipped: 2`。

已排除的疑点：

### S9-1 普通随机回复可能在触发 60 秒后仍继续发送，导致群聊割裂

真实性：真实存在，服务器日志和本地代码可对上。

修复状态（本轮）：代码已修，本地验证通过，待部署与线上验证。随机回复现在携带触发时的群消息版本、显式交互版本和触发时间；文本、随机语音、罕见语音等可见发送前都会统一检查是否过期，群里已有新消息或点名交互时会放弃旧随机。本地 random scenario 用延迟模型响应 + 中途群消息复现并断言旧随机不会外发。

证据：
- 生产日志里一次普通随机回复在 `03:35:15` 命中：`decision=may_reply`、`triggered=true`，随后进入 `chat`。
- 同一轮最终到 `03:36:43` 才记录 `sent random=true parts=1`。从触发到发送约 88 秒，已经超过 `enqueueForChannel()` 里写的 60 秒队列超时。
- `index.js` 的 `enqueueForChannel()` 使用 `Promise.race([fn(), timeoutPromise])`，但没有 `AbortController` 或发送前时效检查。60 秒超时只会让队列 promise 继续往后走，不能取消已经启动的 `fn()`；底层 `chat()`、Agent 或模型请求晚返回后，仍可能执行 `safeSendReply()`。
- 当前 `buildRandomSendOptions()` 只在高风险人格、延迟随机或消息版本变化时强制引用触发消息；普通随机回复没有“超过时效就放弃”的发送前兜底。因此慢模型/慢工具会让主动插话晚到，用户看到时像是在硬接旧话题。

影响：
- 这能解释一类“bot 明明有上下文却突然接得很割裂”的体验：模型当时可能看的是正确触发上下文，但回复发出时群聊节奏已经过去。
- 如果慢请求期间又出现新消息，普通随机回复也缺少发送前的统一时效拦截；即使没有刷屏，也会像突然翻旧账。
- 这不是模型理解力本身的问题，而是随机主动回复链路缺少“过期取消/发送前时效判断”。

建议修复：
- `enqueueForChannel()` 不要只 `Promise.race` 释放队列；对可取消链路传入 `AbortSignal`，至少让 `callOpenAI` / Agent 尽量中断慢请求。
- 随机回复发送前统一检查触发时刻、触发消息版本和当前消息版本：超过短时效或群里已经有新消息时，普通随机直接放弃；高风险人格/明确延迟随机如果仍要发，必须引用触发消息，避免无锚点硬接。
- 这条是发送时效边界，不是语义硬编码；不限制模型怎么接话，只防止已经过期的主动回复继续扰动群聊。

验证方式：
- 场景测试模拟随机回复模型调用超过 60 秒，断言不会在超时后发送可见回复，也不会阻塞后续消息队列。
- 场景测试模拟随机触发后群里有新消息进入，断言普通随机 late reply 放弃；高风险/延迟随机若保留则必须引用触发消息。
- 回归 `npm run test:scenario -- --grep random`，确认正常即时随机、ambient/no_send、延迟随机取消、显式 @ 取消 pending random 仍通过。

### S13-1 连续复读发送绕过 `safeSendReply()`，平台拒发时缺少统一保护

真实性：真实存在，服务器日志与本地最小复现可对上。

修复状态（本轮）：代码已修，本地验证通过，待部署与线上验证。复读路径已改为轻量安全发送：不接入 AI 分段/人格/贴纸，只捕获平台禁言和风控拒发并写可控日志，不再让 `session.send()` 错误冒泡。本地 repeat scenario 已 mock `retcode 1200` 并断言错误被吞掉和记录。

证据：
- 服务器日志至少两次出现 `repeat triggered` 后 OneBot `send_group_msg` 返回 `retcode: 1200`，栈落在 `index.js` 复读发送位置。
- `index.js` 的连续复读链路在命中 `checkGroupRepeat()` 后直接执行 `await session.send(repeatResult.reply)` 并 `return next()`。
- 普通 AI 回复、Agent 转述和文件追问等主回复链路使用 `safeSendReply()`；该函数会先查平台禁言缓存/实时禁言，再通过 `sendReply()` 发送，并对 `retcode 1200` 做风控分类、清洗重试和必要的发送冻结。
- 本地最小复现：开启复读后，两名用户连续发送同一句；第二次复读触发时把 `session.send()` 模拟成抛出 `retcode: 1200 risk control`，结果 `run()` 直接抛出该错误，日志只有 `repeat triggered ...`，没有进入 `safeSendReply: rate limited`、`platform muted` 或其他统一发送保护日志。

影响：
- 复读虽然不是 AI 文本回复，但仍是 bot 主动往群里发消息；绕过统一保护后，平台风控/禁言/发送失败不会被当前发送保护层吸收。
- 如果复读在平台限制期持续触发，可能产生重复错误日志，且不会贡献到现有发送冻结状态，无法像普通 AI 回复一样降噪和保护账号。
- 这不代表“复读内容 666/是的，你的理解完全正确”本身有错；问题是复读发送路径和其他可见回复路径不一致。

建议修复：
- 复读发送改走统一发送保护。若复读需要保持原始短文本/表情，不走 AI 分段和贴纸扩展，也应新增一个轻量 `safeSendRaw()` 或让 `safeSendReply()` 支持 `disableSticker`、`disableQuote`、`maxParts=1` 之类确定性选项，而不是裸 `session.send()`。
- 复读触发后发送失败应吞掉已分类的平台错误，只记录安全日志；不要让风控错误冒泡为中间件 warning。
- 复读仍不应调用模型，不应进入人格/上下文链路；修复点只在发送边界，不改变复读触发语义。

验证方式：
- 场景测试模拟复读触发时第一次发送抛出 `retcode 1200`，断言错误不会冒泡，日志进入统一发送保护或复读专用安全发送日志。
- 场景测试模拟平台禁言缓存命中时复读不发送。
- 回归现有复读场景：文本复读、QQ 表情复读、同用户不触发、同组只跟一次、图片/文件不复读仍通过。

### L11-1 普通群聊语音消息不会进入共享上下文和 scene 目录

真实性：真实存在，本地最小复现可确认。

修复状态（本轮）：代码已修，本地验证通过，待部署与线上验证。普通群聊语音即使不触发 ASR，也会以 `[语音]` 锚点写入共享上下文和 scene；点名/私聊仍按原逻辑尝试 ASR。本地 voice scenario 已断言普通群聊语音会写共享音频锚点且不触发 ASR。

证据：
- `message-reader.js` 能识别 record/CQ record：`hasAudio=true`。
- `index.js` 只在 `(session.isDirect || directAt)` 时尝试 ASR，并把 `plain` 改成 `[语音转文字：...]` 或 `[语音消息]`。
- 非点名普通群聊语音不会 ASR，本身没有可见文本；后续 `sharedRecordText = normalizeText(stripMentions(plain || analyzed.memory || analyzed.plain || ''))` 为空，因此不会调用 `saveSharedChannelTurn()`。
- 本地最小复现：构造群聊 record 消息 `[CQ:record,file=voice-1.silk]`，不点名、不私聊，运行中间件后 `sent=[]` 是正确的，但 `channelSharedCache` 仍为空，`loadGroupScenes()` 返回空 scenes，没有 `[语音]` 锚点。
- `group-scene-index.js` 已经有 `extractSceneAnchors()` 对 `[语音]` 的支持，`buildActiveGroupSceneNote()` 也把语音列为媒体锚点；缺的是入口层把普通语音消息以安全占位写入当前现场。

影响：
- 群友先发语音，随后其他人问“刚才那段语音是什么/他说啥/评价一下”，模型可能完全不知道群里刚出现过语音，只能靠近场文本猜。
- 这会削弱 active scene 的“图片/文件/语音锚点”能力，尤其是快节奏群聊里，语音本身就是一个重要上下文对象。
- 这不是要求 bot 主动听所有语音或主动回复语音；问题只是普通语音消息没有被记录成安全锚点。

建议修复：
- 非点名普通群聊语音不调用 ASR、不主动回复，但应写入共享上下文和 scene：内容用安全占位 `[语音]`，如果已有转写才用 `[语音转文字：...]`。
- 语音占位只保存 messageId、清洗昵称、时间和安全锚点，不保存本地语音路径、URL、file token 或原始 CQ 码。
- 如果后续用户明确追问语音内容，再由模型通过自由路由决定是否使用可用语音/上下文工具；不要把“看到语音”硬编码成必定回复。

验证方式：
- 场景测试构造普通群聊 record 消息，不点名，断言不发送回复，但 `channelSharedCache` 和 `group-scenes` 都出现 `[语音]` 锚点。
- 场景测试构造点名语音且 ASR mock 成功，断言共享上下文记录 `[语音转文字：...]`，可用于后续短追问。
- 回归图片、文件、文字消息的 active scene 场景，确保不会因为语音占位导致随机回复硬接或翻旧账。

已排除的疑点：
- 公开 bot 回复未写入共享上下文：当前 `reply.js` 在每个可见文本气泡发送成功后调用 `saveSharedChannelTurn(session, '东雪莲', part, 'assistant', ...)`，因此当前代码已经能让 active scene 看到 bot 刚才公开说过的话。
- 图片 file-only 历史链路在当前代码和测试里已覆盖：`storeImageUrl()` 允许只有 `file` 无 URL 的图片入库，`analyze_historical_image` 可在当前轮返回分析结果；这不再是当前版本的未修 bug。
