## 关键实现记录

### S37：thinking leak guard 可维护化

- 原来的单条 `THINKING_LEAK_RE` 拆为 `THINKING_LEAK_PATTERNS`。
- 新增 `THINKING_LEAK_INPUT_MAX_CHARS = 4000`，避免对超长输出做无意义全量正则扫描。
- 原括号分支中的 `收到.*新消息` 改为 `收到.{0,40}新消息`。
- 既有事故样例仍然能命中，普通建议句仍然放行。

### N20：复读状态清理

- 新增 `MAX_REPEAT_STATE_SIZE = 5000`。
- 新增 `pruneRepeatState(now)`：
  - 清理超过 `REPEAT_MATCH_WINDOW_MS` 的频道状态。
  - 超过容量时删除最旧状态。
- `checkGroupRepeat()` 入口自动调用清理。

### 旧#8：Agent 工具结果异步外置

- `externalizeToolResult()` 改为 async。
- 使用 `fs/promises.mkdir()` 与 `fs/promises.writeFile()`。
- Agent engine 中以下场景均改为 `await externalizeToolResult(...)`：
  - 普通工具调用结果
  - web_search 超次数阻断消息
  - pre-execute tool 结果
  - pending tool resume 结果

### S28/S29：push log 与 quota 并发治理

- `countLoggedQuota()` 改为 async，通过 `fs/promises` 从日志尾部读取最多 `MAX_PUSH_LOG_READ_BYTES`。
- `getQuota()` 改为 async。
- 新增 `pushLogWriteChain`，串行化 append 和日志裁剪。
- 新增 `quotaOperationChains`，按 quota key 串行化发送额度判断、真实发送、额度更新、日志写入。
- 修正 quota cache 过期清理条件：
  - key 格式是 `YYYY-MM-DD:channel`
  - 清理时应保留 `startsWith(day + ':')` 的 key

## 测试四问

1. 复现了用户哪条真实失败输入？

   本批不是由单条聊天输入触发，而是审计延后项清理。覆盖的真实风险场景包括：
   - thinking leak 事故样例，例如“我得看看现在是什么情况”“用户A发了个消息说……这应该是在回应……”
   - 复读窗口过期后的旧消息不应继续触发旧状态
   - Agent 工具返回超长结果时需要外置保存
   - 两个并发 push 在同频道同日额度为 1 时不能都发送成功

2. 断言了哪个失败现象不会再出现？

   - thinking leak guard 不再依赖一条难维护的大正则。
   - repeat 的频道状态不会无限期留存。
   - Agent 大工具结果不会同步写文件阻塞事件循环。
   - push 日志 append/裁剪不会并发互踩。
   - push quota 不会被同 key 并发发送绕过。

3. 哪些依赖被 mock 了？

   - Koishi session 和 bot 发送链路由 scenario fake 环境提供。
   - push 并发测试使用 fake bot。
   - Agent 配置和运行数据目录使用临时目录。
   - 模型/API/HTTP 等外部链路沿用既有 scenario mock。

4. 因为 mock，哪些真实链路仍未覆盖？

   - 未真实连接 QQ/NapCat。
   - 未在生产数据目录上做长时间 push log 并发压测。
   - Agent 大工具结果只验证本地临时落盘，不覆盖生产高并发 Agent 运行。
   - 未执行部署或服务器重启；部署/重启仍需用户明确确认。
