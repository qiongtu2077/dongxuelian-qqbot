# 模块治理与 TypeScript 渐进迁移方案

日期：2026-05-25
现状适配：2026-05-26
状态：实施中；Phase 1 已完成部分 `core/`、`lifecycle/`、`diagnostics/`、`reply/` 目录分化，本轮代码搬迁收口后暂停，当前重点是补齐执行记录与后续排期。

## 0. 当前结论

本方案现在只覆盖 `packages/koishi-plugin-dongxuelian-ai` 的模块治理与 TypeScript 类型护栏。它不再冒充整个仓库总控，也不替代上下文、人设、Agent、MCP、部署、安全等其他计划。

当前选择很明确：

1. **先做目录分化，再做 TypeScript 类型层。**
2. 先保持 JS 运行时不变，`main: lib/index.js` 不变。
3. 先把现有扁平 `lib/` 收敛成稳定目录边界，再把 TypeScript 类型定义挂到这些边界上。
4. 本方案不启动运行时 `.ts` 迁移，不引入 loader，不生成 `dist/`，不改发布链路。

原因也很直接：当前 `lib/` 顶层仍有大量扁平 JS 文件，虽然 `index.js` / `chat.js` 已经拆薄，但目录边界还没稳定。此时先上 TS，会把类型绑定在马上要移动的旧路径上，后面目录迁移会重复改类型引用，收益低、噪音高。

## 3. 目标与非目标

### 3.1 目标

1. 将 `lib/` 顶层扁平文件逐步归入稳定目录：
   - `core/`
   - `reply/`
   - `routing/`
   - `behavior/`
   - `persona/`
   - `media/file/`
   - `media/image/`
   - `media/voice/`
   - `chat/`
   - `lifecycle/`
   - `diagnostics/`
2. 保留旧路径 shim，避免一次性重写大量 require。
3. 更新直接消费者到新路径，每批最多处理一个责任域。
4. 增加 `tsconfig.json`、`typecheck` 脚本和 `types/` 契约目录。
5. 只给稳定边界加 JSDoc / `@ts-check`，不全仓开启 `checkJs`。

### 3.2 非目标

1. 不把运行时代码从 `.js` 改成 `.ts`。
2. 不新增运行时 loader。
3. 不生成 `dist/`。
4. 不改插件 `main`。
5. 不改模型调用、随机回复、Agent 路由、文件/图片/语音行为。
6. 不借目录迁移顺手重构业务逻辑。
7. 不删除 shim，除非所有消费者已经迁走且测试通过。

## 6. Phase 1：JS 目录分化

Phase 1 只做目录分化，不改运行时技术栈。

每批必须满足：

1. 同一责任域。
2. 文件数量 1 到 3 个优先，最多不超过 5 个。
3. 新路径 + 旧路径 shim 同时存在。
4. 只更新直接消费者。
5. 不做业务逻辑重构。

### 6.1 第一批

建议第一批：

1. `onebot-endpoint.js` -> `core/onebot-endpoint.js`
2. `frontmatter.js` -> `core/frontmatter.js`
3. `redactor.js` -> `core/redactor.js`

理由：

- 文件小。
- 依赖少。
- 适合验证 shim、consumer 更新和 cascade 维护流程。
- 不触达聊天主链路。

### 6.2 第二批

建议第二批：

1. `logging-config.js` -> `core/logging-config.js`
2. `runtime-config.js` -> `core/runtime-config.js`

理由：

- 属于配置和诊断底座。
- 消费者较多，但行为稳定。
- 迁移后能让后续目录统一从 `core/` 取配置。

### 6.3 第三批

建议第三批：

1. `session-compat.js` -> `lifecycle/session-compat.js`
2. `bot-resolver.js` -> `lifecycle/bot-resolver.js`

理由：

- 它们是已拆出的兼容层。

- 适合在 core 试水稳定后推进。

## 7. 文件族执行模板

每批严格按这个顺序：

1. 读本方案和当前 git 状态。
2. 确认本批文件都存在。
3. 用 `rg` 查直接消费者。
4. 创建目标目录。
5. 复制原文件到目标路径。
6. 只修目标文件内部相对 `require`。
7. 旧路径改成最小 shim：
   ```js
   module.exports = require('./new/path')
   ```
8. 只更新本批直接消费者。
9. 更新 `cascade-test.js` 的模块路径、语法检查、重复函数扫描和必要的 cross-file guard。
10. 逐个运行 `node -c`。
11. 运行 `npm run test:quick`。
12. 若触达消息、命令、Agent、媒体链路，再运行 `npm run test:scenario`。
13. 在本文件的执行记录里写明改了什么、测了什么、是否保留 shim。

**与 AGENTS.md "拆文件 5 步法"的关系：**

AGENTS.md 的 5 步法适用于从大文件中拆出函数到新文件（函数级拆分）。本节模板适用于整文件搬迁到子目录（文件级迁移）。两者互补：

| 维度 | AGENTS.md 5 步法 | 本方案执行模板 |
|------|-----------------|---------------|
| 粒度 | 函数/状态块 | 整个文件 |
| 旧位置处理 | 注释旧定义 → 测试通过后删除 | 改为最小 shim（永不删除，直到所有消费者迁走） |
| 消费者更新 | 源文件加 import | 直接消费者切新路径 |
| 适用场景 | index.js/chat.js 内部拆薄 | lib/ 平铺文件归入子目录 |

如果在目录迁移过程中发现目标文件内部需要拆函数，应先完成目录迁移，再按 AGENTS.md 5 步法处理内部拆分，不要在同一批次混合两种操作。

## 8. Phase 2：TypeScript 类型护栏

### 8.1 只做什么

### 8.2 不做什么

2. 不启用运行时编译
3. 不改 `main`
4. 不生成 `dist`
5. 不全仓 `checkJs`

### 8.3 tsconfig 建议

文件：`packages/koishi-plugin-dongxuelian-ai/tsconfig.json`

```json
{
  "compilerOptions": {
    "target": "ES2020",
    "module": "commonjs",
    "moduleResolution": "node",
    "lib": ["ES2020"],
    "strict": false,
    "noImplicitAny": false,
    "allowJs": true,
    "checkJs": false,
    "esModuleInterop": true,
    "resolveJsonModule": true,
    "skipLibCheck": true,
    "forceConsistentCasingInFileNames": true,
    "noEmit": true
  },
  "include": ["lib/**/*", "types/**/*"],
  "exclude": ["node_modules", "test"]
}
```

说明：

- 第一版 `noImplicitAny` 先设为 `false`，避免一开始被历史 JS 噪音淹没。
- 后续只在已加 `@ts-check` 的边界文件上逐步收紧。

**`checkJs: false` 的实际效果：**

- `allowJs: true` 只是允许 `.js` 参与模块解析，不会对 JS 文件做类型检查。
- 只有文件顶部显式标注 `// @ts-check` 的 `.js` 文件才会被 `tsc` 类型检查（覆盖全局 `checkJs: false`）。
- `types/*.d.ts` 的内部一致性（接口定义不矛盾、引用路径存在）始终会被验证。
- 这意味着当前 69 个实体 JS 文件默认不受 `tsc` 约束，类型覆盖率需要逐文件手动 opt-in。
- 好处：避免被历史代码的隐式 any、缺失类型、动态 require 等噪音淹没。
- 代价：无法通过一个开关全量启用检查，需要逐步推进。

### 8.4 typecheck 脚本

## 9.1 AI 全量执行 .ts 迁移的挂机流程

当 Phase 1 目录分化全部完成且 Phase 2 tsconfig 已就位后，可以让 AI 按以下流程全量执行 .js → .ts 转换，用户只需最终审核。

**前提条件：**

1. Phase 1 目录拆分已全部收尾，无未跟踪的实现文件。
2. tsconfig.json 已创建，`tsc --noEmit` 能正常运行。
3. 测试基线绿灯（test:quick + test:scenario 通过）。

**AI 执行流程：**

1. 按目录逐批将 .js 改为 .ts，补全所有函数参数和返回值类型签名。
2. 对无法从代码上下文确定的类型，标注 `// TODO-TYPE: 需用户确认` 并在清单中记录原因。
3. 每完成一个目录，运行 `tsc --noEmit` 确保零编译错误。
4. 每完成一个目录，运行 `npm run test:quick` + `npm run test:scenario` 确保运行时行为不变。
5. 测试文件（test/）保持 .js 不动，不在本流程内改动。
6. 全部目录完成后，输出一份待确认清单，格式为：

```
文件路径:行号 — 当前标注 — 不确定原因 — 建议选项
```

**用户审核：**

- AI 全部完成后，用户集中审核待确认清单（预计 10-20 处）。
- 审核重点：参数个数是否正确、返回值类型是否匹配实际 return、不该是 any 的地方是否被标成了 any。
- 审核通过后提交。

**建议执行顺序（从稳定到复杂）：**

1. `core/` — 最稳定、依赖最少
2. `diagnostics/` — 纯诊断，无状态
3. `lifecycle/` — 生命周期编排
4. `reply/` — 发送链路
5. `routing/` — 路由策略，多为纯函数
6. `behavior/` — 随机/复读/敏感
7. `persona/` — 人格解析
8. `media/` — 文件/图片/语音
9. `message/` — 消息解析
10. `chat/` — chat 子模块（不含 chat.js 主入口）
11. `agent/` — 最复杂，放最后
12. 顶层入口（index.js、chat.js、handler.js、conversation.js）— 单独评估

**不允许：**

- 借 TS 迁移改变任何运行时行为。
- 引入新的 npm 依赖（ts-node 等 loader 除外）。
- 改动测试文件的语言或框架。
- 对标注为 `// TODO-TYPE` 的地方自行猜测并使用具体类型，必须保持 any 或 unknown 等待用户确认。

## 10. 验证矩阵

**`node -c` 局限性：** `node -c` 只验证 JavaScript 语法正确性（等价于 parser pass），不会执行代码。它不检查 `require()` 路径是否存在、导出是否正确、循环依赖等运行时问题。这些问题由 `npm run test:quick`（cascade-test 的模块 require 加载断言）和 `npm run test:scenario` 兜底。`node -c` 的作用是快速排除搬迁过程中的拼写/括号/语法错误，不能替代后续测试。

触达入口、消息、命令、Agent、媒体、发送链路时追加：

```bash
npm run test:scenario
```

TypeScript 类型层追加：

```bash
npm run typecheck --prefix packages/koishi-plugin-dongxuelian-ai
```

阶段收尾：

```bash
npm run check
```

## 11. 停机条件

出现以下情况必须暂停：

1. 目录迁移导致运行时行为变化。
2. shim 路径无法稳定兼容旧消费者。
3. 单批消费者超过 10 个且无法再拆小。
4. `npm run test:quick` 失败且原因不是测试自身缺陷。
5. `npm run test:scenario` 暴露用户可见回归。
6. typecheck 需要大面积改业务实现才能通过。
7. 需要引入 runtime loader 才能继续。
8. 工作区出现与本批无关的用户改动并影响同一文件。

触发停机后的恢复流程见第 12 节"回滚策略"。

## 12. 回滚策略

### 12.1 触发条件

第 11 节停机条件中任一项触发后，若 15 分钟内无法定位并修复问题，启动回滚。

### 12.2 回滚粒度

- **单批回滚**：只还原本批新增文件、shim 和消费者变更。适用于单批迁移引入的路径错误或测试失败。
- **域级回滚**：还原整个责任域的所有批次。适用于 shim 兼容性系统性失败或目录结构设计问题。
- 不允许跨域回滚——如果 `routing/` 出问题，不能连带回滚已稳定的 `core/`。

### 12.3 回滚步骤

1. `git stash` 保存当前工作区（如有未提交改动）。
2. `git log --oneline -10` 确认最近稳定 commit。
3. 单批回滚：`git revert <batch-commit>`（如果该批是独立 commit）。
4. 如果多批打包在一个 commit 中无法简单 revert：手动将 shim 改回完整实现 + 消费者改回旧路径 + 删除新目录文件。
5. 运行完整验证矩阵（`npm run check` + `npm run test:quick` + `npm run test:scenario`）确认恢复。
6. 在执行记录中标注回滚原因和恢复点。

### 12.4 回滚后恢复

- 回滚后必须重新运行 Phase 0 盘点，确认当前状态。
- 分析失败原因，调整迁移策略后再重新尝试。
- 在本方案执行记录中写明回滚原因、恢复 commit、后续调整计划。

### 12.5 预防措施

- 每批迁移尽量是独立 commit，避免多批打包。
- 每批迁移前确认工作区干净（`git status --short` 无非本批改动）。
- 功能开发优先级高于迁移，冲突时迁移侧让步。

## 13. Shim 清理策略

### 13.1 清理前提

满足以下全部条件时，允许清理某个 shim：

1. 该 shim 对应的所有直接消费者已切到新路径（通过 `rg "require.*旧路径"` 确认零引用）。
2. `npm run test:quick` 和 `npm run test:scenario` 均通过。
3. 该 shim 不被外部包（`agent-console`、`koishi-app` 等）引用。
4. 该 shim 对应的责任域已完成全部候选文件迁移。

### 13.2 清理时机

- 每完成一个责任域的全部迁移后，统一清理该域的 shim。
- 不在迁移中途删除 shim。
- 清理批次不超过 5 个 shim/批。
- 警戒线：如果 shim 总数超过 40 个且无清理计划，暂停新迁移，优先清理。

### 13.3 清理步骤

1. `rg "require.*旧文件名"` 确认零消费者（排除 shim 自身和 cascade-test）。
2. 删除 shim 文件。
3. 从 `cascade-test.js` 移除对应 shim 加载项和 forward guard。
4. 运行完整验证矩阵。
5. 更新本方案第 17 节 shim 清单，将状态改为"已清理"。

### 13.4 保留例外

以下 shim 即使消费者为零也暂不清理，等 Phase 2 类型护栏稳定后再评估：

- 与 Koishi 插件外部接口同名的 shim（如 `diagnostics.js`、`reply.js`）。
- 被外部测试脚本或 CI 直接引用的 shim。

## 19. 目录分化实施注意事项

- 状态型模块不能双实例。队列、缓存、定时器、health cache、random state、writeQueues、refresh promise 这类文件，旧路径必须是最小 shim，新逻辑只能存在一份。
- 相对路径必须逐个核对。文件从 `lib/foo.js` 搬到 `lib/reply/foo.js` 后，原来的 `require('./utils')` 通常要变成 `require('../utils')`；必须用 `node -c` 和 require 加载测试兜住。
- 循环依赖边界不能破。尤其禁止新目录模块反向 import `index.js`。
- 只更新直接消费者。不要为了统一风格顺手改旁路文件，避免 diff 变大、回归定位变难。
- 每批完成后立刻补本方案执行记录。文档状态落后会误导下一轮重复迁移。
- 禁止借路径迁移改变业务逻辑。目录分化只改变归属、shim 和 require 路径。
- 如果工作区出现与本批同文件的非本轮改动、测试暴露行为变化、shim 兼容不稳定或消费者过多无法拆小，立即暂停。
