### S1-1 生产目录 Git 状态不是干净发布态，会干扰后续排查与回滚

真实性：真实存在。

证据：服务器只读检查显示生产目录当前 `HEAD` 仍停在旧提交；服务器本地 `origin/bot_ZZY` 也没有更新到本地已经推送的最新提交。同时生产目录有大量源码、前端构建产物、插件包入口和备份 patch 的脏改动。运行包里能看到本轮修复后的函数，例如 QQ 气泡两句兜底和图片历史工具提示，说明线上实际运行代码并不等同于 Git `HEAD`。

影响：
- 以后看服务器 `git status` / `git diff` 很难判断哪些是线上真实运行修复、哪些是历史残留改动。
- 回滚或二次部署时容易把已修复代码覆盖回旧版本。
- 排查人格串台时，无法简单用提交号对应具体线上行为，会让“某条日志到底跑哪版代码”变得不可靠。

建议修复：
- 部署流程完成后，让生产目录的 Git 提交号与已推送提交对齐，或者明确把生产目录改成纯运行目录，不再把它当 Git 工作树排查。
- 在部署脚本里增加发布态校验：记录当前运行包的提交号/构建号到一个非敏感版本文件，重启后日志打印该版本。
- 清理历史部署残留前先备份并确认；不要用 `git reset --hard` 直接覆盖生产脏改动。

验证方式：
- 生产日志启动时能看到最新构建号。
- 服务器只读检查时，运行包版本、Git 版本和本地远端版本能互相对应。
- 再次部署后，除运行数据文件外，生产目录不再出现大量源码脏改动。

### L1-1 Agent 转述分支的安全兜底仍会绕过当前自定义人格

真实性：真实存在，可本地隔离复现。

证据：
- `packages/koishi-plugin-dongxuelian-ai/lib/chat.js` 的 Agent 结果转述分支在拿到 `agentReply` 后，遇到 banned output、thinking leak 或内部上下文泄漏时，直接把回复改成固定短句，例如“这活别找我，换个工具。”、“我还有事，下次再说。”、“我刚刚串台了，重说一句。”。
- 这条分支没有像普通 chat 主链路一样进入当前人格下的重试，也没有用当前 `personaName/personaSkillContent` 生成自然兜底。
- 本地用临时 `DONGXUELIAN_AI_DATA_DIR` 绑定用户人格 `TestPersona`，让 Agent 转述模型返回内部草稿式文本后，最终返回固定句“我还有事，下次再说。”，不包含测试人格要求的口吻标记。

影响：
- 当搜索/fetch、图片工具或 Agent 材料转述遇到模型内部草稿、工具计划泄漏、封禁词等异常时，用户会看到默认固定话术，而不是当前自定义人格的话术。
- 这能解释一部分“工具链/搜索失败后突然不像当前人格”的串味现象；但它还不能单独证明最早聊天记录里“长离与默认人格混搭”的完整根因，因为普通 chat、随机回复、命令回复仍需要继续分入口排查。

建议修复：
- 把 Agent 转述分支的异常处理改成和普通 chat 主链路一致：优先追加简短纠偏 system/user 提示，在同一个当前人格 prompt 下重试一次，而不是直接替换成固定句。
- 如果重试仍失败，再使用“人格感知兜底”：根据当前 `personaName` 和 `personaSkillContent` 生成一条极短自然回复；只有 API 完全不可用、队列失败、超时这类不能再调用模型的情况，才使用统一技术兜底。
- 不把违规原文整段喂回模型，避免强化内部草稿；只给违规类型和短片段。
- 为 Agent 搜索转述、Chat heavy tool 转 Agent 转述、图片工具转述各补一个 scenario：绑定自定义人格，模拟转述阶段输出内部草稿/封禁词，断言最终回复不包含函数名、内部草稿、固定默认话术，并保留当前人格标记。

验证方式：
- 复现输入：自定义人格用户触发搜索/fetch 或图片工具，转述模型首轮返回“用户在质疑我/我需要/保持人设/我会调用 web_search”等内部草稿。
- 断言修复后不会发送固定“我还有事，下次再说。”、“这活别找我，换个工具。”、“我刚刚串台了”。
- 断言最终回复经过当前人格 prompt，且不泄漏 Agent、工具名、内部材料或网页指令。
- 跑 `npm run test:scenario`，并用一条真实搜索类消息做模拟端到端，确认工具结果仍能进入当前人格复述。

### S2-1 线上运行包同样存在 Agent 转述固定兜底绕过人格的问题

### L2-1 Agent 工具上下文会无条件注入同一用户后续普通聊天，导致乱感知

真实性：真实存在，可用最小脚本复现。

证据：
- `packages/koishi-plugin-dongxuelian-ai/lib/agent-chat-bridge.js` 定义了 `isAgentFollowUp(text)`，用于判断“刚刚搜到什么/来源/依据”等工具追问。
- 但 `getRecentAgentContextNote({ channelKey, userId, userMessage })` 当前没有调用 `isAgentFollowUp(userMessage)`，只要同一 `channelKey:userId` 10 分钟内存在 Agent 结果缓存，就直接返回 `[最近 Agent 工具上下文-内部参考]`。
- 最小复现：先 `recordAgentChatResult()` 写入一次搜索结果，再用 `userMessage: 'hello'` 调 `getRecentAgentContextNote()`，返回值仍包含“用户正在追问你刚才的 Agent/搜索/工具结果”；用 `userMessage: '刚刚搜到什么'` 也返回同一注入。这说明普通新话题和真实追问没有被区分。
- 现有 scenario 只覆盖“你刚刚搜到哪些东西”应注入 Agent 搜索摘要，没有覆盖“搜完以后普通闲聊/新话题不应注入”。

影响：
- 搜索/fetch 用完后，同一用户在 10 分钟内继续普通聊天，模型会被系统提示误导成“用户正在追问刚才工具结果”，可能把无关搜索结果硬塞进回答。
- 这会表现为上下文感知过度、答非所问，尤其在群聊里用户很快切换话题时更明显。
- 这也是“不能靠缓存一股脑注入”的典型问题：上下文有了，但候选上下文没有按当前话题和用户意图过滤。

建议修复：
- `getRecentAgentContextNote()` 应先用 `isAgentFollowUp(userMessage)` 或更通用的短追问/工具追问判定过滤；普通新话题不注入 Agent 工具上下文。
- 对“这个呢/还有吗/来源呢/刚才那个”这类省略追问，可结合普通共享上下文和最近 Agent 请求做语义判断，但不要对所有后续消息默认注入。
- 话题切换检测已经会调用 `clearAgentContextForUser()`，但不能只依赖话题切换模型；桥接层本身也要有意图门槛。
- 补 scenario：先记录 Agent 搜索结果，再发“你好/换个话题/你觉得哈耶克对吗”这类非工具追问，断言 prompt 不包含 `[最近 Agent 工具上下文-内部参考]`；再发“你刚刚搜到哪些来源”断言仍会注入。

验证方式：
- 最小单元验证：`getRecentAgentContextNote({ userMessage: 'hello' })` 返回空；`getRecentAgentContextNote({ userMessage: '你刚刚搜到什么' })` 返回摘要。
- 行为验证：模拟 QQ 搜索后普通闲聊，断言模型请求 messages 不包含“用户正在追问你刚才的 Agent/搜索/工具结果”。
- 回归现有 Agent follow-up scenario，确认真实追问仍能看到搜索摘要。

### L3-1 普通 chat 多次重试失败后的最终固定兜底绕过自定义人格

真实性：真实存在，可本地临时 DATA_DIR + mock 模型最小复现。

证据：
- `packages/koishi-plugin-dongxuelian-ai/lib/chat.js` 普通 chat 主链路会在 `isUnsafeThinkingReply(reply)` 时最多重试 `MAX_REPLY_RETRIES` 次，但如果模型每次都继续输出内部草稿，循环结束后仍会进入最终兜底。
- 最终兜底当前按 `retaliationLevel` 直接选择固定短句，例如友好模式下从“想白嫖直说 / 就这？ / 咋了 / 难绷”里取一句；重复兜底也会使用“我还有事，下次再说。”；封禁词兜底会使用“这活别找我，换个工具。”。
- 最小复现：临时绑定用户自定义人格 `TestPersona`，人格要求每次回复包含 `TEST_PERSONA_MARKER`；mock 模型连续 6 次返回“用户在质疑我 / 我需要解释 / 保持人设 / 我会调用 read_image_history 函数”等内部草稿。`chat()` 最终返回“就这？”，不含 `TEST_PERSONA_MARKER`，日志出现 5 次 `thinking output in reply, retrying with sanitized prompt`。

影响：
- 即使普通 chat 的首轮 prompt 已正确注入当前自定义人格，只要模型在异常路径里持续输出内部草稿、重复话术或封禁词，最终用户看到的仍可能是默认莲莲式固定短句。
- 这能解释“平时像自定义人格，但遇到难回答/工具相关/安全兜底时突然串成默认人格”的一部分现象。它和 L1-1/S2-1 属于同类根因：异常处理层没有保持人格一致。

建议修复：
- 抽一个统一的“人格感知纠偏/兜底” helper，普通 chat 与 Agent 转述共用：在仍可调用模型时，用当前 `systemPrompt` 加一条极短纠偏提示重试；不要把完整违规草稿再次喂回模型。
- 当模型重试耗尽但 API 仍可用时，再尝试一次低 token 的人格化短回复生成，明确要求“一句自然回复、保持当前人格、不输出工具/内部分析”。
- 只有 API 不可用、超时、队列拒绝或已经不能再调用模型时，才用技术兜底；技术兜底也应尽量选择中性短句，不带默认人格强风格。

### L4-1 AI 生成类命令只写“用你现在的性格”，但没有注入当前人格内容

真实性：真实存在，可本地临时 DATA_DIR + mock 模型最小复现。

证据：
- `packages/koishi-plugin-dongxuelian-ai/lib/handler.js` 中 `东雪莲吐槽我` 和 `东雪莲帮我说话...` 直接调用 `callOpenAI()`，system prompt 只写“用你现在的性格和语气”，没有读取 `resolvePersona()` / `loadPersonalSkill()` 后把当前人格文件内容传入模型。
- 最小复现：临时给用户绑定 `CommandPersona`，人格正文包含 `COMMAND_PERSONA_MARKER`；直接调用 `handleCommand()` 执行 `东雪莲吐槽我`，mock 模型调用成功。抓到的模型 messages 为：
  - system: `最近群聊消息：没什么特别的事\n用你现在的性格和语气，随便吐个槽。简短一点，30字以内。`
  - user: `吐槽我`
  其中不包含 `COMMAND_PERSONA_MARKER`。
- 这说明模型无法知道当前自定义人格的具体口吻，只能按默认经验理解“你现在的性格”。

影响：
- 用户设置个人人格后，普通聊天可能正常，但 `东雪莲吐槽我` / `东雪莲帮我说话` 这类命令会表现得不像当前人格。

建议修复：
- 给命令层提供一个轻量的当前人格 prompt 构造 helper：基于 `resolvePersona(channelKey, currentUserId)` 和 `loadPersonalSkill(personaName)` 返回“当前人格内容 + 安全边界 + 当前命令任务”的 system prompt。
- `东雪莲吐槽我` / `东雪莲帮我说话` 这类需要模型生成自然话术的命令必须使用该 helper；不需要模型的纯配置命令不应引入人格 prompt。
- 命令输出也要走同一套 `sanitizeReply` / `stripMarkdownForQQ` / thinking leak 守卫，避免命令分支泄漏内部草稿或 markdown。
- 补 scenario：绑定自定义人格，执行 `东雪莲吐槽我` 和 `东雪莲帮我说话 xxx`，断言模型请求包含人格标记；同时 mock 回复含 fenced code / thinking leak 时，断言最终不泄漏。

验证方式：
- 修复前最小复现中 prompt 不含 `COMMAND_PERSONA_MARKER`；修复后必须包含。
- 群聊里用户设置个人人格后，执行 `东雪莲吐槽我`，回复应符合该人格，而不是默认东雪莲语气。
- 跑命令相关 scenario 与 chat thinking guard 场景，确认命令分支没有绕过输出清洗。

### L5-1 Agent 历史图片工具对 file-only QQ 图片仍要求 URL，导致本地图片无法分析

真实性：真实存在，可本地临时 DATA_DIR 最小复现。

证据：
- `packages/koishi-plugin-dongxuelian-ai/lib/agent/tools/read-image-urls.js` 对 file-only 图片输出：
  `URL:` 为空，`ID: m-read-file-only`。
- `packages/koishi-plugin-dongxuelian-ai/lib/agent/tools/analyze-image.js` 虽然会先通过 `messageId` 读取 entry，并调用 `analyzeImageNow(channelKey, messageId)`，但如果同步分析没有拿到结果，随后仍执行 `if (!url) return '无法获取图片 URL。请先用 read_image_history 查看可用图片。'`。
- 最小复现：先 `storeImageUrl('g-file-only', 'm-file-only', '', 'local-only.jpg')` 写入 file-only 图片，再执行 Agent 工具 `analyze_historical_image({ messageId: 'm-file-only' })`，返回 `无法获取图片 URL。请先用 read_image_history 查看可用图片。`。

影响：
- QQ 图片大量是本地 file/segment file，没有公网 URL。Agent 路径下用户问“刚才那张图/评价一下”时，即使图片已经入库且有 messageId/file，工具也可能给出“无法获取图片 URL”的误导性失败。
- Chat 轻量图片工具已经修到能同步尝试 `analyzeImageNow()`，但 Agent 版工具还有旧的 URL 依赖，造成“同一张历史图片，普通 chat 可能能看，Agent 工具链却说拿不到”的链路不一致。

建议修复：
- Agent `analyze_historical_image` 应和 Chat 轻量工具共用同一套 `analyzeImageNow()` 结果处理；当 entry 有 file 但没有 URL 时，不应直接报“无法获取 URL”。
- 如果 file-only 图片当前没有本地缓存、NapCat `get_image` 也取不到，应明确说明“图片记录存在，但本地缓存/适配器取图失败”，而不是让用户再去 `read_image_history`。
- `read_image_history` 输出中应显示 file-only 状态，例如 `文件: local-only.jpg` 或 `本地图片记录，无公网 URL`，帮助模型知道应该用 messageId 分析，而不是依赖空 URL。
- 补 Agent 工具 scenario：file-only 图片入库后，`read_image_history` 显示 ID 和 file 状态；`analyze_historical_image(messageId)` 在有缓存时返回分析，在无缓存且取图失败时返回准确失败原因，不再说“请先 read_image_history”。

验证方式：
- 本地最小复现修复前返回“无法获取图片 URL”；修复后有缓存时返回 `图片分析结果`，无缓存时返回“图片记录存在但无法读取图片文件/适配器缓存”的准确说明。
- 用 QQ file-only 图片现场模拟：先发图，再过几轮问“刚才那张图评价一下”，Agent/Chat 两条路径都能拿到同一张历史图片记录并给出一致行为。

### L6-1 ASR 能识别 file-only 语音 payload，但转写只支持 http URL，QQ 本地语音会退成 `[语音消息]`

真实性：真实存在，可本地最小复现。

### L7-1 发送层会无条件删除所有括号内容，导致正常语义被丢弃

真实性：真实存在，可本地最小复现。

证据：

### L8-1 搜索弱命中防编造 guard 会覆盖已有人格化失败说明，退成固定句

真实性：真实存在，可本地最小复现。

证据：
- `packages/koishi-plugin-dongxuelian-ai/lib/agent-retell-guard.js` 在 Agent 材料包含 `weak_hit`、未读到正文等搜索失败信号时，会检查最终转述是否包含“没拿到/查不到/不确定”等固定失败词。
- 如果没有命中这些词，即使转述本身已经明确表达“来源太弱、不要编造、换关键词继续查”，也会被 `guardAgentRetellReply()` 替换成固定句 `这次没有拿到可靠结果，我就不硬编了。`
- 最小复现：构造 `toolResults=[{ name:'web_search', result:'搜索状态：weak_hit（弱命中，未读到可用正文）' }]`，再传入转述 `PERSONA_MARKER: 来源太水，我先不下定论；你给我一个更具体的平台或链接，我再继续查。`，输出被替换为固定句，不含 `PERSONA_MARKER`。

影响：
- 这条 guard 能防止搜索弱命中后模型瞎编“查到了”，但现在判定太窄，会把已经合格、符合当前人格的失败说明也替换掉。
- 用户看到的就是之前抱怨过的硬兜底“这次没有拿到可靠结果，我就不硬编了”，缺少当前人格语气和可继续操作的方向。
- 这是搜索/fetch “搜不到时不好聊”的真实原因之一：不是工具完全没用，而是失败复述被最后一层固定句覆盖。

建议修复：
- 保留“弱搜索材料不能编造成成功”的安全目标，但把 `replyAcknowledgesSearchFailure()` 扩展成语义更宽的失败/不确定/证据不足判定，例如识别“来源太弱/证据不够/不能下定论/不瞎说/别编/换关键词/给链接继续查”等表达。
- 更好的做法是让 guard 返回结构化判定：`ok` / `fabricated_success` / `acknowledged_failure`，只在明显编造成成功时覆盖；对已承认失败的自然回复只做脱敏，不改写。
- 如果必须覆盖，也应走当前人格的短失败说明生成，而不是固定一句。
- 补测试：弱命中 + “查到了”必须被拦；弱命中 + 人格化失败说明必须保留；可用正文 `usable_hit` 不应触发失败覆盖。

验证方式：
- 修复前最小复现会把 `PERSONA_MARKER` 替换掉；修复后应保留该失败说明。
- 跑 cascade 中 `agent retell guard blocks fabricated success after weak search`，确认防编造仍有效。
- 模拟“我的世界搞笑视频/哈耶克争议最新来源”搜索弱命中，最终回复应说明没拿到可靠依据，并给出换关键词/链接等下一步，而不是只发固定句。

### S11-1 线上 content-only file 图片会被识别为 hasVisual，但不会进入图片历史

真实性：真实存在，有线上日志与本地最小复现互相印证。

证据：
- 服务器只读日志中，近期多条图片消息显示 `plain=""` 后被补成 `"[图片]"`，并且随机诊断里有 `hasVisual=true`、`hasLink=true`、`hasEmbed=true/false`。这说明消息解析层确实知道这些消息有图片。
- 同一时间服务器 `data/image-history/*.json` 多个频道文件仍只有空壳大小，内容等价于没有可用图片记录；这说明“看到视觉消息”没有转化成历史图片入库。
- 本地最小复现 `<img src="file://D:/qq/Pic/demo_720.jpeg" />`：`analyzeIncomingMessage()` 返回 `hasVisual=true`，但 `event.message` 没有结构化 `image` segment，`imgSeg=false`；当前入库逻辑只有 `imgSeg ? extractImageUrls(content)[0] : ''`，因此 `fallbackUrl=''`、`storableUrl=''`。
- 同一复现里调用 `storeImageUrl(channel, messageId, '', null, meta)` 返回 `false`，`getRecentImages()` 为空。也就是说这类 content-only file 图片在当前代码中确实无法入库。

影响：
- 群聊里只以 HTML/文本形式出现的本地 file 图片，bot 会在当前消息解析阶段知道“这里有图”，但不会留下可供后续 `read_image_history` / `analyze_historical_image` 使用的历史记录。
- 用户过几分钟问“刚才那张图评价一下/看看图”时，历史图片工具会说没有图片记录或找不到图，表现为图片上下文感知断裂。
- 这也解释了线上近期 `hasVisual=true` 很多但图片历史文件仍是空壳的现象；它比 S6-1 更靠前，属于图片入库入口遗漏。

建议修复：
- 入库前不要只依赖结构化 `image` segment；当 `analyzed.hasVisual` 为 true 时，应从 `content` 中同时提取 `<img src>` / `<image ...>` 的 `src`、`url`、`file` 字段。
- 对 `file://` 或本地路径不应走 URL 规范化丢弃，而应作为 `file` 记录保存，并在后续分析阶段通过本地缓存、NapCat `get_image` 或安全受控的文件读取路径尝试取图。
- `extractImageUrls()` 可以继续只返回 http(s) URL；建议新增单独的 `extractImageRefs()` 或消息段图片引用提取 helper，输出 `{ url, file, source }`，避免把本地 file 误当公网 URL。
- `storeImageUrl()` 已支持 `file` 非空入库，修复重点在 `index.js` 入库前的图片引用解析。

验证方式：
- 本地复现 `<img src="file://D:/qq/Pic/demo_720.jpeg" />`：修复后应能写入 image-history，`read_image_history` 能看到 messageId 与 file-only 状态。
- 结构化 image segment、CQ image URL、HTML http(s) src 三种既有路径仍能入库。
- 真实 QQ smoke：发一张只表现为 file/html src 的图片，稍后问“刚才那张图是什么”，历史图片工具能找到该 messageId，不再是空历史。

### L11-1 content-only 图片被识别为 hasVisual 后仍不会进入图片历史

真实性：真实存在，可本地最小复现。

证据：
- `message-reader.js` 的 fallback 特征会把 `[CQ:image,...]`、`<img ...>`、`<image ...>` 标为 `hasVisual=true`，即使 `session.event.message` 没有结构化 `image` segment。
- `index.js` 入库逻辑只取 `segments.find(s => s.type === 'image')`。随后 `fallbackUrl = imgSeg ? extractImageUrls(content)[0] : ''`，也就是说没有 `imgSeg` 时，即使正文里有 CQ/HTML 图片 URL，也不会提取。
- 本地最小复现结果：
  - `<img src="file://D:/qq/Pic/a.jpg" />`：`hasVisual=true`，`imgSeg=false`，`extractImageUrls=[]`，`storableUrl=''`。
  - `<img src="https://example.com/a.jpg" />`：`hasVisual=true`，`imgSeg=false`，`extractImageUrls=["https://example.com/a.jpg"]`，但因 `imgSeg=false`，`storableUrl=''`。
  - `[CQ:image,file=a.jpg,url=https://example.com/a.jpg]`：`hasVisual=true`，`imgSeg=false`，`extractImageUrls=["https://example.com/a.jpg"]`，但仍 `storableUrl=''`。
  - 结构化 `{ type:'image', data:{ file:'abc.jpg' } }` 可以拿到 `imgFile`，结构化 `{ type:'image', data:{ url:'https://...' } }` 可以拿到 `storableUrl`。
- `storeImageUrl(channel, messageId, '', null)` 返回 `false`，所以这些 content-only 图片不会产生历史图片记录。

影响：
- 某些 QQ/NapCat 场景下图片只在 `content` 中表现为 CQ/HTML 字符串，或 `<img src="file://...">`，没有结构化 image segment。当前 bot 会知道“这条消息有图”，但不会把它写入 `image-history`。
- 用户后续问“刚才那张图/评价一下”时，历史图片工具没有记录可用，表现为上下文图片感知失效。
- 这也会让线上出现 `hasVisual=true` 日志很多、但 `image-history` 仍是空壳的现象。

建议修复：
- 新增图片引用提取 helper，统一从结构化 segment、CQ 字符串、HTML `<img src>` / `<image url>` / `file` 属性中提取 `{ url, file }`，而不是在 `index.js` 内联 `imgSeg ? extractImageUrls(...) : ''`。
- http(s) 图片继续按 URL 入库；`file://` 与本地文件 token 作为 `file` 入库；mface/face 这类表情应只作为视觉/表情上下文，不强行写入历史图片。
- 保留 `extractImageUrls()` 的公网 URL 语义，避免把本地路径混进 web/fetch 逻辑；图片历史入口单独处理 file 引用。
- 补 scenario：content-only CQ image URL、HTML http src、HTML file src 都能入库；纯 mface/face 不进入历史图片；结构化 image 旧路径不回归。

验证方式：
- 修复前上述 content-only 用例 `storeImageUrl` 参数为空导致无记录；修复后 `getRecentImages()` 能看到对应 messageId、URL 或 file。
- 真实 QQ smoke：发 content-only 图片后不点名，稍后点名问“刚才图里是什么”，历史图片链路能找到记录并尝试分析。

### L12-1 视频/教程资源请求被规划成“官方公告/最新官方”搜索词，容易偏离用户想找可看内容的意图

真实性：真实存在，可本地最小复现。它不是“搜索路由全坏”，而是进入搜索后的 query 规划偏向错误。

证据：
- 用户真实链路里出现过“我的世界最近比较火的视频是什么”后继续问“我想看我的世界的搞笑视频 / 你能帮我找几个吗”。当前本地路由能识别这些话需要搜索，但第二句 `我想看我的世界的搞笑视频` 被当作独立 `general-search-intent`，没有把上一句的“最近比较火”补进预执行 query。
- 本地最小复现 `buildExplicitSearchRunOptions('我想看我的世界的搞笑视频', { recentUserMessages: ['我的世界最近比较火的视频是什么'] })` 生成：
  - `query: 我想看我的世界的搞笑视频`
  - `queries: ["我想看我的世界的搞笑视频 官方 公告 来源", "我想看我的世界的搞笑视频 最新 官方", "我想看我的世界的搞笑视频"]`
- 同类输入 `我想看搞笑视频`、`我想看红石教程视频` 也会生成“官方公告/最新官方”候选，而不是“平台/播放/热门/搞笑/教程/合集/排行榜”等更贴近资源发现的词。
- `search-query.js` 的 `isHotVideoQuery()` 只覆盖“最近/热门/排行”等显式热度词；`GENERAL_LATEST_RE` 又包含“推荐/视频”，导致没有热度词但明显是“找视频看”的请求落进 generic latest/source 分支，自动追加“官方 公告 来源 / 最新 官方”。
- 现有 e2e 只断言“预执行了 web_search、最终转述不泄漏”，没有断言资源类 query 不能被规划成官方公告方向，所以该偏差目前不会被测试挡住。

影响：
- 用户要的是“帮我找几个能看的 Minecraft 搞笑视频/红石教程视频”，搜索却优先朝官方公告、最新官方、来源核验方向跑，容易拿到官网新闻、版本公告或泛搜索摘要，而不是视频平台可观看条目。
- 这会加重用户感知里的“搜索鸡肋”：工具确实被调用了，但搜索词和任务目标不一致，最后更容易出现没有可靠结果、只给泛泛建议、或不能给出几个具体可看的内容。
- 这也会让多轮搜索显得不自由：模型明明拿到了“我想看/找几个/搞笑视频/教程视频”的语义，却被预执行 query 先带偏，后续 Agent 需要额外纠偏。

建议修复：
- 不扩大硬编码主题词列表；把 query 规划拆成更通用的意图维度：时效核验、网页正文读取、资源发现、教程/攻略、视频推荐、观点讨论。主题词只做辅助，不替代模型/上下文判断。
- 对“想看/找几个/推荐几个/来几个 + 视频/教程/攻略/资源/帖子/直播”等资源发现请求，预执行 query 应保留用户核心对象，并加入“视频/推荐/热门/平台/合集/教程/播放”等资源词；只有“官方公告/版本更新/新闻来源/证实真假”才追加“官方/公告/来源”。
- 对多轮场景，若当前句是“我想看 X 视频/找几个/推荐几个”，且最近相关发言含“最近/比较火/热门”，应把热度约束合并进 query，但仍把最近发言标为非指令，避免提示注入。
- 保留用户自由禁搜：用户明确“不用查/禁止外部检索”时仍不暴露搜索工具，稳定观点问题如“哈耶克对吗”继续直接聊。

验证方式：
- 最小单测：`我想看我的世界的搞笑视频`、`我想看红石教程视频` 的 `queries` 不应含“官方公告/最新官方”作为前两项，应包含“视频/教程/推荐/热门/平台”等资源发现词。
- 多轮 scenario：先问“我的世界最近比较火的视频是什么”，再问“我想看我的世界的搞笑视频 / 你能帮我找几个吗”，断言预执行 `web_search` query 同时包含“我的世界、搞笑视频、最近/热门/比较火/推荐”，最终能给出具体可继续看的条目，而不是只说泛泛类型。
- 反向验证：“鸣潮最新角色是谁”“某游戏最新版本公告”“这个新闻是真的吗”仍保留官方/来源优先的核验策略；“禁止进行外部检索，直接告诉我哈耶克理论对不对”仍不进入搜索。

### L14-1 群聊普通文件消息不会入历史，导致后续 analyze_file 找不到文件记录

真实性：真实存在，可从入口条件直接复现。

证据：
- `index.js` 的文件入库分支是 `if (analyzed.hasFile && channelKey && session.messageId && (session.isDirect || directAt))`，也就是说只有私聊或 @bot 的群聊文件消息才会 `storeFile(...)`。
- `analyze-file.js` 的 Agent 工具是基于 `getFileEntry(channelKey, messageId)` 查历史文件记录再分析；如果消息从未入库，后续即使用户明确追问文件内容，也只能得到“找不到这个文件记录”。
- `file-store.js` 的设计是按 `channelKey + messageId` 持久化文件元数据，没有另一个群聊普通文件的补录入口。

影响：
- 群里有人直接发文件但没有 @ 机器人时，bot 虽然看得到这条文件消息的解析特征，却不会留下可供后续 `analyze_file` 使用的历史记录。
- 用户后续再问“刚才那个文件看一下/总结一下”时，系统会因为根本没有记录而失败，表现为文件感知断裂，而不是“下载失败”。
- 这和图片历史入口问题同类，都是“消息解析看到了内容，但历史记录入口太窄”。

建议修复：
- 文件入库条件不要只看 `(session.isDirect || directAt)`；至少对群聊里的文件消息也要建立轻量历史记录，供后续用户明确追问时再下载。
- 如果担心误存，可以像图片历史一样只保存元数据，不立即下载；真正下载放到 `analyze_file` / 用户追问时执行。
- 继续保留白名单/黑名单/大小限制，但入口不要卡死在 @bot。

验证方式：
- 本地最小复现：群聊普通文件消息（未 @bot）现在应能写入 `file-history`，`analyze_file` 能通过 messageId 找到记录。
- 反向验证：被跳过的文件仍应保持 skip 状态，`analyze_file` 不应强行下载。

### L14-2 文件下载重定向没有重新验证目标 URL，存在 SSRF 逃逸边界风险

真实性：真实存在，可本地代码路径确认。

证据：
- `file-analyzer.js` 的 `downloadFile(url, destPath)` 在收到 3xx 且带 `Location` 时，直接 `resolve(downloadFile(res.headers.location, destPath))`。
- 这条跳转处理没有重新调用 `validatePublicHttpUrl()` / `resolveAndValidateHostname()`；和 `agent/fetch-reader.js` 的 `fetchWithManualRedirect()` 相比，后者每次跳转都会重新校验公开 URL、DNS 和最终 response.url。
- 因为 `analyze_file` 的目的就是下载用户上传的文件，如果文件元数据里 URL 被第三方或消息体污染，这条跳转就可能把受控下载引向本机/内网/保留地址，而不被二次拦截。

影响：
- 文件分析链路引入了 SSRF/重定向逃逸风险，安全边界比现有 web_fetch 弱。
- 即使文件类型白名单和 10MB 限制都正常，这条重定向链路仍可能把下载目标带离白名单域。

建议修复：
- `downloadFile()` 每次跟随 3xx 前都要重新执行公开 URL 校验和 DNS 解析验证，逻辑参考 `agent/fetch-reader.js`。
- 不要直接把 `Location` 字符串丢给下一轮下载；应先用当前 URL 解析绝对 URL，再经过同一套 URL 安全函数。
- 继续保留 10MB 限制和文件类型白名单，但把“跳转到哪里”也纳入安全边界。

验证方式：
- 模拟 302 `Location: http://127.0.0.1/...` 或 DNS 解析到内网 IP 时，下载应被拒绝。
- 允许的公开跳转仍应正常下载。

### L14-3 文件后台异步解析队列存在，但当前入口没有把入库记录真正送进队列

真实性：真实存在，可从代码路径确认。它更像“已实现半套”，但对用户表现出来就是文件不会自动后台解析。

证据：
- `file-analyzer.js` 定义了 `enqueueFileAnalysis(channelKey, messageId)`、`drainQueue()`、`runAnalysis()` 三层后台队列。

- `index.js` 收到文件时只执行 `storeFile(channelKey, session.messageId, fileMeta)`，并没有把新入库记录自动送进 `file-analyzer` 队列。
- `analyze-file.js` 也明确写着“只在用户明确追问文件内容时由 Agent 调用，不会自动下载”，说明现有链路实际依赖用户追问或 Agent 工具显式触发，而不是后台自动分析。

影响：
- 文件能力的用户体验和图片历史不一致：图片会后台分析并回写，而文件只落元数据、不会自动产出摘要。

- 这会让新文件链路看起来“加了模块但没真正跑起来”，容易让人误以为文件能力已经具备自动衔接，实际却没有。

建议修复：
- 如果设计目标是“像图片一样先记住再后台分析”，应在文件入库成功后显式调用 `enqueueFileAnalysis(channelKey, messageId)`。
- 如果设计目标是“只在用户明确追问时分析”，那就别保留一个完全不接入口的后台队列，至少要在文档和提示中说明文件不会自动分析。
- 建议保留白名单/黑名单/大小限制不变，但把“自动分析”与“显式追问分析”两个模式分清楚，避免半自动状态。

验证方式：
- 入口接通后，群里发文件后不追问，也能在后台队列里看到待分析任务，最终 `file-history` 出现 `analyzed=true` 的记录。

### L16-1 空正文的群聊普通文件仍会在入库前早退，导致后续 analyze_file 找不到记录

真实性：真实存在，可用 `message-reader` 最小复现和 `index.js` 入口顺序确认。

证据：
- `message-reader.js` 对结构化 `{ type: 'file' }` 会返回 `hasFile=true`，但 `plain=''`、`hasVisual=false`、`hasAudio=false`。
- `index.js` 在文件入库分支之前有早退：`if (!plain && !directAt && !session.isDirect && !analyzed.hasVisual && !analyzed.hasAudio) return next()`。这里没有把 `analyzed.hasFile` 作为需要继续处理的媒体类型。

验证方式：

### L16-2 文件下载链路没有校验初始 URL、DNS 和重定向目标，能直接访问本机/内网地址

真实性：真实存在，可本地最小 HTTP 服务复现。

证据：
- `file-analyzer.js` 的 `downloadFile(url, destPath)` 仅用 `url.startsWith('https') ? https : http` 选择协议，没有调用 `validatePublicHttpUrl()` / `resolveAndValidateHostname()`。
- 同函数遇到 3xx + `Location` 时直接 `resolve(downloadFile(res.headers.location, destPath))`，没有解析相对跳转、没有重定向次数上限，也没有对跳转后的目标重新做公开 URL/DNS 校验。
- 本地最小复现启动 `127.0.0.1` HTTP 服务，再调用 `downloadFile('http://127.0.0.1:<port>/file.txt', dest)`，结果成功写入 `private-local-file`。这证明当前链路不仅重定向会逃逸，初始 URL 本身也能访问本机地址。

影响：
- 文件分析会下载用户消息或 `get_file` 返回的 URL。只靠文件类型白名单和 10MB 限制，不能阻止 URL 指向本机、内网、保留地址或通过 DNS/跳转转向这些地址。
- 该链路安全边界明显弱于现有 `web_fetch`，而且小文件自动缓存也复用 `downloadFile()`，风险覆盖收到文件时的后台缓存和用户追问时的即时分析。

建议修复：
- 让文件下载复用 `agent/fetch-reader.js` 的公开 URL 校验、DNS 校验和重定向思路：初始 URL 和每次跳转都必须验证，只允许 http/https 公网目标。
- 增加重定向次数上限，并用 `new URL(location, currentUrl)` 处理相对跳转。
- `get_file` 返回本地 `file` 路径时只接受可访问的本机文件路径；返回 `url` 时仍走同一套安全下载函数。
- 补单元验证：`127.0.0.1`、`localhost`、DNS 指向内网、302 跳内网都应拒绝；公开 URL 和公开跳转仍能下载。

验证方式：
- 修复前 `downloadFile('http://127.0.0.1:...')` 成功；修复后应抛出“拒绝访问本机、内网或保留地址”类错误。
- 修复后公开测试服务返回 200 小文本仍能成功保存，302 到公开目标在限制次数内能成功。

### L16-3 硬编码“读文件/看文件”兜底直接发送工具包裹内容，绕过统一回复层和人格表达

真实性：真实存在，可从当前入口代码确认。

证据：
- `index.js` 对精确匹配 `读文件|看文件|分析文件|打开文件|文件内容` 的消息，直接 `await session.send(target.analysis)` 或 `await session.send(result)`。
- `analyzeFileNow()` 返回的是 `wrapFileContent()` 生成的内部工具文本，形态为 `[用户上传文件: ...]\n---文件内容开始---\n...\n---文件内容结束---`，最长约 3000 字符。
- 这条路径没有经过 `chat()` 的当前人格 prompt，也没有经过 `safeSendReply()` / `sendReply()` 的 QQ 气泡分段、发送限流、Markdown 清理、输出守卫和共享上下文记录。

影响：
- 用户发“读文件”这种兜底指令时，bot 可能直接在 QQ 发一整段工具包裹原文，观感像调试输出，而不是当前人格自然总结。

建议修复：
- 保留硬编码指令作为确定性兜底，但不要直接发送 `wrapFileContent()`；改为把分析结果交给 Agent/当前人格转述，或生成一条简短摘要后走 `safeSendReply()`。

- 硬指令失败提示也应走统一发送层，避免以后绕过发送限流和上下文记录。
- 补 scenario：发文件后发送“读文件”，断言最终回复不包含 `---文件内容开始---`、`[用户上传文件:`，且不会单条直发超长工具文本。

验证方式：
- 修复前硬指令路径代码中存在 `session.send(target.analysis/result)`；修复后不再直接发送工具结果。
- 模拟端到端：已分析文件内容包含多行文本，用户发“读文件”后，回复为自然可读摘要或整理内容，且通过统一发送层分成合理 QQ 气泡。
