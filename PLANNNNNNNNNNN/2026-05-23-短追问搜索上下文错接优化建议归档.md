# 2026-05-23 短追问搜索与上下文错接优化建议

## 现象

私聊中用户围绕“我的世界搞笑视频”连续追问，中间查询了一次“我的人格”，随后发送“帮我找找吧”。Bot 没有承接“找我的世界搞笑视频”，而是回复成像在找某个人或 UP 主，并声称“刚才试着在网上一搜”。

## 已确认事实

- 这次当前人格仍是“布吕歇尔”，不属于已经确认的人格文件加载错误。
- 该消息走私聊普通 chat 链路，不是显式 Agent 路由直接搜索。
- 旧的“我的世界搞笑视频”上下文确实存在，但已经距离当前消息很久；如果用户没有明确拉回这个话题，它不应该被当作当前 active topic 主动启用。
- “我的人格”这类命令是否打断话题不是唯一重点。更关键的是：命令回复、旧私聊历史、长期背景和当前短句之间的权重/时效边界没有被稳定区分，导致模型既可能乱拉旧话题，也可能完全接不上当前意图。
- 普通 chat 的工具提示让模型知道“视频/热门/推荐可搜索”，但当前 query 很短时，进入 search/fetch 桥接前没有可靠的自由补全与置信度判断，导致模型出现“像是在找某个人/UP 主”的错误对象，并说出“刚才试着在网上一搜”这种不可靠话术。
- 不能把“帮我找找吧 / 找找吧”写成关键词路由。短追问是否需要搜索、是否需要补全上下文，应该由模型基于当前热窗口、引用链、最近有效意图和工具说明自由判断；代码只做安全边界、时效边界和异常兜底。

## 推荐修复方向

- 先溯源确认：这次“我的世界搞笑视频”是从哪一层进入模型的，是 100 条私聊历史、分层摘要、scene index、个人记忆，还是 search/tool bridge 的 query 补全。只有确认来源后再修。
- 给旧背景加明确语义边界：旧摘要/长期记忆只能帮助理解关系、偏好和用户主动拉回的对象；不能在当前短句没有锚点时主动恢复很久以前的话题。
- 当前热窗口和旧背景分层进入上下文：新近消息、引用链、媒体/文件锚点、最近明确任务权重最高；旧私聊历史和摘要必须标注“旧背景，不要主动提起”。
- chat 内部请求 web_search/web_fetch 时，如果当前 query 信息不足，应把最近热窗口和候选旧背景交给模型做一次“是否可补全”的自由判断；能补全再搜，不能补全就自然追问，不要乱搜人名，也不要假装已经搜过。
- 命令回复可以标记为元信息，避免覆盖当前任务，但这只是辅助修复；重点仍是时效、权重和自由补全。
- 增加回归场景：很久前聊过“我的世界搞笑视频” -> 之后出现多轮无关聊天/命令 -> 用户只说“帮我找找吧”。断言 bot 不能擅自拉回很久前的视频话题；如果当前热窗口没有明确对象，应追问“找什么方向”，或者在可用热窗口足够明确时再搜索。
- 增加桥接场景：当前热窗口明确讨论“我的世界搞笑视频”时，短 query 进入 search/fetch 前应由模型自由补全成完整搜索意图；回复不得出现“你是谁/这个人/UP 主线索”，不得假装搜索却不给可靠依据。

## 与群聊上下文窗口架构兼容的初步详细计划

目标一句话：少问废话，但该问时问得准；能接当前就接当前；不能拿旧背景硬续；也不能把别人的任务接到当前用户身上。

### 一、总体原则

本修复不新增“帮我找找吧/来几个/再找点”一类硬编码追问路由。代码只负责：

- 维护时间、引用、媒体/文件/语音、用户归属这些确定性边界；
- 把当前热窗口、旧背景和可检索目录分层给模型；
- 在 search/fetch 执行前做自包含检查，防止空 query 或错对象 query 直接进工具；
- 对明显不完整的搜索意图要求模型先基于当前热窗口补全，补不出来才自然追问。

真正的“这句话是不是追问、是不是该搜索、要不要查旧上下文”，仍交给模型基于窗口内容和工具说明自由判断。

### 二、修复读历史刷新活跃时间

先处理当前最可能导致旧私聊历史复活的底层 bug：

- `conversation.js` 的 `getConversationHistory()` 改为纯读取，不再调用 `touchConversation(session)`。
- 只有 `saveConversationTurn()`、真实用户消息入库、真实 bot 回复保存时才更新时间。
- `getRecentUserMessages()` 等只读辅助函数不能间接刷新活跃时间。
- 新保存的 user/assistant 消息带 `ts`，旧消息没有 `ts` 时默认视为旧背景，不能当 active topic。

这样 `chat.js` 里的 inactive degrade 才有意义，不会因为“为了读历史而读历史”把一小时前的话题刷新成刚刚。

### 三、把私聊也接入窗口分层

沿用《群聊上下文窗口架构计划》的层级，不另起一套系统：

- 私聊热窗口：最近短时间内、连续、和当前用户同一条任务链有关的消息。它可以补全“这个呢/帮我找找吧/再来几个”。
- 私聊旧背景：更早的历史、摘要、长期偏好、用户画像。它只能帮助理解用户偏好和关系，不能主动补全当前任务。
- 明确拉回：用户说“刚才/之前/上次/那个文件/那张图/你刚才说的”时，旧背景或旧记录才允许进入当前推理。

实现上优先做一个轻量 `ContextWindow` 构造层，而不是把所有逻辑塞进 `chat.js`：

- 输入：当前消息、会话历史、共享群聊缓存、引用信息、媒体/文件/语音锚点、是否私聊/群聊/随机。
- 输出：`activeWindow`、`backgroundWindow`、`retrievableIndexHint`、`ownershipHints`、`searchContextHints`。
- `activeWindow` 靠近最终 user message，权重最高。
- `backgroundWindow` 只能放在系统提示里的旧背景区，并明确“不是当前话题，除非用户主动拉回不要提起”。

### 四、群聊复杂环境的需求归属

群聊不能只看“最近几条”，还要看“谁的需求”和“当前用户是不是在接那条线”。

优先级：

1. 引用链、replyTo、明确 @ 的对象。
2. 当前用户自己最近未完成的需求。
3. bot 刚刚公开回复，适合跨用户短追问如“真的吗/怎么说/为啥”。
4. 当前热窗口里的公共话题。
5. 其他用户的旧需求，只能作为背景，不能直接当成当前用户需求。

场景例子：

- A 问文件会不会卡，B 接“8.52mb 吗/太大了”，bot 应围绕文件大小和生成卡顿说，不应跳去别的话题。
- A 问视频推荐，B 又问天气，当前用户再说“帮我找找吧”，不能自动继承 A 的视频需求，除非当前用户明确接 A 的话或引用 A 的消息。
- bot 刚说“我请客”，另一个用户说“真的吗”，可以接 bot 上一句，因为这是公开回复链。

### 五、避免“永远追问”的体验退化

澄清不是默认动作。只有以下情况才问：

- 当前热窗口里有多个同等可能对象，乱选会明显错；
- 当前消息要求执行 search/fetch/文件/图片分析，但 query 或对象不自包含；
- 模型无法从引用、媒体锚点、当前用户任务、bot 上一句里确定对象。

追问也要具体，不能泛泛说“你说的是啥”。例如：

- “你是要找刚才那个文件的问题，还是继续找视频？”
- “找视频的话你想要哪个方向，搞笑、教程还是整活？”
- “这个我没抓到对象，是指刚才那张图还是前面那个文件？”

如果当前只是随机主动插话，窗口薄时不应该追问用户；应由随机模式选择 `ambient_water` 或 `no_send`。点名/私聊/明确请求才允许自然追问。

### 六、search/fetch 前的自包含检查

普通 chat 或 Agent 想执行 `web_search` 前，增加一层语义自检，不让短 query 直接进搜索。

检查内容：

- 当前 query 是否包含可搜索对象、范围或目标；
- 如果 query 很短，是否能从 `activeWindow` 补成完整问题；
- 补全来源是不是当前热窗口，而不是旧背景；
- 是否混入其他用户未关联的任务；
- 是否存在用户明确禁止外部检索。

处理结果：

- 能补全：把补全后的完整 query 交给 `web_search`，并把补全依据作为内部上下文给 Agent，不发给用户。
- 不能补全：不执行搜索，不假装搜过，发一条具体澄清。
- 搜索结果 weak/无正文：保留当前人格自然说明没拿到可靠依据，不能编，也不能固定“这活别找我”。

### 七、工具和旧上下文检索的关系

`read_group_context` 仍只用于旧公共群聊 scene，不替代私聊历史窗口。

- 群聊旧公共上下文：通过 `read_group_context` 自由检索，工具结果只作旧片段。
- 私聊旧历史：通过私聊 `ContextWindow` 分 active/background，不塞进 `read_group_context`。
- 图片/文件/语音：优先作为当前窗口锚点；只有用户明确追问时才调用对应分析工具。
- search/fetch：只在当前问题确实需要外部信息时调用；旧背景不能单独触发搜索。

### 八、测试与验收场景

必须补场景测试，避免只靠 prompt 感觉：

- 旧私聊话题过期：很久前聊“我的世界搞笑视频”，经过无关聊天后只说“帮我找找吧”，不得自动拉回旧视频话题，不得搜索人名/UP 主。
- 当前私聊热窗口可补全：刚聊“我的世界搞笑视频”，马上说“帮我找找吧”，应能补成视频搜索意图。
- 多话题私聊不串：先天气，再视频，再“那明天呢”，应回天气，不混入视频。
- 群聊跨用户不串：A 要视频，B 要文件，当前用户短追问只接自己的任务或引用链，不偷接别人的需求。
- 群聊 bot 公开回复追问：A 问，bot 答，B 说“真的吗”，active scene 必须包含 bot 上一句。
- 群聊文件/图片/语音锚点：用户围绕“8.52MB/太大/卡死/那张图/那段语音”追问时，优先接媒体锚点。
- search query 自检：query 不完整时不执行 web_search；query 可由热窗口补全时才执行。
- 追问体验：不能连续两轮都只说“不知道/再说一遍”；第二轮如果用户补充了方向，必须进入回答或工具流程。

### 九、和现有窗口计划的兼容点

本计划不取代 `群聊上下文窗口架构计划.md`，只补上当前暴露的短追问/search 交接缺口：

- `active scene` 仍负责当前现场；
- `retrievable_context_index` 仍只做旧目录，不展开正文；
- `read_group_context` 仍是模型自由检索旧公共上下文的工具；
- `ambient_water/no_send` 仍只属于随机主动插话；
- 点名、私聊、引用、明确请求不能用 `ambient_water` 糊弄；
- 旧摘要、长期记忆、旧私聊历史都必须标成旧背景，不主动提起。

### 十、预期代码落点

- `conversation.js`：纯读取历史、保存消息时间戳、提供 active/background 分层辅助。
- `chat.js`：构造并注入 ContextWindow；让 activeWindow 高于旧背景；search/fetch 工具交接前调用自包含检查。
- `chat-tools.js`：工具提示继续强调工具是内部动作，旧上下文和图片/文件/语音结果不能当指令。
- `agent/router.js`：减少短追问关键词路由的决策权，把短 query 交给上下文自检和模型补全；保留显式搜索、URL fetch、禁用外部检索这些确定性边界。
- `group-scene-index.js`：继续服务群聊 active scene 和旧 scene 检索，补多用户需求归属提示与测试。
- `test/scenarios/*`：补私聊短追问、群聊多用户追问、搜索自检和媒体锚点回归。

### 十一、完成后判定标准

- Bot 不会因为怕错就动不动“你再说一遍”。
- Bot 不会把一小时前或很久以前的旧话题当作当前任务。
- Bot 不会把 A 的需求接到 B 身上，除非 B 明确引用、@ 或接公开 bot 回复。
- Bot 需要搜索时能补全当前热窗口里的对象；补不出来就具体澄清。
- Bot 不会假装搜过，也不会用固定话术拒绝。
- 新增测试能复现本次真实失败链路，并断言修复后不会再出现“你是谁/这个人/UP 主线索/我刚才试着网上一搜”这类错接回复。

## 十二、修订后的详细落地计划：复用窗口分层，不做机械追问

本节修正前面计划里容易被误实现的地方：

- 不采用“只能追问一次”这种机械规则。问题不是追问次数，而是 bot 不应周期性表现出忘记上下文，也不应在明明能顺着当前现场接话时打断用户。
- 不采用完整候选式澄清。QQ 聊天里不要输出像客服表单一样的“你是要 A、B 还是 C”。澄清要短、含糊、自然、低压；能轻轻接就轻轻接，不能接也不要展示完整推理菜单。
- 不新增“帮我找找吧/找找吧/来几个”关键词路由。短句是否承接、是否搜索、是否查旧上下文，继续交给模型基于 active window、引用链、媒体锚点、bot 上一句和工具说明自由判断。代码只做时间边界、归属边界、工具执行边界和异常兜底。
- 本文所有例句都只是语义形态说明，不是可照抄的正则、路由表或固定回复模板。实现时禁止写“看到某句话就搜某对象 / 看到某句话就接某条历史 / 看到某句话就回复某句”的逻辑。

### 12.1 底层问题：不是“读历史一定错”，而是两个时间语义混用了

当前代码里 `conversationLastActiveAt` 同时承担了两种职责：

1. **缓存访问时间**：内存缓存什么时候被碰过，用来做 TTL 和容量裁剪。
2. **语义活跃时间**：这段对话最后一次真实发生在什么时候，用来判断历史是 active topic 还是 background。

`getConversationHistory(session)` 是只读入口，但它会调用 `touchConversation(session)`。这对“缓存访问时间”可能合理：读过就保活；但对“语义活跃时间”不合理：读历史不等于用户真的继续了那个话题。

影响链路：

- `chat.js` 会先读最近用户消息做话题切换判断。
- 随后再 `getConversationHistory()` 构造 prompt。
- `chat.js` 的 inactive degrade 又依赖 `conversationLastActiveAt` 判断旧历史是否该降级。
- 如果只读历史把 `conversationLastActiveAt` 刷成当前时间，那么“旧历史降级”可能被削弱，旧话题更容易留在 active prompt 或 recent search context 里。

所以这更准确地说是一个**语义时间污染 bug**，不是“读取缓存保活”本身一定错。修法不应该简单删掉所有保活，而是拆语义：

- `conversationLastAccessAt`：可选，用于缓存 TTL 和容量裁剪。
- `conversationLastTurnAt`：真实 user/assistant turn 保存时更新，用于 active/background 判断。

第一版为了小改，可以先不新增完整双 Map，只做到：

- `getConversationHistory()` 不再更新用于语义判断的时间。
- `saveConversationTurn()` 更新真实对话活跃时间。
- 如果还需要缓存保活，另开 `touchConversationAccess()`，不能被 `chat.js` 的 inactive degrade 使用。
- 新消息写入 `ts`，后续窗口分层优先看消息级 `ts`，而不是只看会话级最后活跃时间。

### 12.2 私聊窗口不能照搬群聊 1-3/3-10 分钟，需要更慢

群聊 1-3 分钟热窗口、3-10 分钟暖窗口，是因为群聊节奏快、多人并发、话题切换频繁。私聊节奏更慢，用户可能隔十几分钟继续同一件事，所以私聊要单独调参。

建议私聊第一版窗口：

- **私聊热窗口：0-1 小时**
  - 默认可以承接同一任务链。
  - 可以补全短追问，也可以作为 search query 补全来源。
  - 如果中间出现了明显新任务，热窗口仍要按任务链切段，不能因为时间还在 1 小时内就混用旧任务。

- **私聊暖窗口：1-3 小时**
  - 不默认补全搜索。
  - 只有满足强连续条件时才可补全：用户明确说“刚才/之前/上次/那个”、最近 bot 上一句明显是待执行/待确认任务、同一个搜索/文件/图片任务链没有被其他任务打断。
  - 暖窗口更适合让模型“理解可能在接什么”，但不应该轻易触发工具。

- **私聊冷窗口：3 小时以上**
  - 默认旧背景。
  - 不能单独补全 `web_search` / `web_fetch` / 图片文件分析。
  - 只有用户明确拉回且能找到唯一对象，才可作为理解材料；是否执行工具仍要看当前句是否自包含。

- **私聊很旧背景：一天以上或无 `ts` 旧消息**
  - 只保留身份、偏好、长期关系和用户主动拉回的线索。
  - 不作为 active topic，不作为 search context。

这几个值第一版按私聊慢节奏固定为常量，后续再按真实聊天日志调整：

```js
PRIVATE_ACTIVE_HOT_MS = 60 * 60 * 1000
PRIVATE_ACTIVE_WARM_MS = 3 * 60 * 60 * 1000
PRIVATE_ACTIVE_COLD_MS = 24 * 60 * 60 * 1000
```

### 12.3 Step 1：给私聊历史分 active/background/searchable

目标：私聊也有“当前现场”和“旧背景”的区别，不能把 100 条历史全部当成同等上下文。

建议新增或调整的辅助函数：

```js
buildPrivateConversationWindow(session, history, options = {})
```

输入：

- 当前消息文本；
- 当前时间；
- 会话历史；
- 最近 bot 回复；
- 是否明确拉回旧话题，如“刚才/之前/上次/那个/你刚才说的”；
- 是否准备执行 search/fetch。

输出：

- `activeMessages`：热窗口消息 + 满足强连续条件的暖窗口消息；
- `backgroundMessages`：冷历史、旧摘要、长期偏好；
- `recentSearchableMessages`：只从热窗口和“强连续暖窗口”里提取，给 search query 补全使用；
- `confidence`：hot / warm_strong / warm_weak / cold / none；
- `searchReadiness`：self_contained / can_complete_from_hot / can_complete_from_warm / needs_chat_handling / blocked_by_cold。

规则：

- 当前消息本身永远是最高优先级。
- bot 上一句可用于承接“真的吗/怎么说/帮我找找吧”这类短追问，但私聊里也要看是否仍在热/强暖窗口内。
- “我的人格/切换人格/状态查询/命令回复”这类元信息可以进入历史，但标记为 meta turn，不应打断所有任务，也不应成为 search query 主体。
- 冷窗口和旧摘要可以进入系统提示的旧背景区，但不能出现在 `recentSearchableMessages`。
- 明确拉回时可以从 background 中取线索，但仍要有唯一对象；不能因为旧背景里有一个视频话题就自动搜索。

### 12.4 Step 2：暖窗口搜索策略必须落成 gate，不能只写“谨慎”

短追问搜索不要只分“热窗口足够 / 热窗口不足”。应分成五种：

1. **query 自包含**
   - 例：“搜一下我的世界搞笑视频”“查今天杭州天气”。
   - 不依赖历史，直接搜索。

2. **热窗口可补全**
   - 例：1 小时内刚聊“我的世界搞笑视频”，用户说“帮我找找吧”。
   - 可以补全 query 并预执行 `web_search`。
   - 但热窗口内部仍要过“任务链切段”：如果中间已经出现天气、人格、图片分析等新任务，旧视频不能继续作为搜索对象。

3. **强暖窗口可补全**
   - 例：1-3 小时前聊视频，中间没有新任务；bot 上一句就是“要不要我帮你找”；用户回来一句“找找吧”。
   - 允许搜索，但必须通过下面的强暖 gate。

4. **弱暖窗口只进 chat，不预执行工具**
   - 例：1-3 小时前聊过视频，中间又聊了人格、天气、别的东西，用户说“帮我找找吧”。
   - 不直接搜。把可能相关的暖窗口作为低权重 active/background 交给普通 chat，让模型自然含糊处理；模型如果要问，也只短问，不列候选菜单。

5. **冷窗口阻断工具**
   - 例：3 小时以上以前聊过视频，现在只说“帮我找找吧”。
   - 不搜索，不用旧话题补 query。普通 chat 可以低压回应，但不能说已经搜过，也不能主动提旧视频。

强暖 gate 是具体判定，不是形容词，也不是关键词表。可以先按下面这句人话理解：

```text
1-3 小时暖窗口里只有一个明确搜索对象
且中间没被新任务打断
且当前短句确实是在让 bot 搜
且有显式拉回或 bot 上一句待执行
→ can_complete_from_warm，可以预执行搜索

否则
→ needs_chat_handling，不预执行搜索
```

这里的“当前短句确实是在让 bot 搜”不能靠枚举“找找吧/来几个/发几个”来做。实现上应由模型语义自检或已有轻量语义分类判断“当前动作是不是请求 bot 继续执行搜索/查找/推荐”，代码只校验边界和状态，不根据某个词直接决定搜索对象。

只有同时满足以下条件，`searchReadiness` 才能是 `can_complete_from_warm`：

- **G1 当前短句确实是工具/搜索跟进**：由模型上下文自检或已有语义分类判断当前消息是不是在延续工具/搜索任务；“找找吧/帮我找/来几个/再搜点/发几个”只作为人工阅读例子，不能新增固定关键词路由。正则最多用于过滤明显不是搜索跟进的低风险边界，不能决定搜索对象。模型自检输出只允许变成内部状态，不允许把“我判断这是搜索跟进”发给用户。
- **G2 暖窗口里只有一个可执行搜索对象**：提取最近 1-3 小时里的候选任务，过滤 meta turn 和纯闲聊后，搜索对象数量必须等于 1。多个候选时直接降为 `needs_chat_handling`。
- **G3 候选对象是完整可搜短语**：至少包含主题 + 类型/目标中的两类信息，例如“我的世界 + 搞笑视频”“杭州 + 明天天气”“某游戏角色 + 最新攻略”。只有“那个/他/这个/视频/资料”这种不完整对象不能过。
- **G4 中间没有硬打断任务**：候选任务之后如果出现新的搜索、文件/图片分析、天气/价格/赛程等当前数据任务、人格/记忆命令后又产生新的用户目标，则不能从更早任务补 query。
- **G5 当前用户归属一致**：私聊天然一致；群聊必须是当前用户任务、公共 bot 回复、公共 scene 或明确引用，不能是其他用户私人旧任务。
- **G6 bot 上一句或用户显式拉回提供连接**：暖窗口里如果不是连续发言，至少需要“刚才/之前/上次/那个”等拉回意图，或 bot 上一句是同一任务里的待执行邀请。这里同样不能写死几个拉回词，关键是语义上能把当前短句接回唯一任务。人格命令、状态查询、普通闲聊里的 bot 回复不算待执行邀请。
- **G7 外部检索未被禁止**：当前消息和上下文没有“别联网/不要搜/不用外部工具”等禁止。

通过 gate 后 query 生成也要保守，且只能做结构化补全，不能按句子模板拼接：

- 只用那个唯一候选对象 + 当前短追问动作生成 query。
- 不拼接多条历史原文。
- 不把人格命令、旧闲聊、长期记忆写进 query。
- query 生成后再做一次 `isSelfContainedSearchQuery(query)`：必须有可搜索对象和目标类型，否则降为 `needs_chat_handling`。
- 不能因为当前短句长得像某个例子，就把文档里的示例对象或旧历史对象硬塞进 query。

建议返回结构：

```js
{
  searchReadiness: 'self_contained' | 'can_complete_from_hot' | 'can_complete_from_warm' | 'needs_chat_handling' | 'blocked_by_cold',
  queryCandidate: '',
  gateReason: 'single_warm_task_with_pending_bot_offer',
  blockedReason: '',
}
```

`agent/router.js` 的 `buildExplicitSearchRunOptions()` 应接收结构化上下文，而不是只有 `recentUserMessages`：

```js
buildExplicitSearchRunOptions(userText, {
  recentUserMessages,
  searchContextHints,
  searchReadiness,
  queryCandidate,
  windowConfidence,
})
```

`preExecuteTools` 只允许在 `self_contained`、`can_complete_from_hot`、`can_complete_from_warm` 三种状态出现。`needs_chat_handling` 和 `blocked_by_cold` 不预执行搜索，也不能输出“我刚搜了/网上没找到”这类已经执行过工具的口吻。

### 12.5 Step 3：低压澄清不是文案表，而是生成边界

这里要避免两个极端：

- 极端 A：bot 一不确定就说“不懂前文/你说的是啥”。
- 极端 B：bot 把旧背景硬续成当前任务，甚至直接搜索。

具体逻辑不是写固定话术，而是在 prompt 和工具边界里给模型三个约束：

1. **能接就接**
   - active/hot 或 strong warm 里有唯一对象时，直接接当前任务。
   - 不解释“我根据上下文判断你是……”。

2. **不能接但也不该工具时，轻轻探**
   - 对象不自包含、active 不足、且是私聊/点名/明确请求时，可以短短探一下。
   - 不输出完整候选，不列 A/B/C，不展示时间线。
   - 语气目标是“像 QQ 里顺手问半句”，不是客服澄清。

3. **不能接且不是明确请求时，不打扰**
   - 随机主动插话不能追问用户。
   - 群聊窗口薄时走 `ambient_water` 或 `no_send`。

代码层只做负约束：

- 不让 `web_search` 在 query 不自包含时执行。
- 不把 background 注入到 `recentSearchableMessages`。
- 不把内部 mode、候选、工具计划发给用户。
- 不把“没有对象”统一替换成固定追问句。

### 12.6 Step 4：群聊跨用户不是“绝不接”，而是区分公共现场和私人任务

群聊里不能简单写“B 不能接 A 的需求”。真实情况更细：

- **公共现场可以跨用户承接**：bot 刚刚公开回复、全群都看得见，另一个人说“真的吗/怎么说/为啥/笑死”，可以接 bot 上一句。例：bot 对 A 说“我请客”，B 说“真的吗”，应理解为接 bot 的公开回复，而不是孤立回答“什么真的”。
- **私人任务不能自动转移**：A 让 bot 找视频，B 之后说“帮我找找吧”，如果 B 没有引用 A、没 @ A、也没有明显接 A 的话，不应默认继承 A 的任务。
- **公共话题可以共享**：群里多人连续围绕同一文件、图片、视频、梗说话，B 的短追问可以接公共 active scene。
- **旧需求不能跨用户复活**：A 很久前的任务已经冷却，B 的短句不能把它重新变成当前任务。

关键补充：bot 自己的公开回复也要继承归属，不是“只要是 bot 上一句，任何用户都能接成自己的任务”。

- `open_public_bot_reply`：bot 在公开聊天里说的闲聊、吐槽、公共解释、面向全群的回应。任何用户在短时间内追问都可以接。例如“今晚我请客”“这文件可能会卡，主要看生成时要不要反复读”。
- `task_bound_bot_reply`：bot 正在承接某个用户的私人任务或工具请求，即使这句话发在群里，也仍绑定原任务 owner。例如 A 说“帮我找几个视频”，bot 回“行，我找找”，这条 bot 回复公开可见，但任务 owner 仍是 A。
- 其他用户要接 `task_bound_bot_reply`，需要有明确接入动作：引用那条消息、明确说自己也要、或者当前公共 scene 已经由多人围绕同一任务连续展开。否则只能低压探问或不接，不能直接拿 A 的任务去搜。
- `open_public_bot_reply` 可以被跨用户短追问承接，但仍有短时间限制；过期后只能作为旧背景，不能主动复活。

建议给群聊窗口加 `ownership` 分类，而不是简单按 speakerId 拦截：

```js
ownership: 'current_user_task' | 'open_public_bot_reply' | 'task_bound_bot_reply' | 'public_scene' | 'other_user_task' | 'cold_background'
```

优先级：

1. 引用链 / replyTo / 明确 @：直接绑定被引用对象。
2. `open_public_bot_reply`：bot 上一句开放公共回复可被任何用户短追问承接，但只限短时间内。
3. `public_scene`：多人围绕同一现场连续发言，可被当前用户承接。
4. `current_user_task`：当前用户自己的未完成需求。
5. `task_bound_bot_reply`：bot 回复公开可见，但任务仍绑定某个用户；其他用户只有明确接入才可用。
6. `other_user_task`：其他用户的任务，只有明确接话才可用。
7. `cold_background`：只作背景，不触发工具。

这可以解释“请客吃饭/真的吗”的问题：它不是 B 继承 A 的私人任务，而是 B 在接 bot 刚刚公开回复，属于 `open_public_bot_reply`。也可以解释“行，我找找/帮我找找吧”的区别：后者虽然接在 bot 回复后，但 bot 回复属于 `task_bound_bot_reply`，不能自动把 A 的视频任务转给 B。

#### 群聊预期例子

以下例子只说明归属判断和回复方向，不是可复制的回复模板，也不能写成“匹配某短句就固定接某类上下文”的规则。实现必须先确认 active scene 里确实存在短时间内的 `open_public_bot_reply`、可明确接入的 `task_bound_bot_reply`、`public_scene`、引用链或当前用户任务，再决定是否承接。

例 1：公共 bot 回复，可以跨用户接。

```text
A：莲莲你有钱吗
Bot：有啊，今晚我请客。
B：真的吗
```

预期：bot 应接自己的上一句公开回复，类似“你还真信啊”“先欠着也不是不行”这种自然接话。不要回“什么真的？”也不要去翻旧记录。示例句只表示语气方向，不能固定成模板。

例 2：bot 公开解释，可以跨用户追问。

```text
A：这个 8.52mb 会不会卡
Bot：可能会，主要看生成时要不要反复读文件。
B：怎么说
```

预期：bot 应继续解释刚才公开回复里的“为什么会卡”，而不是把 B 当成新问题孤立处理。

例 3：公共 scene，可以跨用户接。

```text
A：这个表情包太抽象了
B：像刚睡醒
C：再来点这种
```

预期：如果当前现场都在围绕同一表情包/图片，C 的“这种”可以接公共 scene。若要发图或搜索，还要看工具对象是否自包含；普通吐槽可以直接接。

例 4：私人任务不能自动转移。

```text
A：帮我找几个我的世界搞笑视频
Bot：行，我找找。
B：帮我找找吧
```

如果 B 没有引用 A，也没有说“我也要这个”，预期：不能直接继承 A 的视频搜索。可以低压处理成“找啥呀”这种短探，或在群聊随机场景不插话；不能直接搜 A 的视频任务。

实现解释：这里 Bot 的“行，我找找”要被标成 `task_bound_bot_reply(owner=A, task=search_video)`，不是 `open_public_bot_reply`。所以 B 的“帮我找找吧”不能只因为上一句说话者是 bot 就继承搜索任务。

例 5：私人任务被明确接话，可以转成公共/当前任务。

```text
A：帮我找几个我的世界搞笑视频
Bot：行，我找找。
B：我也要这个
```

预期：B 明确接 A 的任务，“这个”可绑定当前公共现场里的视频需求，可以继续找同类视频。

实现解释：这里不是因为匹配“我也要这个”几个字，而是因为 B 的话语语义是“加入当前可见任务”。窗口层只提供 A 的任务、bot 的任务绑定和当前公共现场；是否把 B 绑定进去由模型基于这些信息判断，代码只阻止没有明确接入时自动转移私人任务。

例 6：旧公共回复过期，不应复活。

```text
两小时前：Bot：今晚我请客。
现在 B：真的吗
```

预期：不能硬接两小时前的请客。除非 B 明确说“你之前说请客是真的吗”，否则按当前现场轻处理，不翻旧账。

### 12.7 Step 5：现有调用链冲突点，必须同步处理

按当前代码追溯后，本计划不能只改 `agent/router.js`，否则会留下绕过路径。

#### 12.7.1 `getConversationHistory()` 的只读副作用会影响多个入口

当前这些入口都会读历史：

- `chat.js` 话题切换前用 `getRecentUserMessages(session, 1)` 取上一条用户消息。
- `chat.js` 随后用 `getConversationHistory(session)` 构造 prompt。
- `index.js` Agent 自动路由前用 `getRecentUserMessages(session, 4)` 给 router。
- `index.js` chat heavy tools 复述入口也用 `getRecentUserMessages(session, 4)` 给 router。
- `getQuotedMessageNote()` 会读历史判断引用内容是否已经在历史里。
- 命令和记忆确认也有少量只读历史入口。

因此修复不能只在 `chat.js` 里绕一下；需要保证：

- 所有只读入口都不会刷新“语义活跃时间”。
- 如果缓存确实需要 access 保活，必须写到单独 access 时间，不能被 inactive degrade 或私聊窗口分层使用。
- `getRecentUserMessages()` 需要有新版本可返回带 `ts/meta` 的结构化消息；旧的纯文本版本可以保留给普通用途，但不能继续给搜索补全使用。

#### 12.7.2 搜索预执行有两条入口，必须都过 searchReadiness

当前搜索进入 Agent 不是只有自动路由一条：

1. **显式/启发式 Agent 路由**
   - `index.js` 调 `heuristicRoute(userText, 'qq', { recentUserMessages })`。
   - 命中后再调 `buildExplicitSearchRunOptions(userText, { recentUserMessages })`。

2. **普通 chat 内嵌工具升级为 Agent**
   - `chat.js` 允许模型先请求 `web_search` 这类 heavy tool。
   - `handleChatResult()` 收到 `heavyToolsRequested` 后，会再次调用 `buildExplicitSearchRunOptions()`，然后把模型请求的 `web_search` 追加进 `preExecuteTools`。

第二条是潜在绕过点：即使 router 本身加了 `searchReadiness`，如果 `handleChatResult()` 无条件追加 `webSearchRequests`，短 query 仍可能被预执行。

硬约束：

- `searchReadiness` gate 必须在 `buildExplicitSearchRunOptions()` 内部生效。
- `handleChatResult()` 追加 `webSearchRequests` 前也要检查 gate；如果状态是 `needs_chat_handling` 或 `blocked_by_cold`，不能追加 `preExecuteTools`。
- chat 模型请求了 heavy `web_search` 但 gate 不允许时，应该回到普通 chat 自然回复/低压探问，而不是进入 Agent 搜索。
- `heuristicRoute()` 也不能只看 `recentUserMessages` 是否含搜索词；它应该使用同一份结构化 search context，否则自动 Agent 路由会和 chat heavy tool 路由判断不一致。

#### 12.7.3 `recentUserMessages` 纯文本数组会丢失时间和 meta

当前 router 只拿 `recentUserMessages: string[]`，它不知道：

- 每条消息是什么时候发的；
- 是 user 真实需求，还是人格/记忆/状态命令；
- 中间是否有任务切换；
- 这条消息来自当前用户、其他用户、bot 公开回复，还是旧背景；
- 该消息属于 hot/warm/cold 哪个窗口。

因此如果继续只传字符串，文档里的 hot/warm/cold、强暖 gate、ownership 都无法可靠实现。

需要新增结构化上下文，例如：

```js
{
  recentUserMessages: ['兼容旧接口的文本'],
  searchContextHints: [
    {
      text: '我的世界搞笑视频',
      ts: 0,
      source: 'private_hot' | 'private_warm' | 'group_open_public_bot_reply' | 'group_task_bound_bot_reply' | 'group_public_scene' | 'current_user_task',
      interrupted: false,
      metaTurn: false,
      confidence: 'hot' | 'warm_strong' | 'warm_weak'
    }
  ],
  searchReadiness: 'self_contained' | 'can_complete_from_hot' | 'can_complete_from_warm' | 'needs_chat_handling' | 'blocked_by_cold',
  queryCandidate: '',
  gateReason: '',
  blockedReason: ''
}
```

router 可以保留旧参数兼容，但只要是短追问搜索，就必须优先使用结构化上下文；没有结构化上下文时宁可降级为普通 chat，不要用纯文本数组硬拼 query。

#### 12.7.4 群聊有 `sharedContextNote` 和 `activeSceneNote` 两套提示，不能只改一套

当前群聊上下文至少有两路进入 `chat.js`：

- `getSharedContextNote()`：按回复链、当前参与者、短句跟进可能需要的消息拼出 `[群聊当前话题背景]`。
- `buildActiveGroupSceneNote()`：从 `channelSharedCache` 构造 `[当前群聊现场-最高优先级]`。

如果只给 `activeSceneNote` 加 ownership，但 `sharedContextNote` 仍把旧消息或其他用户任务作为“当前话题背景”塞进去，模型仍可能错接。

硬约束：

- 两套提示必须使用同一套 ownership / public scene / bot reply 语义。
- `getSharedContextNote()` 里的旧消息分隔 `[--- 以下是与当前无关的旧消息 ---]` 不能只靠文本提示；这些旧消息不得进入 searchContextHints。
- `buildActiveGroupSceneNote()` 的短句 fallback 会在 active 太少时取最近 8 条，这些只能作为现场候选给模型理解，不能自动提升成可执行搜索对象。
- 如果当前场景是随机主动插话，fallback 只能影响 `ambient_water/no_send/anchored_reply` 判断，不能触发 search/fetch。

#### 12.7.5 `read_group_context` 不能成为搜索补全后门

`read_group_context` 返回的是旧公共片段。它可以帮助理解“刚才/那个/这张图”，但不能让旧 scene 单独触发搜索。

规则：

- `read_group_context` 结果默认是 background。
- 只有当当前消息本身明确拉回，且工具结果中出现唯一对象，才可把它作为 chat 回答参考。
- 即使 `read_group_context` 找到旧视频任务，也不能自动变成 `web_search` query；还要重新通过 searchReadiness gate。
- 随机回复调用 `read_group_context` 后，如果仍不清楚，应 `ambient_water` 或 `no_send`，不是追问或搜索。

#### 12.7.6 自由路由优先：硬编码和正则不能影响语义决策

本计划的目标不是把 bot 改成“匹配短句 → 选择固定路线”的脚本。`agent/router.js` 里已有 `SEARCH_FOLLOW_UP_RE`、`SEARCH_REFINEMENT_RE`、`RESOURCE_SEARCH_RE` 等正则，后续实现可以保留它们作为安全边界或兼容兜底，但它们不能参与自由路由的核心决策。

硬约束：

- 不能新增“帮我找找吧 / 找找吧 / 来几个 / 真的吗 / 怎么说”这类固定短句路由。
- 不能用正则命中结果决定语义意图、搜索对象、上下文归属、是否继承他人任务、是否调用 Agent、是否预执行 `web_search`。
- 不能让正则结果覆盖模型基于 active scene、引用链、当前用户意图、工具可用性做出的自由判断。
- 不能把 `recentUserMessages` 或正则命中的历史片段拼接成 query 后直接预执行。
- 文档里的所有对话例子只说明期望语义和反例，不是模板、关键词表、测试快照固定文案，也不是可复制的 if/else 规则。

允许保留的确定性逻辑只限边界层：

- 安全边界：用户明确禁止联网、禁止搜索、禁止读图时，必须阻止工具。
- 能力边界：当前工具不可用、URL 格式不合法、query 为空或不自包含时，必须阻止工具。
- 资源边界：超时、并发、重试次数、随机回复过期、生产写入禁用等。
- 兼容边界：旧接口还需要布尔值时，可以返回“可能需要工具”的提示，但这个提示不能单独触发工具，必须交给结构化 `searchReadiness` 和模型自由路由再判断。

最终是否预执行搜索，必须由模型自由路由后的结构化结果进入统一 gate，再结合 `searchReadiness + queryCandidate 自包含检查 + ownership + 外部检索策略` 决定。正则最多能说“这里可能需要进入判断流程”，不能说“这里应该搜什么、接谁的话、怎么回”。

### 12.8 Step 6：代码落点按最小施工面推进

第一阶段只做止血和私聊搜索：

- `conversation.js`
  - 拆清语义活跃时间和只读历史。
  - 新消息写 `ts`。
  - 提供私聊 window 辅助或至少提供带时间过滤的 recent user messages。

- `chat.js`
  - inactive degrade 改用真实 turn 时间或消息级 `ts`。
  - 私聊 prompt 注入 active/background 分层。
  - 低压澄清只作为 prompt 边界，不加固定话术表。

- `agent/router.js`
  - `recentUserMessages` 升级为结构化 search context。
  - 暖窗口分 `can_complete_from_warm` 和 `needs_chat_handling`。
  - 非自包含短 query 不再直接 `preExecuteTools`。

- `index.js`
  - 只做最小接线，把结构化 search context 传给 router；不扩写主业务逻辑。

第二阶段再补群聊 ownership：

- `group-scene-index.js`
  - 在 active scene note 或结构化返回里标记 `open_public_bot_reply` / `task_bound_bot_reply` / `public_scene` / `other_user_task`。
  - bot 回复写入 scene 时继承它正在回答的对象：如果是闲聊或公共解释，标开放公共；如果是承接某用户工具/搜索/文件任务，标任务绑定。
  - 先解决“bot 刚刚公开回复，其他人短问接不上”的场景。

### 12.9 Step 7：测试与验收

行为测试优先放 scenario，覆盖真实失败链路，不用源码字符串扫描替代。

必须覆盖：

1. 语义时间污染：
   - 构造旧历史；
   - 调用只读历史入口；
   - 断言不会把语义活跃时间刷新成当前，旧历史仍会降级。

2. 旧私聊话题过期：
   - 很久前聊“我的世界搞笑视频”；
   - 中间多轮无关聊天或命令；
   - 用户说“帮我找找吧”；
   - 断言不会预执行 `web_search` 搜旧视频，也不会输出“UP 主/这个人/刚才网上搜”这类错接话术。

3. 当前私聊热窗口可补全：
   - 刚聊“我的世界搞笑视频”；
   - 用户马上说“帮我找找吧”；
   - 断言 query 可补成视频搜索意图，并触发 search。

4. 私聊强暖窗口可补全：
   - 1-3 小时内任务未被打断，bot 上一句是待执行确认；
   - 用户说“找找吧”；
   - 允许搜索，但只能使用唯一明确任务。

5. 私聊弱暖窗口不预执行：
   - 1-3 小时内聊过视频，中间聊了人格/天气/其他任务；
   - 用户说“帮我找找吧”；
   - 不预执行 search，不硬拉旧视频。

6. 多话题不串：
   - 天气 → 视频 → “那明天呢”；
   - 应优先回天气类追问，不混入视频。

7. 群聊 public bot reply：
   - A 和 bot 互动，bot 公开说“我请客”；
   - B 说“真的吗”；
   - active scene 应允许承接 bot 上一句，不能孤立回答“什么真的”。
   - 断言该 bot 回复被视为 `open_public_bot_reply`，不是 A 的私人任务。

8. 群聊私人任务不转移：
   - A 要视频，B 之后说“帮我找找吧”；
   - 没有引用/共同现场时，不能继承 A 的视频搜索。
   - 断言 bot 的“行，我找找”被视为 `task_bound_bot_reply(owner=A)`，B 不能仅凭短追问触发同一搜索。

9. 群聊私人任务明确接入：
   - A 要视频，bot 表示会找；
   - B 表达自己也要这个任务；
   - active scene 可以把 B 接入当前任务，但 query 仍要经过 search 自包含检查。

10. 不机械追问：
   - 短追问对象不清时，不允许连续输出同类“我不懂/你说的是啥”；
   - 但也不要求完整候选式追问，只断言非空、低泄漏、未误触工具、未翻旧账。

11. 自由路由不被硬编码替代：
   - 同一语义用不同自然说法表达，行为应保持一致；
   - 同一短句处在不同 active scene、引用链、用户归属下，行为应允许不同；
   - 测试不能只覆盖固定短句，也不能断言固定回复文案；
   - 如果删掉某个短句正则或改写措辞，核心语义路由仍应由结构化上下文和模型判断决定。

12. 明确链接内容问题不能假装查过：
   - 用户发公开 URL，并问“这个视频/网页/帖子/评论区说了什么”时，必须进入工具判断流程；
   - 如果现有工具只能读网页正文、读不到动态评论区或平台 API 受限，只能表达“当前没有拿到可依赖的评论区依据”这一层语义；具体怎么说必须交给当下人格自然生成，不能写固定兜底回复，也不能说“我刚才搜了一下/好像没找到”这种无工具依据的话；
   - 是否读取链接、搜索补充、或说明能力不足，仍由自由路由和工具结果决定，不能靠固定平台名或固定短句写死；
   - 对 B 站评论区这类动态内容，应把“网页正文”和“评论区数据”区分开，通用 `web_fetch` 失败不等于已经检查过评论区。

验收标准：

- 旧背景不会单独触发搜索。
- 私聊热窗口和强暖窗口能补全时不会装作忘记。
- 弱暖/冷窗口不会乱搜、不会假装搜过。
- 群聊能承接 bot 刚刚公开回复的跨用户短追问。
- 群聊不会把其他用户的私人旧任务自动转给当前用户。
- 回复不展示内部窗口、工具计划、候选菜单或推理链。
- 搜索链路要用真实输入 smoke 验证一次，确认工具确实按预期触发或不触发。
