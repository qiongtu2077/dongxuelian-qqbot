## 关键实现记录

### Dashboard 管理员 ID 封装

`fetchAdminIds()` 与 `updateAdminIds()` 现在都走管理员 token。这个接口当前不一定有页面直接调用，但前端封装已和后端权限要求对齐，避免后续接入页面时直接踩 403。

### 部署文档入口收敛

旧示例不再使用 `npx koishi start` / `npm exec koishi start`。文档入口改为：

```bash
bash /root/koishi-app/restart.sh
```

首次手动启动示例保留显式环境变量和本地 binary：

```bash
KOISHI_DIR=/root/koishi-app \
DONGXUELIAN_AI_DATA_DIR=/root/koishi-app/data \
nohup node /root/koishi-app/node_modules/koishi/bin.js start >> koishi.log 2>&1 &
```

### 图片缓存精确匹配

`cacheImageFile()` 仍按 `${getSafeKey(messageId)}.${ext}` 写入。`readCachedImage()` 不再用 `startsWith()` 扫描，而是只接受 basename 完全等于当前 messageId 的缓存文件，避免 `m1` 误读 `m10`。

### 图片分析回写用户会话

图片历史条目增加：

- `conversationKey`
- `userId`

图片消息入库时由 `index.js` 传入 `getConversationKey(session)`。后台分析完成后，`replaceImagePlaceholder()` 先从图片历史读取 `conversationKey`，再读写对应 conversation 文件；如果旧数据没有 `conversationKey`，只保留旧的 `channelKey` 回退路径。

### 连发多图精准替换

`saveConversationTurn()` 现在把 `session.messageId` 写到用户消息对象。`replaceImagePlaceholder()` 不再替换最近一条裸 `[图片]`，而是要求消息对象或 `meta.messageId` 与当前图片 messageId 匹配后才替换。

## 测试四问

1. 复现了用户哪条真实失败输入？

   本批对应的是审计复现出的真实链路风险，不是单条文本事故：
   - 只缓存 `m10` 后读取 `m1`，旧实现会命中错误图片缓存。
   - 用户同一会话连续发两张 `[图片]`，后台分析第二张图时旧实现可能替换最近裸占位符，且会读写 `channelKey` 会话而不是用户 conversation。
   - Dashboard 后续若调用 `fetchAdminIds()`，旧封装会因缺少 `X-Admin-Token` 被 403。
   - 新同学按旧文档执行 `npx koishi start` / `npm exec koishi start`，会绕过当前本地 binary 与显式 DATA_DIR 约束。

2. 断言了哪个失败现象不会再出现？

   - `m1` 不会再误读 `m10` / `m100` 的缓存文件。
   - 图片分析结果不会再默认写入 `conversations/<channelKey>.json`。
   - 连发多图时不会只按最近裸 `[图片]` 替换，必须匹配 messageId。
   - `fetchAdminIds()` 会携带管理员 token。
   - 活动文档中不再出现全局 `npx/npm exec koishi start` 示例。

3. 哪些依赖被 mock 了？

   - 图片链路测试使用临时 `DONGXUELIAN_AI_DATA_DIR`。
   - conversation 文件读写在本地临时目录验证，未写生产数据。
   - Dashboard API 封装通过静态 cascade 防线验证，没有启动真实浏览器。
   - 部署文档通过静态 cascade 防线验证，没有执行服务器重启。

4. 因为 mock，哪些真实链路仍未覆盖？

   - 未连接真实 QQ -> NapCat -> OneBot -> Koishi 的生产图片消息链路。
   - 未真实调用视觉模型对图片扣费分析。
   - 未在 Linux 服务器生产 data 上做真实图片追问 smoke。
   - 未部署、未重启服务器；这些操作仍需用户明确确认。
