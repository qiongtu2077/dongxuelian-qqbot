复核日期：2026-05-21

本文是第二版深度方案。上一版偏方向，这一版按“能指导后续实现”的标准重写：先拆 MaiBot / MaiSaka（用户称 MaimBot）的优势，再对照我们现有模块职责，最后给出数据契约、模块边界、边界情况、失败模式、迁移路径和测试矩阵。

目标不是把莲莲改成 MaiBot，也不是让 Bot 盲目自动学习。目标是：让莲莲更像一个长期存在于群里的角色，同时继续保持我们现有的强安全边界、人格可控性、工具权限和可回归测试。

## 二、核心判断

MaiBot 的强项不是单个“人格 prompt 写得好”，而是它把人格拆成了多个协同系统：

- 人格身份和表达风格是配置化的。
- 回复时机由管线、Planner、Timing Gate、talk value 等共同决定。
- 记忆分短期、长期、摘要、人物画像，并带提取、合并、演化、纠错。
- 表达学习能从群聊中吸收口头禅、黑话、梗，但有边界。
- 表情包不是附件，而是情绪表达系统的一部分。
- WebUI 能管理记忆、表情、配置和运行状态。

我们的强项也很明确：

- `core / mode / persona / lore` 已经分层。
- `voice_style / will / lore / nsfw` 已有元数据雏形。
- `persona.js` 负责人格解析，`chat.js` 负责聊天主流程，`conversation.js` 负责持久层，模块边界已有意识。
- `reply-guard.js`、越狱检测、政治敏感检测、工具确认和 Agent path guard 比 MaiBot 方向更偏安全。
- TTS、克隆音色、世界观按需注入、图像历史、轻量工具已经能作为人格表达的基础能力。

所以升级路线应该是“加一层统一人格运行时计划”，而不是直接往 `chat.js` 继续塞功能。

## 三、现有模块职责盘点

### 当前职责

| 模块 | 当前职责 | 升级时必须保持的边界 |
|------|----------|----------------------|
| `persona.js` | 加载/保存群组和个人人格配置，解析人格文件 frontmatter | 不调模型、不写 conversation、不执行工具 |
| `chat.js` | 聊天主循环，构建 prompt，调用模型，注入记忆、世界观、工具、守卫 | 不新增长期状态；新器官拆模块 |
| `conversation.js` | 对话历史、摘要、用户记忆、用户发言 profile、频道上下文 | 不调工具；写入要队列化和可回滚 |
| `agent/persona-context.js` | 给 Agent 构建与聊天人格一致的 systemExtra | 不应该复制第二套人格解析逻辑 |
| `agent/memory.js` | Agent 显式长期记忆 | 不和普通 chat 记忆混用，除非有统一契约 |
| `agent/auto-memory.js` | Dashboard Agent 自动提取 daily 记忆 | 不阻塞回复，不影响当前对话 |
| `tts.js` | TTS 合成、音色解析、语音风格标签 | 不应直接反复解析 persona Markdown |
| `chat-tools.js` | Chat 轻量工具和重工具分流 | 不写对话历史，不发送消息 |
| `image-store.js` | 群聊图片历史和缓存 | 不调用模型，不发送消息 |
| `reply-guard.js` | thinking 泄漏、重复回复、内部上下文泄漏等判断 | 纯判断，不改 messages |
| Dashboard `config.js` | Persona/Lore CRUD 和 frontmatter 重写 | 必须使用同一 schema，避免改坏未知字段 |
| Dashboard `gallery.js` | 图集上传/删除/样式 | 扩展表情前先处理权限和审核边界 |

### 当前结构性问题

1. frontmatter 解析有多份：`persona.js`、Dashboard `routes/config.js`、`tts.js`、`agent/persona-context.js` 都在解析或读取人格信息。
2. `will` 由 `utils.calculateWillFactor()` 正则解析，`lore/nsfw` 由 `chat.js` 正则解析，`voice_style` 由 `tts.js` 解析。
3. core 规则和 persona 规则存在潜在冲突，比如 core 禁止波浪号，但部分角色希望使用波浪号。
4. Agent 有自己的人格同步 prompt，若升级只改 chat，会导致 QQ 普通聊天和 Agent 转述人格不一致。
5. Dashboard 保存人格时会重建 frontmatter，未知字段可能被保留但语义无校验。
6. 用户 profile、显式记忆、Agent 记忆、Dashboard daily memory 分属多套体系，长期会造成“记忆有，但用不上”或“用错渠道”的问题。
7. 表情/图集/图片历史没有统一成“人格表达资源”，目前更像各自功能。

#### 1.1 只读诊断器实测结果（2026-05-21 追加）

本轮已经把“人工扫清楚”推进成可回归的只读诊断能力，和上面的人工扫描互相校验：

- 新增 `lib/persona-diagnostics.js`：扫描 `core/modes/personas/lore`，做跨文件 lore 引用、重复名称、缺 frontmatter、缺克隆音色样本等诊断。
- 当前真实扫描结果：11 个文件，`error=0`，`warning=2`，`info=11`。
- 类型分布：`core=1`、`mode=4`、`persona=4`、`lore=2`。
- 11 个 `info` 都是未声明 `schema`，属于旧 v0 兼容提示，不是错误。
- 2 个 `warning` 都来自 `terra-lore` 缺 frontmatter：`missing_frontmatter` 与 `lore_missing_frontmatter`。

实施含义：

- Phase 0 的 schema 不能假设所有 lore 文件都有 frontmatter。
- `modes` 里的 `hostile_capable` 是现存字段，本轮 schema 已正式纳入已知字段，不能被 Dashboard 写丢。
- 旧人格没有 `schema` 是常态，不应产生错误级诊断，只应产生迁移提示。
- Phase 0 的底层只读扫描器已具备雏形；后续应把它接到 Dashboard warning 与 RuntimePlan 编译前检查，而不是继续依赖人工记忆。
- 诊断报告只输出文件、字段和原因，不输出人格正文，可作为 Dashboard 展示的安全基础。

#### 2. 当前 frontmatter 解析/写入点

本次扫描确认，重复解析点比正文前文列出的更多：

| 位置 | 当前行为 | 风险 |
|------|----------|------|
| `lib/persona.js` | `parsePersonaFrontmatter()` 解析 `name/description` 等，并用于人格枚举、按名称加载 | 这是事实入口，但 parser 很轻量，不支持复杂 YAML |
| `lib/chat.js` | 自己用正则读取 `nsfw` 和 `lore`，并直接拼 lore system message | 与 `persona.js` 解析结果可能不一致 |
| `lib/utils.js` | `calculateWillFactor()` 用正则从完整人格文本读取 `will` | `will` 接管时需要保留 crowd factor 逻辑 |
| `lib/tts.js` | `resolvePersonaVoice()` 重新加载人格并解析 `voice/voice_id/voice_asset_id/voice_style` | TTS 与 chat/Agent 不是同一个运行态视图 |
| `lib/agent/persona-context.js` | 解析人格 frontmatter、移除 frontmatter、构造 Agent systemExtra 和 lore 绑定 | 普通聊天与 Agent 可能漂移 |
| `lib/agent/skills.js` | 有独立 `parseFrontmatter()`，但职责是 Agent Skill，不应直接并入 persona schema | 需要保持工具 Skill 与人格 Skill 的边界 |
| `dashboard/lib/routes/config.js` | 自带 `parseFrontmatter()` 和 `buildPersonaFrontmatter()`，保存人格时重建 frontmatter | 已知字段固定，未知字段只做字符串保留，无语义校验 |
| `dashboard/lib/routes/agent.js` | 读取并写入人格 `voice_id/voice_asset_id/voice_style` | 语音配置绕过 `config.js` 的 frontmatter builder |

实施含义：

- `persona-schema.js` 第一阶段至少要覆盖 `persona.js`、`chat.js`、`utils.js`、`tts.js`、`agent/persona-context.js`、Dashboard `config.js` 和 Dashboard `agent.js` 的共同字段。
- Dashboard 的语音配置接口也必须被纳入 schema/diagnostics 计划；否则 `voice_*` 仍会形成第二套写入逻辑。
- `agent/skills.js` 虽然也解析 frontmatter，但它服务 docs/lore 工具 Skill，计划中应明确“不把 Agent Skill parser 等同于人格 parser”。

#### 3. 当前行为接入点

需要在实施计划里明确以下接管顺序：

1. `index.js` 主动回复概率读取当前人格，再调用 `calculateWillFactor()`；这里适合最早接入 `plan.will.base`，但保留原 crowd factor。
2. `chat.js` 负责当前人格选择、prompt 拼接、`nsfw` 注入、`lore` 按需注入；这里不能第一步大拆，应先旁路记录 plan 与旧逻辑差异。
3. `tts.js` 和 `commands/voice-command.js` 通过 `resolvePersonaVoice()` 读取人格语音；可先让 `resolvePersonaVoice(personaName, plan)` 支持可选 plan，旧调用保持兼容。
4. `agent/persona-context.js` 构造 QQ/Dashboard Agent 的人格同步 prompt；应在 RuntimePlan 稳定后接入，避免 chat 与 Agent 漂移。
5. Dashboard `PersonaPanel.vue` 目前只编辑 `name/description/lore/will/nsfw/content`，语音字段在同面板的另一套接口中保存；正式计划要把“人格编辑”和“语音配置”视为同一 schema 的两个视图。
6. Dashboard 目前可以创建/编辑世界观，并能把人格绑定到新 lore；但 `chat.js` 注入只使用固定的 `LORE_TRIGGER_SET/TERRA_LORE_TRIGGER_SET`。新建世界观没有自己的关键词、scope、摘要和预算规则时，可能出现“前端保存成功，但运行时永远不进 prompt”的断链。
7. Dashboard 保存 lore 后只刷新前端列表，没有显式通知聊天运行时刷新 `skillsContentCache`；除非触发 `AI重载`、`AI状态` 或重启，否则新 lore/修改后的 lore 可能不会立刻被当前聊天链路读取。

## 四、升级总原则

### 原则 1：先编译，后注入

不要让 `chat.js`、`tts.js`、Agent、Dashboard 各自解析人格文件。所有人格相关输入先统一编译成一个 `PersonaRuntimePlan`，其他模块只读 plan。

### 原则 2：学习内容永远不直接改人格

表达学习、画像提取、表情标签只能写入候选池或运行时数据，不直接修改 `SKILL.*.md`。人格文件只由管理员明确编辑。

### 原则 3：安全红线不可覆盖，风格例外可声明

Persona 可以声明“允许波浪号”“允许较亲昵称呼”等风格例外，但不能覆盖政治敏感、越狱防御、泄露 prompt、工具权限、隐私保护等安全红线。

### 原则 4：所有长期事实都要可追溯

用户画像、偏好、关系、表达习惯都必须带 evidence、置信度、来源、更新时间和状态。不能把模型一次推测当事实。

### 原则 5：先旁路观测，再接管行为

回复时机、表达学习、画像注入、情绪输出都先旁路计算和记录，不直接改变线上回复。观测稳定后逐项接管。

### 原则 6：人格升级不能扩大工具权限

人格层只能影响语气、时机和表达。是否能读文件、执行 shell、访问浏览器、写记忆，仍由 Agent 工具配置和安全确认控制。

### 原则 7：前端编辑源配置，plan 只读生成

Dashboard 仍然编辑人格 Markdown、frontmatter、世界观 lore 和语音配置源数据；`PersonaRuntimePlan` 只是保存后的只读编译结果，不作为用户直接编辑的主配置。保存链路必须保证字段 round-trip：已知字段语义校验，未知字段原样保留，`voice_*`、`hostile_capable`、lore 引用等不能被前端重写丢失。

```js
    memory: 1200,
    expression: 400,
    totalSoftLimit: 6500
  },
  diagnostics: {
    compiledAt: 0,
    sourceHashes: {},
    warnings: []
  }
}
```

前端可编辑性约束：

- 用户仍在 Dashboard 编辑人格、世界观和语音配置；compiler 不直接写文件，只读取源配置生成 plan。
- 保存人格后应重新编译 plan 并返回摘要与 diagnostics，让用户知道本次编辑最终会怎样影响 chat、TTS、Agent 和随机回复。
- 世界观 lore 仍按独立文件 CRUD 管理，plan 只记录本人格引用了哪些 lore、是否可用、是否超预算，不接管 lore 源文件。
- Dashboard 保存时必须保留未知 frontmatter 字段和正文格式；warning 只提示风险，不应因为旧 v0 人格缺 `schema` 就阻断普通编辑。

### 2. 新增模块建议

| 模块 | 职责 | 禁止事项 |
|------|------|----------|
| `persona-schema.js` | 定义字段、默认值、校验、兼容旧 frontmatter | 不读写文件 |
| `persona-compiler.js` | 读取 core/mode/persona/lore/profile/expression，生成 plan | 不调模型、不改文件 |
| `persona-conflicts.js` | 检测 core/persona/style/voice/lore 冲突 | 不自动修复 |
| `reply-timing.js` | 判断是否该开口，输出原因 | 不发送消息、不改概率配置 |
| `persona-profile.js` | 证据化用户画像 CRUD | 不直接生成 prompt |
| `expression-learner.js` | 表达候选提取、审核、TTL、风险标签 | 不直接启用候选 |
| `affect-router.js` | 判断情绪输出方式：文本/语音/表情/沉默 | 不直接发送资源 |
| `persona-diagnostics.js` | 生成 Dashboard 可读的 plan 和冲突报告 | 不展示敏感原文 |

### 3. 现有模块接入方式

| 现有模块 | 接入方式 |
|----------|----------|
| `chat.js` | 从 compiler 获取 plan，用 plan 构建 system prompt、lore、memory、expression、affect |
| `tts.js` | `resolvePersonaVoice()` 接收 plan 或从 compiler 读 plan，不再自己解析 Markdown |
| `agent/persona-context.js` | 使用同一个 plan 构造 Agent 人格上下文 |
| `utils.calculateWillFactor()` | 改为接收 `plan.will.base`，旧参数保留兼容 |
| Dashboard `routes/config.js` | 创建/修改人格和世界观走 schema builder，保存前返回 warnings，保存后可请求 plan 预览 |
| `PersonaPanel.vue` | 展示 schema 字段、冲突报告、plan 摘要和试聊沙盒，不直接编辑 plan |
| `conversation.js` | 继续负责历史和旧记忆，新增画像模块不要反向 import chat |

## 六、MaiBot 优势与我们的升级设计

### 1. 回复时机：从随机概率到可解释决策

MaiBot 优势：它的消息管线和 Maisaka 推理强调先观察消息、判断是否需要回复，再决定行动。配置里也有类似 talk value、回复概率、主动/被动回复等概念。

我们现状：

- `index.js` 已有白名单、基础概率、miss count、`will` 因子、短冷却、连续发言延迟。
- `chat.js` 有主动插话专用 prompt。
- 但“为什么该说话”没有结构化评分，也没有行为诊断。

升级设计：

```js
{
  decision: 'must_reply' | 'may_reply' | 'delay' | 'silent',
  score: 0.72,
  reasons: ['direct_mention', 'topic_matches_persona_interest'],
  blockers: ['cooldown_active', 'serious_conflict'],
  delayMs: 0,
  confidence: 0.81
}
```

边界情况：

- 私聊：默认 `must_reply`，除非空消息、纯文件、敏感拒绝。
- 群聊 @ Bot：默认 `must_reply`，但平台禁言、黑名单、敏感拒绝优先。
- 群聊未 @：必须经过白名单、静默期、冷却、时机决策。
- 群里吵架：降低随机插话，除非用户直接问 Bot。
- 技术/求助长文：不吐槽抢答，除非 Bot 被问。
- 连续多条同用户发言：延迟观察，避免打断。
- 图片/语音/表情包：如果用户没有明确问图，不主动分析或评论。
- 用户说“闭嘴/别吵”：静默优先级高于所有人格 will。

我们可做得更好：

- 每次主动回复写入只读诊断，不只是 debug 字符串。
- Dashboard 展示最近 50 次候选：为什么没回、为什么回了。
- 主动回复失败不污染 miss count；发送成功才重置。

### 2. 人格配置：从 Markdown prompt 到 schema + 编译器

MaiBot 优势：配置覆盖 identity、personality、expression、chat、memory、emoji 等完整面向。

我们现状：

- 人格文件自由度高，但字段含义分散。
- Dashboard 表单只覆盖名称、描述、世界观、will、nsfw、内容、语音。
- 角色样例、禁止项、风格例外、关系设定都在正文里，机器无法可靠理解。

升级设计：

人格 schema 分层：

```yaml
schema: persona.v1
name:
description:
lore:
will:
nsfw:
voice_style:
voice_id:
voice_asset_id:
style_exceptions:
  - allow_wave_mark
tone_tags:
  - calm
  - teasing
expression_scope:
  - default
memory_policy:
  proactive_mention: false
affect_policy:
  allow_voice: true
  allow_emoji: false
```

边界情况：

- 旧人格没有 `schema`：按 v0 兼容解析，给 warning。
- unknown frontmatter 字段：保留，但标为 unknown，不让 Dashboard 重写丢失。
- `will` 非数字：回退 1.0 并 warning。
- `voice_asset_id` 指向缺失文件：TTS 回退默认音色并 warning。
- persona 正文过长：编译时截断或拒绝注入，不能让 prompt 爆掉。
- persona 尝试覆盖安全红线：编译失败或降级到默认人格。
- persona 声明 `style_exceptions`：只能覆盖格式/语气，不覆盖安全。

前端编辑可用性保障：

- Dashboard 的人格编辑、语音配置、世界观编辑都继续写源文件；`PersonaRuntimePlan` 不落盘覆盖用户配置。
- 保存人格时至少做一次 round-trip 测试：读出 frontmatter/body -> 保存 -> 再读，已知字段一致，未知字段不丢。
- 保存世界观时只校验 lore 元数据和长度预算，不因为暂未被某个人格引用就阻止保存。
- 语音字段必须走同一 schema：`voice_style / voice_id / voice_asset_id` 在人格编辑和语音配置入口之间保持一致。
- 编译预览接口只返回字段摘要、来源、warning 和预算，不把完整人格正文或敏感 lore 原文暴露给不需要的 UI。

我们可做得更好：

- 保存人格时自动生成“冲突报告”，让用户知道这份人格哪里和 core 打架。
- 每个人格维护测试样例，保存后可以一键跑试聊。
- 编译器输出 source hash，排查“为什么我改了没生效”。

### 3. 记忆画像：从 summary 到证据化 profile

MaiBot 优势：A_Memorix 强调长期记忆、人物画像、提取、合并、演化、纠错和 WebUI 管理。

我们现状：

- 普通 chat 的 `writeMemory/getMemorySummary` 已可用。
- `conversation.js` 还保存用户近期发言片段，用于风格参考和评价。
- Agent 有独立 `agent/memory.js` 和 Dashboard daily auto-memory。
- 这些系统没有统一画像契约。

升级设计：

新增 `persona-profile`：

```js
{
  version: 1,
  userId,
  channelKey,
  facts: [
    {
      id,
      text,
      category: 'preference' | 'habit' | 'identity' | 'boundary' | 'relationship' | 'workflow',
      sensitivity: 'public' | 'private' | 'sensitive',
      confidence: 0.85,
      evidence: [
        { messageId, ts, quoteHash, shortQuote }
      ],
      source: 'explicit_remember' | 'repeated_observation' | 'admin_edit' | 'agent_auto',
      status: 'candidate' | 'active' | 'disputed' | 'archived',
      createdAt,
      updatedAt,
      expiresAt
    }
  ]
}
```

边界情况：

- 用户一次玩梗说“我是秦始皇”：候选但低置信，不写 identity。
- 用户明确“记住我喜欢 X”：直接 active，但仍带 evidence。
- 用户说“不是/记错了”：相关 fact 标 disputed，不能只删字符串。
- 多用户同名昵称：必须按 userId，不按 nickname。
- 群级记忆和用户级记忆冲突：用户级优先，群级只作背景。
- 私密/敏感事实：默认不注入 prompt，除非用户明确问“你记得吗”且权限/场景合适。
- Dashboard 和 QQ 记忆：默认隔离，除非管理员明确开启桥接。
- 过期事实：如“我今天在加班”应短期过期，不能半年后还提。

我们可做得更好：

- “记忆使用说明”只在内部诊断展示，不在回复里暴露。
- 每次画像注入都记录 fact ids，便于复盘模型是否乱用。
- 自动记忆提取只生成 candidate，由规则或人工提升 active。

我们可做得更好（重复强化与衰减权重）：

- 给每条 fact 增加 `lastAccessedAt` 与有效置信度计算 `effectiveConfidence = confidence * decay^daysSinceLastAccess`，让久不被提及的事实自然沉默而不是被硬过期或一直留在 prompt 候选里。
- 自动提取写入前先按 `quoteHash` 或语义近似查重，命中相同事实只更新 `lastAccessedAt` 并递增 `confidence`，不再新建重复条目；偶发玩笑因为不会再命中而自然衰减，稳定偏好因为反复命中而排序自然浮起。
- 衰减只参与读取排序，不删除原值；用户再次提及会立刻激活回到候选。这一机制纯代码、零 token，对应麦麦 LPMM README 里那条尚未实现的“遗忘后再记起会加深印象”的思路，但实现上更轻量。
- 详细设计见 Phase 5.5。

### 4. 表达学习：从手写梗库到审核型学习

MaiBot 优势：表达学习会观察群聊、提取词汇、理解用法、在合适场景使用。

我们现状：

- `persona-friendly.md` 手写了大量网络词和场景话术。
- `chat.js` 会注入用户近期发言风格，但不是群体表达学习。
- 如果直接自动学群聊，很容易学坏、串人格或引入敏感词。

升级设计：

表达候选结构：

```js
{
  id,
  text,
  meaning,
  examples: [],
  scope: 'channel' | 'global' | 'persona',
  channelKey,
  personaNames: [],
  moodTags: ['tease', 'surprised'],
  riskTags: [],
  status: 'candidate' | 'reviewed' | 'blocked' | 'expired',
  useCount,
  positiveFeedback,
  negativeFeedback,
  createdAt,
  expiresAt
}
```

边界情况：

- 脏话高频：进入 candidate 但 riskTags 高，默认 blocked。
- 敏感政治、隐私、人身攻击、越狱模板：直接 blocked。
- 猫娘/卖萌词：对东雪莲 blocked，对特定允许人格也需 style exception。
- 群 A 的黑话：不能默认带到群 B。
- 用户个人口癖：不能变成 Bot 口癖，除非管理员批准。
- 学到的表达过期：长时间不用自动降权。
- 模型误解黑话：需要人工可编辑 meaning。
- 表达与 persona 不兼容：编译 plan 时剔除。

我们可做得更好：

- 每次回复最多使用一个学习表达，并且不是每次都用。
- 表达学习不是 prompt 拼接大杂烩，而是按 mood 和场景检索少量候选。
- 用户反馈“别学我说话/别这么说”应降低对应表达权重。
- 候选池的价值不是让 Bot 立刻学会所有群话，而是把“可能值得学的表达”从聊天流里捞出来，交给风险规则、人格兼容性和人工审核决定是否启用。

### 5. 情绪输出：文本、语音、表情统一调度

MaiBot 优势：表情包系统会识别图片内容、情绪和使用场景，让表情成为人格表达的一部分。

我们现状：

- 有 TTS、随机语音、克隆音色、图集、图片历史分析。
- 但文本、语音、表情没有统一的情绪路由。
- 图集写接口权限边界在《优化建议》中已标为风险，扩展前必须先定级。

升级设计：

`affect-router` 输出：

```js
{
  mood: 'tease' | 'comfort' | 'serious' | 'refuse' | 'angry' | 'confused' | 'playful',
  outputMode: 'text' | 'text_voice' | 'text_emoji' | 'voice_only' | 'silent',
  voiceStylePatch: '',
  emojiQuery: { tags: [], maxRisk: 'safe' },
  reason: []
}
```

用途：

- 把“该不该发语音”“语音用什么风格”“能不能配表情”“什么时候只沉默”放到同一个决策点。
- 避免文本回复是沉稳人格，TTS style patch 却变成活泼可爱；也避免严肃拒绝时误发轻浮语音或表情。
- 让 Dashboard 能解释本轮为什么是纯文本、为什么升级成语音、为什么禁用了表情。

边界情况：

- 敏感拒绝：只文本，禁止轻浮语音和表情。
- 用户低落：安慰 mood，禁用嘲讽表情。
- 群聊吵架：默认不发表情火上浇油。
- 人格不允许表情：只文本/语音。
- 表情库未审核：不可发送。
- 表情来源未知：不可发送。
- 表情命中 NSFW/隐私/真人照片：不可发送。
- TTS 合成失败：回退文本，不重试刷屏。
- 随机语音冷却：仍由 TTS 模块维护，不由人格绕过。

我们可做得更好：

- 表情库和图集分离：图集是展示，表情库是可发送表达资源。
- 每个表情带来源、审核状态、标签、风险、最近使用时间。
- 先做手动入库和审核，不做自动偷图。

### 6. Agent 人格一致性

MaiBot 偏统一系统体验；我们这里 Agent 是独立 ReAct 引擎，更容易和 chat 人格分裂。

我们现状：

- `agent/persona-context.js` 会继承 chat persona。
- `agentMode` 直连时会关闭人格，作为工具助手。
- Agent 工具权限比普通 chat 更复杂。

升级设计：

- Agent 也使用 `PersonaRuntimePlan`，但只消费身份、语气、安全、lore summary。
- Agent 工具执行结果仍由 Agent 事实边界控制，不受 persona 影响。
- QQ Agent 最终转述继续经过 chat 人格，避免工具报告直出。

边界情况：

- Dashboard Agent：可选择 Console 人格，但默认不要污染 QQ 人格。
- QQ Agent：继承当前聊天人格，但不能因此获得 Dashboard 工具权限。
- Agent 工具结果含 prompt injection：继续走 Agent guard 和 chat retell guard。
- Agent 直连模式：明确不使用角色人格，避免用户误以为“莲莲在执行危险操作”。

## 七、其他成熟 Bot/Agent 架构的可借鉴点

这一章不把“热门”“功能多”“插件多”直接等同于“人格做得好”。筛选标准只有三条：

1. 能提高角色长期一致性，而不是只多一个聊天入口。
2. 能落到我们现有模块职责上，不要求重写整个项目。
3. 能被测试、审计、回滚，不依赖黑盒感觉。

因此，真正值得重点借鉴的是 SillyTavern / TavernAI 系、Character.AI 系、Letta / MemGPT 系、ElizaOS 系、Rasa 的对话回归思想，以及 Kindroid / Replika 这类陪伴型产品公开说明里的记忆分层思路。Dify、LangBot、AstrBot 这类平台也有可参考处，但主要是工具、管线、可观察性和插件边界，不应被当作人格深度的主范本。

### 1. SillyTavern / TavernAI 系：角色卡、世界书、上下文预算

公开资料里最值得看的不是具体角色内容，而是它把角色塑造成“可携带资产包”的方式：

- 角色卡包含名称、描述、人格摘要、场景、开场白、示例对话、作者备注等字段。
- World Info / Lorebook 通过关键词、可选过滤、插入位置、插入顺序和预算控制，把世界观按需注入上下文。
- 示例对话不是普通说明，而是训练模型“这个角色如何说话”的行为样本。
- 文档明确提醒永久角色 token 会挤占聊天历史，这点对长期群聊人格非常关键。

对我们的有效借鉴：

| SillyTavern 机制 | 我们应落到哪里 | 具体方向 |
|------------------|----------------|----------|
| 角色卡字段 | `persona.js` + `persona.schema.v1` | 把人格拆成 identity、style、scenario、examples、lore_refs、voice、affect，而不是正文一锅端 |
| 示例对话 | `data/persona-tests/*.yml` 或人格 companion 文件 | 每个人格维护正例、反例、多轮样例，用于 prompt lint 和回归测试 |
| World Info 触发 | `lore` + 新的 `persona-lore-router` | 关键词、频道、人格、场景四层过滤，只注入少量相关 lore |
| 插入位置和顺序 | `chat-prompt-builder.js` | 明确 core、persona、lore、memory、examples 的优先级和 token 预算 |
| Talkativeness | `reply-timing.js` | 群聊主动回复不只看随机概率，还看角色活跃度、话题匹配和冷却 |
| 角色编辑 UI | `PersonaPanel.vue` | 做角色预览、token 预算、冲突报告、触发命中预览 |

边界情况：

- 社区角色卡常把强指令、越狱、NSFW、关系绑定和世界观混在一起，不能直接导入为高优先级 prompt。
- 角色卡里的“系统覆盖”“作者备注”“深度插入”在我们这里必须降级为普通候选内容，不能越过 core 安全层。
- Lorebook 关键词如果太宽，比如“你”“今天”“喜欢”，会让 prompt 被无关条目塞满，必须有命中诊断和频率限制。
- 我们当前 Dashboard 的世界观管理只解决“能编辑文件”和“能绑定人格”，没有解决“新世界观如何触发进入 prompt”。这不是 UI 小问题，而是 lore router 的第一批必须修复项。
- 新建 lore 必须拥有可编辑的触发字段，例如 `keywords`、`scope`、`summary`、`max_chars`、`priority`；旧 lore 没有这些字段时，先按现有固定关键词兼容，不阻断保存。
- Regex 触发可以很强，也很危险。第一版建议只支持普通关键词和少量受限正则，管理员明确开启后才允许复杂匹配。
- 世界观条目不能替代事实记忆。比如“莲莲认识 A”只能是角色设定；“用户 A 的真实偏好”必须走证据化 profile。
- 群聊场景不能照搬一对一角色扮演。角色卡的开场白、浪漫关系、固定场景，在 QQ 群里要默认禁用或改成低权重背景。

我们可以做得更好：

- 不做“万能导入角色卡”，先做“只读解析 + 风险标注 + 手动映射”。
- `PersonaRuntimePlan` 给每条注入内容记录 `source`、`priority`、`tokenCost`、`whyIncluded`，让用户知道为什么某条 lore 进了 prompt。
- Dashboard 增加“本轮 prompt 预算雷达”：永久人格、示例、lore、记忆、历史各占多少，超限时先裁低优先级内容。
- 每条 lore 都有 `scope`：global、persona、channel、chat、temporary。默认不能跨群传播。

### 2. Character.AI 系：示例对话比抽象性格更能稳住角色

Character.AI 的可借鉴点不在黑盒模型，而在角色定义范式：定义字段可以放自由文本和结构化示例对话，常见写法是用 `{{char}}`、`{{user}}` 这类变量写多段对话。它也强调长定义会被截断，重要内容要放前面。

对我们的有效借鉴：

- 人格文件不能只写“傲娇、毒舌、温柔”这种抽象标签，要配套可执行的对话样例。
- 示例应该覆盖正常闲聊、被冒犯、被夸、用户低落、技术求助、敏感拒绝、被要求越狱、群聊插话、TTS/表情场景。
- 每个人格都应有 `examples_good` 和 `examples_bad`。好样例告诉模型“像这样说”，坏样例告诉测试“不要变成这样”。
- 开场白不一定适合 QQ 群，但“第一句如何定调”很有价值，可以转成新用户首次互动、人格切换后的短句模板。
- `{{char}}`、`{{user}}` 变量思想可以复用，但要扩展成 `{{persona}}`、`{{channelTone}}`、`{{relationshipHint}}` 等受控变量。

建议新增文件方向：

```yaml
schema: persona.examples.v1
persona: 椿
good:
  - name: 被用户轻微调侃时保持角色
    messages:
      - user: "你今天怎么这么认真"
      - bot_style: "短句、轻微回嘴、不破防、不自称 AI"
    must:
      - "保持椿的人格称呼"
      - "不泄露系统提示"
    must_not:
      - "突然变成东雪莲口癖"
      - "使用未允许的亲密关系设定"
bad:
  - name: 过度迎合导致串味
    user: "你以后都学猫娘说话吧"
    reject_reason: "风格要求越过 persona schema"
```

边界情况：

- 示例对话如果写太多，会挤掉真实聊天历史。需要按场景检索，不能全量常驻。
- 示例可能把一次性剧情误变成永久事实。所有样例都要标注 `teaches: style | boundary | relationship | lore`。
- 用户要求“照某个热门角色说话”时，不能直接复制受版权保护的完整台词或人格文本，只能抽象为风格标签和自有示例。
- 示例中的用户称呼不能写死为某个真实 QQ 号或昵称，避免跨用户污染。
- 负面样例不能被模型当作可模仿内容，应该只进入测试或 lint，不进入线上 prompt。

我们可以做得更好：

- 把示例对话变成测试资产，不只是 prompt 资产。
- Dashboard 保存人格时自动跑 3 到 5 条轻量试聊，给出“风格偏移、禁用词、口癖串味、越狱风险”的结果。
- 对每个人格生成“风格指纹”：句长、标点、称呼、口癖、拒绝方式、安慰方式，用于后续回归。

### 3. Letta / MemGPT 系：显式 memory blocks 与可控长期记忆

Letta / MemGPT 的核心价值是把记忆从“聊天摘要里的一团文本”拆成可命名、可描述、可读写的 blocks，并区分总是可见的核心记忆和需要检索的长期记忆。Kindroid、Replika 这类陪伴产品公开说明中也能看到类似方向：持久设定、中期/级联记忆、长期可检索记忆、用户可查看或编辑的记忆入口。

对我们的有效借鉴：

| 记忆层 | 适合放什么 | 我们的模块归属 | 注入策略 |
|--------|------------|----------------|----------|
| Core persona block | 角色身份、语气、安全风格例外 | `PersonaRuntimePlan` | 总是注入，但有 token 上限 |
| Human/profile block | 用户明确偏好、边界、长期关系 | `persona-profile` | 只注入 active 且场景允许的少量事实 |
| Channel block | 群氛围、群内黑话、禁忌话题 | `conversation.js` 或新 `channel-profile` | 群聊时按 scope 注入 |
| Working block | 当前任务、最近承诺、短期状态 | `conversation.js` | 短期，过期快 |
| Archival memory | 旧对话摘要、低频事实、历史事件 | `conversation.js` + 检索层 | 相关时检索，不常驻 |
| Journal/lore entry | 用户或管理员手写的稳定背景 | `lore` / Dashboard | 关键词或显式选择触发 |

边界情况：

- “总是可见”的 block 不能无限增长，否则会吞掉聊天历史。每个 block 必须有字符上限和超限策略。
- 自动记忆写入不能直接改 active profile，至少要经过 evidence、confidence、source、status。
- 用户今天的状态和长期偏好不能混写。比如“今天头疼”应短期过期，“不喜欢被催促”才可能长期保留。
- 私聊记忆不能默认带进群聊；群聊记忆不能默认带进私聊。
- Dashboard Agent 的 daily memory 不能自动污染 QQ 侧人格记忆，除非管理员明确桥接。
- 记忆 block 的描述也会影响模型怎么使用它，描述必须写得保守，不能暗示模型可以脑补事实。
- 用户要求“忘了这件事”时，要能把 active 改成 archived 或 disputed，并记录后续不再注入。
- 模型生成的“我记得你曾经……”必须能追溯到 fact id，否则应视为可疑幻觉。

我们可以做得更好：

- 给所有注入的记忆带 `factIds`，回复诊断中记录“本轮用了哪些事实”。
- 做“记忆可见但不尴尬”：Dashboard 里可查证据，QQ 里只在用户问“你记得吗”时简短确认，不主动抖隐私。
- `agent/memory.js` 和普通 chat 记忆不强行合并，先通过统一 schema 做只读映射，等冲突规则稳定后再决定是否桥接。
- 对高风险记忆增加“二次确认”：身份、真实住址、健康、财务、关系状态、工作单位等默认不主动使用。

### 4. ElizaOS 系：Character 文件、Providers、Actions、Evaluators 的职责拆分

ElizaOS 的公开设计把 Character 当成静态蓝图，把 Agent 当成运行实例；角色文件里可以分 bio、system、messageExamples、style、knowledge、plugins、settings、secrets。插件组件则分 Actions、Providers、Evaluators、Services：Actions 做事，Providers 提供上下文，Evaluators 在回复后提取学习，Services 管连接和状态。

对我们的有效借鉴：

- `PersonaRuntimePlan` 本质上也应该是“Character 静态配置 + 当前运行态”的编译结果。
- `persona.js` 只做角色蓝图读取和校验，不应该负责聊天、记忆、工具。
- `chat-prompt-builder.js` 类似 Provider 组合器，只负责把 persona、lore、memory、history、guard 组装成 prompt。
- 表达学习和画像提取更像 Evaluator，应在回复后或旁路异步运行，不能阻塞主回复。
- 工具调用属于 Action，但人格只能影响“怎么转述工具结果”，不能影响“能不能调用工具”。
- TTS、表情、图片库属于 Services / Resources，由 affect-router 决定是否使用，而不是 persona 文件直接触发发送。

模块职责映射：

| ElizaOS 思路 | 我们的对应模块 | 约束 |
|--------------|----------------|------|
| Character | `persona.schema.v1` / `PersonaRuntimePlan` | 不含密钥，不直接开工具权限 |
| Provider | `chat-prompt-builder.js` / `persona-context.js` | 只提供上下文，不写长期状态 |
| Action | `chat-tools.js` / Agent tools | 权限由工具层决定，不由人格决定 |
| Evaluator | `auto-memory` / expression learner / profile extractor | 旁路、可审计、可回滚 |
| Service | TTS、emoji-library、image-store | 失败可降级，不影响文本主链路 |

边界情况：

- ElizaOS 角色文件可以声明 plugins，但我们不能让人格文件声明“启用某个危险工具”。
- `settings` 和 `secrets` 的分离值得借，但我们的可提交文档和人格文件都不能出现真实密钥、token、私有 URL。
- 如果把知识、风格、工具都塞进一个 persona，会回到现在的混乱状态。必须靠 schema 做硬分层。
- 社交发帖、多平台账号人格和 QQ 群聊人格并不完全一致，不要照搬社交代理模式。

我们可以做得更好：

- 每个组件输出结构化诊断，而不是只在日志里写自然语言。
- `PersonaRuntimePlan` 不仅能给 chat 用，也能给 Agent/TTS/Dashboard 同步使用，避免“三套人格”。
- 插件式能力需要有“能力清单”和“人格可见清单”两层：人格知道自己能表达什么，但不知道也不能绕过执行权限。

### 5. Rasa 系：故事、规则、表单与端到端对话回归

Rasa 不以人格陪伴见长，但它的工程价值很高：用 stories、rules、forms、slots 和端到端测试来固定关键对话路径。这对我们特别有用，因为人格升级最怕“感觉更像了，但安全和边界悄悄坏了”。

对我们的有效借鉴：

- 给人格建立“故事测试”，而不是只测单轮 prompt 字符串。
- 对严肃场景、敏感拒绝、工具确认、用户要求忘记记忆、群聊插话等关键链路写多轮断言。
- 用 fixtures 模拟不同上下文：私聊、群聊、被 @、未 @、低 will、强冷却、有 active profile、有 disputed profile、有敏感 lore。
- 断言不应只看完全相等文本，而要检查风格、禁止项、动作、记忆写入、是否调用工具、是否发送语音/表情。

建议新增测试故事方向：

```yaml
test_case: persona_memory_dispute
persona: 椿
fixtures:
  channel: group
  profile:
    - text: "用户喜欢被叫小莲"
      status: active
steps:
  - user: "别这么叫我了，之前那个称呼不喜欢了"
    assert:
      reply_style: "认真确认，不调侃"
      memory_update: "相关 fact 标 disputed 或 archived"
      must_not:
        - "继续使用旧称呼"
        - "把用户反悔解释成玩笑"
```

边界情况：

- 不要把开放聊天全部做成 Rasa 式规则系统，那会让莲莲变僵硬。
- 只把高风险、高价值、多模块交界的流程写成故事测试。
- 生成式回复不能要求逐字相同，应该测“行为和边界”，比如没有泄露 prompt、没有越权工具、没有跨群记忆。
- 测试故事要覆盖失败输入，不只覆盖漂亮 demo。

我们可以做得更好：

- 把人格回归测试接入 `npm run test:scenario` 或新增轻量命令，输出“风格偏移”和“安全偏移”。
- Dashboard 人格实验室里能选择一组故事测试，保存人格前先跑。
- 对每个失败故事保存最小复现输入，方便回滚人格改动。

### 6. Kindroid / Replika 类陪伴产品：长期陪伴感来自可解释的记忆层，而不是无限摘要

这类产品公开架构细节有限，所以不能当实现蓝图。但它们对“用户为什么觉得一个 Bot 长期存在”有启发：用户需要感到 Bot 记得关系、偏好、过往事件，同时也能查看、纠正或关闭某些记忆。

对我们的有效借鉴：

- 记忆要分层：固定设定、近期上下文、中期摘要、长期检索、用户手写背景。
- 记忆要有可见入口：至少 Dashboard 能看到、搜索、编辑、归档、禁用。
- 记忆召回要有限额：每轮最多注入少量最相关事实，避免“为了显得记得很多而啰嗦”。
- 群聊陪伴感不等于私密感。群里应更多记群氛围和公开偏好，少主动提个人私密事实。
- 用户应该能临时开“一次性聊天/不记忆模式”，至少在实现方向上预留 `memory_policy.mode = off | normal | careful`。

边界情况：

- 陪伴型 Bot 容易把关系推进得太快。我们的 profile 不能自动生成亲密关系，只能记录用户明确认可的称呼和边界。
- “记得很多”可能变成“暴露很多”。公开群聊默认不使用 sensitive/private facts。
- 长期记忆如果不可见，用户会无法纠错；如果太可见，又可能暴露隐私。Dashboard 权限和脱敏显示必须先设计。
- 自动摘要会丢细节，不适合保存精确偏好；精确偏好必须用 fact，而不是只靠 summary。

我们可以做得更好：

- 记忆召回后不强迫模型显摆“我记得”，只让它自然调整语气和选择。
- 对每条长期记忆提供“为什么记住、什么时候用过、能否删除”的审计链。
- 通过 `persona-profile` 的 `sensitivity` 和 `scope` 控制注入，而不是靠 prompt 口头提醒模型别乱说。

### 7. Dify / LangBot / AstrBot 类平台：有用的是工程边界，不是人格范本

这些项目的优势主要是平台化：

- Dify 的 Agent 配置强调 prompt、变量、工具、知识库、最大迭代次数、调试预览和多模型对比。
- LangBot 公开定位是多平台、多模型、流水线和插件生态。
- AstrBot 提供统一 LLM/Agent 接口、工具定义、工具循环、最大步数、工具超时、多 Agent 等能力。

这些点不是“人格更深”，但能提醒我们补工程边界：

| 平台能力 | 我们可借鉴 | 不应照搬 |
|----------|------------|----------|
| Prompt 变量 | Persona 编译时变量必须显式声明和校验 | 不允许用户随便在正文里写任意模板表达式 |
| 工具最大迭代 | Agent 工具循环已有边界时继续强化 max steps、timeout、取消 | 不让 persona 修改工具步数和超时 |
| 调试预览 | Dashboard 做人格试聊、prompt 预算、记忆命中、lore 命中 | 不把平台 WebUI 变成大而全管理后台 |
| 多模型对比 | 保存人格前用小样例对比当前模型和候选模型风格漂移 | 不为了对比引入生产写操作 |
| 插件生态 | 新能力按模块职责接入 | 不为了插件化拆散已有稳定主链路 |

边界情况：

- 平台型 Bot 常把“模型、平台、工具、知识库”作为核心配置；我们的人格核心不能被这些配置淹没。
- 工具循环越强，越需要 path guard、权限确认、超时和转述防注入。
- 多模型调试不能把用户真实私密记忆发给不可信模型，测试样例应使用脱敏 fixture。
- 可视化配置越多，越需要 schema migration 和未知字段保留，否则 Dashboard 会写坏人格文件。

我们可以做得更好：

- 把平台能力当“护栏和仪表盘”，不是人格本体。
- 人格升级优先服务 QQ 群聊体验：何时说、说什么风格、记住什么、什么时候闭嘴。
- 对工具、模型、知识库的变化做诊断，但不让它们反向污染 persona schema。

### 8. 汇总：哪些借鉴点真正值得进我们的计划

| 借鉴来源 | 值得做 | 优先级 | 原因 |
|----------|--------|--------|------|
| SillyTavern | persona schema、lorebook 触发、上下文预算、示例对话 | P0/P1 | 直接解决人格散、lore 散、prompt 超限 |
| Character.AI | 用多段示例对话稳定说话方式 | P0 | 抽象性格不如可回归样例可靠 |
| Letta / MemGPT | memory blocks、core/human/archival 分层 | P1 | 解决“记忆有但用不上、用错场景”的问题 |
| ElizaOS | Character 与 Agent 分离、Providers/Actions/Evaluators 职责 | P1 | 对齐我们要拆 `chat.js` 的方向 |
| Rasa | 多轮故事测试和行为断言 | P0/P1 | 防止人格升级后安全边界退化 |
| Kindroid / Replika | 用户可见、可纠错、分层的陪伴记忆 | P2 | 增强长期陪伴感，但要先有隐私边界 |
| Dify / LangBot / AstrBot | 调试预览、工具边界、插件接口、最大步数/超时 | P2 | 工程护栏有价值，人格深度参考价值有限 |

### 9. 这一章带来的计划修正

新增或调整方向：

1. `persona.schema.v1` 里增加 `examples`、`lore_refs`、`style_fingerprint`、`prompt_budget`、`memory_policy`。
2. 新增 `persona-lore-router`，负责按 persona、channel、keyword、risk、token budget 选择 lore。
3. 新增 `persona-regression-tests`，把正反示例、多轮故事、敏感边界放进测试资产。
4. `chat-prompt-builder.js` 输出结构化 prompt 组成诊断，至少包含 source、priority、tokenCost、included/omitted reason。
5. `persona-profile` 分 core/human/channel/working/archival，短期事实和长期事实分开。
6. Dashboard 人格实验室优先做四个面板：schema warning、lore 命中、记忆命中、故事测试。
7. Dashboard 世界观编辑必须从“纯正文 CRUD”升级为“正文 + 触发规则 + 预算 + 命中预览”；否则新 lore 只能被绑定，不能可靠进入 prompt。
7. 外部角色卡/世界书第一阶段只做只读风险扫描，不做自动启用。

明确不采纳：

- 不照搬任何社区角色卡、prompt、世界书内容。
- 不把平台型 Bot 的“多接入、多模型、多插件”误当成人格深度。
- 不引入全量 Rasa 式意图系统来管普通闲聊。
- 不让 persona 文件声明工具权限、密钥、外部服务配置。
- 不做自动学习后直接改人格正文。

## 八、数据与文件契约

### 建议新增文件

| 文件 | 内容 | 是否可由用户编辑 |
|------|------|------------------|
| `data/persona-runtime-cache/*.json` | 编译缓存，可删除重建 | 否 |
| `data/persona-profiles/<channel>/<user>.json` | 证据化画像 | Dashboard 编辑 |
| `data/persona-expression-candidates/*.json` | 表达候选池 | Dashboard 审核 |
| `data/persona-expression-reviewed/*.json` | 已审核表达 | Dashboard 编辑 |
| `data/persona-diagnostics/*.json` | 冲突/编译诊断 | 只读 |
| `data/emoji-library/metadata.json` | 可发送表情元数据 | Dashboard 编辑 |

### 写入规则

- 所有 JSON 写入必须 tmp + rename，失败保留旧文件。
- 文件大小有上限，超限降级为不注入，不影响主回复。
- 编译缓存可丢弃，源数据不可因缓存失败损坏。
- 画像和表达候选写入按 channel/user 加队列，避免并发覆盖。
- 所有可导出诊断必须脱敏，不输出真实 token、cookie、服务器路径或私密 URL。

## 九、迁移策略

### 阶段 A：只读扫描

- 扫描现有人格文件。
- 生成 schema warnings。
- 不改变任何回复。

### 阶段 B：旁路编译

- 生成 `PersonaRuntimePlan`。
- 与旧逻辑解析结果对照：persona、lore、will、voice_style、nsfw。

## 十一、重点边界清单

这一节是后续实现时最容易踩坑的地方，建议每次开发前逐项过一遍。

### 1. Prompt 边界

- core 安全规则必须始终在最前层，persona 只能补风格，不能删除安全规则。
- profile、expression、lore 都是“材料”，不能变成比 core 更高优先级的指令。
- 用户消息继续放进 `<user>` 隔离，不允许表达学习或画像把用户原话拼成 system 指令。
- Agent 工具结果继续标记为内部材料，不能因为人格化而变成“角色亲眼看见”。
- Prompt budget 超限时降级顺序：expression -> lore full text -> old history -> profile -> persona examples；core 不降级。

### 2. 记忆隐私边界

- QQ 群记忆、私聊记忆、Dashboard Agent 记忆默认隔离。
- 用户画像不能跨群自动共享，除非配置了显式共享 scope。
- 任何敏感画像默认不注入，Dashboard 也只展示摘要和风险等级。
- 画像证据引用只保存短摘和 hash，不保存过长原文。
- 删除/纠错应留下 tombstone 或 disputed 状态，避免下一轮自动提取又写回来。

### 3. 学习边界

- 自动学习永远先进入 candidate。
- candidate 不能影响回复、TTS、表情推荐。
- reviewed 表达也要受人格兼容表限制。
- 学习到的表达不能被模型解释成新规则，例如“以后都要这样说”。
- 表达学习不读取管理员私密命令、token、日志、工具输出。

### 4. 权限边界

- 人格不能开启 Agent 工具。
- 表情/图集上传、删除、审核必须走 admin 或明确权限矩阵。
- Dashboard 试聊沙盒不写真实 conversation、不触发 TTS 文件、不发送 QQ 消息。
- 回复时机诊断是只读数据，不允许通过诊断接口改概率。
- Persona 编译器不读取超出 `ai-skills` 和明确运行时数据目录的文件。

### 5. 资源边界

- profile 自动提取、表达学习、图片/表情标签识别必须异步，不能阻塞主回复。
- 每个群/用户的学习任务要有限流和队列上限。
- VLM/embedding 这类重任务默认关闭，按群或管理员开启。
- plan 缓存有 source hash，文件没变化不重复编译。
- 失败时记录 warning，不反复重试打爆模型额度。

### 6. 体验边界

- “像人”不等于一直主动插话；沉默也是人格的一部分。
- 不要让 Bot 每次都展示“我记得你”，否则会像监控。
- 学来的梗不要高频使用；越像人，越要有克制。
- 温柔/庄重人格不能被群聊黑话污染。
- 默认东雪莲的“有态度”不能被表达学习推成无差别攻击。

### 7. 回滚边界

- 每个新能力必须有全局开关、群级开关、人格级开关。
- 保存人格前备份上一版。
- plan 编译缓存可清，源文件不自动改。
- 任何新模块接管旧逻辑前都要有旁路对照期。
- 回滚后旧命令、旧人格切换、旧 TTS 配置仍能工作。

## 十二、模块接线顺序

建议按下面顺序接线，避免一次性重构把 chat、Agent、TTS、Dashboard 全搅在一起。

1. `persona-schema.js` 只做解析和校验，不被业务调用。
2. `persona-compiler.js` 生成 plan，但只写 debug/diagnostics。
3. Dashboard 读取 diagnostics，展示 warning，不改变保存格式。
4. Dashboard 保存人格/世界观后请求 plan 预览，确认前端编辑仍会被 compiler 识别。
5. `tts.js` 增加可选参数 `plan`，没传则走旧逻辑。
6. `agent/persona-context.js` 增加可选 `plan`，没传则走旧逻辑。
7. `chat.js` 只在构建 prompt 前获取 plan，不改变主流程。
8. `chat-prompt-builder.js` 接管 system prompt 拼装。
9. `reply-timing.js` 旁路记录，至少观察一轮真实群聊数据后再接管主动回复。
10. `persona-profile.js` 先从显式记忆桥接，不急着自动提取。
11. `expression-learner.js` 先只收集 candidate，不注入。
12. `affect-router.js` 先只给 TTS style patch，不发额外表情。

说明：第 11、12 步暂缓实现，先只保留设计文档。表达学习和情绪输出直接影响人格风格与 OOC 风险，必须等前面的 plan、prompt、lore、reply-timing、profile 链路稳定后再做。

### Phase 5.5：Profile 重复强化与衰减权重

状态：已完成影子层第一版，仍不接管 prompt，不写生产 profile。

目标：让 profile 的 confidence 从“写入时的快照”变成“随观察次数自然变化、随时间自然沉默”的可计算值，纯代码实现，不消耗 token，不引入新模型调用。

适用前提：Phase 5 已经把旧记忆/最近发言桥接成 read-only block。本阶段只在 `persona-profile.js` 内部增强字段与读取函数，不接管 prompt 注入。

任务：

- 在 `buildPersonaProfileBlock()` 字段集合中新增 `lastAccessedAt`、`reinforceCount`，默认值与 `updatedAt`、`evidence.length` 对齐，向后兼容旧 block。
- 新增纯函数 `computePersonaProfileEffectiveConfidence(block, options)`：返回 `confidence * decay^daysSinceLastAccessed`；`decay` 默认 0.95，`daysSinceLastAccessed = (now - lastAccessedAt) / 86400000`，结果保留 3 位小数，最小不低于 0。
- 新增纯函数 `reinforcePersonaProfileBlock(existing, incoming, options)`：当 `incoming.text` 与 `existing.text` 经 `quoteHash` 或归一化文本判定为同一事实时，返回新的 block 副本，`confidence += increment`（默认 0.05，钳制到 [0, 1]）、`reinforceCount += 1`、`lastAccessedAt = now`、追加最多 N 条 evidence（默认 5，超出截尾），不新建条目。
- 新增 `buildPersonaProfileReinforcementShadow(blocks, options)`：只在内存里对当前 block 列表做去重/强化影子计算，输出 `originalCount/dedupedCount/reinforcedCount/reasonCounts`，不落盘、不覆盖旧 profile。
- 新增 `selectPersonaProfileBlocksByEffectiveConfidence(blocks, options)`：按 `effectiveConfidence` 排序、按阈值过滤（默认 0.1），用于后续 prompt 选择层调用，本阶段只输出诊断不接管。
- `disputed` 状态的 block 在 `effectiveConfidence` 计算中直接归零，避免被反复强化或被衰减后再激活时绕过纠错。
- `chat.js` 只在 `isDebugLogEnabled('persona-profile')` 为真时运行影子诊断，并输出两类日志：`profile_reinforce_shadow` 和 `profile_selection`。关闭 debug 后不运行 profile 影子选择，也不输出日志。

边界：

- 衰减只影响读取排序，不删除原 fact，也不修改 `confidence` 原值；effectiveConfidence 只是计算结果，不持久化。
- 强化只发生在自动提取入口，管理员显式编辑、`status=active by admin` 的事实不被自动衰减覆盖（仍计算 effectiveConfidence，但有最低保护值）。
- `reinforceCount` 不暴露给模型 prompt，仅用于 Dashboard 诊断与排序。
- 重复判定优先用 `quoteHash` 完全相同；其次允许在同一 `block/category` 下用归一化文本相等近似匹配；不引入 embedding 或 LLM 语义判等。
- 短期事实（如 `expiresAt` 已设置）继续按硬过期处理，衰减权重作为额外排序信号，不替代过期。
- `sensitive` 类事实即使被多次强化也不自动注入 prompt，依旧受 sensitivity 策略约束。
- 当前日志走 Koishi debug log，不写 `data/persona-diagnostics/profile-reinforce-*.jsonl`；未来若要落盘，必须复用同一套脱敏 formatter。
- `profile_reinforce_shadow` 只输出计数和原因，不输出 fact 原文、用户 id、群 id、message id。
- `profile_selection` 只输出 user/channel hash、top fact hash、effectiveConfidence、status、block/category 和 skipped 计数。

验收：

- 同一事实文本被 N 次写入只产生一条 block，`reinforceCount=N`，`confidence` 单调上升至上限被钳制。
- 偶发玩笑事实在 30 天后 `effectiveConfidence` 显著低于持续被命中的稳定事实，且能在诊断日志中观察到排序差异。
- `disputed` 标记后，无论是否再次命中，effectiveConfidence 始终为 0。
- 衰减/强化全程不调用模型、不读写人格文件、不影响 chat 输出；关闭旁路诊断 flag 后无任何日志输出。
- 单元测试覆盖：重复写入合并、玩笑事实自然沉默、稳定偏好排序浮起、disputed 归零、`expiresAt` 与衰减不冲突、Dashboard 诊断脱敏。

日志查找：

- 开启方式：运行时 `DATA_DIR/debug-log-config.json` 写入 `enabled: true` 且 `modules.persona-profile: true`。
- 复查关键字：`[D] [persona-profile] profile_reinforce_shadow`、`[D] [persona-profile] profile_selection`。
- `profile_reinforce_shadow total=... deduped=... reinforced=... reasons=quote_hash:N,normalized_text:N mode=shadow_only prompt=unchanged`：看重复事实是否会被影子合并。
- `profile_selection user=<hash> channel=<hash> total=... considered=... selected=... top=<factHash:effective:status:block/category,...> skipped=status:N,expired:N,sensitive:N,lowConfidence:N reasons=shadow_only,no_prompt_injection`：看哪些 fact 会进入未来 top-N，以及为什么被跳过。
- 两三天后复查时重点看：`reinforced` 是否异常暴涨、`sensitive/expired/disputed` 是否被选中、`top` 是否长期被一次性玩笑占据、是否出现 `profile_selection_failed`。

## 十六、不建议做的事

- 不要直接把 MaiBot 代码或 prompt 搬进来。
- 不要直接导入社区角色卡、世界书或示例对话作为高优先级指令。
- 不要把 Dify / LangBot / AstrBot 这类平台型项目误当作人格深度范本。
- 不要让 persona 文件声明插件、工具权限、密钥或外部服务配置。
- 不要把自动学习结果直接写进 persona Markdown。
- 不要把用户画像无证据注入 prompt。
- 不要让人格影响 Agent 工具权限。
- 不要让表情自动收集绕过审核。
- 不要在 `chat.js` 里继续堆新状态。
- 不要一口气接管主动回复，必须先旁路观测。
- 不要为了“像人”牺牲可解释性和可删除性。

## 十七、建议下一步

1. 先做只读 `persona.schema.v1` 和冲突扫描。
2. 给现有人格补回归样例和多轮故事测试：东雪莲、椿、特蕾西娅、长离、爱弥斯。
3. 给人格 schema 增加 `examples`、`lore_refs`、`prompt_budget`、`style_fingerprint`。
4. 做 `PersonaRuntimePlan` 旁路编译，并和旧逻辑对照。
5. 把 prompt 构建从 `chat.js` 拆到 `chat-prompt-builder.js`，同时输出 prompt 组成诊断。
6. 做 `persona-lore-router`，让 lore、示例、记忆按触发和预算进入上下文。
7. 先让 TTS 和 Agent 读取 plan，减少多头解析。
8. 回复时机层先只记录诊断，不接管行为。
9. 再做 memory blocks、证据化 profile 和表达学习审核池。在 profile 接入 prompt 前先落 Phase 5.5 的重复强化与衰减权重，让排序信号先就位。
10. 最后做 affect-router、外部角色卡只读风险扫描和 Dashboard 人格实验室。

这 10 步做完后，按架构升级整体口径约等于完成 70% 到 80%：人格运行态、prompt 组装、lore、回复时机、profile、表达、情绪输出这些核心链路已经成型。剩下 20% 到 30% 主要是长期真实数据观察、Dashboard 人格实验室打磨、外部角色卡导入风险扫描、自动表情标签、更多回归样例和逐步接管后的线上调参。

   - Dashboard 删除人格、模式列表仍有旧 LF-only 正则。

   影响：

   - Dashboard 正常保存通常写 LF，不会马上触发。
   - 如果用户或其他工具把人格文件改成 CRLF，普通聊天可能读不到 `lore:` 绑定，删除/模式展示也可能找不到名称。

   建议：

   - 后续把所有人格/lore/mode frontmatter 读取统一改用 `persona-schema.js` 或同一个 parser。
   - 增加 CRLF 人格文件回归：人格绑定 lore、Dashboard 删除、模式列表均应正常。

4. P2：Dashboard 人格编辑 round-trip 还没有完全统一到 schema builder。

   现状：

   - lore 编辑已新增 `keywords/scope/summary/max_chars/priority` 并做清洗。
   - 人格编辑仍只暴露 `name/description/lore/will/nsfw/content`，语音配置由另一个接口写入。
   - `buildPersonaFrontmatter()` 会保留未知字段，但 `description/name/will` 等字段的语义校验还不如 lore 严格。

   影响：

   - 当前测试覆盖了 voice frontmatter 不被保存丢失。
   - 但长期看，前端人格编辑和语音配置仍是两个入口，后续扩展字段时容易再次出现“一个入口保留、另一个入口覆盖”的问题。

   建议：

   - 下一步做 `persona-schema` builder/service，Dashboard 人格编辑和语音配置都调用同一套读写函数。
   - 增加 round-trip 测试：未知字段、`hostile_capable`、`voice_*`、`lore_refs`、CRLF、空字段都不能丢。

5. P2：PowerShell 管道写入/中文脚本仍会干扰验证。

   现象：

   - 本轮用 PowerShell here-string 管道给 `node -` 跑中文正则时，中文被转成问号，导致正则语法错误。
   - 这是验证脚本编码问题，不是项目代码问题。

   建议：

   - 临时验证脚本尽量使用 ASCII 断言，或写入临时 `.js` 文件后用 UTF-8 安全方式运行。
   - 继续遵守 AGENTS 中的 PowerShell 规则：中文文件不使用管道/重定向写入，正式改文档用 `apply_patch`。

开放建议：

- 可以先开放 `web_fetch` 给 Dashboard 和 QQ，但建议默认只在用户明确给出公开 URL 时由 Agent 使用。
- `web_search` 不建议宣传成“稳定搜索答案”，目前更适合做候选池；必须让 Agent 在 weak/hard_fail 时承认没有可靠结果。
- 如果要把 `web_fetch` 和 `web_search` 一起正式开放，下一步优先做：
  1. `web_search` 返回结构化状态和候选可信度。
  2. 官方/站点类查询优先构造 direct-domain 候选，再交给 `web_fetch`。
  3. QQ 侧频率限制和失败提示。
  4. 真实线上样例复查：明确 URL、官网查询、失败查询、chat 转述四类。

#### 2026-05-21 search/fetch 协同优化已落地

状态：已完成本地实现和回归验证，待部署与推送。

本轮设计定稿：

- `web_search` 只负责候选 URL 发现、排序、去噪和有限重试。
- `web_fetch`/`fetch-reader` 读取到的网页正文才算高可信依据。
- 搜索页标题、摘要、API 搜索摘要只作为“选链接的线索”，不能作为事实依据。
- `weak_hit` 明确表示“没有读到可用正文”，Agent 和 retell guard 都不能把它包装成“已经查到”。
- `usable_hit` 必须来自已打开候选页正文，输出中会标注 `已打开候选网页正文`、`正文质量：usable` 或 `已用 web_fetch 验证正文`。

已完成代码调整：

- `web_search` 对 API 搜索结果先抽取 URL，再调用共享 `fetch-reader` 读取候选正文；API 摘要不再直接当答案返回。
- HTTP 搜索输出增加候选 URL 区块，明确提示“未读取正文前不要当事实”。
- `runHttpSearch()` 返回 `candidates/pages/status`，`weak_hit` 会携带候选但不当成功结果。
- HTTP 搜索读到候选正文时会显式输出 `搜索状态：usable_hit`，避免调用方只靠中文正文片段猜测状态。
- `agent-retell-guard` 收紧成功判定：只有 `usable_hit`、可用正文或 `web_fetch` 验证正文才算成功搜索；带 URL 的 weak hit 不再算成功。
- 增加直达候选：IANA example domains、Node.js 下载/发布、OpenAI 新闻/文档。
- 过滤搜狗翻译、问问、应用、内部搜索跳转等噪音候选。
- `web_fetch` 默认开放给 QQ 和 Dashboard，但仅在用户明确给出公开 URL 并要求读取/总结时自动路由；旧 `ai-tool-config.json` 会从 v1 迁移到 v2，避免历史配置继续把 `web_fetch` 卡成关闭。
- `web_fetch` 增加按渠道/群/用户的轻量频控，防止普通用户连续刷公开 URL 把外部读取打爆。
- Agent system prompt 与 retell guard 都补充了 web_fetch 失败、频控、正文过短、非文本、拒绝访问时不能编造页面内容的规则。
- CRLF frontmatter 兼容已补到普通聊天 lore 解析、Dashboard 人格删除和模式列表读取，避免 Windows 工具保存后 lore 或模式名失效。

新增测试防线：

- 搜索摘要未打开正文时必须标注“不能作为事实依据”。
- 打开候选正文时必须标注 `usable_hit`。
- weak hit 不能被 chat retell 包装成“查到了”。
- usable hit 仍能正常通过 retell guard。
- API 搜索 URL 必须走 fetch 读取正文；fetch 失败时降级为 weak/fallback，不直接返回 API 摘要。
- Sogou 内部入口会被候选排序过滤。
- IANA/Node.js 查询能生成 direct-domain 候选。
- 旧工具配置 v1 会迁移并打开 `web_fetch`；显式关闭时仍能在测试中观察到 disabled 路由。
- `web_fetch` 连续调用会触发频控；无上下文的内部单元测试调用不受影响。
- CRLF 人格 lore、Dashboard lore 和 Dashboard mode frontmatter 均有回归断言。

仍保留的边界：

- `web_search` 仍不能保证任意 query 都搜得准，它只是候选发现器。
- 对没有 direct-domain 规则的冷门问题，仍可能返回 weak hit；此时 bot 必须承认没有可靠正文。
- Chromium 浏览器搜索仍默认关闭，避免低内存服务器被拉爆。
- `web_fetch` 仍不是浏览器，不执行 JavaScript；遇到 SPA、登录墙或反爬页面仍可能只能返回正文过短或失败。
- DNS 重绑定仍是理论边界：当前有请求前 DNS/redirect/final URL 校验，但没有 socket 级 DNS pinning；如果未来给全体普通用户高频开放，应再评估更强网络隔离。
