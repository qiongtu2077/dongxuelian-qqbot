# 架构债优化计划

复核日期：2026-05-21

本文只讨论“先解决架构债”。人格升级、表达学习、证据化画像、情绪输出、外部角色卡、Dashboard 人格实验室等体验型升级全部后置。

重要修正：本项目已经拆过一轮，模块化本来就是当前优势。现在剩下的不是“再多拆几个文件”就能解决的低级债，而是主入口、聊天核心、持久化和 Dashboard 这些协调层的复杂度。继续强行大拆，可能只会制造跳转成本。

本计划因此采用“协调层治理”路线：

> 先让复杂决策可解释、可测试、可回滚；只在接口稳定后拆低风险纯函数和 store。

## 一、范围声明

### 本轮要做

- 给 `index.js` 的主动回复、队列、冷却、静默等逻辑补“决策对象”和诊断。
- 给 `chat.js` 的 prompt 组成补 section 结构和诊断。
- 给 `conversation.js` 的状态职责画清读写边界，优先抽通用 store/helper，不急着迁移数据。
- 给 Dashboard routes 增加 service 接缝，先从低风险接口开始，不做大搬家。
- 增强架构边界测试，防止后续把新职责继续塞进主链路。

### 本轮不做

- 不做完整人格升级。
- 不做自动学习群聊表达。
- 不做新的长期用户画像系统。
- 不做 affect-router。
- 不做 Dashboard 人格实验室。
- 不改变线上回复风格。
- 不改变主动回复策略的最终行为。
- 不追求把 `index.js/chat.js/conversation.js` 立刻拆到很短。
- 不为了“看起来模块化”增加无意义跳转层。

人格相关只作为“重复解析和重复契约”的一个债务样本记录，不作为本计划主线。

## 二、当前真实状态

### 1. 不是缺模块，而是协调层难拆

当前已经拆出来的健康模块很多：

- Agent 工具、安全、path guard、queue、pending、plan、skill scanner。
- TTS、voice assets、image store、reply guard、send guard。
- commands、runtime-config、api、conversation、persona 等稳定模块。
- `check / test:quick / test:scenario / npm test` 已形成基础测试体系。

问题在于：

- `index.js` 是 Koishi 中间件总控，天然会碰所有消息状态。
- `chat.js` 拥有模型调用所有权，天然会碰 prompt、工具、记忆、guard。
- `conversation.js` 是历史和上下文事实源，天然会被很多地方依赖。
- Dashboard routes 有实际 HTTP、权限、文件写入职责，简单拆 service 可能只增加跳转。

所以本轮优化不以“拆出多少文件”为成功标准，而以“主协调层是否更可解释、更可测试、更少隐式状态”为成功标准。

### 2. 债务清单

| 债务 | 现状 | 更真实的优化方向 | 优先级 |
|------|------|------------------|--------|
| 主动回复决策隐式 | 白名单、概率、miss count、冷却、延迟、闭嘴识别散在入口流程 | 先形成 `RandomReplyDecision`，记录 reasons/blockers，不急着搬完整流程 | P0 |
| prompt 组成隐式 | `chat.js` 直接 push 多段 system/user message | 先形成 `PromptSection[]` 和 diagnostics，再决定是否拆 builder | P0 |
| 状态归属不够显式 | 多个 Map/缓存存在，但读写边界靠代码上下文理解 | 做状态清单、读写者、生命周期、大小限制、清理策略 | P0 |
| 持久化工具重复 | 多模块都有 tmp/rename、read/write JSON 变体 | 先抽 `json-store` 这类低风险工具，不急着迁移所有数据 | P1 |
| Dashboard routes 偏厚 | route 中同时做权限、校验、业务读写 | 先给高复用逻辑加 service 接缝，避免整块搬迁 | P1 |
| 诊断不足 | 关键行为出错时靠日志和读代码复盘 | 加结构化 diagnostics，默认脱敏 | P1 |
| 架构防回潮不足 | 已有边界注释，但自动化约束不够 | 加 arch check，限制主链路新增长期状态 | P0 |

## 三、优化原则

### 原则 1：不以行数为目标

`index.js` 和 `chat.js` 可以继续作为协调层存在。目标不是把它们机械切碎，而是让它们的复杂分支变成命名对象、可测函数和可复盘诊断。

### 原则 2：先加接缝，再搬代码

例如主动回复：

1. 先在原位置生成 `RandomReplyDecision`。
2. 测试 decision 的 reasons/blockers。
3. 观察稳定后再抽纯函数。
4. 最后才考虑独立 controller。

### 原则 3：优先抽纯函数和 store

适合先抽：

- 纯判断。
- 诊断构造。
- JSON 原子写工具。
- 参数标准化。
- source/budget/section 描述对象。

不急着抽：

- Koishi middleware 主流程。
- chat 主流程。
- 工具调用循环。
- 多分支发送流程。

### 原则 4：主流程保留叙事性

协调层不是坏东西。主流程应该能读出“消息进来后发生了什么”。过度 service 化会让主流程变成一串看不懂的跳转。

### 原则 5：每次优化都必须能回滚

新增 decision/diagnostics 默认旁路，不改变行为。行为接管必须有开关或兼容路径。

## 四、目标对象

### 1. RandomReplyDecision

用于解释群聊未 @ 时为什么主动回复、延迟或沉默。

```js
{
  shouldConsider: true,
  shouldReplyNow: false,
  shouldDelay: true,
  delayMs: 1200,
  rate: 0.008,
  willFactor: 1.3,
  randomHit: false,
  reasons: ['whitelist_enabled', 'text_message', 'persona_will_applied'],
  blockers: ['random_miss', 'cooldown_active'],
  stateReads: ['randomWhitelistCache', 'lastRandomReplyTs'],
  stateWrites: ['channelMissCount']
}
```

第一版只记录，不改变现有主动回复行为。

### 2. PromptSection

用于解释 `chat.js` 中每段 prompt 的来源。

```js
{
  id: 'lore:wuwa-lore',
  type: 'lore',
  included: true,
  reason: '用户消息命中旧 lore 关键词',
  source: 'skillsContentCache[lore:wuwa-lore]',
  tokenEstimate: 900,
  priority: 60
}
```

第一版可以和原 messages 并行维护，不急着把 prompt 拼装搬出去。

### 3. StateOwnershipMap

用于梳理主链路状态归属。

```js
{
  name: 'channelMissCount',
  owner: 'index.js/random reply flow',
  readers: ['random candidate branch'],
  writers: ['random miss branch', 'successful reply branch'],
  lifecycle: 'memory only',
  cleanup: 'per channel implicit reset',
  risk: 'miss count 与延迟回复、冷却耦合'
}
```

目标是先看清楚状态，再决定是否值得抽。

### 4. StoreBoundary

用于给 `conversation.js` 的持久化职责分层。

```js
{
  store: 'conversation-history',
  filePattern: 'conversations/<key>.json',
  readApis: ['getConversationHistory', 'readConversationDisk'],
  writeApis: ['saveConversationTurn'],
  formatMigration: 'none',
  concurrency: 'write queue'
}
```

第一版只记录和补测试，不急着迁移格式。

## 五、阶段计划

### Phase 0：架构热点地图

目标：先把“难拆在哪里”讲清楚。

任务：

1. 生成主链路热点清单：
   - `index.js` 中所有 Map/Set/Timer。
   - `chat.js` 中所有 prompt push 段。
   - `conversation.js` 中所有文件读写职责。
   - Dashboard routes 中所有直接文件写入点。
2. 写入待审核文档或 diagnostics。
3. 标注每个热点：
   - 是否需要拆。
   - 是否只需要命名对象。
   - 是否已有测试。
   - 是否能旁路观测。

验收：

- 不改业务逻辑。
- 能回答“哪些债值得还，哪些不值得拆”。

### Phase 1：主动回复 Decision 旁路

目标：先让 `index.js` 中最难理解的主动回复逻辑可解释。

任务：

1. 在现有流程旁边构造 `RandomReplyDecision`。
2. 记录 reasons/blockers：
   - directAt/nameMentioned。
   - whitelist。
   - blacklist。
   - cooldown。
   - will factor。
   - random hit/miss。
   - delayed observe。
   - 用户闭嘴/别吵。
3. 加单测或 scenario 断言 decision 不改变旧行为。
4. 不迁移 Map，不改最终回复逻辑。

验收：

- 旧 random scenario 通过。
- 能在 debug/diagnostics 中看到为什么不回。
- 行为完全不变。

### Phase 2：PromptSection 旁路

目标：先让 `chat.js` 的 prompt 组成可观察。

任务：

1. 保留现有 messages push。
2. 每 push 一类内容，同时记录 `PromptSection`。
3. 覆盖至少这些 section：
   - core/persona/mode。
   - nsfw。
   - lore。
   - search rule。
   - quote。
   - history summary。
   - memory summary。
   - agent context。
   - vision。
   - tool hint。
4. diagnostics 默认只输出 section，不输出完整 prompt。

验收：

- persona prompt scenario 通过。
- chat scenario 通过。
- 能看到 lore 为什么注入/不注入。
- 没有新增人格能力。

### Phase 3：状态归属文档化 + 轻量检查

目标：防止主链路继续长隐式状态。

任务：

1. 建立 `StateOwnershipMap`。
2. 给每个状态标注：
   - owner。
   - readers/writers。
   - cleanup。
   - max size。
   - 是否持久化。
3. 新增轻量 arch check：
   - `index.js` 新增 Map/Set 需要白名单。
   - `chat.js` 新增长期状态需要白名单。
   - 子模块禁止 require `index.js`。
4. 不强行移动现有状态。

验收：

- 架构检查能指出新增隐式状态。
- 现有状态都有归属说明。

### Phase 4：低风险 helper/store 抽取

目标：只抽“低跳转成本”的代码。

优先候选：

- `json-store.js`：统一 tmp + rename、大小限制、JSON read/write。
- `prompt-section.js`：section 构造和 token 粗估。
- `decision-diagnostics.js`：decision 脱敏输出。
- `dashboard/service-utils.js`：通用参数校验和路径安全。

暂不抽：

- 完整 random reply controller。
- 完整 chat prompt builder。
- 完整 conversation store 迁移。

验收：

- 抽出的 helper 有单测。
- 调用点少，不造成全局跳转。
- 行为不变。

### Phase 5：稳定后再决定是否搬迁

目标：不预设一定要拆。

评估标准：

- 某段逻辑是否已有 decision/section/store 边界？
- 是否有测试覆盖？
- 是否在 3 次以上改动中反复被触碰？
- 抽出去后是否减少理解成本，而不是增加跳转？
- 是否能保留 facade，低风险回退？

只有满足这些条件，才进入搬迁。

可能搬迁：

- `random-reply-controller.js`
- `chat-prompt-builder.js`
- `conversation-store.js`
- Dashboard service

也可能不搬，只保留命名对象和诊断。

## 六、测试策略

### 必跑

```bash
npm run check
npm run test:quick
```

### 涉及主链路时

```bash
npm run test:scenario
```

重点关注：

- `random.test.js`
- `chat.test.js`
- `persona-prompt.test.js`
- `concurrency.test.js`
- `sensitive.test.js`
- `voice-tts.test.js`
- `agent-phase3.test.js`

### 新增测试重点

- Decision 只解释，不改变结果。
- PromptSection 只记录，不改变 messages。
- arch check 能拦住新增隐式状态。
- diagnostics 不包含完整 prompt 或完整用户消息。

## 七、回滚策略

### 旁路对象回滚

`RandomReplyDecision`、`PromptSection`、`StateOwnershipMap` 都是旁路对象。出问题时可以直接关闭 diagnostics，不影响主行为。

### helper 抽取回滚

低风险 helper 抽取必须保留旧行为等价测试。出现问题时：

1. 回旧调用点。
2. 保留测试。
3. 用失败输入补 scenario。

### 不做大规模一次性搬迁

不允许在一个改动里同时：

- 搬状态。
- 改 prompt。
- 改 Dashboard。
- 改持久化格式。
- 改主动回复结果。

## 八、成功标准

第一阶段成功：

- 能解释主动回复为什么回/不回。
- 能解释 prompt 每段为什么注入。
- 能列出主链路状态的读写归属。
- 架构检查能阻止新隐式状态随手进入主链路。

第二阶段成功：

- 后续改主动回复时，先改 decision 测试，而不是猜分支。
- 后续改 prompt 时，先看 section 诊断，而不是全读 `chat.js`。
- 后续要拆模块时，有稳定接缝和测试，不靠勇气硬拆。

最终成功：

- 承认协调层存在的必要性，但让协调层更透明。
- 保留当前模块化优势，不为了拆而拆。
- 为后续人格升级、记忆升级、表达学习留出可观察、可测试、可回滚的地基。
