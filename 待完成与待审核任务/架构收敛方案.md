# 架构收敛方案

日期：2026-05-25

## Context

项目以"功能驱动"方式增长，同一能力在多个入口点重复实现（5 个入口：index.js middleware、chat.js、agent/engine.js、commands/、mcp/local-server.js）。已有成功收敛的先例（path-guard 12 处调用、tools/registry 5 处、queue 5 处），证明统一基础设施可行。本方案将剩余碎片化能力逐步收敛为共享模块，降低维护成本。

---

## Phase 0: 工具元数据统一（最小改动，最大收益）

**问题**: 工具安全元数据分散在 3 处定义（chat-tools.js 内联、agent/tools/*.js 各自声明、mcp/local-server.js 重复映射）

**方案**:
- 在 `lib/tools/registry.js` 中为每个工具增加元数据字段：
  - `safety: { destructive, requiresConfirm, rateLimit }`
  - `weight: 'light' | 'heavy'`（驱动 chat 层轻重路由决策）
  - `timeout: number`（毫秒，executor 读取此值做超时控制）
- 所有入口点从 registry 读取元数据，不再各自硬编码
- 文件: `lib/tools/registry.js`, `lib/chat-tools.js`, `lib/agent/tools/*.js`, `lib/mcp/local-server.js`

**验证**: grep 确认无入口点残留硬编码安全标记

---

## Phase 1: 输出净化收敛

**问题**: 5+ 处独立的 sanitize/escape 实现（index.js、chat.js、agent/engine.js、mcp 各有变体）

**方案**:
- 新建 `lib/sanitize.js`，统一导出 `sanitizeForQQ(text, options)` 和 `sanitizeToolOutput(text, maxLen)`
- 各入口点改为 `require('./sanitize')` 调用
- 文件: 新建 `lib/sanitize.js`；修改 `lib/index.js`, `lib/chat.js`, `lib/agent/engine.js`, `lib/mcp/local-server.js`

**验证**: 单元测试覆盖 CQ 码过滤、长度截断、特殊字符转义

---

## Phase 2: 工具执行统一（只统一 HOW，不动路由）

**问题**: chat-tools.js 和 agent/tools/ 各有独立的工具调用→结果→错误处理链路，重复实现参数校验、path-guard、错误格式化

**边界约定**:
- executor 管 HOW：参数校验、path-guard 检查、超时、结果截断、错误格式化
- chat 层管 WHEN：根据 registry 的 `weight: 'light' | 'heavy'` 决定内联执行还是交给 agent
- 轻重路由逻辑保留在 chat 层，executor 不干预调度决策

**方案**:
- 在 `lib/tools/executor.js` 中实现统一执行器：`async executeToolCall(toolName, params, context)`
- chat 轻工具：chat 直接调 executor，拿结果内联返回
- chat 重工具：chat 判断后交给 agent engine，agent 内部也通过 executor 执行
- 超时值从 registry 元数据读取（轻工具短超时，重工具长超时），executor 不硬编码
- 文件: 新建 `lib/tools/executor.js`；修改 `lib/chat-tools.js`, `lib/agent/engine.js`

**验证**: 现有 test/scenarios/ 测试全部通过；新增 executor 单元测试；确认 chat 轻工具仍内联返回、重工具仍走 agent

---

## Phase 3: 超时/取消机制统一

**问题**: 4 种超时机制并存（setTimeout 手动清理、AbortController、Promise.race、queue 内置超时）

**方案**:
- 在 `lib/timeout.js` 中实现 `withTimeout(promise, ms, label)` 和 `createCancellable(fn)`
- 所有异步操作统一使用，取消时抛出 `TimeoutError`
- executor（Phase 2）内置调用 `withTimeout`
- 文件: 新建 `lib/timeout.js`；修改 `lib/tools/executor.js`, `lib/agent/engine.js`, `lib/chat.js`

**验证**: 模拟慢工具调用，确认超时后资源正确释放

---

## Phase 4: 搜索能力收敛

**问题**: 搜索分 3 条路径（chat-tools 内联 web_search、agent/tools/web-search.js、commands/search.js），参数处理和结果格式各异

**方案**:
- 在 `lib/abilities/search.js` 中实现 `async search(query, options)` 统一接口
- 3 条路径均调用此接口，各自只负责入口参数适配和结果呈现
- 文件: 新建 `lib/abilities/search.js`；修改对应 3 个调用点

**验证**: 3 个入口点搜索同一关键词，结果格式一致

---

## Phase 5: 文件分析收敛

**问题**: 文件分析 4 条路径（chat 内联、agent/tools/read-file.js、commands/analyze.js、mcp file tool），重复实现编码检测、大小限制、摘要截断

**方案**:
- 在 `lib/abilities/file-analyze.js` 中实现 `async analyzeFile(filePath, options)`
- 统一：编码检测、大小上限、二进制判断、摘要生成
- 文件: 新建 `lib/abilities/file-analyze.js`；修改 4 个调用点

**验证**: 对同一文件从不同入口分析，输出一致

---

## Phase 6: index.js 拆分（最后执行）

**问题**: index.js 1919 行，承担中间件编排、消息路由、上下文构建、工具调度等多重职责

**方案**:
- 拆分为：
  - `lib/middleware/router.js` — 消息路由与分发
  - `lib/middleware/context-builder.js` — 上下文组装
  - `lib/middleware/orchestrator.js` — 流程编排
- index.js 缩减为入口胶水（<200 行），只做 require + 注册
- 文件: `lib/index.js` → 拆分为 3 个新文件 + 精简后的 index.js

**验证**: 全量回归测试；bot 启动后正常响应消息

---

## 执行顺序与依赖

```
Phase 0 (独立) ──→ Phase 1 (独立) ──→ Phase 2 ──→ Phase 3 (依赖 Phase 2)
                                         ↓
                                    Phase 4, 5 (依赖 Phase 2)
                                         ↓
                                      Phase 6 (最后)
```

Phase 0 和 1 可并行，互不依赖。Phase 2 是后续的基础。Phase 6 放最后，因为前面的收敛会自然减少 index.js 的体积。

## 不动的部分

- `lib/path-guard.js` — 已收敛，12 处调用，不需要改
- `lib/tools/registry.js` 的工具注册机制 — 只扩展元数据，不改结构
- `lib/queue.js` — 已统一，5 处调用
- `lib/safety.js` — 已收敛
- `lib/retell-guard.js` — 已收敛
- 前端 dashboard — 不在本次范围

## 验证策略

每个 Phase 完成后：
1. `node -e "require('./packages/koishi-plugin-dongxuelian-ai')"` 确认无 require 错误
2. 运行 `test/scenarios/` 下相关测试
3. 本地启动 bot，手动触发对应功能确认正常
4. Phase 6 完成后做全量回归
