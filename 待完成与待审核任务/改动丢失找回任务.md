# 改动丢失找回任务

日期：2026-05-27
状态：审计中

## 1. 任务目标

本任务用于彻查历史提交中“曾经存在、后续改动中意外丢失或失去保护”的功能点。

重点不是恢复所有旧行为，而是逐项判断：

1. 历史上是否真实存在该能力。
2. 当前实现是否已经丢失、漂移、失去路由保护或变成误导性文案。
3. 该能力按当前产品形态是否本应继续存在。
4. 如果本应存在，则记录为待修复项，并标明可复现现象、引入/丢失 commit、当前影响和建议修复方向。

## 2. 审计范围

审计范围已扩大为全项目能力，不限于命令、菜单、供应商、路由或前端配置。

首轮全量范围：

- `packages/koishi-plugin-dongxuelian-ai`
- `packages/koishi-plugin-dongxuelian-help`
- `packages/koishi-plugin-dashboard`
- 其他 `packages/koishi-plugin-*`
- 根目录启动、配置、部署脚本中影响运行时能力的代码。
- 与 QQ 指令、帮助菜单、模型供应商、Dashboard 配置联动相关的历史提交。
- 与以下能力相关的历史提交：
  - 聊天、随机回复、引用回复、上下文窗口、消息缓存。
  - Agent 工具、搜索、网页读取、文件读取、图片读取、语音/TTS。
  - 人格、lore、skill、记忆、表达学习。
  - 群日报、谁艾特我、集合/昵称、白名单/黑名单。
  - Dashboard 页面、接口、前端操作、配置保存。
  - 定时任务、健康检查、诊断、日志、启动生命周期。

暂不在本任务中处理：

- 部署、重启、推送。
- 服务器数据清理。
- 运行时 TypeScript 迁移。
- 与“是否丢失能力”无关的重构建议。

## 3. 审计方法

使用本地 Git 历史和当前源码对照：

- `git log -S/-G` 查找命令、帮助菜单、供应商、前端配置等关键词的新增/删除提交。
- `git show <commit>` 对照关键提交前后的代码差异。
- 建立当前能力清单：
  - Koishi 插件入口、`ctx.command`、`ctx.middleware`、内部命令路由。
  - HTTP API 路由、Dashboard 页面、前端按钮/表单入口。
  - 定时器、后台任务、健康检查、诊断入口。
  - Agent 工具、媒体工具、搜索/fetch 工具、文件读写能力。
  - 数据目录、配置文件、状态文件、缓存文件。
- 扫描历史提交：
  - 按 commit 提取新增/删除的能力关键词和文件迁移痕迹。
  - 对出现“新增后删除”“迁出后未接线”“前端仍展示但后端失效”的项目做人工复核。
  - 对已明确替换的新入口记录为“已替代”，不当作丢失。
- 当前源码对照：
  - AI 主插件实际命令路由。
  - AI 主插件 `RESERVED_PREFIXES`。
  - help 插件公开菜单和中间件处理。
  - Dashboard 功能地图/指令速查公开文案。
  - Dashboard 配置面板和后端配置保存逻辑。

判断标准：

- 仅文案变更，不影响真实入口：记录为文案漂移，不算真实丢失。
- help 或 Dashboard 宣传存在，但当前路由可能被 AI 聊天吞掉：记录为真实路由保护缺失。
- 历史能力被迁移到其他插件但缺少 `next()` / reserved 保护：记录为真实丢失风险。
- 历史能力被明确替换且新入口完整：不记录为丢失。
- 每个疑似项必须回答“当前是否有等价替代实现”：
  - 有等价入口、测试和用户路径：记为已优化/已替代。
  - 只剩文案或半截代码，入口不可达、数据不通或路由被截：记为真实丢失。
  - 代码存在但缺少现场验证：记为疑似丢失待复核。

## 4. 已确认问题

### L-001 `供应商 <id>` 帮助指令从 AI 插件迁出后失去路由保护

级别：高

现象：

- `/help供应商` 能列出 `供应商 mimorium` 等入口。
- 用户发送 `供应商 mimorium` 时，本应由 help 插件列出小米 MiMo 可切换模型。
- 当前 AI 插件未处理该命令，也未将裸 `供应商` 加入 `RESERVED_PREFIXES`。
- help 插件支持 `help供应商` / `help mimorium` 一类模糊搜索，但 AI 只对斜杠前缀做放行，裸 `helpxxx` 也可能被聊天链路截走。
- 在 AI 插件先接到消息的场景下，这些消息可能进入普通聊天链路，出现人格化闲聊回复。

历史定位：

- `2026-04-27 16:36:06`：`9fd471845f3e... add dashscope provider, rename qwen models, fix UI`
  - AI 插件内直接处理 `切换模型`、`供应商 opencode/deepseek`、`可用模型`、`切换xxx`。
- `2026-04-28 18:48:46`：`5bcacf4f32e... v4.1 模型菜单重构 + 供应商GLM + 防御插件 + 父子菜单`
  - commit message 明确写明“模型显示命令从 AI 插件移至 help 插件，避免重复回复”。
  - `供应商 <id>` 处理迁入 `packages/koishi-plugin-dongxuelian-help/lib/index.js`。
  - AI 插件删除了对应显示命令，但没有给 `供应商` 增加保留前缀。
- `2026-05-02 18:56:19`：`3d6dc5328b78... handler.js命令路由拆分+fallback数组配置+gitignore细化+版本0.9.5`
  - 新 `handler.js` 继承了 `切换xxx`，但没有恢复 `供应商 <id>`。
  - `RESERVED_PREFIXES` 仍无 `供应商`。

当前判断：

- 这是一个真实存在的路由保护缺口，不是单纯优化。
- 该能力本应继续存在，因为 help 菜单、README 和当前用户路径都仍然公开它。

建议修复：

- 将 `供应商` 加入 AI 插件 `RESERVED_PREFIXES`，保证交给 help 插件。
- 同时考虑在 AI 命令路由内实现只读 `供应商 <id>` 响应，避免跨插件顺序影响。
- 增加场景测试：`供应商 mimorium` 不得进入聊天模型，应返回模型列表。

### L-002 help 插件供应商模型清单与 AI 真实供应商配置漂移

级别：中

现象：

- `packages/koishi-plugin-dongxuelian-help/lib/index.js` 维护了一份独立 `PROVIDERS`。
- `packages/koishi-plugin-dongxuelian-ai/lib/constants.js` 也维护真实 `PROVIDERS`。
- 两份清单当前已经不一致。

当前差异：

- `dashscope`：help 少了 `qwen-turbo`。
- `mimorium`：help 少了 `mimo-v2.5`。
- `mimorium`：`mimo-v2.5-pro` 在 AI 中显示为 `mimo 2.5pro`，help 中显示为 `mimo 2.5`。

当前判断：

- 这是一个真实文案/能力漂移问题，不是能力消失。
- 该能力本应一致，因为 `供应商 <id>` 和 `可用模型` 是用户选择模型的入口。

建议修复：

- help 插件不要复制维护供应商清单，优先复用 AI 插件 `constants.PROVIDERS`。
- 如果必须独立运行，则至少增加测试对账，防止模型清单漂移。

### L-003 help 菜单入口未全部加入 AI 保留前缀，存在被聊天链路吞掉风险

级别：中

现象：

help 插件支持以下菜单入口，但 AI 插件 `RESERVED_PREFIXES` 当前未完整覆盖：

- `集合`
- `记忆`
- `黑名单白名单管理`（help 里是反向别名，AI 里只保住了 `白名单黑名单管理`）
- `供应商 <id>`
- 非斜杠形式的泛搜索 help，例如 `help供应商`、`help mimorium`

当前判断：

- 这是与 L-001 同机制的问题。
- 其中 `供应商 <id>` 已有线上复现。
- `集合`、`记忆`、`黑名单白名单管理` 和裸 `helpxxx` 都还需要补场景测试，确认不同群聊/私聊/点名/随机触发条件下是否会被聊天链路吞掉。

建议修复：

- 将 help 插件所有一级入口、别名入口和 `help xxx` 泛搜索入口纳入保留策略。
- 最好建立“help 公开入口 -> AI reserved/AI handler/help handler”的自动对账测试。

### L-004 Dashboard 模型配置面板供应商与 API 地址显示/保存错配

级别：中

现象：

- 前端选择供应商“小米”、模型 `mimo v2` 后，API 地址仍显示 `https://api.deepseek.com`。
- 用户看到的是供应商、模型、API 地址三者不一致。
- 输入框提示“留空使用默认”，但保存时前端发送 `baseUrl: undefined`，后端不会清空旧 `ai-base-url.txt`。
- Dashboard 的状态接口和配置接口在文件缺失时也默认返回 `deepseek`，但 AI runtime `loadConfig()` 的默认 provider 是 `opencode`，会进一步造成“面板显示”和“真实运行默认值”不一致。

历史定位：

- `2026-05-06 01:07:31`：`50a10f189f80... feat: Bot Dashboard 管理面板 v0.1`
  - ConfigPanel 初版已经存在该设计：切换供应商只修正模型，不联动 baseUrl；保存空值不会显式清空后端旧值。

当前判断：

- 这不是最近某次提交造成的能力丢失，而是初版遗留 bug。
- 与本任务相关，因为它会让用户误判当前供应商是否真实生效。

建议修复：

- 切换内置供应商时自动显示该供应商默认 `baseURL`，或显示“使用默认：xxx”。
- 保存时若用户清空 API 地址，应显式写空字符串或删除旧配置。
- 后端保存配置时校验内置供应商与 baseUrl 的关系，避免显示 DeepSeek 地址但 provider 是 MiMo。

### L-005 Fallback 重置字段名错配，轻量功能开关只有前端缓存

级别：中

现象：

- `/api/fallback` 后端返回的是 `defaults`，但 `ConfigPanel.vue` 读取的是 `default`。
- 于是“重置为默认”拿到的是空对象，可能把链清空或者重置成空状态。
- “轻量功能 Fallback”的“主模型兜底”开关只存进 `localStorage`，保存时没有发给后端，AI runtime 也不会读它。

当前判断：

- 这是一个真实前端 bug + 半实现控件，不是能力优化。
- 重置按钮和开关都会误导用户，以为改动已经写入运行时。

建议修复：

- 统一 `/api/fallback` 的返回字段名，前后端只保留一种键。
- 把 `lightweightMainToggle` 接入后端配置或 runtime 读取链路，不要只留本地缓存。

### L-006 记忆系统是双体系并存，help/Dashboard 文案还停留在旧口径

级别：低

现象：

- 旧聊天记忆仍然存在，入口是 `记住/记下`（带空格）、`东雪莲忘记我`、`东雪莲清空群记忆`、`东雪莲群记忆定时`，对应 `chat-memory.js` / `handler.js`。
- 新的 Agent 长期记忆也存在，入口是 `莲莲记住`、`莲莲回忆`、`莲莲记忆列表`、`莲莲忘记 mem_xxx`，对应 `commands/memory-command.js`。
- help 和 Dashboard 仍写成“记住xxx / 查看、删除记忆”的单一路径，容易让人误以为某条记忆能力被删了。

当前判断：

- 这不是能力丢失，而是双体系并存后的文案漂移。
- 需要把 help/Dashboard 话术改成“旧聊天记忆 + 新 Agent 记忆”并列，避免继续误判。

建议修复：

- help 和 Dashboard 把两套记忆入口分开写清楚。
- 对 `记住 xxx` 的真实匹配格式补上测试，避免“看起来有、其实少了空格”的误导。

### 4.1 已确认不是丢失的项

- `集合/昵称`、`群聊日报`、`谁艾特我`、`今日情绪`、`AI状态`、`AI诊断`、`AI重载`、`东雪莲测试开/关` 这些当前都有真实入口，不计为消失。
- `其他` 触发词移除是有意替换为 `其他帮助`，不是误删。
- 跨分支出现过的 `desktop-app`、Agent Console 语音 UI、远程 MCP 浏览器桥，先记为另线候选，不计入当前 `bot_ZZY` 主线丢失。

## 6. 本轮并行审计结论

截至 2026-05-27 本轮多 agent 只读审计，当前 `bot_ZZY` 主线中最明确的问题不是“大量功能被删”，而是：

1. help/provider 入口迁移后，AI 插件没有完整保留路由保护。
2. help、Dashboard、AI runtime 各自复制的供应商/模型/默认值开始漂移。
3. Dashboard 配置面板存在“看起来可改、实际没写入后端或没被 runtime 读取”的半实现控件。
4. 记忆功能从旧聊天记忆扩展到 Agent 长期记忆后，文案没有拆清楚，造成“好像丢了”的错觉。
5. 若追全仓库历史，确实存在一些侧枝完整能力未进入当前主线，但需要单独判定是否要找回，而不是直接按当前主线 bug 修。
