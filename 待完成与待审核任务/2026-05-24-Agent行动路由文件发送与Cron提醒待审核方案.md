# Agent 行动路由、文件产物发送与 Cron 提醒待审核方案

## 背景

2026-05-24 现场暴露三类行动能力问题：

1. 用户发文件后说“这个文件说了什么”“你看一下吧”，Bot 没有自然调用文件分析，只有用户明确说“读文件”时才命中字面指令。
2. 用户要求“把刚才文件标题重命名为 1 然后发给我”，Bot 只能口头否认或让用户复制粘贴，不能创建安全产物并发回。
3. 用户说“十分钟后提醒我起床”，Bot 没有通过自由路由创建定时任务。

本方案只描述待审核修复逻辑，不包含部署、重启或推送授权。

## 总原则

- 主路径是模型基于当前消息、active scene、最近文件锚点、可用工具说明进行自由路由。
- 代码只做权限、时效、路径、大小、危险动作和发送目标边界。
- 旧的“读文件/看文件/分析文件”字面指令可以保留为兜底，但不能继续作为唯一入口。
- 不开放 QQ 侧通用写文件、任意读路径、任意发本地文件能力。
- 定时提醒复用现有 `agent/cron.js` 基础设施，不新造第二套 reminders 系统。

## 方案一：通用行动路由层

新增或扩展一个 `action router`，输入：

- 当前消息文本。
- active scene。
- 最近文件/图片/引用链锚点。
- 可用工具清单。
- 当前会话类型、发送者、频道。

输出：

- 是否需要执行工具。
- 工具名和参数。
- 是否需要用户确认。
- 不执行时回到普通聊天。

核心要求：

- “这个文件说了什么”“你看一下吧”“就是刚刚那份文件”应能路由到 `analyze_file`。
- “重命名为 1 然后发给我”应能路由到受限文件产物工具。
- “十分钟后提醒我起床”应能路由到现有 cron 的一次性任务注册。
- 随机主动回复不能执行写文件、发文件、创建提醒等行动，只能在明确交互里执行。

## 方案二：文件锚点与安全产物

用户发文件后，生成 active file anchor：

- fileId / messageId。
- 文件名、大小、类型。
- 发送者、频道、时间。
- 缓存状态、分析状态。
- 是否可创建派生产物。

新增受限工具 `create_uploaded_file_variant`：

- 只允许基于最近上传文件创建副本或轻量改写产物。
- 输出目录固定到安全产物目录，例如 `DATA_DIR/agent-user-files/...`。
- 文件名必须净化，保留合理扩展名，例如 `1.txt`。
- 禁止写仓库、配置、日志、运行数据根目录、`AGENTS.md`、任意绝对路径。
- 禁止把真实服务器路径、token、cookie、key 写入产物。

发送文件：

- 复用现有 QQ 发文件工具。
- 发送目标从当前 session 推断，模型不能自己填写 QQ 号、群号或路径。
- 群聊可以发文件，但只能发安全产物或用户上传文件派生副本。
- 不能发任意本地文件、仓库文件、日志、密钥、配置。

## 方案三：复用并扩展现有 Cron

不新增独立 `reminders.js`。在 [cron.js](../packages/koishi-plugin-dongxuelian-ai/lib/agent/cron.js) 基础上扩展：

- `mode: 'cron' | 'once'`。
- `runAt` 或 `dueAt`：一次性任务触发时间。
- `targetChannel`：当前会话安全 channel key。
- `targetUserId`：创建者，用于私聊或权限核对。
- `createdFrom`: `qq | dashboard | agent`。
- `status`: `pending | running | done | failed | cancelled`。

一次性提醒注册流程：

1. 模型自由路由识别“十分钟后提醒我起床”。
2. 代码解析相对时间，生成 `runAt`。
3. 调用扩展后的 `registerCron()` 或新增 `registerOnceTask()`，仍写入现有 `agent-crons.json`。
4. 立即自然回复“好，十分钟后提醒你起床”。
5. 到点后通过现有 `push.cronResult()` 发送提醒。
6. 成功后标记 `done`，不再计算下一次 `nextRunAt`。

多用户异步处理：

- 继续使用现有 `timers` Map 管理定时器。
- 任务 id 包含安全随机段，避免不同用户同名任务互相覆盖。
- 到点执行仍通过 `queue.enqueueAgentTask()` 或轻量 text push，不绕过 Agent 队列。
- 同一频道/同一用户可加并发上限，防止大量提醒同时触发刷屏。
- 写文件继续走现有 `cronWriteChain` 串行化，避免 JSON 并发写坏。

配置边界：

- 周期任务仍受 `config.cron.enabled` 控制。
- 用户明确创建的一次性提醒可以单独有 `config.cron.onceEnabled` 或等价开关，避免被周期推送总开关误伤。
- 如果产品上希望总开关统一控制，也必须在 Dashboard 文案里区分“周期自动化”和“用户主动提醒”。

## 测试计划

1. **自然文件读取**
   - 输入：文件消息后，用户说“这个文件说了什么”“你看一下吧”。
   - 断言：路由到 `analyze_file`，不是普通闲聊，也不是只有“读文件”才触发。

2. **文件重命名并发回**
   - 输入：文件消息后，用户说“把刚才文件重命名为 1 发给我”。
   - 断言：创建安全产物 `1.<ext>`，调用发文件工具，目标来自当前 session。

3. **拒绝任意路径发送**
   - 输入：要求发送仓库文件、日志、配置、绝对路径文件。
   - 断言：拒绝或要求明确安全来源，不调用发文件工具。

4. **一次性提醒**
   - 输入：“十分钟后提醒我起床”。
   - 断言：注册 `mode='once'` 任务；fake timer 到点后发送提醒并标记 `done`。

5. **多用户提醒互不覆盖**
   - 输入：同一群内多个用户分别创建提醒。
   - 断言：任务 id 不冲突，到点分别按创建者/频道发送。

6. **重启恢复**
   - 输入：注册一次性提醒后重启 scheduler。
   - 断言：未到点任务恢复；已完成任务不重复触发。

## 验收标准

- `npm run check` 通过。
- `npm run test:quick` 通过。
- `npm run test:scenario` 覆盖文件自由路由、文件产物发送、一次性 cron、多用户并发。
- 测试报告必须说明 mock 范围：fake Koishi session、fake QQ 发文件、fake timer、fake file-store。
- 线上部署前必须再次确认服务器无未保存修改，并经用户明确同意。
