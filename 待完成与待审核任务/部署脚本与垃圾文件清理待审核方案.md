# 部署脚本与垃圾文件清理待审核方案

更新时间：2026-05-21

## 一、当前结论

本次只是只读盘点，没有执行删除、部署、推送，也没有修改已有计划文档。

当前仓库确实存在多套部署入口，建议后续把部署主线收敛为：

- 更新部署主线：Dashboard 远程部署接口 + `scripts/restart-bot.sh`
- 首次 Linux 安装：`setup.sh`
- Windows 新用户部署：`local-deployer/`
- 单插件排错部署：`scripts/deploy-package.sh` 与各插件 wrapper 脚本

核心原则：主线部署必须覆盖插件后端、Dashboard 前端、Dashboard 后端、重启脚本、数据目录封口脚本和健康检查，避免只同步一部分文件导致线上版本不完整。

## 二、推荐保留的部署入口

### 1. Dashboard 远程部署接口

位置：

- `packages/koishi-plugin-dashboard/lib/routes/deploy.js`
- `packages/koishi-plugin-dashboard/lib/deploy-helpers.js`

建议定位：日常更新部署主线。

保留原因：

- 会构建并同步 Dashboard 前端。
- 会同步 Dashboard 后端、插件 `lib/` 与 `package.json`。
- 会上传 `scripts/restart-bot.sh` 作为远端 `restart.sh`。
- 会同步 `seal-data-dir.sh` 与 `watchdog.sh`。
- 会执行重启与健康检查。

注意事项：

- 需要继续保证敏感服务器信息只来自本地配置或环境变量。
- 远程路径、用户、端口等不能写死进可提交文档。

### 2. `scripts/restart-bot.sh`

建议定位：服务器标准重启脚本模板。

保留原因：

- 比旧 `scripts/restart.sh` 更适合作为当前主线。
- 只针对 Koishi worker/start 做重启，不粗暴杀掉 Dashboard。
- 显式设置 `KOISHI_DIR`、`DONGXUELIAN_AI_DATA_DIR`、`NODE_PATH`。
- 会调用 `seal-data-dir.sh`。
- 会检查端口和 `adapter connect to server`。

待确认事项：

- Windows 本地没有 Bash，语法检查需要在 Linux/服务器或带 Bash 的环境再跑一次。
- 脚本文本在 PowerShell 默认显示下有中文乱码，后续如编辑中文注释，必须用 UTF-8 安全方式。

### 3. `setup.sh`

建议定位：首次 Linux 安装、重建环境入口。

保留原因：

- 文档和测试都有覆盖。
- 职责是初始化系统依赖、Node、NapCat、Koishi、配置文件和数据目录。
- 不适合替代日常更新部署，但适合新机器或重建环境。

### 4. `local-deployer/`

建议定位：Windows 新用户主入口。

保留原因：

- 图形化处理本机部署流程。
- 覆盖 Node/npm、NapCat、Koishi 配置、扫码登录、健康检查等体验。
- 比手动执行 `deploy.bat` 更适合普通用户。

### 5. `scripts/deploy-package.sh` 与插件 wrapper

相关文件：

- `scripts/deploy-package.sh`
- `scripts/ai.sh`
- `scripts/help.sh`
- `scripts/name.sh`
- `scripts/poke.sh`
- 其他同类单插件脚本

建议定位：维护者小范围补发和排错工具。

保留原因：

- 可以快速同步单插件。
- 有路径安全检查和基础语法检查。
- 被现有测试覆盖。

限制：

- 不适合作为完整更新部署主线。
- 容易漏 Dashboard 前端、后端、脚本、数据种子等跨模块内容。

## 三、建议废弃或删除的旧入口

### 1. `scripts/restart.sh`

建议：废弃，后续可删除或改成调用 `restart-bot.sh` 的兼容 wrapper。

原因：

- 会同时杀 Koishi 和 Dashboard。
- 没有 `restart-bot.sh` 那么完整的环境变量处理。
- 逻辑更粗，线上排障时更容易扩大影响面。

删除前需要做：

- 同步 README/readme2/部署教程中的引用。
- 同步测试里对重启入口的断言。
- 确认服务器实际使用的是由 `restart-bot.sh` 上传生成的远端 `restart.sh`。

### 2. `scripts/deploy-frontend.bat`

建议：废弃或删除。

原用途：Windows 本地手动构建并同步 Dashboard 前端。

问题：

- 只同步前端 dist/src。
- 不同步 Dashboard 后端和插件代码。
- 容易造成线上前后端版本不一致。

如果保留，只建议标注为紧急前端补发工具，不作为主线。

### 3. `scripts/deploy-and-restart.bat`

建议：废弃或删除。

原用途：日报插件快速同步并远程重启。

问题：

- 只针对 `koishi-plugin-daily-report`。
- 覆盖面太窄，容易漏依赖和公共脚本。
- 与当前全量更新部署思路冲突。

### 4. `.deploy-current-code.remote.sh`

建议：删除。

原用途：一次性远端解包、同步当前代码、重启和健康检查。

删除原因：

- 已被 Dashboard 远程部署流程替代。
- 属于历史临时脚本，继续保留会增加部署入口混乱。

### 5. `deploy.bat` 与 `setup.bat`

建议：暂时保留，后续再评估是否合并到 local-deployer 文档。

原用途：

- `deploy.bat`：传统 Windows 本地手动部署。
- `setup.bat`：Windows 本地运行前准备与提示。

问题：

- 体验和完整性不如 `local-deployer/`。
- 容易让新用户走到旧流程。

处理建议：

- 短期保留为兜底。
- 文档中明确新用户优先使用 `local-deployer/`。
- 等 local-deployer 稳定后，再考虑删除或迁移说明。

## 四、可清理的本地 ignored 文件

这些文件或目录已被忽略，不需要提交删除；清理前确认没有正在运行的本地服务依赖它们。

### 强烈建议清理

- `packages/desktop-app/node_modules/`

原因：

- 体积约 505MB。
- 目录未被 git 跟踪。
- 内部出现嵌套依赖和构建产物，导致 `git status --ignored` 大量路径过长警告。
- `packages/desktop-app` 本身没有 tracked 文件，疑似历史残留。

### 可以清理

- `dist-portable/`
- `packages/koishi-plugin-dashboard/frontend/node_modules/`
- `debug.log`
- `koishi.log`
- `tmp/*.log`

原因：

- 属于构建产物、依赖目录或日志。
- 需要时可以重新安装、重新构建或重新生成。

### 谨慎清理

- 根目录 `node_modules/`

原因：

- 不是垃圾，但体积较大。
- 删除后需要重新 `npm install`。

## 五、建议提交删除的 tracked 历史残留

这些文件已经被 git 跟踪，不能只在本地删；如果决定清理，需要单独提交删除，并补充忽略规则防止再次进入仓库。

### 1. `tmp/` 下的 tracked 文件

数量：约 25 个。

类型：

- Dashboard 视觉预览 html/png。
- 临时测试输出。
- 临时部署片段。

建议：删除，并在 `.gitignore` 增加对 `tmp/` 的整体忽略。

原因：

- 临时产物不应长期跟踪。
- 继续保留会干扰搜索和审查。

### 2. `packages/koishi-plugin-dongxuelian-ai/data/agent-tool-results/*.txt`

数量：约 11 个。

原用途：测试或 agent 工具执行结果记录。

建议：删除，并确认测试不会继续生成 tracked 文件。

原因：

- 属于运行/测试产物。
- 不应作为源码长期维护。

### 3. `.deploy-current-code.remote.sh`

建议：随旧部署入口清理一起删除。

原因：

- 一次性脚本。
- 当前部署主线已替代它。

### 4. `personas-api.txt`、`server-sidebar.txt`

建议：删除前再做一次引用确认，若无引用则删除。

原用途：

- 看起来是历史 API 片段或前端组件片段。

问题：

- 不像正式源码位置。
- 容易和真实实现混淆。

### 5. 根目录 `SKILL.爱弥斯.md`

建议：删除前确认正式人格文件已经在插件 data 目录中。

原因：

- 看起来像人格文件副本。
- 正式人格种子文件应位于 `packages/koishi-plugin-dongxuelian-ai/data/ai-skills/personas/`。
- 当前根目录副本格式疑似不规范，容易误导后续编辑。

### 6. `data/nickname-collections.json`

建议：删除或改成 example 文件。

原因：

- 根 `data/` 是运行数据目录，整体应视为本地状态。
- 当前内容为空对象，长期跟踪价值低。

## 七、建议执行顺序

### 阶段一：只清理本地 ignored 大垃圾

优先处理：

- `packages/desktop-app/node_modules/`
- `dist-portable/`
- 无用日志

验收：

- `git status --short --branch` 不出现新的源码改动。
- `git status --ignored` 不再出现大量路径过长警告。

### 阶段二：收敛部署文档

目标：

- 明确主线为 Dashboard 更新部署 + `restart-bot.sh`。
- 明确 `setup.sh` 是首次安装入口。
- 明确 `local-deployer/` 是 Windows 新用户入口。
- 将旧 bat 脚本标注为废弃或维护者工具。

注意：

- 文档只能写占位符，不能写真实服务器信息。

### 阶段三：提交删除 tracked 临时文件

候选：

- `tmp/` tracked 文件。
- `agent-tool-results/*.txt`。
- `.deploy-current-code.remote.sh`。
- 无引用的历史片段文件。

验收：

- `npm run check`
- `npm run test:quick`
- 重点检查 cascade 测试中是否硬编码引用了待删除文件。

### 阶段四：废弃旧部署脚本

建议顺序：

1. 先把 `scripts/restart.sh` 改成兼容 wrapper 或文档标记废弃。
2. 再处理 `deploy-frontend.bat` 和 `deploy-and-restart.bat`。
3. 最后评估 `deploy.bat`、`setup.bat` 是否保留。

验收：

- README/readme2/部署教程引用同步。
- 测试中部署入口断言同步。
- 服务器实际部署流程仍可通过健康检查。

## 八、风险点

- 删除 tracked 临时文件可能触发 cascade 测试失败，需要同步测试断言。
- 删除旧部署脚本前必须确认文档和实际使用习惯，否则用户可能继续按旧教程执行。
- 清理 `data/` 下文件前要区分“种子数据”和“运行数据”。
- Windows PowerShell 读取中文 shell 文件时容易显示乱码，不能据此判断文件内容损坏。
- 本机没有 Bash 时，shell 脚本语法检查应放到 Linux/服务器或带 Bash 的环境执行。

## 九、待用户确认

- 是否先清理本地 ignored 大垃圾，尤其是 `packages/desktop-app/node_modules/`。
- 是否单独做一个仓库卫生提交，删除 tracked 临时文件。
- 是否把旧部署脚本先标注 deprecated，而不是直接删除。
- 是否将部署文档统一收敛到 README/readme2 中的一处主线说明。
