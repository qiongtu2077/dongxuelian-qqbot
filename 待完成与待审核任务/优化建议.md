### L12-1 B 站视频过大时返回硬编码英文兜底，绕开当前人格语气

真实性：真实存在，用户现场复核 + 本地源码确认。

用户补充口径：
- 真实群聊里发送 B 站大视频时，同一条现场消息包含视频标题、缩略图和短链；随后插件兜底发出固定英文“视频太大请去 B 站看”的系统式回复，并暴露类似 `Size: 331.6MB` 的纯工具口吻。归档时不保存用户贴出的本地图片缓存路径、账号目录或短链原文。
- 这不是“视频过大不能发”的边界错，而是执行层把最终可见话术硬编码了。事实边界应保留为：视频超过发送大小限制、bot 不能代发、建议去原站观看、可带大小；说法应交给当前人格/群绑定自定义人格生成。
- 期望不是把英文改成另一句固定中文，而是让当前人格接管可见表达：默认人格可以自然吐槽“东西太大所以发不了、去原站看”，自定义人格也应按自己的说话方式说明同一事实。
- 示例措辞只能作为人格表达风格参考，禁止把某个比喻、某句原话或某个人格名硬编码进插件。

证据：
- 用户现场输入是 B 站视频链接，消息中包含视频标题、缩略图和链接；插件返回固定英文：视频太大，请去 B 站观看，并附大小。
- 本地 `packages/koishi-plugin-local-video-sender/lib/index.js` 在 `picked.totalSize > MAX_SIZE` 时直接 `return` 英文模板。
- 下载完成后发现实际文件超过限制时，同一文件也直接返回另一条英文模板。
- `packages/koishi-plugin-local-video-sender/test/plugin-test.js` 当前断言也绑定 `Video is too large`，等于把硬编码英文兜底固化为期望行为。

影响：
- 群聊中其他回复都按东雪莲/当前人格说话，但这个插件兜底突然切成英文系统提示，割裂感明显。
- 用户实际感知不是“视频处理工具失败”，而是 bot 本人突然机械报错；尤其在群里会破坏人格连续性。
- 仅把英文改成固定中文也不够，仍会变成另一种硬编码模板；正确方向是让兜底说明走人格化表达层，同时保留事实信息：视频过大、无法直接发送、建议去原站看、大小。

建议修复：
- **原建议过度设计。** 不需要”结构化事实返回 + 人格表达层 + 可注入 formatter”这套抽象。视频插件的返回值已经会被 AI 模型消费并转述——模型本身就是”人格表达层”。
- 最小修法：把两处英文硬编码模板改为简洁中文事实描述，例如 `视频太大（${sizeText}），无法通过 QQ 发送，建议去 B 站观看。`。模型拿到这个工具返回后会用当前人格语气转述给用户。
- 如果插件返回值直接作为最终消息发送（不经过模型），则改为中文模板即可满足当前需求。后续如果要支持多人格差异化表达，再考虑 formatter 注入。
- 测试更新：断言改为匹配中文关键语义（”太大”/”无法发送”/”B站”），不绑定具体措辞。
- 保留确定性安全边界：超过大小仍绝不下载/发送；人格化只改变可见回复文案。

验证方式：
- 修复前：超大视频返回固定英文 `Video is too large...`。
- 修复后：同样输入下仍不下载/不发送超限视频，但回复按当前人格自然说明太大；测试不再绑定英文模板。
- 回归：预览消息仍能发送，短链仍保留，超限时不会执行 downloader，实际下载后超限仍会删除临时文件。

### L14-1 文件追问守卫在模糊指代时可退回旧文件/他人文件，缺少“需要澄清”的执行级边界

真实性：真实存在，可本地纯函数复现；服务器版本同源且更原始。

证据：
- 本地 `file-followup-guard.js` 的 `selectActiveFileAnchor()` 会先取 30 分钟内 fresh 文件；如果没有 fresh，就回退到所有历史文件 `const candidates = fresh.length ? fresh : files`。
- 同函数只在 `candidates` 内优先同用户；如果当前有别人 5 分钟内发的新文件、自己只有 2 小时前旧文件，模糊追问会选别人新文件。
- UTF-8 安全复现：`looksLikeFileFollowup("这个文件里面说了什么", oldFiles)` 返回 true；两个文件都超过 30 分钟时，`selectedSameUser` 和 `selectedOtherUser` 都会返回旧文件 `old-a`。
- 另一组复现：`fresh-other` 为 5 分钟内他人文件、`old-self` 为 2 小时前自己文件，当前用户模糊问“这个文件”时 `selectActiveFileAnchor()` 返回 `fresh-other`。
- `resolveUnguardedFileFollowup()` 会把选中的 `messageId` 传给 `analyze_file`，也就是说这是自动补读路径，不只是给模型看的候选列表。

影响：
- 用户确实可以主动拉回旧文件，但模糊句“这个文件/里面说了什么”过了活跃窗口时，bot 不应自行猜一个旧文件来读；更合理的是列候选或自然澄清。
- 群聊里其他人刚发文件时，当前用户的模糊追问不一定是在问他人文件；如果没有 replyTo、同用户上传、文件名关键词或 active scene 锚点，自动读他人文件可能错接公共/私人任务。
- 这和用户强调的“旧图旧文件不是绝对错误，问题是权重、归属、锚点和时效”一致：问题不在使用旧文件，而在模糊自动补读缺少强锚点。

建议修复：
- **原建议过度设计。** 不需要”自动补读 vs 候选展示”的双模式抽象。
- 最小修法（1 行）：`selectActiveFileAnchor()` 在没有同用户 fresh 文件时，不要 fallback 到其他用户的文件。改为返回 null，让模型自然澄清：
  ```js
  // 原：return sameUser[0] || candidates[0] || null
  // 改：
  return sameUser[0] || (userId ? null : candidates[0]) || null
  ```
  当 `userId` 已知但没有同用户文件时返回 null，上层不会自动调用 `analyze_file`，模型会自然地问”你指哪个文件”。
- 30 分钟窗口保留：fresh 文件筛选已经限制了时效，不需要额外的过期逻辑。
- 补 scenario：只有他人 fresh 文件时模糊追问不自动读；同用户 fresh 文件仍可自动读；引用文件消息或说出文件名时仍能读取。

验证方式：
- 修复前：模糊追问会通过 fallback 选中过期旧文件或他人 fresh 文件，并进入 `analyze_file`。
- 修复后：模糊且弱锚点时不自动补读；强锚点旧文件仍可读。
- 回归：最近同用户文件追问、文件名唯一命中、read_group_context 拉回公共文件讨论等正例仍可用。

## 本地第 16 轮（群聊 URL 自由路由与 active scene 裁决）

范围：继续扫描裸 URL、链接读取、搜索追问和群聊 active scene 的路由边界。本轮不把“私聊裸 URL 自动读”或“群聊 URL 可被读取”本身当 bug；只确认群聊里是否存在绕过上下文裁决、直接预执行外部读取的路径。

### L16-1 群聊带图链接在随机/弱交互路径中可绕过 active scene 裁决直接 `web_fetch`

真实性：真实存在，可本地纯函数复现；服务器当前运行包同源。

证据：
- `message-reader.js` 对“图片缩略图 + URL + 文本”的消息会得到 `hasLink=true`、`hasVisual=true`、`shouldSkipForRandomReply=false`。因此群聊非点名消息如果在随机白名单里命中主动回复，仍可能进入主 chat/route 链路。
- `search-context.js` 对非私聊会返回 `searchReadiness: 'needs_chat_handling'`，也就是这类群聊上下文按设计需要交给聊天层结合 active scene 判断。
- 但 `agent/router.js` 的 `heuristicRoute()` 在检查 `searchContext` 之前，先判断 `isExplicitUrlFetchRequest(text)`；命中“这个视频的评论区说了什么 + URL”时直接返回 `{ useAgent:true, reason:'explicit-url-fetch' }`。
- 同一路径的 `buildExplicitSearchRunOptions()` 会直接构造 `forceTools:['web_fetch']` 和 `preExecuteTools:[{ name:'web_fetch', args:{ url } }]`。
- 本地最小复现：群聊 session、文本为“这个视频的评论区说了什么 + 占位 URL + 图片标签”，`searchReadiness=needs_chat_handling`，但 route 仍是 `explicit-url-fetch`，并生成 `web_fetch` 预执行。

影响：
- 这不是“群聊 URL 一律不能读”。真正问题是群聊里 URL 是否该读，应该由 active scene、点名/引用、当前公共任务、用户是否主动让 bot 参与、上下文是否足够明确来裁决；当前 explicit URL route 把“读链接意图”当成足够条件。
- 对 B 站/视频类链接尤其明显：用户可能是在和群友讨论、贴视频卡片或吐槽评论区，并不一定是在请求 bot 去读网页；随机主动命中时直接 fetch 会显得像误入话题。
- 即使 `web_fetch` 最后读不到评论区，也已经发生外部访问和 Agent 链路占用；这会削弱“群聊 URL 要按 active scene 和上下文自由路由”的长期要求。

建议修复：
- **原建议方向正确但过于复杂。** 不需要给 `heuristicRoute()` 增加 `isPrivate`/`directAt`/`nameMentioned`/`randomTriggered`/active scene 摘要等大量元数据输入。
- 最小修法：在 `index.js` 调用 `buildExplicitUrlFetchRunOptions()` 后，对随机触发且非点名的群聊消息，删除 `preExecuteTools`（保留 `forceTools` 让模型仍可自由调用）：
  ```js
  const urlRunOptions = buildExplicitUrlFetchRunOptions(userText)
  if (randomTriggered && !directAt && !nameMentioned) delete urlRunOptions.preExecuteTools
  ```
  这尊重”自由路由/工具调用为主”的约束——工具仍在列表中可用，模型仍可决定调用，只是不再未经模型判断就预执行。
- 私聊和明确点名/引用的正路不受影响：`randomTriggered=false` 或 `directAt=true` 时 `preExecuteTools` 保留。
- 补 scenario：群聊非点名随机命中 + URL 文本，断言 `web_fetch` 不被预执行但仍在工具列表中；点名/私聊同样文本仍预执行。

验证方式：
- 修复前：群聊 `searchReadiness=needs_chat_handling` 仍被 `explicit-url-fetch` 抢先路由，并生成 `web_fetch` 预执行。
- 修复后：非点名/随机群聊 URL 先进入 chat active scene 裁决，不直接预执行；私聊和明确点名请求的 URL 读取保持可用。
- 回归：用户明确“不要联网/不要读链接”仍过滤 `web_search` / `web_fetch`；web_fetch 读取失败仍不能编造评论区内容。

### L25-1 Agent 允许根本身是符号链接/junction 时，读写工具和 Dashboard 文件预览会误报“超出允许范围”

真实性：真实存在，可本地临时目录复现；服务器当前运行包源码同源。

证据：
- `agent/path-guard.js` 的 `realpathOrResolvedAgentPath(target)` 先 `path.resolve(target)`，如果 `fs.existsSync(resolved)` 为真就直接返回 resolved，后面的 `fsp.realpath(resolved)` 对已存在目录永远不会执行。
- `assertExistingAgentPathInsideRoots()` 却会对目标文件执行 `fsp.realpath(abs)`，再用 `isAgentPathInside(real, root)` 和 allowed roots 比较。
- 本地最小复现：临时 DATA_DIR 下创建一个 junction 作为 `readFileRoots`，真实目录放在另一个临时根；通过该 junction 读取 `note.txt` 时，`read_file.execute()` 返回“文件超出允许范围”，但该路径正是管理员配置的允许根下文件。
- 同一轮排除项：Dashboard `GET /dashboard/api/agent/sessions` 和 `GET /dashboard/api/agent/sessions/<id>` 都有 `requireAdmin`；文件列表、预览、下载、上传接口也都有管理员鉴权。本轮问题不是未授权访问，而是已授权/已配置路径被守卫误拒。

影响：
- 如果管理员把 Agent 工作区、外部资料库、共享目录或部署目录通过符号链接/junction 挂到允许根，Dashboard 文件列表/预览/下载、`read_file`、`list_files`、`grep_search`、`write_file` 等都会出现“明明配置了允许根但读不了/写不了”的失败。
- Windows 本地更容易用 junction 规避权限或路径长度问题，开发环境会更明显；Linux 服务器如果用软链接组织数据目录或工作区，也会同源触发。
- 这会让用户误以为 read root 配置、工具权限或 Dashboard 鉴权坏了，实际是 root 和目标的 realpath 归一化不一致。

建议修复：
- `realpathOrResolvedAgentPath()` 应优先尝试 `fsp.realpath(resolved)`；只有目标不存在或 realpath 失败时才回退到 `resolved`。
- allowed roots 最好同时保留“展示用原始 root”和“比较用 real root”。路径安全判断只用 real root；Dashboard 展示可以继续显示用户配置的原始路径，避免 UI 突然跳到真实物理路径。
- `resolveAgentPathInput()` 接收 roots 时要确认语义候选、相对路径拼接和真实 root 比较不会分裂；配置的是链接路径时，用户仍应能用链接路径访问，最终比较用 realpath。
- 补测试：配置 `readFileRoots` 为符号链接/junction 目录时，`read_file`、`list_files`、Dashboard `previewAgentWorkspaceFile()` 能访问链接根内文件；链接根内再指向根外的二级 symlink 仍必须被拒绝。

验证方式：
- 修复前：配置允许根为 junction/符号链接目录，读取该目录下普通文件会报“超出允许范围”。
- 修复后：同样输入可以读取/预览；把链接根内某个文件再指到允许根外时仍会被拒绝。
- 回归：普通真实目录允许根、默认 DATA_DIR、写安全配置黑名单、工作区外绝对路径拒绝逻辑不变。

## 本地第 30 轮（Agent 队列超时与定时任务取消语义）

范围：继续扫描 Agent 定时任务、队列超时、运行中任务重入和无人值守链路。本轮重点不是“任务应该永远不超时”，而是确认超时以后底层 Agent 是否真的停止，避免外层已判失败但旧任务继续做副作用。

结论：本轮新增 1 个真实问题。`agent/queue.js` 的超时实现只用 `Promise.race()` 让外层 promise 失败并释放队列槽，没有给底层 `fn` 传入 `AbortSignal`，也没有取消仍在运行的 Agent。`cron.runCronNow()` 又把 scheduled agent 的 `runPolicy.maxRuntimeMs` 接到该队列上，因此定时任务超时后，cron 可能已记录失败/释放重入锁，但原 Agent run 仍继续执行工具、写状态或尝试外发。

### L30-1 Agent 队列 timeout 释放槽位但不取消底层任务，scheduled agent 超时后仍可能继续副作用

真实性：真实存在，可本地最小复现；服务器当前运行包源码同源。

证据：
- `packages/koishi-plugin-dongxuelian-ai/lib/agent/queue.js` 的 `withTimeout(fn, timeoutMs)` 使用 `Promise.race([Promise.resolve().then(fn), timeoutPromise])`；timeout 只 reject 外层 promise，未创建 `AbortController`，也未把 signal 传给 `fn`。
- `startTask()` 在 timeout 后进入 `catch/finally`，会增加 `timeoutCount`、清理 `activeKeys`、减少 `activeCount` 并 `drainAgentQueues()`；也就是说队列认为任务已经结束。
- 本地最小复现：入队一个 5 秒 timeout、内部 5.2 秒后写入 `events` 的异步任务。结果外层在约 5001ms 返回 `AGENT_QUEUE_TIMEOUT`，但 5201ms 时内部仍写入 `late-side-effect`；此时队列统计已显示 `activeCount: 0`。
- `packages/koishi-plugin-dongxuelian-ai/lib/agent/cron.js` 的 scheduled agent 分支调用 `queue.enqueueAgentTask({ timeoutMs: cron.runPolicy?.maxRuntimeMs, fn: () => engine.run(...) })`。一旦 timeout，`runCronNow()` 会进入失败收尾、写 cron history/status，并在 finally 中释放 `runningCrons`；但原 `engine.run()` loser promise 仍可能继续跑。
- 计划恢复 `plan/plan-runner.js` 也通过同一个队列包裹 `engine.run()`；虽然它不是 cron history 问题，但同样会出现“队列层已超时、底层计划 Agent 仍继续”的取消语义缺口。

影响：
- 定时 Agent 是无人值守链路。外层超时后如果底层模型调用、搜索/fetch、文件工具、计划工具、提醒工具或推送工具仍继续执行，会出现“任务面板显示失败/已过期，但稍后又写状态或发消息”的错位。
- 队列槽和 `runningCrons` 提前释放后，同一用户/同一任务可能启动下一轮执行；旧任务和新任务并发写 cron、计划、记忆或文件，放大竞态。
- `runPolicy.maxRuntimeMs` 会给用户一种强运行上限的承诺，但当前实现更接近“等待上限”，不是“执行上限”。对 scheduled agent、自动计划和未来外部工具链路来说，这个差异会变成真实可见副作用。

建议修复：

**审核批注**：原建议要求全链路 AbortController + signal 传播，涉及 engine、所有工具、模型调用、fetch 等改动面过大。JS 中 Promise.race loser 无法被 GC 前强制取消，全量 signal 检查成本高且容易遗漏。最小修法应聚焦"超时后禁止副作用"而非"取消底层执行"。

- 最小修法：给每个队列任务分配 `runId`（递增整数即可）。`startTask()` timeout 后把该 `runId` 加入 `expiredRuns` Set。
- `cron.runCronNow()` 在 push/写 history/写 status 前检查 `expiredRuns.has(runId)`，命中则跳过副作用并记录"超时后丢弃"日志。
- `engine.run()` 的 `pushResult()` / `recordAgentChatResult()` 同样在写入前检查 runId 是否已过期。
- 这样底层 Promise 仍会自然完成（无法阻止），但不会产生用户可见副作用。
- 补测试：构造一个超时后才尝试 push 的假工具，断言 timeout 后 push 不执行；同时覆盖正常未超时任务仍完成。

验证方式：
- 修复前：5 秒 timeout 的队列任务外层失败后，内部异步函数仍能在 5.2 秒执行副作用。
- 修复后：timeout 会触发取消信号；底层 Agent/工具检测到取消后停止，队列释放槽位后不再有晚到副作用。
- 回归：正常未超时任务仍完成；队列满、per-user 串行、scheduled text 发送和 cron history 写入逻辑不受影响。

### L38-1 active scene 短句回填会把冷旧群聊记录标成最高优先级当前现场

真实性：真实存在，可本地最小复现；服务器当前运行包源码同源。

证据：
- `packages/koishi-plugin-dongxuelian-ai/lib/group-scene-index.js` 的 `buildActiveGroupSceneNote()` 会先按 hot/thin/reply/media 条件构造 `active`。

影响：
- 群聊短句、随机主动插话或“真的吗/这个呢/这张图呢”这类弱指代消息，可能被 1-2 小时前的群聊缓存牵走，表现为翻旧账、错接他人话题或把旧媒体当当前主语。
- 即使工具层没有立刻读旧图旧文件，prompt 层已经把旧材料提升成最高优先级，模型更容易生成锚定旧内容的回复或选择后续 `read_group_context`、图片/文件工具。
- 这会削弱“旧摘要和长期记忆只能作背景”的提示，因为回填材料本身不被标为旧背景，而被放在比摘要更高的当前现场区。
- 对随机主动回复更危险：没有明确用户请求时，冷旧记录也可能被作为锚点，导致 bot 延迟补发旧话题。

建议修复：

**审核批注**：原建议方向正确但过于冗长，把媒体锚点、随机主动回复策略、关键词硬编码警告等全部混入。核心修法只需给 fallback 回填加时效门槛。

- 最小修法：`fallbackNeeded` 回填时加时效检查：
  ```js
  const HOT_WINDOW_MS = 10 * 60 * 1000 // 10 分钟
  const recentHot = recent.filter(r => (Date.now() - r.timestamp) < HOT_WINDOW_MS)
  if (recentHot.length === 0) return '' // 没有热记录，不生成 active scene note
  finalItems = recentHot.slice(-ACTIVE_SCENE_MAX_ITEMS)
  ```
- 超过 10 分钟的记录不进入 `[当前群聊现场-最高优先级]`。如果需要旧背景，可以单独返回 `[旧群聊背景-低优先级]` 标签，但不和当前现场混用。
- 随机主动回复路径：`fallbackNeeded && options.randomTriggered` 时，如果只有冷旧记录，直接返回空（不生成 scene note），让随机回复走 `ambient_water` 或 `no_send`。
- 补 scenario：2 小时前记录 + 当前短句不生成最高优先级现场；5 分钟内记录仍可作为当前锚点。

验证方式：
- 修复前：冷旧缓存记录在短句场景下进入 `[当前群聊现场-最高优先级]`。
- 修复后：冷旧记录要么不进入 active scene，要么被标为低权重旧背景候选；只有强锚点旧材料才可被明确拉回。
- 回归：当前热群聊、多轮公开 bot 回复承接、引用链、近期图片/文件/语音锚点、群聊随机主动插话的轻量背景策略仍正常。

### L39-1 MCP 文件诊断工具可在只开诊断时写入文件历史和缓存

真实性：真实存在，可本地临时 DATA_DIR 复现；服务器当前运行包未发现同源新增诊断入口。

证据：
- `packages/koishi-plugin-dongxuelian-ai/lib/mcp/local-server.js` 新增 `diagnose_analyze_file`，描述为“复现 QQ chat 的文件分析工具调用”，但 handler 直接执行 `analyzeFileTool.execute(...)`。
- `simulate_file_followup` 会调用 `resolveUnguardedFileFollowup()`，该函数在需要补证时同样执行 `analyzeFileTool.execute(...)`。
- `analyze_file` 在未命中已有分析时会调用 `analyzeFileNow()`；`file-analyzer.js` 的 `runAnalysis()` 会通过 `setLocalPath()`、`markFileAnalyzed()` 写回文件缓存路径、分析结果、失败状态等运行数据。
- 这两个 MCP 工具只调用 `ensureEnabled()`，不检查 `allowWriteWorkspace`、`allowRunLocal`，也没有单独的“允许写生产/运行 DATA_DIR”开关。`write_file` / `edit_file` 反而会走 `ensureWriteAllowed()`。
- 本地临时 DATA_DIR 复现：配置 MCP enabled=true、allowWriteWorkspace=false、allowRunLocal=false，构造一个未分析文件记录后调用 MCP `diagnose_analyze_file`。返回结果为诊断 JSON，但同一 file-history 记录从 `analyzed=false` 变成 `analyzed=true`，`analysis` 被写成下载失败/过期状态。

影响：
- MCP 使用者以为只是在“诊断/复现”文件追问，实际会改变 bot 后续聊天可见的文件分析状态，甚至把一次临时下载失败永久写成“已分析失败”，影响之后真实用户追问。
- 如果文件 URL 或 OneBot fileId 仍可用，诊断调用还可能触发外部下载、解析 PDF/DOCX/XLSX、写 file-cache、本地路径回填和 file-history 更新；这不是纯只读观测。
- 这违反 MCP 计划里的权限分级：写生产 DATA_DIR/运行状态应属于更高风险动作，不能被“诊断工具”绕过 `allowWriteWorkspace=false` 和危险动作默认不暴露的边界。
- 后续服务器上启用 MCP 时，维护者可能只打开诊断能力用于排查线上文件问题，却意外污染生产文件历史。

建议修复：

**审核批注**：原建议要求 dry-run 路径、影子 DATA_DIR、独立 `allowWriteRuntimeData` 权限、工具副作用元数据等，改动面过大。核心问题很简单：诊断工具不该调用真实 `analyzeFileTool.execute()`。

- 最小修法：`diagnose_analyze_file` 不调用 `analyzeFileTool.execute()`，改为只读取 file-history 中已有的分析结果并返回诊断 JSON。如果文件尚未分析，返回 `{ analyzed: false, wouldCallAnalyze: true, targetFile: ... }` 说明”若真实执行会分析此文件”，不触发下载/解析/回写。
- `simulate_file_followup` 同理：只读取候选锚点和已有分析状态，返回”会选哪个 messageId、是否已有缓存、是否需要补证”，不调用 `resolveUnguardedFileFollowup()` 的写入分支。
- 如果确实需要在 MCP 中触发真实分析，应要求 `allowWriteWorkspace=true` 或单独的 `allowReplay=true` 开关，并在工具描述中标注”会写入 file-history”。
- 补测试：MCP `diagnose_analyze_file` 调用后 file-history 不变；已分析文件能返回已有结果。

验证方式：
- 修复前：MCP `diagnose_analyze_file` 会把未分析文件记录写成 analyzed，并保存失败或摘要结果。
- 修复后：默认诊断只返回候选和计划，不改变 file-history/file-cache；只有明确开启写运行数据权限或使用临时 replay 数据目录时才会执行真实分析。
- 回归：Dashboard/QQ 正常用户明确追问文件时仍可触发 `analyze_file`；MCP `diagnose_recent_files` 仍只读展示最近文件锚点。

- 修复后：泛问返回摘要；精确问题返回对应行/字段/判断；无法从证据回答时说明证据不足。
- 回归：文件取证失败仍直接说明失败；文件包裹不外泄；模型不得按文件名猜内容；随机主动回复不主动翻旧文件。

结论：本轮新增 1 个真实问题。`analyze_file` 被放在 Chat 轻量工具集合里，但 `handleChatToolCalls()` 只给它普通轻量工具的 3 秒超时；超时后结果被写成泛化“工具执行失败”。同时 `chat.js` 只要看到模型调用过 `analyze_file`，就设置 `usedAnalyzeFileTool=true`，后续 `resolveUnguardedFileFollowup()` 会因为“已经调用过 analyze_file”而不再补证。结果是大文件、首次下载、PDF/DOCX/XLSX 解析稍慢时，当前轮会丢掉真实文件证据，即使底层分析 Promise 后来完成。

### L44-1 `analyze_file` 走 3 秒轻量超时，超时后文件补证守卫不会重试

真实性：真实存在，可本地 monkey patch 纯函数复现；服务器当前运行包源码同源。

证据：
- `packages/koishi-plugin-dongxuelian-ai/lib/chat-tools.js` 定义 `CHAT_TOOL_TIMEOUT_MS = 3000`，`CHAT_TOOL_ANALYZE_TIMEOUT_MS = 25000`。
- 同文件 `LIGHTWEIGHT_TOOLS` 包含 `analyze_file`，因此文件分析不会进入 heavy tool 分支。
- `handleChatToolCalls()` 的超时选择只有 `name === 'analyze_historical_image' ? CHAT_TOOL_ANALYZE_TIMEOUT_MS : CHAT_TOOL_TIMEOUT_MS`，没有给 `analyze_file` 使用 25 秒分析类超时。
- 同函数 catch 后统一把工具结果写成 `{ content: '工具执行失败' }`，丢失是 timeout、下载失败、解析失败还是权限失败的区别。
- `packages/koishi-plugin-dongxuelian-ai/lib/chat.js` 在工具调用开始时设置 `usedAnalyzeFileTool = toolCallsIncludeAnalyzeFile(reply.tool_calls)`，并把 `results` 交给 `toolResultsIncludeFileEvidence()` 判断是否有证据。
- `packages/koishi-plugin-dongxuelian-ai/lib/file-followup-guard.js` 的 `resolveUnguardedFileFollowup()` 开头是 `if (state.usedAnalyzeFile || state.hasFileEvidence) return null`。所以只要模型尝试过 `analyze_file`，即使结果是 3 秒 timeout 的“工具执行失败”，守卫也不会再补一次。
- 本地最小复现：把 `analyzeFileTool.execute` 临时替换成 3.5 秒后返回真实文件证据，调用 `handleChatToolCalls([{ name:'analyze_file' }])`。结果约 3001ms 返回 `工具执行失败`，`heavyTools=0`；随后用 `usedAnalyzeFile=true, hasFileEvidence=false` 调 `resolveUnguardedFileFollowup()`，返回 null；再等 0.7 秒底层 Promise 已完成，说明真实证据只是被当前超时层吞掉。

影响：
- 用户问“文件第二条是什么/这个文档说了啥/读一下刚才文件”时，如果首次文件分析超过 3 秒，bot 当前轮会拿不到文件证据，并可能把“工具执行失败”交给模型或固定兜底，表现为没读到、答非所问或让用户重发。
- 后台分析可能已经写入 file-history/file-cache，但当前回复没有等待或二次取证；用户要再追问一次才可能拿到结果，体验像“第一次必失败”。
- 超时信息被泛化成“工具执行失败”，后续回答层无法区分“正在解析，稍后再问”与“文件过期/不支持/没有文件”。
- 这和 L40-1 不同：L40 记录的是读到证据后固定摘要接管；本轮记录的是证据还没被当前轮拿到时，被 3 秒超时和 usedAnalyzeFile 标记组合吞掉。

建议修复：

**审核批注**：原建议提出结构化 pending/timeout 状态系统和补证守卫重构，改动面过大。核心问题只有两个：(1) analyze_file 用了错误的超时值；(2) 补证守卫判断条件不精确。

- 最小修法 1：`handleChatToolCalls()` 的超时选择改为：
  ```js
  const timeout = (name === 'analyze_historical_image' || name === 'analyze_file')
    ? CHAT_TOOL_ANALYZE_TIMEOUT_MS : CHAT_TOOL_TIMEOUT_MS
  ```
  这样 `analyze_file` 也有 25 秒分析时间，和图片分析一致。
- 最小修法 2：`resolveUnguardedFileFollowup()` 的跳过条件从 `usedAnalyzeFile || hasFileEvidence` 改为 `hasFileEvidence`。只有真正拿到证据才跳过补证；仅仅”尝试过但失败”不应阻止重试。
- 如果 25 秒仍不够（极大文件），catch 分支返回”文件正在分析中，稍后再问”而非泛化”工具执行失败”，让模型能自然转述。
- 补测试：`analyze_file` 3.5 秒返回证据时当前轮能拿到；真超 25 秒时返回可区分的超时信息。

验证方式：
- 修复前：`analyze_file` 超过 3 秒返回 `工具执行失败`，且补证守卫不重试。
- 修复后：3.5 秒文件分析可以拿到证据进入回答层；真正超长分析返回可区分状态，并允许后续基于缓存/状态继续。
- 回归：轻量计算、时间、记忆、read_group_context 仍受短超时保护；图片历史分析和文件分析各自有合理上限，不阻塞整条队列。

### L45-1 全局 cron 开关关闭时定时工具仍回复“已创建/下次触发”，但实际不会调度

真实性：真实存在，可本地临时 DATA_DIR 复现；服务器当前运行包源码同源。

证据：
- `packages/koishi-plugin-dongxuelian-ai/lib/agent/config.js` 默认 `cron.enabled=false`、`cron.onceEnabled=true`。
- `packages/koishi-plugin-dongxuelian-ai/lib/agent/cron.js` 的 `scheduleCron()` 在 `cron.mode === 'once'` 且 `config.cron.onceEnabled === false` 时直接 return；周期任务则在 `!config.cron.enabled` 时直接 return。

- `packages/koishi-plugin-dongxuelian-ai/lib/agent/tools/reminder-tools.js` 的 `executeCreateReminder()` 调用 `registerOnceTask()` 后返回“已创建提醒...触发时间...”，没有检查 `cron.onceEnabled`。

影响：
- 用户要求“每天 8 点发一句/每周总结/周期运行 agent”时，会收到看似成功的“已创建周期任务，下次触发 ...”，但默认配置下不会触发。
- Dashboard 或 Agent 工具列表里任务仍显示 active/enabled，进一步强化“已经设好”的错觉；实际问题直到触发时间过去才暴露。
- 如果 L43 导致 `cron.enabled` 被 Dashboard 保存重置为 false，已经存在或新建的周期任务会更隐蔽地停摆；创建工具仍继续给成功回执。
- 对一次性提醒，默认 `onceEnabled=true` 暂时不踩；但管理员关闭一次性提醒总开关后，`create_reminder` 仍会给“已创建提醒”的假成功。

建议修复：

**审核批注：原建议过度设计。** 不需要引入四态状态模型或让 `registerCron()` 返回结构化调度结果。核心修法是创建工具内加一个 config 检查：

- `executeCreateScheduledTask()` 在 `registerCron()` 之后、返回成功消息之前，读取 `getAgentConfig().cron.enabled`。如果为 false，返回文案改为”已保存周期任务，但周期任务总开关当前未开启，不会自动触发。”

- 不需要阻止写入（任务仍保存，管理员开启开关后即可调度），只需要让回复诚实反映调度状态。
- 补测试：`cron.enabled=false` 时创建周期任务不返回”下次触发”；`cron.enabled=true` 时正常返回；`onceEnabled=false` 时提醒不承诺触发。

验证方式：
- 修复前：默认配置创建周期任务返回“已创建周期任务...下次触发...”，但没有 timer；`onceEnabled=false` 时提醒也返回已创建但不触发。
- 修复后：全局开关关闭时，工具结果明确说明未调度或拒绝创建；全局开关开启时才承诺下次触发。
- 回归：一次性提醒默认仍能创建并触发；周期任务在 `cron.enabled=true` 时正常 schedule；pause/resume/list/get/run_now 的可见状态与实际调度一致。

## 本地第 48 轮（cron misfire 修补后的持久化状态）

范围：继续扫描当前本地未提交的定时任务错过触发修补。本轮不重复 L36-1 的“过期周期任务会立刻补跑”旧问题；只确认当前修补把过期任务改为 reschedule/skip 后，磁盘状态、列表显示和重启恢复是否也同步更新。

结论：本轮新增 1 个本地真实问题。当前本地 `scheduleCron()` 在发现周期任务 `nextRunAt` 已过期且 `misfirePolicy` 为 `reschedule` 或 `skip` 时，会把内存里的 `cron.nextRunAt` 改成未来时间并递归 `scheduleCron(cron)`，因此不会立刻补发旧任务；但这个新的 `nextRunAt` 没有写回 `agent-crons.json`。结果是任务实际不会马上跑，文件和 `list_scheduled_tasks` 仍显示一个已经过去的“下次触发”，重启后又会重新从旧过期时间进入同一分支。

### L48-1 周期任务 misfire reschedule/skip 只改内存不落盘，列表和重启恢复仍保留过期 `nextRunAt`

真实性：真实存在，可本地临时 DATA_DIR 复现；服务器当前运行包未包含这个本地修补分支，暂不是服务器同源回归。

证据：
- 当前本地 `packages/koishi-plugin-dongxuelian-ai/lib/agent/cron.js` 的 `scheduleCron(cron)` 在 `delay < -5000` 时读取 `cron.runPolicy?.misfirePolicy`。
- `skip` 分支和 `reschedule` 分支都会在周期任务上执行 `cron.nextRunAt = getNextRunAt(cron.schedule)`，然后 `scheduleCron(cron)` 并 return。
- 这两个分支没有调用 `updateCron()`、`saveCrons()`、`writeCronFile()` 或其它持久化写入；只修改了当前函数参数对象。
- `startCronScheduler()` 每次启动都会 `loadCrons()` 后按磁盘里的 cron 调 `scheduleCron(cron)`；如果磁盘仍是旧过期 `nextRunAt`，重启后会重复进入 misfire 分支。
- `executeListScheduledTasks()` 和 `executeGetScheduledTask()` 读取的是 `loadCrons()` 的磁盘状态，所以会继续把旧过期时间显示成“下次”。
- 本地临时 DATA_DIR 复现：写入一个 `schedule='*/10 * * * *'`、`nextRunAt` 为 1 小时前、`misfirePolicy='reschedule'` 的周期 text 任务，开启 `cron.enabled=true` 后启动 scheduler。等待 1.2 秒，mock bot 发送数为 0，说明不会立刻补发；但 `loadCrons()` 读到的 `nextRunAt` 仍等于旧过期值，`list_scheduled_tasks({ status:'all' })` 仍显示该旧时间为“下次”。

影响：
- 管理员或用户查看任务列表时会看到一个 active 周期任务的“下次触发”停在过去，无法判断任务是已重新排程、卡死、还是即将补跑。
- 这会削弱 L36 修补效果：虽然当前进程内不会立刻补发，但重启后仍从同一个过期时间开始，继续重复执行修补分支；状态文件永远不收敛到真实未来时间。
- 如果有外部巡检、Dashboard 或 Agent 根据 `nextRunAt` 判断是否过期，会误报任务异常或反复尝试恢复。
- `skip` 策略同样没有记录“错过并跳过”的 history，也没有把未来 `nextRunAt` 写回；用户看不到任务为什么没跑，也看不到下一次正确时间。

建议修复：
**审核批注：原建议过度设计。** 不需要抽出新的 `rescheduleMisfiredCron()` 函数和 `enqueueCronFileUpdate()` 包装。实际修复只需在 `skip` 和 `reschedule` 分支重算 `nextRunAt` 后，调用已有的 `updateCron(cron.id, { nextRunAt: cron.nextRunAt })` 落盘，再递归 `scheduleCron()`。`updateCron` 内部已经走 `enqueueCronFileUpdate` + `writeCronFile`，不需要额外封装。
- `reschedule`：重算 `nextRunAt` 后 `await updateCron(cron.id, { nextRunAt })` 写回磁盘，再 `scheduleCron(updated)`。
- `skip`：同上写回未来 `nextRunAt`；可选在 `addCronHistory()` 记录一条 `{ type:'skipped', reason:'misfire' }`。
- `run_once`：保留当前补跑语义不变。
- 注意 `scheduleCron` 需要改为 `async` 或在 misfire 分支用 `.then()` 处理 `updateCron` 的 Promise，避免未处理 rejection。
- 补测试：过期周期任务 `reschedule` 启动后不发送且磁盘 `nextRunAt` 变成未来；`skip` 不发送；重启第二次不会再看到旧过期 `nextRunAt`；列表和详情显示未来”下次触发”。

验证方式：
- 修复前：过期周期任务启动后不补发，但 `agent-crons.json` 和 `list_scheduled_tasks` 仍保留旧过期 `nextRunAt`。
- 修复后：同样任务启动后不补发，磁盘和列表都显示重算后的未来 `nextRunAt`，重启不会重复处理同一个旧 misfire。
- 回归：L36 的目标仍成立，默认 `reschedule` 不补跑旧周期任务；正常未来周期任务、pause/resume、run_now 和一次性提醒不受影响。
