# index.js / chat.js 主干拆分 0 风险待审核计划

> 状态：待审核  
> 目标：在不改变用户可见行为、不改变线上配置、不引入循环依赖的前提下，把 `index.js` 与 `chat.js` 的主干职责逐步拆薄。  
> 范围：只讨论 `packages/koishi-plugin-dongxuelian-ai/lib/index.js` 与 `packages/koishi-plugin-dongxuelian-ai/lib/chat.js` 的结构拆分，不包含部署、重启、推送、线上改配置。

## 一、当前判断

当前不是“补丁太多拆不了了”，而是已经进入高耦合维护区：

- `index.js` 约 80 KB / 1791 行，最大函数 `exports.apply()` 约 651 行。
- `chat.js` 约 72 KB / 1409 行，最大函数 `chat()` 约 908 行。
- 两个文件都有架构红线注释，说明项目本来就希望“入口只编排、聊天核心保留所有权、新器官拆模块”。
- 目前已经有一部分拆分成果：`chat-prompt-builder.js`、`reply-guard.js`、`chat-memory.js`、`file-followup-guard.js`、`random-reply-mode.js`、`group-scene-index.js` 等，说明拆分路径是可行的。

本计划的核心原则：**先做函数溯源和行为锁定，再做纯搬运；每一步只移动一个清晰职责，不顺手改逻辑。**

## 二、0 风险定义

这里的“0 风险”不是承诺任何重构天然无风险，而是把每一步限制成可验证的 0 行为差异改动：

1. **纯搬运优先**：先复制函数和状态到新模块，接口保持原返回值、参数、异常行为不变。
2. **不改业务判断**：随机回复概率、Agent 路由、文件/图片/语音处理、敏感词处理、工具调用、发送策略都不在拆分提交里改规则。
3. **不新增运行时状态到主干**：新状态必须归属到对应模块，`index.js` / `chat.js` 不再新增 Map/Set/全局缓存。
4. **不反向 import `index.js`**：新模块只能依赖稳定模块或通过参数注入依赖，禁止 `require('./index')`。
5. **一刀一测**：每拆一个模块，至少跑 `node -c`、`npm run test:quick`；触碰主链路时补跑相关 scenario。
6. **可回滚**：每一步拆分后都能用一个小提交回滚，不和功能开发混在一起。
7. **脏工作区冻结**：真正开始拆分前必须确认当前未提交修改归属；如果分支 ahead/behind 或工作区异常，先停下汇报。

## 三、开工前必须完成的只读检查

每次拆分开始前，先执行并记录结果：

```bash
git rev-parse --show-toplevel
git branch --show-current
git status --short --branch
git rev-parse HEAD
git rev-parse origin/bot_ZZY
```

如果出现以下情况，暂停拆分：

- 不在 `E:\莲莲Bot`。
- 不在 `bot_ZZY`。
- 分支 ahead/behind 状态和预期不一致。
- 工作区有不属于本轮拆分的修改，且涉及同一文件。
- `AGENTS.md` 被 git 跟踪或不再被 `.gitignore` 忽略。

涉及任何 commit / push 前，还要按隐私规则做扫描；本计划不授权部署、重启或推送。

## 六、推荐拆分阶段

### P0：冻结与溯源，不改代码

目标：先把“当前行为是什么”固定下来，避免拆分时不知道哪里变了。

动作：

1. 记录 `index.js` / `chat.js` 顶层函数清单、文件大小、最大函数行数。
2. 用 `rg` 查所有外部依赖和测试引用：
   - `require('./index')` / `require("../lib/index")`
   - `buildRepeatCandidate`、`checkGroupRepeat`、`loadRuntimeSettings`、`callOpenAI`、`loadSkillsContentCache`
3. 对要拆的函数做“入参、返回值、副作用、异常、状态读写”五列表。
4. 标记共享状态：
   - `randomWhitelistCache` / `randomRateCache`
   - `channelPendingRandom` / version maps
   - `sendFailState`
   - `skillsContentCache`
   - `hostileLevelCache`
5. 给每个目标模块写最小契约注释，不写实现。

验收：

- 没有源码改动，只有计划/台账文档。
- 能清楚回答每个函数依赖哪些状态，哪些测试覆盖它。

### P1：纯 helper 和兼容补丁拆分

优先拆没有业务策略的函数。

候选模块：

- `session-compat.js`
- `bot-resolver.js`
- `message-segment.js`
- `chat-skills.js`

拆分方法：

1. 新建目标文件，完整复制函数和状态。
2. `node -c` 目标文件。
3. 源文件加 import，但暂时不删旧函数。
4. 用新 import 替换调用点。
5. `node -c index.js/chat.js`。
6. `npm run test:quick`。
7. 通过后删除旧函数。
8. 再跑 `node -c` + `npm run test:quick`。

重点风险：

- `session-compat.js` 有 monkey patch，必须保证插件加载时仍然立即安装补丁。
- `chat-skills.js` 的缓存必须仍是单例，不能每次 require 产生多套状态。
- `message-segment.js` 不能改 CQ/XML 属性解析行为。

建议新增/确认测试：

- cascade 检查新模块可 require。
- session stripped / parsed / send 兼容仍可用。
- 图片/文件 segment 从 session 和 content 两路都能解析。
- `AI重载` 仍会刷新 skill cache。

### P2：发送、诊断、定时器、事件 dump 拆分

候选模块：

- `safe-send.js`
- `event-dump.js`
- `startup-schedulers.js`
- `diagnostics.js`
- `channel-task-queue.js`
- `agent-chat-retell.js`

拆分方法：

1. 优先通过依赖注入传 `ctx`、`session`、`sendReply`、`chat`、`agentEngine`，避免新模块回头 import `index.js`。
2. `safe-send.js` 自己持有 `sendFailState`，导出：
   - `safeSendReply`
   - `safeSendRepeat`
   - `safeSendRareVoice`
   - `resetSendFailState`
3. `startup-schedulers.js` 导出 scheduler 创建/清理函数，`index.js` 只保存 timer dispose 句柄。
4. `agent-chat-retell.js` 不直接拥有 Agent engine，只接收运行函数或依赖对象。

验收：

- 限流、禁言、失败通知逻辑不变。
- dispose 时 timer 全部清理。
- Agent 结果仍经过 chat 人格化转述。
- 随机罕见语音 freshness 判断仍在发送前执行。

建议测试：

- `sendReply` 抛 rate limit 后走精简重试。
- 非 rate-limit 错误不会重复刷屏。
- Agent heavy tool 请求返回后仍由 chat 转述，不直出工具报告。
- dispose 后 pending timer 不再发消息。

### P3：运行时设置、黑名单、话题切换、chat 输出守卫

候选模块：

- `runtime-settings.js`
- `user-blacklist.js`
- `topic-switch.js`
- `chat-output-flow.js`
- `chat-jailbreak-flow.js`

拆分原则：

- `runtime-settings.js` 只管配置缓存，不接管随机回复决策。
- `user-blacklist.js` 只管读取和缓存，不决定“是否记录上下文”。
- `topic-switch.js` 可持有 `topicSwitchLocks`，但清历史和清 Agent context 仍由调用方显式传入回调。
- `chat-output-flow.js` 处理模型输出后的 retry/fallback，但不调用发送。

验收：

- 用户黑名单仍然“记录上下文，但不回复”。
- 话题切换检测失败时，历史仍降级为背景，不直接误删。
- jailbreak 输入和 jailbreak 输出仍走专用兜底。
- 输出中出现内部工具计划、`<user>` 包装、banned output 仍会重试或 fallback。

建议测试：

- 短追问没有误触发旧搜索上下文。
- prompt injection 输入不会污染正常 chat 历史。
- 模型返回 JSON/random mode 时不会原文发群。
- 文件工具拒绝后 fallback 能调用对应工具。

### P4：随机回复状态与延迟随机调度

这是 `index.js` 中风险最高的拆分之一，必须晚一点做。

候选模块：

- `random-state.js`
- `random-send-state.js`
- `random-scheduler.js`
- `random-gate.js`

拆分边界：

- `random-state.js`：只管 state map、版本、pending、mute、cooldown。
- `random-gate.js`：只算候选、概率、miss count，不发送。
- `random-scheduler.js`：只负责 15 秒延迟随机的 timer 和 freshness 检查。
- `random-send-state.js`：只构造 send options 和 stale 日志。

高风险点：

- 新显式交互必须取消旧随机回复。
- 延迟随机等待期间，如果频道出现新消息，旧随机不能补发。
- `ambient_water` 不能引用、不能 replyTo、不能 @。
- rare voice 与普通文本的 freshness 判断必须一致。

验收场景：

1. 普通随机命中后立即回复。
2. 连续发言触发延迟随机。
3. 延迟期间出现点名/私聊/命令，旧随机取消。
4. 延迟期间出现新群消息，旧随机过期。
5. `ambient_water` 发送时不 quote、不 @、不 replyTo。
6. 高风险人格切换时随机回复不能错绑旧人格。

### P5：persona、affect、emotion、hostile 等旁路状态整理

这一阶段不是为了“变小”而拆，而是为了让人格/情绪/随机回复边界更清楚。

候选：

- `chat-retaliation-state.js`
- `random-persona-risk.js`
- `message-recording.js`
- `emotion-state.js`
- `persona-runtime-adapter.js`

原则：

- 不在这一阶段改变人格解析结果。
- 不引入新的 `PersonaRuntimePlan` 行为接管，除非另有审核计划。
- affect-router / expression shadow 继续保持旁路诊断，不改变 prompt 和回复。

验收：

- 自定义人格仍绕过 hostile 模式。
- `will` 因子仍按旧逻辑影响随机概率。
- 旁路日志开启/关闭不影响 chat 输出。

### P6：最后整理 `apply()` 与 `chat()`

前面阶段完成后，才可以拆最大函数。

目标形态：

- `index.js`
  - 只保留 `exports.name`
  - 安装 session compat
  - `exports.apply = createPluginApply(deps)` 或直接注册 lifecycle/middleware
  - 不再持有大量全局 Map/Set

- `chat.js`
  - 保留 `chat()` 主流程所有权
  - 保留 `callOpenAI()` 或明确迁入 `llm-call.js`
  - prompt 构建、工具流、输出守卫、topic switch 等都用独立模块
  - `chat()` 负责“按顺序编排”，不再内联所有细节

必须禁止：

- 一次性把 `apply()` 拆成多个互相调用但状态不清的闭包。
- 把 `chat()` 拆成另一个同样 800 行的 `chat-flow.js`。
- 为了拆分顺手重写随机回复、搜索路由、人格逻辑。

## 七、每次拆分的标准流程

每个模块拆分都按下面流程走：

1. **溯源**
   - 列出函数名、行号、调用点。
   - 列出读取的外部状态。
   - 列出写入的外部状态。
   - 列出可能抛出的异常。
   - 列出测试覆盖点。

2. **复制**
   - 新建目标模块。
   - 原样复制函数，先不删旧函数。
   - 必要状态也搬到目标模块，但不改默认值。

3. **编译**
   - `node -c 新模块`
   - `node -c index.js/chat.js`

4. **接线**
   - 源文件 require 新模块。
   - 调用点切到新模块。
   - 如果目标模块需要旧模块函数，通过参数注入，不反向 import。

5. **验证**
   - `npm run test:quick`
   - 触碰 chat 主链路：`npm run test:scenario`
   - 触碰图片/文件/语音/随机/Agent 时跑对应 scenario。

6. **删除旧定义**
   - 测试通过后删除源文件旧函数。
   - 再跑一次 `node -c` + `npm run test:quick`。

7. **记录**
   - 在提交信息或待审核记录写明“移动了什么、为什么、验证了什么、未覆盖什么”。

## 八、场景验证矩阵

拆分不是只看语法，必须覆盖真实链路。

| 链路 | 必测输入/行为 | 断言 |
|---|---|---|
| 普通点名聊天 | 群里 @bot 问普通问题 | 回复仍走 chat，不触发随机链路 |
| 私聊 | 私聊普通问题 | 不受群随机 gate 影响 |
| 随机主动回复 | 白名单群普通消息命中概率 | 能回复，miss count/cooldown 正常 |
| 延迟随机 | 同一用户连续发言 | 15 秒后仍需 freshness 检查 |
| 显式打断 | 延迟随机期间 @bot | 旧随机取消 |
| ambient water | 随机 mode 返回 `ambient_water` | 不引用、不 replyTo、不 @ |
| 图片当前消息 | 发图并点名 | `storeImageUrl` + `enqueueAnalysis` + vision request 正常 |
| 引用图片 | 回复旧图片问“这是什么” | 能走引用图片上下文，不误看别图 |
| 文件上传 | 上传小文件后问读文件 | 文件缓存/分析/总结链路正常 |
| 文件追问 | “改名发我/生成副本” | `create_uploaded_file_variant` 工具链路正常 |
| 语音 | 点名或私聊语音 | ASR 超时有降级 |
| Agent 搜索 | 明确搜索请求 | Agent run 后由 chat 转述 |
| 搜索误触发防线 | 短追问“哪个/然后呢” | 不凭旧冷上下文乱搜 |
| 敏感话题 | 开启检测群触发敏感词 | 固定拒答/通知处理者逻辑不变 |
| 发送限流 | mock send 抛 rate limit | 精简重试、禁言标记、管理员通知不变 |
| reload | `AI重载` | config/skills/runtime cache 都刷新 |
| dispose | 插件 dispose | timer、pending random、cron scheduler 清理 |

## 九、测试报告必须回答四问

任何拆分完成后，报告必须回答：

1. 复现了用户哪条真实失败输入或真实风险链路？
2. 断言了哪个失败现象不会出现？
3. 哪些依赖被 mock 了？
4. 因为 mock，哪些真实链路仍未覆盖？

如果只是纯搬运，没有真实失败输入，也要写：

- 本次是结构等价拆分，没有修复用户可见 bug。
- 断言的是“拆分前后导出、调用、状态副作用一致”。
- mock 了哪些平台发送/API/文件系统。
- 尚未覆盖的线上真实链路是什么。

## 十、提交拆分时的 commit message 模板

拆分提交不能只有标题，建议格式：

```text

- packages/koishi-plugin-dongxuelian-ai/lib/<source>.js:
  - 移出 <函数列表>
  - 原因：<入口/聊天主干减重，职责边界>

- packages/koishi-plugin-dongxuelian-ai/lib/<target>.js:
  - 新增 <模块职责>
  - 依赖边界：只依赖 <稳定模块/注入参数>
```

## 十一、优先级建议

推荐顺序：

1. `message-segment.js`：纯 helper，收益小但风险低，适合练手。
2. `chat-skills.js`：能明显减轻 `chat.js` 顶部缓存和加载逻辑。
3. `safe-send.js`：收益高，但要认真测限流和禁言。
4. `event-dump.js` + `startup-schedulers.js`：入口文件减负明显。
5. `topic-switch.js` + `chat-jailbreak-flow.js`：开始整理 chat 主流程。
6. `chat-output-flow.js`：把输出守卫从 `chat()` 拆出。
7. `random-state.js` / `random-scheduler.js`：最后做，必须配完整随机场景测试。
8. `apply()` / `chat()` 编排瘦身：等前面小模块都稳定后再做。

不建议第一刀：

- 直接拆 `exports.apply()`。
- 直接拆 `chat()` 主循环。
- 直接重写随机回复状态机。
- 同时拆 Agent、搜索、随机、发送多个链路。

## 十二、审核通过标准

这份计划通过审核后，真正实施前还需要明确：

- 当前工作区哪些修改属于谁，是否可以基于当前状态拆。
- 第一刀选哪个模块。
- 本轮是否允许只做结构拆分，不夹带功能修复。
- 每一步拆完是否需要单独提交。
- 是否需要先补对应 scenario 测试，再拆模块。

建议第一刀选择 `message-segment.js` 或 `chat-skills.js`。这两块对用户可见行为影响最小，能验证拆分流程是否稳。
