# 群聊上下文窗口架构计划

> 待审核正式计划。用于设计“群聊随机回复接话割裂、旧消息误提、富媒体锚点丢失、弱锚定水群、旧上下文自由检索”的统一窗口架构。
>
> 本计划与 [表达学习候选池详细设计](表达学习候选池详细设计.md) 绑定：表达学习只作为 `ambient_water` 的可选口吻增强来源，不负责上下文理解，也不能在旁路未正式启用前被生产链路直接读取。

## 一、问题背景

近期现场出现两类强相关问题：

1. 群聊随机回复只抓到当前短句，例如“先试试看吧”，没有稳定理解前面正在聊文件大小、生成、卡死等公共话题，导致回复成“那我们开始吧”一类割裂话术。
2. 群聊节奏很快，旧消息即使存在于历史或摘要里，也不应该被 bot 主动拿出来续聊。突然提起一小时前的话题会让群友反感。

这不是单纯“模型不会聊天”，也不适合用输出守卫硬拦自然语言。正确方向是调整上下文输入结构，让模型清楚区分：

- 现在正在聊的内容；
- 可以辅助理解身份和偏好的背景；
- 已过期、不能主动提起的旧消息。

## 二、现有上下文事实

当前代码里已经有多层上下文和摘要：

- 个人对话历史：
  - `MAX_HISTORY_MESSAGES = 100`，磁盘最多保留 100 条。
  - `MEMORY_HISTORY_LIMIT = 30`，运行时/进入 prompt 的近期历史主要取最近 30 条。
  - `CONVERSATION_SUMMARY_INTERVAL = 100`，每 100 轮压缩较旧个人历史为摘要。
- 个人历史摘要：
  - 作为 `[历史摘要-仅作为背景参考]` 进入 prompt。
  - 明确要求“除非用户主动问及历史内容，否则不要主动提及”。
- 个人历史降权背景：
  - 话题检测失败或长时间不活跃时，近期历史会降级为 `[历史对话背景-仅供理解用户身份和偏好]`。
- 群聊公共上下文：
  - `channelSharedCache` 保留 `MAX_CHANNEL_SHARED_MESSAGES = 100` 条公共消息。
  - `getSharedContextNote()` 每轮从公共缓存里筛选 12/24 条左右，生成 `[群聊当前话题背景]` 和短句跟进候选。
- Agent 上下文：
  - Agent 有独立结构化压缩摘要，不等同于普通群聊随机回复上下文。

因此本次不是“完全没有摘要”，而是群聊随机回复时，公共上下文没有成为最终输入的主导层。最终 user message 仍可能只剩孤立短句，导致人格口癖或旧个人历史盖过当前现场。

## 三、设计目标

1. 不靠“接管话术守卫”限制模型表达。
2. 不让模型乱回当前短句，把短句绑定到最近公共现场。
3. 不让模型主动提起旧消息，尤其是一小时前的群聊内容。
4. 保留长期记忆、个人摘要和人格，但它们默认只作背景。
5. 让文件、图片、语音稳定成为公共上下文锚点，方便后续“评价一下”“太大了”“这个呢”等短句正确指代。

## 四、窗口架构

建议把上下文分成 7 层，每层有不同权限。

### L0 当前消息

当前用户本轮发言。

用途：

- 始终进入模型。
- 点名、私聊、命令时是主任务入口。
- 群聊随机回复时不能孤立使用，必须和 L1 当前现场绑定。

风险：

- “先试试看吧”“真的吗”“也可以”“评价一下”这类短句脱离前文没有语义，不能让它单独压轴。

### L1 当前活跃群聊现场

最近公开群聊中仍处于活跃状态的连续话题。

建议来源：

- 最近 1 到 3 分钟内的连续公共消息。
- 当前消息前后同一批发言者的短连续对话。
- 当前消息附近的文件、图片、语音、转发锚点。
- 当前回复链或引用链。

建议进入方式：

- 群聊随机回复时，放到最终 user message 附近，作为模型最重视的输入。
- 形式类似：

```text
<active_group_scene>
群友A：[文件：xxx，8.52MB，已接收]
群友B：8.52mb吗
群友B：希望能生成吧
群友B：感觉很大概率卡死
群友A：大了？
群友B：先试试看吧
群友B：太大了
</active_group_scene>

<current_message>
群友B：先试试看吧
</current_message>

这是一段公开群聊现场。当前短句优先按上面的现场理解；如果插话，只围绕当前现场自然接一句，不要主动延续更早的话题。
```

权限：

- 是群聊随机回复的最高优先级语境。
- 可以主动使用。
- 可以覆盖个人历史和长期摘要。

### L2 回复链/引用链

用户明确回复或引用的消息链。

用途：

- 优先级高于普通活跃窗口。
- 即使引用内容较旧，也可以短暂进入当前现场，因为用户明确把它拉回来了。

边界：

- 只使用被引用链条和必要前后文。
- 不顺手拉入同时间段所有旧话题。

### L3 富媒体锚点

文件、图片、语音、转发等非纯文本事件。

必须先稳定写入公共上下文，否则后续短句会失去指代对象。

建议格式：

```text
[文件：xxx，8.52MB，已接收，等待用户追问时再分析]
[文件：xxx，8.52MB，超过解析限制，已跳过自动解析]
[图片]
[图片：画面大意...]
[语音转文字：...]
[合并转发：摘要...]
```

边界：

- 不写真实 URL。
- 不写本地路径。
- 不写 token。
- 不把文件正文自动塞入公共现场。
- 文件内容仍应由用户明确追问后再触发分析。

### L4 个人近期对话

当前用户和 bot 的最近个人对话历史。

点名和私聊：

- 可以作为活跃历史参与回答。

群聊随机回复：

- 降权。
- 只用于称呼、稳定偏好、关系感，不主动延续旧私聊话题。

风险：

- 如果随机回复时让 L4 靠近最终 user message，模型容易把当前群聊短句误解成对 bot 的私人邀请。

### L5 长期摘要/记忆

包括：

- `[历史摘要-仅作为背景参考]`
- `[历史对话背景-仅供理解用户身份和偏好]`
- `[记住的信息-仅作背景]`

权限：

- 只能辅助理解身份、偏好、称呼和长期设定。
- 不允许主动作为当前话题。
- 用户明确问“之前那个”“你记得吗”“上次说的”时才可主动使用。

建议加强提示：

```text
长期摘要只用于理解用户身份、偏好和稳定关系。除非当前消息明确引用历史内容，否则不得把摘要中的旧话题当作当前群聊话题主动提起。
```

### L6 冷历史

超过当前窗口、没有引用链、没有短句指代证据的旧消息。

默认行为：

- 不进入当前 prompt。
- 不主动提起。

可被激活条件：

- 用户明确引用。
- 用户明确说“刚才/之前/上次/那张图/那个文件/你刚才说的”。
- 与当前文件、图片、语音锚点存在明确 ID 或消息链关联。

## 五、时间窗口策略

建议基于时间衰减和线程边界，而不是硬编码话题词。

### 热窗口

范围：

- 最近 1 到 3 分钟。

用途：

- 默认可进入 L1 当前活跃群聊现场。
- 群聊随机回复主要使用热窗口。

### 暖窗口

范围：

- 3 到 10 分钟。

进入条件：

- 当前消息是短句/指代跟进。
- 存在回复链、引用链。
- 最近有同一文件、图片、语音锚点。
- 同一批用户围绕同一事件连续发言。

### 冷窗口

范围：

- 10 分钟以上。

默认：

- 不进入当前现场。
- 只可作为长期背景或被明确引用后进入。

### 一小时前旧消息

默认：

- 绝不主动提起。

例外：

- 用户明确引用或询问。
- 用户明确说“刚刚那个/之前那个/上次那个”并且能从上下文找到唯一对象。

## 六、随机回复专用规则

随机回复不是用户明确请求，因此要更依赖当前现场，也更允许不插话。

随机回复可主动使用：

- L0 当前消息。
- L1 热窗口当前现场。
- L2 明确回复链/引用链。
- L3 最近富媒体锚点。
- 当前人格语气。

随机回复只能背景参考：

- L4 个人近期对话。
- L5 长期摘要/记忆。

随机回复默认不用：

- L6 冷历史。
- 一小时前群聊旧消息。
- 旧 Agent 工具结果。

如果没有清晰 L1/L2/L3 支撑，随机回复不应由程序立刻用硬阈值砍掉。更合理的完整链路是：

1. 先给模型当前热窗口和可用工具说明；
2. 如果模型发现当前消息适合锚定回复但热窗口不够，可以自主调用 `read_group_context` 查旧公共上下文；
3. 如果模型判断不适合锚定到某个人、某条消息或某个旧话题，但群聊气氛适合水一句，可以切到 `ambient_water`；
4. 工具结果仍然只作为历史片段，不允许把旧内容当成当前话题硬续；
5. 如果检索后仍不能自然接上，且非锚定水群也会打扰，模型应选择不插话，程序不发送。

这里不是让模型输出可见 `__SILENT__`，也不是接管话术守卫，而是给随机回复一个“先理解，再决定说话模式”的自由路由。程序只负责工具权限、结果边界、发送形态和最终“不发送”动作。

随机回复建议拆成四种模式：

- `anchored_reply`：当前现场清楚，围绕热窗口、引用链、文件/图片/语音锚点自然接话。
- `context_lookup`：当前消息明显需要旧公共上下文，先调用 `read_group_context`，再基于原文片段接话。
- `ambient_water`：不适合锚定回复，但适合像群友一样随口水一句；不引用任何人、不接管任务、不翻旧账。
- `no_send`：说话会打扰、误解或破坏气氛时不发送。

`ambient_water` 不是正式总结，也不是“我看不懂所以糊一句”。它是非锚定群聊插话，应该像群里真实水群句式一样轻、短、口语化。

## 七、与现有摘要的关系

本方案不替代已有摘要。

已有摘要继续负责：

- 个人长期对话压缩。
- 旧个人历史降权。
- Agent 工具链上下文压缩。
- 日报/情绪/转发等专用摘要。

新增或调整的是：

- 当前群聊活跃窗口的提取和放置位置。
- 随机回复时公共现场高于个人历史。
- 富媒体锚点稳定进入公共 100 条缓存。

## 八、建议实现步骤

### Step 1：修复富媒体上下文锚点

当前 `memoryText` 计算早于文件/图片/语音补全。建议在富媒体处理后生成 `contextRecordText`，用于 `saveSharedChannelTurn()`。

验收：

- 空文本文件消息也能在 `channelSharedCache` 中留下安全文件锚点。
- 图片、语音、转发同理留下可指代锚点。

### Step 2：新增全局 ContextWindow 构造器

上下文窗口不是随机回复专用能力，而是普通 chat 的全局能力。随机回复只是其中权限最窄、最容易出事故的一种使用场景。

`ContextWindow` 从 `channelSharedCache` 的 100 条、引用链、富媒体锚点和落盘 scene 目录里构造当前可用上下文，然后按交互类型给模型不同权限。

建议输入：

- `session`
- `currentUserId`
- `currentText`
- `replyToId`
- `mentionUserIds`
- `randomTriggered`
- `interactionType`

建议输出：

```js
{
  activeSceneText: string,
  retrievableIndexText: string,
  confidence: 'hot' | 'thin' | 'none',
  items: [],
  hasMediaAnchor: boolean,
  hasReplyChain: boolean,
  hasRecentAssistant: boolean,
  interactionType: 'direct_at' | 'private_chat' | 'random_reply' | 'quote_reply' | 'agent_retell',
  retrievalPolicy: {
    allowGroupContext: boolean,
    maxAgeMinutes: number,
    maxScenes: number,
  },
  randomModeHint: 'direct' | 'needs_context' | 'weak',
}
```

随机回复不要只靠 `confidence = none` 直接取消，否则会严重损害水群能力。active scene 的职责是给模型一个清晰的“当前现场可信度”，而不是替模型做最终语义判断。

建议输出扩展为：

```js
{
  activeSceneText: string,
  confidence: 'hot' | 'thin' | 'none',
  items: [],
  hasMediaAnchor: boolean,
  hasReplyChain: boolean,
  hasRecentAssistant: boolean,
  retrievalHint: string,
  randomModeHint: 'direct' | 'needs_context' | 'weak'
}
```

- `direct`：热窗口足够，随机回复可以直接基于 active scene 生成。
- `needs_context`：热窗口很薄，但当前消息像短句、接话、追问或承接，模型可以自主调用 `read_group_context` 查旧公共上下文。
- `weak`：现场很薄，模型仍可判断是否轻轻水一句；如果没把握，应不插话。

取消随机回复不再是前置硬规则，而是发生在两种情况：

- 延迟随机触发时，频道版本已经前进且 active scene 已经换话题，旧随机回复过期；
- 模型在随机链路里选择“不插话”，程序不发送。

这样不会因为“短句 + 暂无锚点”就直接砍掉水群能力，但也避免模型孤立硬接。

发送形态需要跟模式绑定，且“不引用、不 @、不 replyTo”必须是代码级发送策略，不是提示词里的自觉要求：

- `anchored_reply`：可按普通随机回复策略发送；延迟或高风险时可以引用触发消息。
- `context_lookup`：如果工具取回明确 scene，可以自然接话；是否引用取决于当前消息是否点名/回复链。
- `ambient_water`：发送层强制 `quote=false`、`replyToId=''`、`mention=false`、`forceQuote=false`，作为普通群聊消息发出。
- `no_send`：不发送，不保存为空回复，不污染对话历史。

### Step 3：按交互类型注入 ContextWindow

所有 chat 场景都应该看见当前现场，只是权限不同。

- 群聊 @ / 点名：可用 active scene、retrievable index、`read_group_context`、图片/文件/搜索工具。用户明确请求时，应优先解决问题，不走 `ambient_water`。
- 引用回复：引用链优先，即使内容较旧也可临时进入当前现场。
- 跨用户短追问：active scene 应包含最近 bot 回复和公共话题，避免“真的吗”接不上。
- 私聊：默认主要用个人历史和长期记忆；只有用户明确带有群上下文绑定时，才查群聊 scene。
- 随机回复：可用 active scene 和受限 `read_group_context`，并允许选择 `anchored_reply/context_lookup/ambient_water/no_send`。

随机回复时，最终 user message 不再只有孤立短句，而是携带 active scene 和 mode schema。@ 回复也应携带 active scene，但不需要 `ambient_water/no_send` 发送模式。

### Step 4：随机回复 mode schema，不做 skill

当前 bot 没有“模型自己选择技能卡再加载”的正式能力。`ambient_water` 不应被设计成 Agent skill 或动态 skill 选择，而应是随机回复链路的 mode schema + 代码发送策略。

随机回复 mode schema 要短，不塞长篇提示：

```text
随机插话模式：
- anchored_reply：现场清楚时接当前话题。
- context_lookup：当前像在追旧上下文但现场不够时，可调用 read_group_context。
- ambient_water：不适合锚定但可水群时，只发一句短反应，不续旧话题、不接管任务。
- no_send：说了会打扰或容易误解时不发。
```

随机主动插话时，个人历史、用户画像、长期摘要只作背景，不能靠近最终 user message。@ 回复和私聊仍可正常使用个人历史，但也要让 active scene 高于旧背景。

### Step 5：ambient_water 基础形态与表达学习增强

`ambient_water` 的语言风格不应写成固定模板，否则会显得正式、生硬、像系统总结。但《表达学习候选池详细设计》当前仍是旁路诊断，尚未正式投入生产，因此不能把候选池作为 `ambient_water` 的硬依赖。

基础形态：

- 不依赖表达学习候选池。
- 由主模型按当前人格和极短 mode schema 生成一句非锚定群聊短反应。
- 不能引用旧话题、不能接管任务、不能总结讲道理。

增强形态：

- 等表达学习候选池正式通过旁路观察和审核链路后，才可作为 `ambient_water` 的可选口吻增强。
- 候选池不可用时，`ambient_water` 回退基础形态，而不是取消水群能力。

表达学习候选池接入边界：

- 只在 `ambient_water` 模式使用表达学习候选，不用于锚定事实回复。
- 复用现有学习侧硬过滤：跳过 bot 自己、图片/表情包、敏感词、复读窗口、敏感话题窗口、at bot 等。
- 复用候选池状态：`candidate | reviewed | archived`。未 reviewed 不进真实 prompt。
- 复用人格表达策略：`expressionPolicy.injectionMode` 为 `off` 的人格完全不查池；`abstract` 只给抽象提示；`on` 才给具体骨架。
- 复用冷却和原作者在场降权：候选 `lastUsedAt` 冷却，contributors 近期在场时跳过，避免“偷学某个人说话”的感觉。
- 不跨群使用候选，A 群骨架不进 B 群。

`ambient_water` 注入示例应是骨架级别，而不是成句模板：

```text
本轮如果选择非锚定水群，可以参考以下句式骨架，但必须换内容、贴合当前人格，不要复述原话：
- 场合：事情走向抽象；骨架：这下 X 起来了
- 场合：围观等待结果；骨架：先看一眼 X 怎么收场
```

注意：上面只是形式示例，不要求固定这些句式。真实候选来自表达学习池。

表达学习候选不承担上下文理解职责。它只解决 `ambient_water` 的语气自然度，不能替代 active scene、scene card 或 `read_group_context`。

对接要求：

- 窗口架构不得直接读取 expression-pool 文件内部结构。
- 表达学习正式接入时，必须提供稳定接口，例如 `selectAmbientExpressionSkeletons(context)`，返回已审核、已过滤、已冷却的骨架列表。
- 接口返回空数组时，`ambient_water` 继续走基础形态。
- 接口必须隐藏候选池内部字段，只返回 `situation/style` 等 prompt 可用骨架和诊断原因。
- 接口内部负责 reviewed、人格策略、原作者在场、冷却、敏感窗口、跨群隔离等过滤，调用方不得重复实现一套不一致逻辑。
- 未通过 v2.4 正式启用前，该接口只能用于影子诊断，不得把候选注入生产 prompt。

### Step 6：新增可检索目录 scene cards

暖窗口和冷窗口不直接展开正文进入 prompt，而是生成可检索目录。目录只告诉模型“旧上下文里可能有什么”，不能作为回答依据。模型需要旧上下文时，必须通过上下文检索工具读取原文片段。

随机回复也允许自由检索，但边界不同：

- 不预先把 warm/cold 目录正文展开给随机回复；
- 可以提供极短“可检索能力说明”，让模型知道接不上时能调用 `read_group_context`；
- `read_group_context` 在随机链路中默认只返回较近、较少、和当前消息最相关的片段；
- 如果工具没有拿到明确相关片段，随机回复不发送。

目录来源：

- `channelSharedCache` 最近公共消息；
- 当日公开消息缓存和已落盘的公共记录；
- 文件、图片、语音、转发等富媒体锚点；
- bot 自己的公开回复记录。

目录单位为 scene card：

```js
{
  id: 'scene_20260523_020017_020142_ab12',
  channelKey: '...',
  startTs: 1779472817000,
  endTs: 1779472902000,
  messageIds: ['m1', 'm2', 'm3'],
  speakers: ['群友A', '群友B'],
  speakerCount: 2,
  anchors: [
    { type: 'file', messageId: 'file-msg-id', label: '文件：xxx，8.52MB' }
  ],
  title: '围绕 8.52MB 文件连续讨论',
  summary: '约 02:00-02:01，2 位群友围绕 [文件：xxx，8.52MB] 连续发言。片段：8.52mb吗 / 希望能生成吧 / 感觉很大概率卡死 / 太大了。',
  keywords: ['8.52MB', '生成', '卡死', '太大'],
  samples: ['8.52mb吗', '希望能生成吧', '感觉很大概率卡死', '太大了'],
  state: 'warm',
  source: 'deterministic'
}
```

scene 切分规则只看结构，不看主题硬编码：

- 距上一条消息 1 到 3 分钟内，默认可并入当前 scene；
- 当前消息回复/引用 scene 内消息，继续并入；
- 当前消息共享文件、图片、语音、bot 回复等锚点，继续并入；
- 距上一条消息超过 10 分钟，默认新开 scene；
- 新富媒体锚点和上一 scene 无关联时，倾向新开 scene；
- 明确回复链可以把较旧消息临时拉回当前 scene。

目录摘要第一阶段只用确定性生成，不使用 AI 摘要。AI 摘要会浪费 token，也可能引入幻觉，暂不纳入本计划。

确定性目录摘要只拼接：

- 时间范围；
- 发言人数；
- 锚点类型；
- 清洗后的文件名/大小；
- 2 到 4 条代表性公开短句；
- 自动抽取的数字、单位、文件名、重复短词。

目录持久化：

- scene card 必须落盘，否则 bot 重启后 100 条磁盘历史和当日公共记录无法被稳定检索，等于只保留了原文而没有检索入口。
- 建议按频道写入 `group-scenes-<channelKey>.json` 或等价目录，使用安全 channel key。
- 写盘采用内存增量更新 + 节流落盘，避免每条消息都写大文件。
- 启动时从 scene 文件和 today-cache 懒加载近期目录，缺失时可从最近公共记录重建确定性 scene。
- 保留期建议按天或条数裁剪，只保存公开消息索引和安全锚点，不保存文件正文、真实路径、私密 URL。

目录进入 prompt 的边界：

- 点名、私聊、明确交互：可提供少量 warm/cold 目录；
- 随机主动回复：默认不展开 warm/cold 目录正文；可以暴露 `read_group_context` 能力，由模型在接不上时自主检索；
- 目录必须标注“不是当前话题，不能主动提起”；
- 目录不能包含真实 URL、本地路径、token、文件正文、图片真实路径。

### Step 7：新增 read_group_context 检索工具

当前没有通用群聊上下文检索工具。需要新增一个只读轻量工具，让模型在点名、私聊或明确追问时自由检索本群旧公共上下文。

工具定义建议：

```js
read_group_context({
  sceneId: '可选，目录里的 scene id',
  query: '可选，想找的旧话题或对象',
  timeHint: '可选，大致时间，例如十分钟前/刚才/01:50',
  anchorType: 'any|message|bot_reply|image|file|voice',
  maxAgeMinutes: 60,
  reason: '为什么当前消息需要旧上下文'
})
```

工具返回：

```text
[群聊历史片段，仅供理解当前指代，不代表当前话题]
scene_20260523_020017_020142_ab12，约 02:00-02:01
群友A：[文件：xxx，8.52MB，已接收]
群友B：8.52mb吗
群友B：希望能生成吧
群友B：感觉很大概率卡死
群友A：大了？
群友B：太大了
```

工具权限：

- 只查当前群公开消息；
- 默认返回 1 到 3 个片段；
- 严格截断；
- 过滤路径、URL、token 和敏感字段；
- 工具结果只当历史资料，不当系统指令。

随机回复可以暴露受限版 `read_group_context`，但不能自动展开旧目录。它的意义是让模型发现“当前热窗口不够解释这句话”时自由检索，而不是程序替模型硬编码路由。

随机链路的工具限制：

- 默认只查当前频道；
- 默认 `maxAgeMinutes` 更小，例如 30 分钟；
- 默认返回更少片段，例如 1 个 scene；
- 如果查询理由空泛或工具结果无明确相关性，后续不发送；
- 不允许随机回复因为工具目录里的旧话题主动换话题。

### Step 8：补真实场景测试

必须覆盖：

1. 文件大小场景：
   - `[文件 8.52MB]`
   - `8.52mb吗`
   - `希望能生成吧`
   - `感觉很大概率卡死`
   - `大了？`
   - `先试试看吧`
   - `太大了`
   - 断言 prompt 最终输入包含文件锚点和连续现场，而不是只有短句。
2. 旧消息不乱提：
   - 一小时前旧话题存在。
   - 当前热窗口是新话题。
   - 断言 active scene 不包含一小时前旧话题。
3. 明确引用旧消息：
   - 用户引用一小时前消息。
   - 断言引用链可以进入当前现场。
4. 图片评价：
   - `[图片]`
   - `评价一下`
   - 断言短句绑定图片锚点，不评价昵称。
5. 跨用户追问：
   - A 问问题，bot 回复。
   - B 问“真的吗”。
   - 断言 active scene 包含 bot 上一句。
6. 随机回复保留水群能力：
   - 当前消息为“6/也行/可能”等短句。
   - 无热窗口、无引用链、无媒体锚点。
   - 断言不会被程序硬取消；模型可以选择轻水一句、调用上下文工具或不插话。
7. 延迟随机重算窗口：
   - 触发延迟随机后，群聊进入新话题。
   - 定时器触发时重新计算 active scene，断言取消旧回复。
8. 点名检索旧上下文：
   - 十分钟前有文件 scene。
   - 用户点名问“那个还能生成吗”。
   - mock 模型调用 `read_group_context`，断言工具返回旧 scene 原文片段。
9. 普通闲聊不检索旧上下文：
   - 有 warm/cold 目录。
   - 用户说“好烦/6/可以”。
   - 断言模型不应被迫检索，prompt 中目录也标注不能主动提起。
10. 随机回复自主检索：
   - 热窗口很薄，但十分钟前有相关 scene。
   - mock 模型先调用 `read_group_context`，工具返回相关片段。
   - 断言最终回复基于工具片段自然接话，且没有主动提起无关旧话题。
11. 非锚定水群：
   - 当前短句没有明确对象，也不值得检索旧上下文。
   - mock 模型选择 `ambient_water`。
   - 断言发送层不引用、不 @、不 replyTo，并且不会提具体旧文件/旧图片/旧消息。
12. 表达学习候选池接入：
   - 候选池有 reviewed 骨架，且当前人格允许 `expressionPolicy`。
   - `ambient_water` prompt 可见骨架参考。
   - 原作者近期在场、候选冷却、敏感窗口、人格 off 时均不注入。

## 九、不要做的事

- 不做“禁止说某几句话”的接管话术守卫。
- 不把旧群聊摘要全部塞到最终 user message。
- 不让随机回复读取完整个人私聊历史后硬接群聊短句。
- 不把文件正文、图片路径、真实 URL 写入公共上下文。
- 不用主题词硬编码判断具体话题。
- 不用 AI 摘要优化可检索目录，第一阶段只做确定性 scene card，避免 token 浪费和摘要幻觉。
- 不用 `confidence = none` 这类硬阈值直接砍掉大量随机水群能力；取消应优先来自模型判断“不插话”或延迟回复过期。
- 不把 `ambient_water` 写成固定模板库；应复用表达学习候选池的审核骨架，并让主模型按当前人格改写。

## 十、临时结论

这次修复的核心不是让模型少说，而是给模型更正确的上下文窗口：

```text
当前热窗口负责“现在聊什么”。
引用链负责“用户明确拉回什么”。
富媒体锚点负责“短句指代什么”。
可检索目录负责“旧上下文可能在哪”，但不主动展开。
read_group_context 负责在模型判断需要时取回原文，包括点名追问和随机回复发现接不上话的场景。
ambient_water 负责“不适合锚定回复但可以水一句”的场景，并可借表达学习候选池获得更像群里的轻句式。
长期摘要负责“用户是谁、偏好是什么”，但不能主动变成当前话题。
```

只要窗口层级清楚，模型就可以自由接话；不需要用输出守卫把自然语言锁死。

## 十一、与现有上下文机制的重复和平衡

本方案会和 `getSharedContextNote()`、个人历史摘要、today-cache 有重叠，但重叠不是问题，问题是如果边界不清，会产生以下后果：

1. 同一段群聊被重复塞进 prompt，浪费 token。
2. system 里的公共背景和最终 user message 里的 active scene 表述不一致，模型不知道哪个更优先。
3. 旧个人历史、群聊目录、当前现场混在一起，模型误把旧事当当前话题。
4. 随机回复和点名回复共用一套上下文权重，导致随机插话翻旧账，或点名追问找不到旧内容。

平衡方式：

- `getSharedContextNote()` 继续服务普通点名、跨用户短追问、引用链背景；
- `active_group_scene` 服务随机回复和当前现场，靠近最终 user message，优先级最高；
- `retrievable_context_index` 只做目录，不做正文背景；
- `read_group_context` 才返回旧正文片段；
- 长期个人摘要只作身份、偏好和稳定关系参考；
- 如果 active scene 已经包含某条消息，sharedContextNote 和检索目录不再重复列出同一条正文，只保留更高层级那份。

换句话说：

```text
当前现场直接给；
旧现场给目录；
需要时工具取原文；
长期摘要只作背景；
重复内容按最高优先级保留一份。
```

## 十二、当前讨论共识记录

为防止上下文压缩后丢失，本段记录当前已达成的设计共识：

1. 不再做“接管话术输出守卫”。它会限制模型表达，且不能解决上下文结构问题。
2. 上下文窗口架构是全局能力，不是随机回复专用。@ 回复、私聊、引用回复、跨用户追问也应该能看 active scene，并在需要时调用 `read_group_context`。
3. 随机回复不能只因为 active scene 薄就硬取消，否则会损害水群能力。
4. `anchored_reply/context_lookup` 是可广泛复用的上下文回答思路；`ambient_water/no_send` 是随机主动插话专用发送模式，@ 回复不应走 `ambient_water` 闪避用户请求。
5. 随机回复应由模型自由选择模式：`anchored_reply`、`context_lookup`、`ambient_water`、`no_send`。
6. `ambient_water` 是“非锚定水群”，不是硬接当前短句，也不是跳过回复。它不能翻旧账、不能接管任务。
7. `ambient_water` 的“不引用、不 replyTo、不 @”必须由发送层代码硬保证，不写进提示词指望模型自觉。
8. 当前 bot 没有“模型选择技能卡”的正式能力；`ambient_water` 应做成随机回复 mode schema + 发送策略，不做 Agent skill。
9. 表达学习候选池当前仍是旁路诊断，不能作为 `ambient_water` 的生产硬依赖。基础版 `ambient_water` 必须不依赖候选池也能工作。
10. `ambient_water` 的语言材料之后可考虑接入《表达学习候选池详细设计》里的候选池，只借 reviewed 的句式骨架和场景，不复述原话。
11. 表达学习候选池必须继续遵守硬过滤、人格 `expressionPolicy`、原作者在场降权、冷却、跨群隔离和审核边界。
12. `read_group_context` 是自由路由工具。模型觉得需要旧公共上下文时可以调用，而不是程序按主题词硬编码检索。
13. 随机回复也可以使用受限版 `read_group_context`，但不能默认展开旧目录；工具返回无明确相关片段时应不发送或改走非锚定水群。
14. 可检索目录必须落盘，否则 100 条磁盘历史和当日公共记录无法变成稳定检索入口。
15. 可检索目录不用 AI 摘要，避免 token 浪费和摘要幻觉。目录用确定性 scene card，回答时取原文片段。
16. `getSharedContextNote()`、`active_group_scene`、`retrievable_context_index`、`read_group_context` 不互相取代，而是分层：当前现场直接给；旧现场给目录；需要时工具取原文；长期摘要只作背景。
17. 如果同一内容同时出现在多个层级，按最高优先级保留一份，避免 prompt 重复和权重冲突。

## 十三、最新边界补充

本节记录 2026-05-23 继续讨论后的补充边界。这里尽量写主要文字逻辑，只保留少量关键接口名，避免把设计变成函数堆。

### 1. 防止 JSON、工具计划和乱码发到群里

随机回复内部可以让模型先选择模式，例如锚定回复、查旧上下文、非锚定水群或不发送。但这个模式选择只属于内部协议，不能把 JSON、模式名、工具计划、Markdown 围栏或半截代码块原样发到 QQ。

具体边界：

- 如果随机回复 planner 返回结构化内容，只能由程序解析后取出自然语言回复；解析失败时不能把原文发出去。
- 用户可见内容只能是正常聊天文本，不能出现 `{"mode":...}`、`__SILENT__`、函数名、工具名、`read_group_context` 调用说明、```html 之类格式残留。
- 这不是为了限制自然表达，而是为了防止内部协议、模型草稿和格式垃圾穿透到群聊。
- 随机链路解析失败时，优先重试一次生成自然语言；仍失败就不发送。点名/私聊链路如果出现明显内部协议或格式垃圾，应重新生成自然回复，而不是把垃圾发出。

### 2. 工具调用过程中不发中间消息

工具调用是内部动作。无论是查旧群聊记录、看历史图片、分析文件，还是 search/fetch，默认都不向群里发送“我去查一下”“我会调用某工具”这类中间消息。

用户只应该看到两种结果：

- 工具完成后的最终自然回复；
- 随机回复判断不适合发言时什么都不发。

阻塞边界：

- 如果随机回复正在等待工具结果，此时群里又出现新的点名、私聊、命令或明确交互，新交互优先，旧随机回复应取消或过期，不能几秒后再把旧话题补发出来。
- 如果是用户明确点名后的工具调用，可以等待有限时间；超时后给自然降级回复或请用户补充，不发工具过程。
- 随机回复最多做一次受限 `read_group_context` 查询；点名/私聊可以更宽，但仍要有轮数和时间上限，避免查记录把聊天拖慢。

### 3. 旧背景必须写清楚是旧背景

长期摘要、个人历史、旧群聊目录都不能和当前现场混在一起。它们进入上下文时必须明确标注：

- 这是旧背景，只能帮助理解身份、偏好、关系和被用户明确拉回的旧对象；
- 不是当前话题；
- 除非用户主动问“刚才/之前/上次/那张图/那个文件/你刚才说的”，否则不要主动提起。

当前热窗口、引用链、媒体锚点和用户本轮消息的权重必须高于旧背景。旧背景可以帮助 bot 记得“这个人是谁、喜欢什么、以前有什么稳定设定”，但不能让 bot 突然把一小时前的话题翻出来继续聊。

### 4. 查记录要靠自由路由，但不能一直查

`read_group_context` 的意义是给模型自由补上下文，不是让程序按关键词硬查，也不是让模型每轮都翻记录。

平衡方式：

- 默认先看当前热窗口和引用/媒体锚点；能接上就直接答。
- 当前消息明显像短跟进、指代、追问，但热窗口不够解释时，模型可以自主调用 `read_group_context`。
- 工具返回的旧片段只用于理解当前指代，不代表旧话题重新变成当前话题。
- 如果工具结果为空、很弱或无关，随机回复应转为 `ambient_water` 或 `no_send`；点名/私聊应自然说明没抓到指代，向用户确认。
- 每轮必须有查询上限和总时间上限。随机回复只允许很轻的一次查询；点名/私聊允许更完整，但不能变成循环查记录。
- 目录只告诉模型“哪里可能有旧上下文”，回答仍要基于工具取回的原文片段，不能凭目录摘要编。

### 5. scene card 落盘安全边界

可检索目录必须落盘，否则重启后 100 条磁盘内消息记录无法形成稳定检索入口。但落盘只能保存公开上下文索引，不能变成隐私或文件内容仓库。

scene card 允许保存：

- 安全 channel key；
- scene 起止时间；
- messageId 列表；
- 清洗后的显示昵称；
- 清洗后的短文本样本；
- 安全锚点标签，例如“文件：xxx，8.52MB”“图片”“语音转文字摘要可用”；
- 确定性抽出的数字、单位、文件名片段和短关键词；
- scene 状态，例如 hot/warm/cold。

scene card 禁止保存：

- 本地文件路径；
- 真实 URL；
- token、cookie、key、webhook；
- 文件正文；
- 图片真实路径；
- 未清洗的 HTML/XML/CQ 原始片段；
- 任何可以反向定位部署环境或用户本机路径的信息。

实现侧应使用安全 channel key、原子写、文件大小上限、保留期裁剪和懒加载。scene card 是“检索目录”，不是模型可直接采信的事实来源；真正回答前仍应通过 `read_group_context` 取回清洗后的原文片段。

### 6. 表达学习候选池暂时不进生产

表达学习候选池现在仍是旁路/诊断能力，不能为了 `ambient_water` 直接读取生产候选文件，也不能把未审核候选注入 prompt。

当前阶段：

- `ambient_water` 必须不依赖表达学习候选池也能工作；
- 候选池只在文档里预留接口和边界；
- 将来如果候选池正式启用，只能通过稳定接口提供已审核、已过滤、已冷却的句式骨架；
- 窗口架构不得直接读取 `data/expression-pool/<channelKey>.json`。

预留接口可以叫 `selectAmbientExpressionSkeletons(context)`，但现阶段只写清楚未来接法，不把它接到生产回复里。

### 7. 点名回复不能用水群逃避

`ambient_water` 只属于随机主动插话。用户点名、私聊、引用追问、命令或明确请求时，bot 必须正面处理当前问题：能答就答，需要工具就内部调用工具，需要确认就自然追问。

点名回复不能因为上下文薄就用“随口水一句”糊弄过去。上下文薄时，它应该：

- 看 active scene；
- 必要时调用 `read_group_context`、历史图片、文件分析或 search/fetch；
- 仍不清楚时向用户确认指代。

这条用于防止把“水群能力”误用成逃避回答能力。
