# 表情包学习与发送方案

## 状态

待审核。本方案承接 [`affect-router 情绪输出路由详细设计`](affect-router情绪输出路由详细设计.md) 的 `text_emoji` 输出模式与 `emojiQuery`，承接 [`表达学习候选池详细设计`](表达学习候选池详细设计.md) 的"硬过滤 → 候选池 → 影子注入"分层范式，复用现有 [image-store.js](../packages/koishi-plugin-dongxuelian-ai/lib/image-store.js)、[image-analyzer.js](../packages/koishi-plugin-dongxuelian-ai/lib/image-analyzer.js)、Dashboard Gallery 面板与 agent 工具体系，不另起观察队列。

## 核心目标

让莲莲在群里**像群友一样会用表情包**，但不学坏、不串人格、不需要人工逐张审核。

具体地：

- **接收侧**：群里别人发的图，自动判定是否是"可爱莲莲会发的表情包"，是的话沉淀进表情库；不是的话只用作一次性视觉理解，跟现状一样滚动删除。
- **发送侧**：莲莲想发表情时，agent 调一个 `send_sticker` 工具，传一句意图描述（如"对周一抗拒"），工具内部检索表情库返回最贴切的图，走 OneBot/Koishi 发出。
- **审核侧**：Dashboard 复用 [GalleryPanel.vue](../packages/koishi-plugin-dashboard/frontend/src/components/GalleryPanel.vue) 的视觉风格，新增"表情库审核"页，可视化增删，支持批量操作。

## 决策摘要（用户已拍板）

| 维度 | 决策 |
| --- | --- |
| 画风统一 | **要统一**——只收"可爱/温馨/二次元/萌宠"系，恶搞/吊图/黑深残拒收 |
| 决策权 | **LLM 主动 + 被动兜底**——agent 工具优先，reply.js 概率触发兜底 |
| 入库门槛 | **设门槛**——pHash 去重 + 出现次数门槛 + VLM 画风审核 |
| 误判处理 | **Dashboard 可视化人工纠错**——不靠文字命令 |

## 现状缺口（已确认）

来自前期调研：

- 收到的图字节缓存仅 10 张/群滚动删除，**不会沉淀**到表情库。
- mface 表情段、低分辨率方图、生活照走同一存储桶，**不区分表情包 vs 普通图**。
- 发送侧靠 [reply.js#L90-L143](../packages/koishi-plugin-dongxuelian-ai/lib/reply.js#L90-L143) 的 50 条 `STICKER_MAP` 硬编码，加图必须改源码 + 重启。
- Agent 工具不对称：能"看图、分析图"，**没有"发某张已存图"**，链路长且脆。

## 数据资产与存储

```
data/
  stickers/                    # 现存：50 张硬编码表情包（沿用，作为 v1 启动种子）
  sticker-pool/                # 新增：自动学习入库的表情包
    images/
      <pHash>.<ext>             # 文件名 = 16 位 pHash 前缀
    index.json                  # 元数据索引（见下）
    banlist.json                # pHash 黑名单
    pending.json                # 观察池：被发过 1 次但未达入库门槛
  sticker-cache/               # 已存在 image-cache 旁路使用，无需新建
```

`sticker-pool/index.json` 单条元数据：

```js
{
  hash,             // pHash 16 位前缀，作为唯一 ID
  ext,              // jpg/png/gif/webp
  size,             // 字节数
  width, height,    // 像素
  ocrText,          // 图里的文字（OCR），可空
  description,      // VLM 一句话描述，≤30 字
  vibe,             // 'cute' | 'warm' | 'neutral'，只有这三种入库
  tags,             // VLM 给的语义标签，3-5 个，如 ["开心","撒娇","吃饭"]
  source,           // 'auto' | 'manual' | 'seed'
  contributors,     // [userId]，发过该图的人，去重
  occurrences,      // 出现次数（含复读）
  channelKeys,      // 出现过的群，跨群去重
  firstSeenAt,
  lastUsedAt,       // 莲莲发出过的最近时间（冷却用）
  useCount          // 莲莲发出过的总次数
}
```

`pending.json` 同结构，状态为"已被发过 ≥1 次但未满足入库门槛"。

`banlist.json` 极简：

```js
{ "<hash>": { reason, bannedAt, byUserId } }
```

## 数据流（端到端）

### 接收侧

```
群里有人发图
  ↓
existing image-store.js 写 image-cache + image-history
  ↓ (新增旁路)
sticker-ingest.tryIngest(buffer, mime, channelKey, userId)
  ├─ 1. 计算 pHash + 文件 hash
  ├─ 2. 命中 banlist → 丢弃（结束）
  ├─ 3. 命中 index.json → occurrences++ / 记录 contributors / 结束
  ├─ 4. 命中 pending.json → occurrences++
  │     若 occurrences ≥ 2 且 contributors ≥ 2（不同人）
  │       → 调 sticker-vetter 审核
  │       → vibe in (cute|warm) → 升级到 index.json
  │       → vibe = neutral → 留在 pending（再观察）
  │       → vibe = meme_dark → 加入 banlist
  │     否则继续留在 pending
  └─ 5. 全新图 → 写入 pending.json，等下次复读
```

**关键点**：**第一次见到的图不调 VLM**，只是记账。这样恶意刷一次性图根本不消耗审核成本。这是 Pallas-Bot 隐藏的招式：**用群友的复读行为做粗筛**。

### 审核侧（VLM）

`sticker-vetter` 单次调用 prompt 大致：

```
你是图片画风分类助手。判断这张图是否符合"可爱莲莲"的表情包画风：

输出 JSON：
{
  vibe: "cute" | "warm" | "neutral" | "meme_dark",
  description: "一句话 ≤30 字描述",
  ocrText: "图中文字，无则空",
  tags: ["3-5 个语义标签，如 开心 撒娇 吃饭"]
}

判定标准：
- cute: 萌宠、二次元、软萌表情、温馨日常 → 入库
- warm: 治愈系、积极向上的卡通 → 入库
- neutral: 风景、生活照、纯文字截图 → 暂存观察
- meme_dark: 恶搞、吊图、黑深残、低俗、政治、色情、广告 → 拉黑
```

复用 [image-analyzer.js](../packages/koishi-plugin-dongxuelian-ai/lib/image-analyzer.js) 的 VLM 调用通道（OneAPI/同款模型），新增一个 prompt 模板即可，**不新增 AI 提供方**。

### 发送侧（agent 工具）

新增 [agent/tools/send-sticker.js](../packages/koishi-plugin-dongxuelian-ai/lib/agent/tools/send-sticker.js)，注册到 [agent/tools/registry.js](../packages/koishi-plugin-dongxuelian-ai/lib/agent/tools/registry.js)：

```js
{
  name: 'send_sticker',
  description: '从已学习的表情包库里挑一张并发送给当前用户/群。' +
               '只在情绪输出场景下用，比如开心、撒娇、抱抱、无语。',
  schema: {
    query: 'string',     // 必填：意图描述，如"对周一抗拒"
    mood: 'string?',     // 选填：affect-router 给的 mood
    vibeFilter: 'string?' // 选填：cute|warm，默认全选
  },
  handler: async ({ query, mood, vibeFilter }, ctx) => {
    // 1. sticker-search 三路召回 → top-5
    // 2. （可选）让 LLM 在 5 选 1（用现有小模型，cost 低）
    // 3. 检查 lastUsedAt 冷却（同图 5 分钟内不重发）
    // 4. 通过 ctx 发送 h.image()
    // 5. 写回 lastUsedAt / useCount
    return { hash, description, sent: true }
  }
}
```

### 触发兜底

[reply.js](../packages/koishi-plugin-dongxuelian-ai/lib/reply.js) 现有的 `[图:xxx]` 标记和 30% 概率触发**保留**，只把"挑哪张图"从硬编码 `STICKER_MAP` 改为调用 `sticker-search`。这样 agent 主动发图为主，被动概率为辅，不丢现有功能。

**触发概率从 30% 降到 12-15%**——前期调研结论：30% 偏高、容易刷屏，10-15% 才像真人。

```
GET    /dashboard/api/sticker          列出 index/pending/banlist 三个集合
POST   /dashboard/api/sticker          手动上传（source=manual，跳过审核）
DELETE /dashboard/api/sticker          批量删除 + 加 banlist
PUT    /dashboard/api/sticker/promote  pending → index（管理员强制入库）
PUT    /dashboard/api/sticker/ban      pending|index → banlist
DELETE /dashboard/api/sticker/ban      banlist 移除
GET    /dashboard/api/sticker/image/:hash   读取图片二进制（带 cache 头）
```

## 与 affect-router 的对接

[`affect-router 情绪输出路由详细设计`](affect-router情绪输出路由详细设计.md) 已经规划了 `outputMode: 'text_emoji'` 和 `emojiQuery: { tags, maxRisk }`。本方案的 `send_sticker` 工具就是 affect-router 输出 `text_emoji` 时的执行端：

- affect-router 决定**是否发表情**（情绪 + 人格 + 冷却）
- `send_sticker` 决定**发哪张表情**（库内三路召回）

两套职责干净分离，不互相侵入。affect-router 启用前，agent 也可以独立调用 `send_sticker`。

## 与 expression-pool 的边界

`sticker-pool` 与 [expression-pool-store.js](../packages/koishi-plugin-dongxuelian-ai/lib/expression-pool-store.js) **完全不复用存储**，只复用"硬过滤 → 观察池 → 审核入库"的设计模式：

| | expression-pool | sticker-pool |
| --- | --- | --- |
| 存的什么 | 文本句式骨架 | 图片二进制 + 元数据 |
| 学习触发 | 23:55 离线扫描 today-cache | 在线 middleware 旁路（图片不会落到 today-cache） |
| 注入方式 | 影子日志 → 主 prompt | agent 工具直接发送 |
| 风险 | OOC、串人格 | 画风崩坏、违规图、版权 |

## 风险与回滚

| 风险 | 触发条件 | 缓解 |
| --- | --- | --- |
| VLM 误判把恶搞图判 cute | 模型在某些梗图上失准 | banlist 兜底 + Dashboard 巡检 + 入库前要求"出现 ≥2 次且 ≥2 人发过" |
| 表情库膨胀 | 长期跑下来几千张 | index.json 单文件大小上限 5MB 提示；按 `useCount=0 且 firstSeenAt > 30 天` 自动归档 |
| 同图反复发 | lastUsedAt 不生效 | `send_sticker` 内部强制 5 分钟单图冷却 + 1 分钟全局冷却 |
| pHash 碰撞 | 不同图哈希相同（极罕见） | 同时存文件 sha256 做二次校验，碰撞时拒绝合并 |
| OneBot 发送失败（mface vs image） | 协议端兼容差异 | 走现有 [reply.js](../packages/koishi-plugin-dongxuelian-ai/lib/reply.js) 已验证的 `sendGroupMsg` + Koishi `h.image()` 双通道兜底 |
| 用户自动退订 | 配置开关 `stickerLearning.enabled = false` | 关闭后不再 ingest、不再 send_sticker；index 数据保留 |

回滚顺序：v3 → v2 → v1，**任何一阶段都可以独立关闭**，不影响主聊天链路。

## 不在本方案范围

- **CLIP 向量检索**：库 < 1000 张前不上，等 v3 跑稳后视库规模决定。
- **梗图生成**（图上加字）：[emotion-renderer.js](../packages/koishi-plugin-dongxuelian-ai/lib/emotion-renderer.js) 已经在做类似事情，本方案不重叠。
- **跨群语料聚合**：每张图记录 `channelKeys` 但不做"用 A 群学到的图发给 B 群"，避免隐私顾虑；如需开放再单独评审。
- **Telegram/Discord sticker 协议**：当前只考虑 OneBot 群聊场景。

## 配置示意

`packages/koishi-plugin-dongxuelian-ai/lib/agent/config.js` 新增：

```js
stickerLearning: {
  enabled: false,              // 默认关，渐进开
  minOccurrences: 2,           // 入库门槛：被发次数
  minContributors: 2,          // 入库门槛：不同发送者数
  vetterModel: 'default',      // 默认走 image-analyzer 的模型
  pendingTtlDays: 14,          // 观察池 14 天未升级则丢弃
  maxIndexSize: 2000,          // 表情库总数上限
  cooldownMs: 300000,          // send_sticker 同图 5 分钟冷却
  globalCooldownMs: 60000      // 任何图 1 分钟全局冷却
}
```

人格端按 [`affect-router`](affect-router情绪输出路由详细设计.md) 已规划的 `outputMode` / `emojiQuery` 配置，不重复定义。
