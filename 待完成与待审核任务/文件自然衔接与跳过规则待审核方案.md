## 一、待实现：自由路由 + 硬编码兜底

### 1. 设计目标

让 bot 在合适的时机主动分析文件，但不能乱分析浪费 token。
同时保留硬编码指令作为兜底，确保用户总有办法触发。

### 2. 触发层级（从严到宽）

#### 第一层：硬编码指令（最高优先级，无条件触发）

用户消息包含以下关键词时，强制触发最近一个可分析文件：

- "读文件"
- "看文件"
- "分析文件"
- "打开文件"
- "文件内容"

逻辑：匹配关键词 → 找最近一个未分析且未跳过的文件 → 调用 analyzeFileNow → 返回结果。
不走 Agent，不消耗 Agent token。

#### 第二层：私聊文件处理（比群聊宽松）

私聊场景不怕打扰，策略比群聊宽松：

**小文件（纯文本 ≤500KB）：** 收到后直接后台预解析，存 file-store。
- 读本地缓存 → 提取文本 → 存 analysis → 不发消息
- Agent 后续调工具时秒回

**大文件 / 二进制文档（PDF/DOCX/XLSX 等）：** 触发正常 Agent 回复流程。
- 私聊收到大文件时，走正常的 bot 触发流程（等同于用户发了条消息）
- Agent 看到上下文里有 `[文件: report.pdf (fileId:xxx)]` + 私聊场景
- Agent 用 bot 当前的人格自然地回应（可能是"这个要我看看吗"、"发了个 PDF 呀，需要我帮你总结吗"等）
- 不硬编码任何话术，完全由 Agent 按人格决定怎么说
- 用户确认后 → Agent 调 analyze_file → 小文件读本地缓存 / 大文件下载 URL → 返回内容

**私聊文件过期时间：** 24 小时（比群聊的 4 小时长）。
理由：私聊节奏慢，用户可能隔几小时才追问。

**私聊 vs 群聊行为对比：**

| | 私聊 | 群聊 |
|---|---|---|
| 小文本文件 | 自动预解析 | 只记标记 |
| 大文件/PDF | bot 主动问要不要看 | 沉默，等 Agent 判断 |
| 不确定时 | 可以问 | 不问 |
| 过期时间 | 24 小时 | 4 小时 |

#### 第三层：Agent 自由路由（最灵活，但最贵）

当 Agent 被正常触发时（@bot、私聊、随机回复命中），它能看到对话历史里的文件占位符。
Agent 自行判断是否需要调用 analyze_file 工具。

Agent 的 tool description 已经写明：
- 用户明确提到文件时才调用
- 不确定时先列表再确认
- 模糊匹配用 keyword 参数

这一层不需要额外代码，靠 Agent 的 LLM 推理能力。

#### 第四层：群聊被动感知（只记录不分析）

群里有人发文件：
- 记录元数据 ✓（已实现）
- 对话历史出现占位符 ✓（已实现）
- 不自动分析 ✓
- 用户后续 @bot 追问时，Agent 能找到并分析

### 3. 防滥用规则

- 同一文件不重复分析（analyzed 标记）
- 同一频道同时最多 2 个文件在下载/解析
- 队列上限 100，超出丢弃
- 下载超时 30 秒
- 下载过程中超 10MB 中断
- 解析结果最多保留 3000 字符（不会把整个文件塞进上下文）

### 4. 自然回复风格

文件被自动分析后（第二层），分析结果存入 file-store，不写入对话历史。
下次 Agent 被触发时如果判断相关，调工具读取结果，自然接话。

如果用户用硬编码指令（第一层），bot 直接回复文件摘要。

如果 Agent 路由分析（第三层），Agent 自己决定怎么回复。

所有情况下，文件内容都不写入对话历史。

### 6. 不做的事

- 不做群聊自动分析（太浪费）
- 不做大文件自动分析（风险高）
- 不做二进制文档自动分析（PDF/DOCX 需要调解析器，有成本）
- 不做文件内容全文入模（只入摘要）
- 不主动发消息通知"我看到文件了"（除非用户在跟 bot 对话）

### 7. 文件缓存策略（双储存兜底）

跟图片一样做双储存，防止 URL 过期后无法下载：

#### 小文件本地缓存（≤1MB）

- 收到文件时，如果通过安全检查且 ≤1MB → 立即下载到 `data/file-cache/{频道key}/`
- 每频道最多保留 10 个文件，超出时删最旧的
- 不设过期时间，常驻磁盘（直到被新文件挤掉）
- 这样即使 URL 过期了，本地还有原文件可以解析

#### 大文件只存 URL（>1MB）

- 收到时只存 URL 到 file-store 元数据
- 不自动下载
- URL 约 2 小时后过期（NTQQ rkey 机制），过期后无法下载
- 私聊场景 bot 会主动问要不要看，引导用户在 URL 有效期内触发分析
- 群聊场景只能靠用户在 2 小时内 @bot 追问

#### 元数据过期时间

- 私聊：24 小时（节奏慢，用户可能隔很久才追问）
- 群聊：4 小时（消息量大，老文件很快失去意义）
- 过期后元数据从 file-store 删除，轻量提示注入里也不再出现

#### 对比图片缓存

| | 图片 | 小文件（≤1MB） | 大文件（>1MB） |
|---|---|---|---|
| 收到时 | 立即下载缓存 | 立即下载缓存 | 只存 URL |
| 本地上限 | 每频道 10 张 | 每频道 10 个 | 无本地文件 |
| 过期清理 | 删最旧的 | 删最旧的 | URL 2h 后失效 |
| URL 过期后 | 有本地缓存兜底 | 有本地缓存兜底 | 无法下载 |

#### 下载失败时 bot 的回复

当 Agent 调用 analyze_file 但下载失败时，工具返回：
```
这个文件下载失败了，可能已经过期。如果还需要，请重新发一次文件。
```

Agent 拿到这个结果后自然地转述给用户，不会硬邦邦地报错。

### 7.1 轻量文件提示注入

在 Agent 上下文头部注入一行近期文件列表（不占对话历史位置）：
```
[近期文件: config.yaml(2小时前,已分析), 周报.docx(30分钟前,可分析)]
```

作用：
- 文件标记滚出对话历史后，Agent 仍然知道有文件存在
- 用户模糊表述时，Agent 有文件名可做语义匹配
- 不含文件内容，不会污染上下文

不需要清除机制：
- 这行只是背景知识，不会导致 bot 主动提起文件
- 工具 description 约束了调用条件
- 文件从 file-store 过期删除时，提示自然消失

### 8. 上下文污染防护

核心原则：**文件内容永远不写入对话历史。**

对话历史里只保留标记：
```
[文件: config.json (fileId:msg123)]
```

没有摘要、没有内容、没有"已读取"。就是一个纯标记，告诉 Agent "这里有个文件"。

文件的完整分析结果只存在 file-store 的 analysis 字段里。

当 Agent 被触发时：
- Agent 看到标记 → 结合用户当前发言判断是否相关
- 相关 → 调 analyze_file 工具 → 工具返回内容 → Agent 基于内容回复
- 不相关 → 不调工具 → 文件内容根本不进当前上下文

工具返回值是临时的（只在当次 Agent 推理时可见），不会写回对话历史。
下次 Agent 被触发时，如果用户还在聊文件，Agent 再调一次工具。
如果用户已经换话题了，Agent 不调，文件内容自然消失。

这意味着：
- 不需要硬编码"谁在聊文件"的判断规则
- 不同用户聊不同话题时互不干扰（Agent 按当前对话者的意图决定）
- 不会出现 bot 没事提起文件的情况
- token 只在真正需要时才消耗（调工具那一次）

对比图片链路的区别：
- 图片：摘要很短（~20字），写入对话历史无害，且图片描述对后续对话有用
- 文件：内容可能很长，写入必然污染，且大部分后续对话不需要它

所以文件和图片的策略应该不同：
- 图片 = 分析后写入上下文（短，无害）
- 文件 = 永远不写入上下文，按需通过工具获取（长，有害）

实现改动：
- 删除 conversation.js 里的 replaceFilePlaceholder 逻辑（不再替换占位符）
- file-analyzer.js 分析完只写 file-store，不动对话历史
- analyze_file 工具从 file-store 读 analysis 返回给 Agent（临时）

### 8.1 边界情况：擦边话题的处理

问题：用户的话可能跟文件"有点关系但不确定"，比如：

| 用户发言 | 上下文有文件 | 是否在说文件 |
|----------|-------------|-------------|
| "帮我看看那个文件" | report.pdf | 明确是 |
| "这报告写得不错" | report.pdf | 大概率是 |
| "配置好复杂" | config.json | 可能是，也可能在聊别的 |
| "这有bug吧" | main.py | 可能是，也可能在说之前讨论的代码 |
| "今天好热" | config.json | 明确不是 |

设计原则（写入 Agent 的工具描述或系统提示）：

1. **明确相关** → 直接调工具分析，不用问
2. **擦边/模糊** → 不分析，也不问（宁可漏掉，不要打扰）
3. **明确无关** → 不调工具，不提文件

判断依据（Agent 自行推理，不硬编码）：
- 时间距离：文件刚发不久 + 用户紧接着说了相关的话 → 大概率在说文件
- 语义距离：用户的话跟文件名/类型有语义关联 → 可能在说文件
- 指代词："这个"、"那个"、"刚才的" → 结合上下文判断指的是什么
- 多人场景：A 发了文件，B 在聊别的话题，C @bot 问问题 → Agent 要区分 C 问的是文件还是 B 的话题

关键：宁可不分析，不要擅自把文件内容拉进来浪费 token。但一旦决定分析了，就自然地说内容，不要问用户。

Agent 的行为准则：

**进入：主动感知，不等指令**
- bot 被触发时（@、随机命中、私聊），Agent 看到上下文有文件标记
- Agent 判断当前对话是否围绕这个文件（看群友在聊什么）
- 如果是 → 自己调 analyze_file → 拿到内容 → 自然接话
- 全程不需要任何人说"bot 帮我看看"

**接话：自然融入，不宣告**
- 不说"我帮你分析了文件，内容如下..."
- 直接说内容相关的话："这个配置里数据库连接用的 localhost:5432，看起来是开发环境的"
- 像一个看过文件的群友一样参与讨论

**退出：话题转移，自然消失**

不存在"退出文件分析模式"这个动作。bot 没有状态机，每次被触发都是一次独立的 LLM 调用。

每次 bot 被触发时，Agent 看到的是：
- 对话历史（最近 N 条消息，包含文件标记和 bot 之前的回复）
- 当前触发消息
- 可用工具列表

Agent 每次都重新判断："现在的对话在聊什么？需要调 analyze_file 吗？"

具体场景：

场景 1：自然退出
```
msg1: 张三 [文件: config.json (fileId:abc)]
msg2: 张三: 这个配置对吗
msg3: bot: 端口8080没问题，但数据库密码明文不太安全  ← Agent 调了工具
msg4: 李四: 今天中午吃什么
msg5: 张三: 去食堂吧
msg6: 李四: @bot 你觉得呢
→ Agent 看到最近话题是午饭，不调 analyze_file，正常聊天
```

场景 2：持续讨论
```
msg1: 张三 [文件: config.json (fileId:abc)]
msg2: 张三: 这个配置对吗
msg3: bot: 端口8080没问题，但数据库密码明文不太安全
msg4: 张三: 那怎么改
→ Agent 看到张三还在问配置的事，再次调 analyze_file 获取细节回答
```

场景 3：话题混杂
```
msg1: 张三 [文件: config.json (fileId:abc)]
msg2: bot: 这配置有几个问题...
msg3: 李四: 什么问题
msg4: 王五: 今晚打游戏吗
msg5: 张三: @bot 那个端口要改成什么
→ Agent 看到张三明确在追问配置，调工具；王五的话题不影响判断
```

场景 4：时间衰减
```
msg1: 张三 [文件: config.json (fileId:abc)]
msg2-msg30: 群友聊了 28 条别的话题
msg31: 李四: @bot 那个配置文件还在吗
→ 文件标记可能已经滚出对话历史窗口
→ Agent 调 analyze_file 不传 messageId → 从 file-store 列表里找
→ 如果找到且 URL 未过期 → 分析；如果 URL 过期 → 回复"文件可能过期了"
```

为什么不需要"退出"机制：
1. Agent 没有持久状态 — 每次触发都是全新的 LLM 推理
2. 不调工具 = 文件内容不进当前上下文 = bot 不会提到文件
3. bot 之前关于文件的回复虽然在历史里，但随着新消息增多，LLM 注意力自然转移到最近的话题
4. 对话历史有长度限制，老消息会被裁剪或摘要压缩

唯一的风险：bot 上一条回复刚聊了文件，紧接着又被触发，可能惯性地继续聊文件。
缓解方式：analyze_file 的 description 里明确写"只在当前对话明确围绕文件时调用，不要因为自己上一条回复提到了文件就继续调用"。

**类比图片链路：**
- 图片：自动分析 → 描述常驻上下文 → bot 随时能引用 → 因为便宜所以无脑做
- 文件：不自动分析 → 内容不常驻 → bot 感知到需要时才去读 → 读完自然接话 → 话题过了就忘 → 因为贵所以按需做

**核心区别只有一个：触发时机**
- 图片：收到就分析（后台静默）
- 文件：bot 被触发 + 对话在聊文件时才分析（Agent 主动判断）

两者的"接话方式"是一样的：自然地提到内容，不宣告，不问。

类比图片链路的真实逻辑（图片也不是无脑自动分析）：

图片实际分两层：
1. 轻量预处理（后台静默）：收到 → 下载缓存 → 调视觉模型生成短描述（~20字）→ 写入对话历史
2. 深度分析（按需触发）：bot 被触发时通过 prepareVisionRequest 判断是否把图片发给模型；Agent 模式下通过 analyze_historical_image 工具按需分析

图片能做轻量预处理是因为：下载快、描述短、不污染上下文。
文件不做轻量预处理是因为：下载可能慢、内容长会污染、解析有成本。

所以文件对齐图片的"深度分析"层，但没有"轻量预处理"层：
- 收到时只记标记，不下载、不解析、不写内容到上下文
- bot 被触发时，Agent 自己判断要不要调 analyze_file
- 调了就拿到内容，自然接话；不调就不提

文件分析的触发信号（Agent 综合判断，不硬编码为代码逻辑，只通过工具 description 引导）：

| 信号 | 权重 | 示例 |
|------|------|------|
| 用户直接提到文件名 | 高 | "那个 config.json 怎么回事" |
| 用户用指代词 + 上下文只有一个文件 | 高 | "这个写得对吗" |
| 用户的话跟文件类型/内容领域强相关 | 中 | 发了代码文件后说"这有bug" |
| 文件刚发不久（<5条消息内） | 中 | 时间距离近 |
| 多人在讨论同一个话题且话题跟文件相关 | 中 | A发文件，B说"这个不错"，C说"哪里不错" |
| 用户只是随口一提，话题重心在别处 | 低 | "刚才那个文件先不管，我想问..." |

规则：
- 单个高权重信号 → 可以分析
- 多个中权重信号叠加 → 可以分析
- 只有低权重或无信号 → 不分析
- 不确定时 → 不分析（而不是问用户）

这比图片严格在哪：
- 图片：收到就分析，无条件
- 文件：需要对话信号确认后才分析，且分析后不留痕（不写入历史）

这个原则通过 analyze_file 工具的 description 传达给 Agent：
```
只在对话明确围绕某个文件时调用。判断标准：用户提到了文件名、用指代词指向文件、或多人正在讨论文件内容。
如果不确定，不要调用，也不要询问用户是否需要分析。
分析后自然地在回复中引用内容，不要说"我帮你分析了文件"之类的话。
```

### 9. 下载链路验证

当前问题：file-analyzer.js 直接用 HTTP GET 下载 URL，但 QQ 文件的 URL 不一定能直接访问。

图片链路的做法：调 OneBot `get_image` API → 拿到本地路径或可用 URL → 再读取。

文件应该也需要类似的 `get_file` API：

```
下载流程：
1. 先尝试 URL 直接 HTTP GET
2. 如果失败（404/403/超时），调 OneBot get_file API 拿真实路径
3. 如果 get_file 返回本地路径，直接 fs.readFile
4. 如果 get_file 返回新 URL，再次 HTTP GET
5. 全部失败 → 标记为下载失败
```

需要验证的事项（部署后测试）：
- NapCat 的文件 segment 里 `data.url` 是否可直接下载
- NapCat 是否支持 `get_file` API
- 文件 URL 的有效期实际是多长
- 大文件（5-10MB）下载是否稳定

## 二、原始设计（保留参考）

本方案只讨论“让 bot 学会处理文件，但不会见文件就读”的自然衔接方式。

现有图片链路已经证明了一套可用节奏：

- 先记录元数据
- 再异步分析
- 再把结果回写到对话上下文

文件能力可以照着这条链路做，但不能直接把所有文件都塞进模型。文件必须先分层，再决定：

1. 该不该处理
2. 该用哪种解析器
3. 结果要不要回写
4. 是否需要跳过

## 二、推荐目标

### 1. 自然衔接

目标不是让 bot “看到文件就立刻回答”，而是让它像图片一样先说：

- 我看见了
- 我先记下来
- 我能不能读、怎么读，后面再决定

这样用户在 QQ 里不会觉得 bot 死板，也不会觉得它乱碰文件。

### 2. 分层处理

建议把文件能力拆成四层：

- 接收层：只负责记录文件消息元数据
- 落盘层：只负责缓存或下载到临时目录
- 解析层：按类型抽文本、结构、摘要
- 回写层：把结果写回会话或历史记录

### 3. 明确跳过

不是所有文件都要读。必须有跳过规则，不然 bot 很容易误碰二进制、压缩包、密钥、超大文件。

## 三、建议流程

### 1. 收到文件消息

先像图片那样记录一条文件历史：

- `messageId`
- 文件名
- 大小
- 类型 / mime
- 来源群或私聊
- 是否已分析
- 是否被跳过

这一层不要直接进模型。

### 2. 判断是否可处理

先走跳过规则。

建议优先跳过：

- 二进制可执行文件
- 压缩包
- 超大文件
- 密钥 / 证书 / 令牌类文件
- 明显不适合聊天上下文的缓存文件

建议优先处理：

- 文本
- 日志
- 配置
- Markdown
- JSON
- CSV
- 纯图片
- 音频
- PDF / 文档类

### 3. 异步解析

解析不要阻塞主聊天链路。

建议复用图片分析的思路：

- 先入库
- 再后台跑
- 成功后写回摘要
- 失败后写回失败原因

### 4. 回写上下文

解析成功后，不要把全文硬塞给模型。

更合理的是回写：

- 文件名
- 文件类型
- 摘要
- 关键段落
- 来源消息 ID

然后当用户后续问“刚才那个文件”时，再基于历史命中继续读。

## 四、模块建议

### 1. 新增文件存储层

建议新增类似 `file-store.js` 的模块，职责对齐图片历史：

- 存元数据
- 存本地缓存路径
- 存摘要
- 存跳过状态
- 存分析状态

### 2. 新增文件分析层

建议新增类似 `file-analyzer.js` 的模块，职责对齐图片后台分析：

- 统一队列
- 限并发
- 限总超时
- 按类型选择解析器
- 写回历史和会话

### 3. 新增文件上下文注入

建议在 `conversation.js` 或聊天拼接层里加一层轻量注入：

- 最近处理过的文件
- 最近跳过的文件
- 最近分析结果

只注入摘要，不注入全文。

## 五、跳过规则建议

### 1. 默认跳过

建议默认跳过：

- `exe`
- `dll`
- `bin`
- `so`
- `zip`
- `7z`
- `rar`
- `tar`
- `gz`
- `key`
- `pem`
- `crt`
- `pfx`

### 2. 条件跳过

建议按大小、类型和内容再判断：

- 超大文本文件只读前几段
- 解析失败就标记为跳过
- 像密钥、证书、配置口令的内容直接拒绝展开

### 3. 白名单优先

对文本类文件，先白名单再扩展。

也就是说，先保证这些能稳定读：

- `.md`
- `.txt`
- `.json`
- `.csv`
- `.yml`
- `.yaml`
- `.log`

## 六、用户交互建议

### 1. QQ 里

QQ 里默认还是聊天优先，文件能力只做辅助。

建议的自然回复风格：

- “我看见这个文件了，想让我总结还是找关键点？”
- “这个文件我先记住了，但它太大/不适合直接读。”
- “这份文件我能读，先帮你提个摘要。”

### 2. Dashboard 里

Dashboard 可以给更强的文件操作：

- 读取
- 列目录
- 搜索文件
- 编辑文件
- 上传文件

但这些能力应保留更严格权限。

## 七、实现顺序

### 第 1 步

先做文件元数据存储，仿照图片历史的 `image-store` 结构。

### 第 2 步

再做文件分析队列，仿照 `image-analyzer` 的异步模式。

### 第 3 步

接入跳过规则，先保证危险文件不会被误处理。

### 第 4 步

把摘要写回会话，让后续追问能自然接上。

### 第 5 步

最后再补 QQ 侧和 Dashboard 侧的不同工具入口。

## 八、验收标准

- 文件消息能被记录，但不会默认全文入模
- 能处理的文件会自动摘要
- 不该处理的文件会被明确跳过
- 后续追问“刚才那个文件”能接上
- 图片链路不被破坏
- QQ 侧仍然以聊天为主，不会变成乱读文件的工具人
