# Agent 定时任务体系优化待审核计划

日期：2026-05-24
状态：待审核，未实施，未部署

## 背景

当前定时能力已经有基础骨架：`agent/cron.js` 负责持久化、计算下次触发、恢复 timer、执行 `text` / `agent` 两类任务；`reminder-tools.js` 已接入一次性提醒的创建、查看、取消；触发后通过 `push.cronResult()` 投递到 QQ 群/私聊。

但这还只是“能响一下”的级别，距离真正的 Agent 时间维度还差很多。定时任务应该能承载长期动作：每日早安、周期总结、定时分析文档、定时搜索/检查、到点执行工具链、失败重试、暂停恢复、用户查看和修改。它不是装饰功能，而是让 Agent 从被动聊天变成可靠协作者的核心能力。

参考方向：

- QwenPaw 的定时任务体系把任务分成 `text` 与 `agent`，并提供创建、列表、详情、状态、暂停、恢复、运行等管理动作。
- Qwen Code / Claude Code 这类 Agent 的 scheduled prompt 思路是“按时间重复运行一个 prompt”，结果可投递回会话。
- Cloudflare Agents / Qoder 一类系统把 schedule 当成 agent run 的触发源，而不是单独的闹钟模块。

本计划的原则：沿用现有 `agent/cron.js`，不另造调度器；增强工具、状态模型、管理接口和测试，让模型通过工具说明自主控制定时任务，代码只做权限、安全、时间解析、持久化和异常兜底。

## 现有能力确认

- 支持一次性任务：`mode: once`，触发后标记 `done` 或 `failed`，不再重排。
- 支持周期 cron：`mode: cron`，五字段 cron 表达式，最小分钟步长为 10 分钟，触发后重新计算 `nextRunAt`。
- 支持两种执行类型：
  - `type: text`：直接把 `prompt` 当消息发出。
  - `type: agent`：调用 `engine.run()`，再把 agent 回复发出。
- 支持启动恢复：`startCronScheduler()` 会加载 `agent-crons.json` 并重新 schedule。
- 支持持久化写串行化，避免并发写坏 JSON。
- 支持一次性提醒绕过主动推送总开关，避免用户请求的提醒被 `push.enabled=false` 卡住。

## 主要缺口

1. 工具语义太窄

现有 `create_reminder` 只适合一次性提醒。用户说“每天早上八点说早安”“每晚总结今天群里聊了什么”“明天帮我分析这个文件”时，agent 缺少通用定时任务工具。

2. 管理能力不完整

目前只补了提醒的 list/cancel。完整定时任务需要 list/get/update/pause/resume/run/delete/history，且要能区分一次性提醒、周期文本、周期 agent 任务。

3. Agent 任务上下文不够稳

周期 agent 任务不能只保存一句 prompt。它还需要保存创建时的目标会话、创建人、可见范围、时区、任务说明、可引用的安全锚点、是否允许读旧上下文、是否允许用工具、结果投递策略。否则每日总结、定时分析文档等任务会忘记上下文或乱用旧消息。

4. 周期任务和一次性提醒混在体验上不清晰

一次性提醒可以叫 reminder，但周期任务应该是 scheduled task。它们底层可共用 cron，前台工具语义需要区分。

5. 失败、重试、并发和跳过策略不足

现在触发失败只写 history，并把 once 标为 failed；周期任务失败后仍会计算下次，但缺少失败次数、重试、超时、同任务重入保护、错过任务恢复策略。

6. 时间表达靠模型自由填参数，缺少结构化兜底

不能靠大量中文关键词做主路由，但需要一个“时间解析辅助工具/兜底”：模型主路径使用工具参数；代码兜底只在明确时间表达下补齐相对时间、每天/每周/工作日等结构化参数。

7. Dashboard / Agent Console 不够可观测

定时任务应该可查看状态、下次触发、最近结果、失败原因、创建人、目标会话，并能暂停/恢复/立即运行。否则线上一出问题只能翻日志。

## 目标行为

### 一次性提醒

用户：

> 十分钟后提醒我起床

期望：

- 创建 `mode: once`, `type: text`。
- 立即回复确认触发时间。
- 到点发“提醒：起床”。
- 任务完成后保留历史，列表默认不显示已完成，历史可查。

### 周期文本任务

用户：

> 每天早上 8 点跟我说早安

期望：

- 创建 `mode: cron`, `type: text`。
- 解析为每日 08:00。
- 周期触发，不会一次后消失。
- 用户可说“暂停早安提醒”“恢复早安提醒”“取消每天早安”。

### 周期 Agent 任务

用户：

> 每天晚上 11 点总结一下今天这个群聊了什么

期望：

- 创建 `mode: cron`, `type: agent`。
- 任务 prompt 保存为“总结今天这个群聊了什么，并发到当前群”。
- 触发时通过 agent 队列运行，允许使用 `read_group_context` 等安全工具。
- 结果发回当前群。
- 不把创建时的旧聊天当作事实；只把任务定义、频道和时间窗口作为上下文。

### 定时分析文件

用户上传文件后说：

> 明天上午 9 点帮我再分析这份文档并发给我

期望：

- 创建 `mode: once`, `type: agent`。
- 保存安全文件锚点：文件消息 ID、文件名、频道、创建人、创建时间，不保存本地真实路径进 scene card。
- 触发时通过 `analyze_file` 读取锚点文件，如果文件不可用则自然说明失败。
- 结果发回原会话。

## 计划设计

### Phase 1：任务模型升级

在 `agent/cron.js` 的 cron 对象上增加兼容字段，不破坏旧数据：

- `title`：短标题，如“早安”“每日群聊总结”。
- `description`：用户原始意图的安全摘要。
- `taskKind`：`reminder | scheduled_text | scheduled_agent | file_agent`。
- `timezone`：默认 `Asia/Shanghai`，后续可按用户配置。
- `visibility`：`private | channel`。
- `scheduleText`：用户可读的时间描述，如“每天 08:00”。
- `runPolicy`：
  - `maxRuntimeMs`
  - `allowOverlap: false`
  - `misfirePolicy: skip | run_once | reschedule`
  - `retry: { maxAttempts, backoffMs }`
- `contextPolicy`：
  - `allowReadGroupContext`
  - `contextWindow`
  - `anchorMessageIds`
  - `fileAnchor`
  - `allowedTools`
- `delivery`：
  - `targetChannel`
  - `targetUserId`
  - `quoteSource: false`
  - `silentOnNoResult`
- `stats`：
  - `runCount`
  - `failCount`
  - `lastError`
  - `lastResultPreview`

兼容要求：

- 旧任务缺字段时仍正常 normalize。
- 已存在的 `mode/type/prompt/targetChannel/runAt/nextRunAt` 继续有效。
- `agent-crons.json` 文件大小上限保持，history 需要尾部裁剪。

### Phase 2：通用定时任务工具

新增或扩展工具，不替代现有 reminder 工具：

- `create_scheduled_task`
  - 创建一次性或周期任务。
  - 参数包含 `mode`, `type`, `schedule`, `runAt`, `title`, `prompt`, `timezone`, `contextPolicy`, `delivery`。
  - 可创建 `text` 或 `agent` 任务。
- `list_scheduled_tasks`
  - 查看当前用户/当前会话可见任务。
  - 支持过滤 `active | paused | done | failed | all`。
- `get_scheduled_task`
  - 查看详情、下次触发、最近历史。
- `update_scheduled_task`
  - 修改标题、prompt、时间、投递目标、上下文策略。
  - 对危险变更走确认策略。
- `pause_scheduled_task`
  - 暂停任务，不删除。
- `resume_scheduled_task`
  - 恢复任务并重算 `nextRunAt`。
- `delete_scheduled_task`
  - 删除任务。
- `run_scheduled_task_now`
  - 手动试跑一次，结果仍走同样投递/日志。

保留 `create_reminder/list_reminders/cancel_reminder` 作为轻量入口，但内部转到通用工具：

- 一次性短提醒继续使用简单工具名，降低模型调用难度。
- 周期和 agent 任务用 `create_scheduled_task`。
- 管理工具可同时管理 reminder 和 scheduled task。

### Phase 3：自然语言时间解析辅助

不要把“每天/明天/每周”写成主路由硬编码。做法：

- 主路径：模型根据工具说明调用 `create_scheduled_task`，直接给出结构化 `runAt` 或 `schedule`。
- 辅助：提供 `parse_schedule_expression` 工具或内部纯函数，用于把自然语言时间转成候选结构。
- 兜底：只有当用户明确提出定时动作，而模型没有调用工具时，才对清晰表达做兜底解析。

支持范围：

- 相对一次性：`10 分钟后`、`2 小时后`、`明天上午 9 点`。
- 每日：`每天早上 8 点`。
- 每周：`每周一 9 点`。
- 工作日/周末：可先作为待实现，或转成多值 cron。
- 每隔 N 分钟/小时：遵守最小 10 分钟限制。

所有解析结果都要让工具返回确认文本，例如：

> 已创建周期任务：每天 08:00 说早安。下次触发：2026-05-25 08:00。

### Phase 4：Agent 执行上下文

定时 agent 任务触发时，不应该像普通用户聊天那样混入错误现场。需要专门的 cron agent context：

- `userMessage` 使用任务 prompt。
- `userName` 使用 `ScheduledTask` 或创建者昵称。
- `userId` 使用创建者 ID，保证权限和记忆可归属。
- `channelKey` 使用目标会话。
- 注入系统消息：
  - “这是一个定时任务触发，不是用户刚刚发言。”
  - “只根据任务定义、当前时间、允许的上下文工具执行。”
  - “旧背景必须通过工具读取，不能主动臆测。”
- 根据 `contextPolicy.allowedTools` 限制工具。
- 允许定时任务调用安全工具：
  - `read_group_context`
  - `analyze_file`
  - `web_search/web_fetch`，仅当任务允许外部信息。
  - 禁止随机主动回复创建新定时任务。

### Phase 5：调度可靠性

沿用当前 timer + JSON 持久化，但补可靠性：

- 同任务重入锁：任务运行中不再触发第二次。
- `running` 状态恢复：进程重启后发现长期 running，按超时转 failed 或重试。
- misfire 策略：
  - `skip`：错过周期直接算下一次。
  - `run_once`：启动后补跑一次。
  - `reschedule`：只重算，不补跑。
- 周期任务失败不应丢失；记录失败并计算下一次。
- 一次性任务失败可保留 `failed`，用户可“重试这个提醒/任务”。
- history 从 50 扩展为按任务保留最近 N 条摘要，避免全局 history 太短看不到问题。

### Phase 6：发送和权限边界

- 一次性用户提醒可以绕过 `push.enabled`，因为这是用户显式请求。
- 周期任务默认不绕过主动推送总开关，除非任务是用户显式创建并有 `delivery.userRequested=true`。
- 群聊周期任务需要当前频道可见，不允许把 A 群创建的任务发到 B 群。
- 私聊任务只发创建者。
- 随机主动回复不能创建/修改/删除任务。
- 删除、修改跨用户任务需要管理员权限或创建者本人。
- 任务 prompt、history、scene card 不保存本地真实路径、真实 URL token、cookie、密钥。

### Phase 7：Dashboard / Agent Console 可观测

新增“定时任务”视图：

- 列表：标题、类型、状态、下次触发、目标会话、创建者、失败次数。
- 详情：prompt、schedule、timezone、最近历史、最后错误。
- 操作：暂停、恢复、立即运行、删除、编辑。
- 创建：表单创建 text/agent/once/cron 任务。
- 风险提示：agent 任务是否允许读上下文、联网、文件分析。

不在 dashboard 中硬编码服务器信息；所有 API 继续走现有 admin token。

## 需要避免的硬编码

- 不用关键词作为主路由判断“这是定时任务”。主路由依旧由模型看工具说明决定。
- 代码中的中文解析只做兜底，不作为唯一入口。
- 不为 PDF/DOCX/PPTX 写固定分支。定时分析文件只保存文件锚点，触发时交给 `analyze_file` 的能力体系处理。
- 不把“每日早安”“日报”等写死成特殊功能。它们都只是 `scheduled_text` 或 `scheduled_agent`。
- 不把 QQ 号、服务器路径、部署信息写进任务、文档、测试。

## 测试计划

### 单元/契约测试

- cron 能注册 `once` 和 `cron`。
- cron 周期任务触发后重算 `nextRunAt`，不会变成 done。
- once 任务触发后标 done，不重排。
- `text` 任务直接发文本。
- `agent` 任务调用 queue + engine，再发结果。
- pause 后不触发，resume 后重算。
- delete 后 timer 清理。
- run_now 不改变周期任务的未来排程。
- 多用户并发创建任务不会写坏 JSON。
- running 超时恢复为 failed 或按策略重试。

### 场景测试

- “十分钟后提醒我起床”：创建 once text，到点发提醒。
- “每天早上八点说早安”：创建 cron text，触发后仍保留 active。
- “每天晚上 11 点总结今天群聊”：创建 cron agent，触发时调用 agent，并发回群。
- “明天九点分析刚才文件”：创建 once agent，保存 file anchor，触发时调用 `analyze_file`。
- “暂停早安任务 / 恢复早安任务 / 取消早安任务”：状态正确变化。
- “我有哪些定时任务”：只列出当前用户/当前会话可见任务。
- 多用户各自创建提醒：列表和取消互不串。
- 群聊任务不能被非创建者随便删除，管理员除外。

### 真实链路待验证

- 线上 QQ 群聊创建周期任务后，重启 bot，任务仍能恢复。
- 到点触发 agent 任务时，NapCat/OneBot 投递成功。
- agent 任务读文件时，确实能从文件历史下载/分析，而不是编内容。
- push disabled 时：一次性提醒能发，周期主动任务按配置行为执行。

## 实施顺序

1. 扩展 cron 数据模型和 normalize，保证旧任务兼容。
2. 加 pause/resume/delete/run_now/list/get/update 基础函数。
3. 新增通用 scheduled task 工具，并在 registry/config/chat-tools 暴露。
4. 把 reminder-tools 改为通用工具的轻量封装。
5. 增加 cron agent context，限制工具和上下文读取方式。
6. 补时间解析辅助和明确动作兜底。
7. 补 Dashboard / Agent Console 管理视图。
8. 跑 `npm run check`、`npm run test:quick`、`npm run test:scenario`。
9. 经用户确认后再部署。

## 验收标准

- 用户不用指令，只自然说定时需求，agent 能自主创建对应任务。
- 一次性提醒和周期任务都可创建、查看、暂停、恢复、删除。
- 周期任务触发后不会消失。
- agent 型定时任务能调用 agent 能力，而不是只发固定文本。
- 文件分析定时任务不会把旧聊天回复当事实缓存；触发时必须重新通过文件锚点/工具拿证据。
- 所有任务操作都有可查历史和失败原因。
- 不引入服务器信息、真实路径、token 到仓库文件。
