# 优化建议

生成日期：2026-05-20

本文是对当前莲莲 Bot 项目的阶段性优化建议汇总。重点按 Linux 服务器长期运行来评估，Windows 本地部署问题暂不作为主线。本文只写建议和方向，不代表已经修复、部署或重启。

## 一、总体评分与判断

如果按 100 分制评估当前项目，我给出的阶段性评分是：

**76 / 100**

这个分数的意思不是“项目不行”，而是：项目已经过了玩具阶段，功能很丰富，也有安全意识和测试入口，但还没有完全进入“服务器长期运行可以少盯”的生产稳定阶段。

### 分项评分

| 维度 | 评分 | 判断 |
|------|------|------|
| 功能完整度 | 84 | 聊天、人格、Agent、Dashboard、语音、图片、日报、工具系统都已经成型。 |
| 安全意识 | 78 | 有危险工具确认、路径限制、SSRF 防线、Dashboard token、并发限制等，但还需要继续按“默认会错写、会泄露、会卡住”审视。 |
| 稳定性 | 70 | 隐藏状态 bug、长跑队列、浏览器释放、图片历史和会话 key 不一致等问题仍会影响服务器运行质量。 |
| 可维护性 | 72 | 模块化已经开始，但 `chat.js`、`index.js`、Dashboard 大组件、部署脚本仍有继续膨胀风险。 |
| 测试可信度 | 68 | 测试入口不少，但很多仍是“能跑起来”的防线，距离“真实失败输入稳定复现并防回归”还有差距。 |
| 运维成熟度 | 73 | 有 restart 脚本、data-dir 规则和版本约束，但部署状态、服务器运行态、本地 dirty worktree 还需要进一步收敛。 |

### 总体结论

现在最适合的路线不是继续猛烈加功能，而是做 2 到 3 轮“隐藏 bug 审计 + 小修复 + 回归测试”。先把信任底座垫起来，再继续扩功能。做到这一阶段，我预计项目可以提升到 **84 分左右**。

## 二、最高优先级原则

### 1. 不追覆盖率，追事故样本可复现率

测试的核心目标不是覆盖率数字，而是回答：

- 这个测试复现过哪个真实失败？
- 它能阻止哪个 bug 重新出现？
- 它 mock 了哪些外部依赖？
- 还有哪些真实链路没有覆盖？

覆盖率高但没有真实失败输入，价值有限。少量高质量 regression 测试，比一堆泛泛 smoke 测试更能提升项目可靠性。

### 2. 先修“会让机器人认真说错”的 bug

崩溃类 bug 很容易发现，最危险的是静默错：

- 图片读成另一张。
- 会话历史写到另一个 key。
- 已经分析出的图片摘要没有进入后续聊天上下文。
- Agent 工具结果被误当成用户原话。
- Dashboard 保存成功但实际写到另一份 data。

这类 bug 不一定报错，但会直接损害用户对机器人的信任。

### 3. 服务器运行态优先于本地体验

当前用户重点是 Linux 服务器运行。优化时优先考虑：

- Linux 路径和权限。
- `DONGXUELIAN_AI_DATA_DIR` 是否绝对明确。
- Koishi / Dashboard / Agent 是否读取同一份 data。
- Chromium、日报、浏览器工具是否有并发限制和退出口。
- 日志能不能定位到真实问题。
- 部署后跑的是不是本地刚修的版本。

Windows 本地部署可以另开一个阶段处理。

## 三、测试体系优化

### 1. 新增 `test:regression`

建议新增一个专门的回归测试入口，和现有 `test:quick`、`test:scenario` 分开。

建议职责：

| 命令 | 职责 |
|------|------|
| `npm run test:quick` | 导出、常量、脚本、静态防线。 |
| `npm run test:scenario` | fake Koishi 集成场景。 |
| `npm run test:plugins` | 其他插件基础行为。 |
| `npm run test:regression` | 已确认 bug 的最小复现和防回归。 |
| `npm test` | quick + scenario + plugins + regression。 |

`test:regression` 只放确认过的真实 bug，不放“也许以后会有用”的测试。

### 2. Regression 测试命名规则

测试名应该写成事故说明，避免泛泛描述。

不建议：

```txt
image store works
conversation works
agent tools ok
```

建议：

```txt
image-store does not read m10 cache when querying m1
image-analysis writes placeholder back to guild-user conversation key
agent returns fallback when tool call produces empty model reply
dashboard rejects sensitive writes without admin token
```

测试失败时，测试名本身就应该告诉你它守住的是哪条事故。

### 3. 每个回归测试必须附带四问

可以用代码注释、测试输出或报告格式记录：

1. 复现了用户哪条真实失败输入？
2. 断言了哪个失败现象不会再出现？
3. 哪些依赖被 mock 了？
4. 因为 mock，哪些真实链路仍未覆盖？

建议模板：

```js
// Regression:
// 1. Real failure: 用户追问“刚才那张图是什么”，messageId=m1 误读 m10 缓存。
// 2. Assertion: readCachedImage('g', 'm1') 在只存在 m10 缓存时必须返回 null。
// 3. Mocked: 使用临时 DONGXUELIAN_AI_DATA_DIR，不连接真实 QQ / NapCat / 模型。
// 4. Not covered: 未覆盖真实 NapCat 图片下载和视觉模型调用质量。
```

### 4. 第一批最该补的回归测试

建议优先补这些，价值最高：

1. `readCachedImage('m1')` 不允许读到 `m10`。
2. 后台图片分析必须写回 `guild::user` 会话，而不是 `guild` 会话。
3. 同一用户连续发多张图，分析结果不能替换错 `[图片]`。
4. `DONGXUELIAN_AI_DATA_DIR` 必须落到预期 data 目录，不能漂回包内 `data`。
5. Agent 工具失败、空回复、reasoning-only 时，最终 QQ 回复不能空。
6. Dashboard 敏感写接口无 admin token 必须 403。
7. 日报 Puppeteer 渲染失败时，必须释放浏览器并给用户失败提示。
8. 语音克隆的 asset id 不存在时，必须回退或报清晰错误，不能静默用错人格音色。
9. 搜索失败时不能编造结果，必须明确失败或降级。
10. 依赖版本必须锁住 `@satorijs/core@3.7.0`。

### 5. Mock 边界建议

可以 mock：

- 模型 API。
- QQ / NapCat 网络。
- 外部网页请求。
- 浏览器启动。
- 时间。
- 临时 data 目录。

尽量不要 mock：

- `getConversationKey()`。
- `saveConversationTurn()`。
- `image-store`。
- Agent 路由。
- Dashboard 鉴权逻辑。
- 路径安全函数。
- data-dir 解析逻辑。

隐藏 bug 往往发生在内部模块之间的 key、状态、顺序不一致上。如果把这些都 mock 掉，测试很容易“看起来很稳，其实没测到”。

### 6. 异步和落盘测试必须确定性

图片、会话、Agent 队列、日报、Dashboard 配置都涉及异步和文件系统。测试要尽量做到：

- 每个测试使用独立临时 `DONGXUELIAN_AI_DATA_DIR`。
- 修改环境变量后清理相关 `require.cache`。
- 等待队列实际完成，而不是靠固定 sleep 碰运气。
- 明确读取磁盘文件检查内容。
- 同时检查内存缓存和磁盘是否一致。
- 测试结束后恢复环境变量和模块缓存。

### 7. 建议增加 Linux regression 层

可以先很轻，不必一步到位。

建议命令：

```bash
npm run test:linux-regression
```

第一阶段可覆盖：

- Node 版本是否支持当前用到的 `fetch`、`TextDecoder` 等能力。
- `/proc/meminfo` 读取失败时浏览器/日报是否安全降级。
- `DONGXUELIAN_AI_DATA_DIR` 是否为预期绝对路径。
- `@satorijs/core` 是否等于 `3.7.0`。
- Chromium 不存在时日报和 browser_action 是否给出清晰错误。
- `restart.sh` 是否使用本地 `node_modules/koishi/bin.js`。

## 四、数据一致性优化

### 1. 统一 key 设计

当前项目里存在多类 key：

- `channelKey`：群/频道级。
- `conversationKey`：群/频道 + 用户级。
- `userId`：用户级。
- `messageId`：消息级。
- 文件安全 key：用于落盘。

建议写一份 `docs/data-key-contract.md` 或放进 `TESTING.md`：

| 数据 | key 粒度 | 典型文件 |
|------|----------|----------|
| 会话历史 | `channelKey::userId` | `conversations/*.json` |
| 图片历史 | `channelKey + messageId` | `image-history/*.json` |
| 图片缓存 | `channelKey/messageId.ext` | `image-cache/*/*` |
| 群共享上下文 | `channelKey` | 内存 / today-cache |
| 用户记忆 | `userId + channelKey` | memory 相关文件 |
| 人格配置 | `channelKey / userId` | persona 相关文件 |

每新增功能前先确认：它需要群级、用户级还是消息级 key。

### 2. 图片历史需要补上下文归属

当前图片历史只知道 `channelKey` 和 `messageId`，但写回会话需要知道 `conversationKey` 或 `userId`。

建议图片 entry 至少包含：

```json
{
  "url": "...",
  "file": "...",
  "ts": 123,
  "userId": "123456",
  "conversationKey": "guild::user",
  "analyzed": false,
  "analysis": null
}
```

这样后台分析完成后可以写回正确用户的会话历史。

### 3. 图片占位符需要可定位

只找最近一条裸 `[图片]` 风险很高。用户连续发多张图时，分析完成顺序可能和发送顺序不同。

建议把历史文本从：

```txt
[图片]
```

升级为内部可定位格式，例如：

```txt
[图片 id=messageId]
```

或者在 message 对象里保存 metadata，不把 metadata 混在自然语言文本中。

展示给模型时再转成：

```txt
[图片]: 分析结果
```

### 4. 文件名安全规则要统一

现在有些地方允许 `:`，有些地方不允许。Linux 可以接受冒号，但跨平台和工具链会有差异。

建议统一做两个函数：

- `safeRuntimeKey()`：运行时 Map key，不需要文件安全。
- `safeFileKey()`：落盘文件名，必须跨平台安全。

然后全项目禁止临时手写：

```js
String(key).replace(...)
```

这样可以减少一类非常隐蔽的数据漂移 bug。

## 五、Linux 服务器运行优化

### 1. 部署前状态收敛

每次部署前建议固定检查：

```bash
git status --short
node -e "console.log(require('@satorijs/core/package.json').version)"
test -d /root/koishi-app/data && echo data-ok
```

必须确认：

- 本地改动是否都明确属于本次部署。
- 服务器是否有未保存修改。
- 不会把 `AUDIT-REPORT-*.md`、`.claude/`、`*.tgz` 推送或打包进仓库。
- 本次是否经过用户明确同意部署。

### 2. 部署后健康检查固定化

部署后不要只看进程存在，至少检查：

- Koishi 端口监听。
- Dashboard 端口监听。
- 日志中出现 `adapter connect to server`。
- `DONGXUELIAN_AI_DATA_DIR` 指向根 data。
- `@satorijs/core` 仍是 `3.7.0`。
- Dashboard 能打开基础页面。
- QQ 侧能收发一条低风险测试消息。

建议把这些整理成只读脚本，例如：

```bash
scripts/healthcheck-server.sh
```

但要注意：执行部署、重启、推送仍必须先经用户确认。

### 3. 运行态版本可追踪

建议启动时在日志写入：

- package version。
- git commit hash。
- Node version。
- Koishi version。
- `@satorijs/core` version。
- `DATA_DIR`。
- Dashboard host/port。
- Agent tool mode。

这样以后服务器出现问题，不需要猜“跑的是哪一版”。

### 4. data-dir 漂移防线继续加强

所有运行入口必须明确：

```bash
KOISHI_DIR=/root/koishi-app
DONGXUELIAN_AI_DATA_DIR=/root/koishi-app/data
```

建议增加启动时强校验：

- 如果 `DONGXUELIAN_AI_DATA_DIR` 为空，打印 warning。
- 如果 data-dir 指向包内 `packages/.../data`，打印 error 或拒绝启动。
- 如果检测到包内 data 有真实运行数据，提示迁移或软链接状态。

### 5. 日志结构化一点点

不用上复杂平台，先统一日志字段就很有用：

```txt
[module=image-store] [channel=xxx] [message=yyy] cache miss
[module=agent] [tool=web_search] [ok=false] reason=timeout
[module=dashboard] [route=/api/config] admin=false status=403
```

重点是让日志能回答：

- 哪个模块错了？
- 哪个 channel/user/message 相关？
- 是失败、降级、拒绝还是超时？
- 有没有写入磁盘？

## 六、Agent 系统优化

### 1. 工具执行结果要分层

建议 Agent 工具结果统一结构：

```js
{
  ok: true,
  text: "...给模型看的摘要...",
  data: {...机器可读数据...},
  warnings: [],
  source: "web_search",
  degraded: false
}
```

这样可以避免工具返回字符串时，模型分不清是事实、错误、警告还是内部提示。

### 2. 空回复和 reasoning-only 必须是硬防线

Agent 最终输出给 QQ 时，必须保证：

- 不为空。
- 不只包含 reasoning。
- 不泄露工具内部日志。
- 不泄露 system prompt。
- 工具失败时不编造。

建议这条链路有专门 regression。

### 3. 危险工具确认链路继续收紧

建议每个危险工具都明确：

- 是否默认对 QQ 开启。
- 是否默认对 Dashboard 开启。
- 是否需要确认。
- 确认后执行时是否带齐上下文，比如 `bot`、`channelKey`、`userId`。
- 执行失败是否能把错误反馈给用户。

尤其要关注“确认后执行”和“普通自动执行”是否传入了不同 context。

### 4. 工具权限配置要有可视化差异

Dashboard 上最好能清楚区分：

- 只读工具。
- 外部网络工具。
- 文件写工具。
- shell / browser / javascript 高风险工具。
- 默认 QQ 可用。
- 默认 Dashboard 可用。

避免未来新增工具时无意中开放到 QQ。

### 5. Agent 记忆与聊天记忆边界

Agent 工具链结果、普通聊天历史、长期记忆应该分清：

- 工具结果是事实材料，不一定进入长期记忆。
- 用户明确要求记住，才写长期记忆。
- 模型推测出的结论不能自动变成用户事实。
- 搜索结果摘要不能污染人格或用户画像。

建议为自动记忆加“证据来源”和“置信度”字段。

## 七、图片与多模态优化

### 1. 图片缓存必须精确匹配

当前已确认 `m1` 会误读 `m10`。修复后建议测试：

- 只存在 `m10.png` 时读 `m1` 返回 null。
- 同时存在 `m1.jpg` 和 `m10.png` 时读 `m1` 返回 `m1.jpg`。
- 多扩展名并存时有明确优先级，或禁止并存。

### 2. 图片分析结果要进入后续上下文

用户问“刚才那张图是什么”，模型应能拿到：

- 图片 messageId。
- 图片发送者。
- 图片时间。
- 分析结果。
- 用户追问和图片之间的关联。

建议把图片历史作为独立上下文注入，而不仅依赖替换会话文本。

### 3. 图片下载链路分级

建议明确优先级：

1. 本地缓存。
2. NapCat `file`。
3. 原始 URL。
4. 失败提示。

每级都记录日志，不要静默吞掉所有错误。

### 4. 分析模型不支持视觉时要记录

如果当前模型不支持视觉，后台分析会跳过。建议：

- image-history 标记 `analysisStatus: skipped_no_vision_model`。
- 用户追问时能明确说当前模型不支持图片分析，而不是装作看过。

## 八、语音与 TTS 优化

### 1. 克隆音色资产继续强化元数据

建议每个 voice asset 包含：

- assetId。
- displayName。
- persona 引用列表。
- 原始文件名。
- 文件大小。
- 上传时间。
- 创建者。
- 模型名。
- 试听文本。
- 最近一次使用时间。

这样以后排查“为什么这个人格声音变了”会容易很多。

### 2. TTS 模型输入约束写清楚

项目规则里已经明确：

- 普通 TTS 用 `mimo-v2.5-tts`。
- 语音克隆必须用 `mimo-v2.5-tts-voiceclone`。

建议把这些约束也写进测试：

- 克隆资产存在时必须使用 voiceclone 模型。
- 普通 TTS 不应误用 voiceclone。
- voice asset id 失效时有清晰错误或回退策略。

### 3. 语音链路的真实 e2e 要单独分层

语音链路涉及外部扣费和文件转换，不适合每次 CI 全跑。

建议分三层：

- 静态测试：参数、模型名、配置。
- mock 测试：上传、选择、保存、删除、引用检查。
- 手动真实测试：外部 API、真实音频、真实发送。

## 九、Dashboard 优化

### 1. Admin API 封装一致性

所有敏感接口都必须经过同一层封装：

- GET 敏感信息也要带 `X-Admin-Token`。
- POST / PUT / DELETE 默认需要 token。
- 403 时前端弹 AdminDialog。
- 非 403 不要误弹密码框。

建议给 `frontend/src/api.js` 做一次接口表：

| 方法 | 路径 | 是否需要 admin | 当前封装 |
|------|------|----------------|----------|
| GET | `/admin-ids` | 是 | 需要确认 |
| PUT | `/config` | 是 | 是 |
| PUT | `/keys` | 是 | 是 |
| POST | `/deploy/run` | 是 | 是 |

### 2. 异步按钮统一交互

项目规则里已经写了：

- 立即改变按钮文字。
- 禁用按钮。
- 完成后滚动到结果区域。
- 取消时清除 loading。

建议抽一个小 helper 或 composable，避免每个组件自己写一套。

### 3. Dashboard 写操作分两种 smoke

建议把 smoke 分成：

- 只读 smoke：打开页面、切换 tab、查看列表，不改状态。
- 写入 smoke：保存配置、上传文件、部署、重启等，需要明确人工确认或测试环境。

现在最怕的是测试脚本名叫 smoke，但里面混入真实写操作。

### 4. 前端构建不等于运行正常

每次改 Vue 组件后，仍建议真实浏览器打开对应页面。

至少检查：

- 控制台无 error。
- 页面没有白屏。
- 关键按钮能点击。
- Admin 弹窗 z-index 足够。
- 结果区域能显示。
- 移动端不严重溢出。

## 十、日报与浏览器优化

### 1. Puppeteer 资源释放继续做硬测试

日报和 browser_action 都依赖 Chromium。必须保证：

- `browser.close()` 在 finally。
- `page.close()` 在 finally。
- 超时后能释放。
- 并发超过限制会排队或拒绝。
- 低内存时拒绝启动。

建议用 fake browser 写测试，模拟：

- launch 成功，screenshot 失败。
- setContent 超时。
- browser.close 抛错。
- 内存不足。
- 浏览器路径不存在。

### 2. 日报失败不应污染冷却

日报生成失败时，要确认：

- 用户能收到失败提示。
- cooldown 不应误认为成功。
- 队列 slot 会释放。
- 日志保留失败原因。

这也是一个值得写 regression 的点。

### 3. 外部头像和资源要有降级

日报模板里会引用 QQ 头像。建议确认：

- 外部头像加载失败不影响截图。
- 广告/追踪资源被拦截。
- 图片过慢时有超时。
- 页面高度有上限。

## 十一、安全优化

### 1. 默认按“会泄露”审视新功能

新增以下功能时默认先补防线：

- 浏览器。
- 抓取网页。
- 文件读写。
- shell。
- JS 执行。
- 上传下载。
- 长文本注入。
- 自动记忆。
- 定时任务。

每个外部资源必须有退出口：

- `browser.close()`。
- `page.close()`。
- `clearTimeout()`。
- `abortController.abort()`。
- 临时文件清理。

### 2. SSRF 防线继续统一

当前 web_fetch 和 browser_action 都有 SSRF 防线，但建议统一抽象：

- URL 协议限制。
- 用户名密码禁止。
- localhost / 内网 / 保留地址禁止。
- DNS 解析到内网禁止。
- redirect 后重新校验。
- response.url 再校验。

避免两个工具以后修一个漏一个。

### 3. Prompt injection 防线分层

建议区分：

- 用户输入越狱。
- 网页内容越狱。
- 工具结果越狱。
- 图片 OCR / 视觉结果越狱。
- 历史记录越狱。

不同来源进入模型时应该有不同 system 包裹，尤其是网页和工具结果必须明确“是不可信资料，不是指令”。

### 4. 文件写工具要有双重边界

Agent 文件写工具建议同时满足：

- path guard 限制目录。
- 工具权限配置允许。
- 危险工具确认通过。
- 写入前展示摘要。
- 写入后返回 changed files。

并且测试 path traversal、符号链接、绝对路径、大小限制。

## 十二、架构优化

### 1. 不要继续把新逻辑塞进 `index.js`

`index.js` 应保持为 Koishi 接入层：

- 解析 session。
- 判断是否命令。
- 交给 handler / chat / agent。
- 发送结果。

新功能优先独立模块。只有补旧行为且非常贴近入口时才改 `index.js`。

### 2. `chat.js` 保留主流程所有权，但继续瘦身

`chat.js` 可以继续拥有模型调用主流程，但旁支能力应拆出：

- 图片上下文构建。
- Agent 结果转述。
- 话题切换检测。
- jailbreak 处理。
- 记忆确认处理。
- 输出守卫。

不要为了拆而拆。判断标准是：函数超过 50 行且职责不单一，或新增逻辑超过 10 行明显属于旁支。

### 3. Dashboard 大组件逐步拆

建议优先拆：

- `DeployPanel.vue`。
- `PersonaPanel.vue`。
- `AgentPanel.vue`。
- `SettingsPanel.vue`。

拆分方向：

- API 调用 composable。
- 表单状态 composable。
- 列表组件。
- Modal 组件。
- 操作结果组件。

但不要一轮大重构。每次只拆一个明确边界，并跑对应页面。

### 4. 配置读写统一

现在有 runtime-config、agent config、Dashboard settings、voice assets 等多种配置。建议逐步统一：

- 读小 JSON 文件时有大小上限。
- 写 JSON 使用 tmp + rename。
- 写失败返回明确错误。
- 所有配置文件路径集中在 constants 或对应 config 模块。
- Dashboard 不直接散落 `fs.writeFileSync` 到各处。

## 十三、文档与流程优化

### 1. 文档里的启动命令统一

所有文档都应该统一到：

```bash
node node_modules/koishi/bin.js start
```

并明确：

```bash
KOISHI_DIR=/root/koishi-app
DONGXUELIAN_AI_DATA_DIR=/root/koishi-app/data
```

避免新人照旧文档启动，导致 data 写回包内目录。

### 2. 每次修复写“事故卡片”

建议每个确认 bug 修复后写一小段：

```md
### 事故：图片 m1 误读 m10

- 真实失败输入：
- 失败现象：
- 根因：
- 修复：
- 回归测试：
- 未覆盖风险：
```

这个比单纯 commit message 更适合长期维护。

### 3. 提交前检查清单

每次准备 commit 前：

- `git status --short`。
- 确认没有误带 `AUDIT-REPORT-*.md`。
- 确认没有误带 `.tgz`。
- 确认没有误带 `.claude/`。
- 跑对应测试。
- commit message 写清楚位置、原因、修复。

### 4. 部署前必须人工确认

这个规则继续保持：

- 不擅自部署。
- 不擅自重启。
- 不擅自 push。
- 不擅自 `git reset --hard`。
- 部署前确认服务器没有未保存修改。

## 十四、建议的阶段计划

### Phase 1：止血回归层

目标：把已经确认的隐藏 bug 固化成 regression。

建议任务：

1. 新增 `test:regression`。
2. 加图片缓存前缀误读测试。
3. 加图片分析写回 conversationKey 测试。
4. 加 Agent 空回复兜底测试。
5. 加 Dashboard admin 403 测试。
6. 把四问写进测试注释或报告。

验收标准：

- 确认 bug 修复前测试失败。
- 修复后同一测试通过。
- `npm test` 能包含 regression。

### Phase 2：数据一致性修复

目标：消除 key 不一致和 data-dir 漂移。

建议任务：

1. 统一 safe file key。
2. 图片历史补 `conversationKey` 或 `userId`。
3. 图片占位符按 messageId 定位。
4. 启动时输出 data-dir。
5. 阻止服务器运行态读包内 data。

验收标准：

- 图片追问稳定命中正确图片。
- 同一用户多图不会替换错。
- 服务器日志能明确 data-dir。

### Phase 3：服务器健康检查

目标：部署后能快速知道是否真的健康。

建议任务：

1. 增加只读 healthcheck 脚本。
2. 输出 Koishi / Dashboard / core 版本。
3. 检查端口和 `adapter connect to server`。
4. 检查 Dashboard 基础 API。
5. 检查 data-dir 和关键文件权限。

验收标准：

- 不需要猜服务器跑的是哪版。
- 部署后 1 分钟内能判断成功或失败。

### Phase 4：Agent 和 Dashboard 稳定性

目标：减少工具链和管理界面的隐性风险。

建议任务：

1. 工具结果结构化。
2. 危险工具权限矩阵可视化。
3. Dashboard admin API 封装统一。
4. Dashboard 写操作 smoke 与只读 smoke 分离。
5. Agent 自动记忆增加证据来源。

验收标准：

- 工具失败不空回复、不编造。
- 写操作不混入普通 smoke。
- 新增工具不会意外开放到 QQ。

### Phase 5：架构减压

目标：减少大文件继续膨胀。

建议任务：

1. 从 `chat.js` 抽旁支能力。
2. 从 `index.js` 抽入口辅助逻辑。
3. Dashboard 大组件按边界拆。
4. 配置读写统一。
5. 对关键模块补模块边界说明。

验收标准：

- 新功能不需要总改 `index.js`。
- `chat.js` 主流程更清晰。
- Dashboard 页面修改后更容易局部验证。

## 十五、优先级总表

| 优先级 | 项目 | 原因 |
|--------|------|------|
| P0 | 图片缓存精确匹配 | 已确认会读错图片，影响用户信任。 |
| P0 | 图片分析写回正确 conversationKey | 已确认会写不回用户会话，影响后续追问。 |
| P0 | 新增 regression 测试层 | 修复后必须防止同类 bug 回来。 |
| P1 | data-dir 启动强校验 | 服务器长期运行最怕读错数据目录。 |
| P1 | Agent 空回复和工具失败兜底 | 直接影响 QQ 用户体验。 |
| P1 | Dashboard admin API 封装一致 | 避免后续页面接入时踩 403 或误暴露。 |
| P1 | 日报/浏览器资源释放测试 | 长跑服务器稳定性关键。 |
| P2 | 运行态版本日志 | 排查服务器问题时减少猜测。 |
| P2 | 配置读写统一 | 降低 silent failure。 |
| P2 | Dashboard 写入 smoke 分层 | 避免测试误改生产状态。 |
| P3 | 大文件逐步拆分 | 提升长期维护效率。 |
| P3 | 文档命令统一 | 降低人为部署错误。 |

## 十六、最终建议

最推荐的下一步不是大重构，而是：

1. 先把本轮确认的两个图片 bug 写成 regression。
2. 再修这两个 bug。
3. 修完后跑 quick、scenario、regression。
4. 把测试四问写入修复报告。
5. 然后再进入下一轮隐藏 bug 审计。

这样每一轮都会留下“钉子”：发现一个真实 bug，固定一个测试，修掉一个风险。几轮下来，项目就会从“能跑的复杂项目”变成“有自我防回归能力的长期项目”。
