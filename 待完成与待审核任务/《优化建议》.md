## P0：安全与权限

### 1. `edit_file` 可绕过安全配置黑名单

证据：

- `packages/koishi-plugin-dongxuelian-ai/lib/agent/path-guard.js:13-17` 定义了 `WRITE_BLOCKED_BASENAMES`，包含 `ai-tool-mode.txt`、`ai-admin-ids.json`、`ai-tool-config.json`。
- `path-guard.js:87` 只在 `assertNewAgentPathInsideRoots()` 检查黑名单。
- `packages/koishi-plugin-dongxuelian-ai/lib/agent/tools/edit-file.js:48` 只走 `assertExistingAgentPathInsideRoots()`，随后 `edit-file.js:67` 直接写回。

影响：Dashboard Agent 的 `edit_file` 是危险工具，但一旦被允许执行，就能编辑现有安全配置文件，修改 admin 列表或工具开关，形成权限提升。

更好修复方案：

- 在 `path-guard.js` 导出 `assertNotWriteBlockedBasename(abs, label)`。
- `edit-file.js` 在写入前显式调用该函数。
- `write-file.js`、`append-file.js` 也显式调用一次，保留防御一致性。
- 回归测试：对 `ai-admin-ids.json`、`ai-tool-mode.txt`、`ai-tool-config.json` 执行 `edit_file`，断言报“禁止写入安全配置文件”。

### 2. 用户媒体 URL 下载缺 SSRF 防线

证据：

- `packages/koishi-plugin-dongxuelian-ai/lib/api.js:473-533` 的 `downloadImageAsBase64()` 只检查协议前缀、状态、content-type 和大小，没有 localhost、私网、保留地址、DNS 解析到私网等校验。
- 调用点包括 `vision.js:117`、`image-analyzer.js:58`、`agent/tools/analyze-image.js:57`。
- `packages/koishi-plugin-dongxuelian-ai/lib/voice.js:33-49` 的 `downloadVoiceFile()` 也只按 `http/https` 下载，没有 URL guard。
- `voice.js:44` 流式超限时只 `req.destroy()` 并 `return`，没有立即清 timer 或 settle promise，可能拖到错误事件或 15 秒超时才结束。

影响：用户可通过图片/语音 URL 触发服务端请求内网地址；语音超大流还会额外占住 ASR 下载链路直到错误事件或超时收尾。

更好修复方案：

- 抽出共享 `public-url-guard`，复用 `agent/fetch-reader.js` 的 `validatePublicHttpUrl()`、`resolveAndValidateHostname()` 逻辑。
- 图片和语音下载前先校验协议、用户名密码、localhost、私网、保留地址、DNS 解析结果；如将来支持 redirect，每次 redirect 后也复查。
- 语音下载增加一次性 `finish()`，所有成功、失败、超时、超限、error、end 路径都只 settle 一次，并清理临时文件。
- 回归测试：localhost、127.0.0.1、IPv6 loopback、内网段、DNS 到内网、超大流。

### 5. Dashboard 日志普通登录可读且无统一脱敏

### 6. Agent shell 继承完整环境变量

### 7. 远程部署目标配置普通登录可读

证据：

- `packages/koishi-plugin-dashboard/lib/router.js:43` 对 Dashboard API 只先要求普通登录。
- `packages/koishi-plugin-dashboard/lib/routes/deploy.js:34-42` 的 `handleGetDeployConfig()` 没有 `requireAdmin`，会返回部署配置里的 `server`、`appDir`、`botRunning` 和本地 fingerprint。
- `packages/koishi-plugin-dashboard/frontend/src/api.js:158` 的 `fetchDeployConfig()` 使用普通 `get('/deploy/config')`，不带 admin。

影响：普通 Dashboard 登录用户可以读取远程部署目标的主机标识和应用目录这类运维信息。仓库规则明确禁止把真实服务器 host、SSH 用户、部署路径写入可提交文档；运行接口同样不应对低权限登录暴露这组信息。

## P1：可靠性与数据一致性

### 7. 日报失败会提前污染 cooldown

证据：

- `packages/koishi-plugin-daily-report/lib/index.js:130-135` 在发送“正在生成”后立刻 `cooldown.set(channelKey, Date.now())`。
- 后续 `analyzeWithAI()`、`renderReport()`、`session.send(image)` 失败都会让用户仍被成功 cooldown 拦住。

影响：一次失败会阻断用户立即重试。

更好修复方案：

- 成功 cooldown 只在最终图片发送成功后写入。
- 失败防刷用独立短 backoff，不复用成功 cooldown。
- 回归测试：模拟 AI 分析失败、渲染失败、图片发送失败，断言失败后可重试或只进入短失败 backoff。

### 8. cron 执行后保存失败会停止后续调度

证据：

- `packages/koishi-plugin-dongxuelian-ai/lib/agent/cron.js:162` timer 只 `runCronNow(...).catch(() => {})`。
- `cron.js:203-205` 先 `saveCrons()`、再 `appendHistory()`、最后 `scheduleCron(cron)`。
- 如果保存或历史写入抛错，下一次 `scheduleCron()` 不会执行，错误还会被外层吞掉。

影响：一次磁盘或 JSON 写入异常可让定时任务永久停摆。

更好修复方案：

- `runCronNow()` 把下一次 `scheduleCron(cron)` 放进 `finally`。
- 保存 `lastRunAt` 和 history 的失败单独记录，不阻断调度。
- 回归测试：mock `saveCrons()` 抛错，断言下一次 timer 仍被安排。

### 9. cron 持久化读改写无锁

证据：

- `packages/koishi-plugin-dongxuelian-ai/lib/agent/cron.js:114-139` 的 append/register/unregister 都是 read -> modify -> write。
- `cron.js:167-205` 的 `runCronNow()` 也先读旧快照，任务完成后再写回。
- 这些路径没有模块级写锁。

影响：并发注册 cron 与 cron 正在执行时，后写者可覆盖前写者，导致新增任务、lastRunAt 或 history 丢失。

更好修复方案：

- 增加 module 级写队列，例如 `let writeChain = Promise.resolve()`。
- register/unregister/appendHistory/runCronNow 的文件更新都通过同一写事务重新读最新文件后合并。
- 回归测试：并发注册两个 cron、并发触发两个 cron，断言都保留。

### 10. `compactWithLLM` 永远吃不到结构化摘要

证据：

- `packages/koishi-plugin-dongxuelian-ai/lib/agent/context.js:106-122` 期望 `requestFn()` 返回字符串。
- `packages/koishi-plugin-dongxuelian-ai/lib/api.js` 的模型请求返回 `{ type, content, reasoning }` 对象。
- `context.js:116` 的 `typeof summary !== 'string'` 导致成功返回对象也走 catch，退化为简单截断。

影响：Agent 长上下文压缩功能实际失效，长任务只保留最近消息。

更好修复方案：

- 兼容对象返回：`const summaryText = typeof raw === 'string' ? raw : raw?.content`。
- `tool_calls`、空 content、缺少 `## 目标` / `## 下一步` 时明确回退。
- 回归测试覆盖字符串、对象、空对象、tool_calls 四种返回。

### 11. cron 字段接受逗号/范围但静默误解析

证据：

- `packages/koishi-plugin-dongxuelian-ai/lib/agent/cron.js:67-78` 用 `parseInt()` 解析字段。
- `cron.js:92-100` 匹配时也用 `parseInt()`。
- `0,15,30,45` 被解析成 `0`；`1-5` 被解析成 `1`。

影响：用户以为配置了多个触发点，实际只在第一个数字触发。

更好修复方案：

- 要么完整支持逗号列表并返回 values 数组，要么明确 reject。
- 范围、别名等未支持语法必须报错，不能 `parseInt()` 吞掉。
- 回归测试：`0,15,30,45 * * * *` 正确触发四次或被明确拒绝；`1-5 * * * *` 必须报错。

### 12. 插件 dispose 未停止 cron scheduler

证据：

- `packages/koishi-plugin-dongxuelian-ai/lib/index.js:929-937` 的 dispose 清理了多个本模块 timer，但没有调用 `stopCronScheduler()`。
- `packages/koishi-plugin-dongxuelian-ai/lib/agent/cron.js:221-223` 已提供停止函数。

影响：插件 reload 后旧 cron timer 可能继续用旧 runtime 执行，造成重复发送或旧 bot 实例调用。

更好修复方案：

- dispose 中调用 `require('./agent/cron').stopCronScheduler()`。
- 同步排查 Agent 子模块定时器是否也需要 dispose 钩子。
- 回归测试：启动 cron 后触发 dispose，断言 cron timers 清空。

### 13. 根运行数据文件被 git 跟踪且服务器已被写脏

### 14. 昵称插件 JSON 保存没有原子写和写队列

证据：

- `packages/koishi-plugin-group-name-at/lib/index.js:173-179` 的 `saveStore()` 直接 `fs.writeFile(DATA_FILE, JSON.stringify(nicknameStore))`。

## P2：低风险正确性、体验与配置

### 16. 上传标称 8MB 与全局 body 上限错配

- `packages/koishi-plugin-dashboard/lib/paths.js:47` 图集文件上限为 8MB。

### 17. Dashboard Agent 历史默认持久化到 localStorage

证据：

- `packages/koishi-plugin-dashboard/frontend/src/components/AgentPanel.vue:264-267` 将最近 30 条历史写入 `dashboard_agent_history`。
- 服务器只读检查确认部署代码同样包含该存储。

影响：Agent 对话里可能包含文件路径、命令输出、日志摘要或配置片段，默认落到浏览器本地持久存储。

更好修复方案：

- 默认改为内存历史。
- 增加显式“记住本机历史”开关，并在退出登录/切换人格时清理。
- 存储前截断和 redactor。

### 18. OneBot endpoint 多处写死

证据：

- `packages/koishi-plugin-dongxuelian-ai/lib/api.js:384` 写死 `ws://127.0.0.1:8080/onebot/v11/ws`。
- `packages/koishi-plugin-dongxuelian-ai/lib/agent/tools/send-file-to-user.js:25` 同样写死。
- `packages/koishi-plugin-pet-bridge/lib/protocol.js:43` 也写死同一 endpoint。

影响：端口或路径变化时需要改源码；也不利于统一限制“只能 loopback”。

更好修复方案：

- 抽统一 `ONEBOT_WS_URL` 配置读取，默认仍为 loopback。
- 校验配置只能是 `127.0.0.1`、`localhost` 或显式允许的本机地址。
- 错误返回只说明来源和占位 endpoint，不输出 token。

### 19. `send_file_to_user` 对非数字 ID 产生 NaN

证据：

- `packages/koishi-plugin-dongxuelian-ai/lib/agent/tools/send-file-to-user.js:62-67` 对 `groupId` / `userId` 直接 `Number(...)`。

影响：非数字输入会把 `NaN` 传给 OneBot，错误信息延迟到下游，Agent 难以给出可读修正。

更好修复方案：

- 入参先用 `/^\d+$/` 校验。
- 失败时直接返回 `groupId/userId 必须为纯数字`。
- 回归测试：`groupId='abc'` 不连接 OneBot，直接失败。

### 20. Skill Pool frontmatter 仍是 LF-only

证据：

- `packages/koishi-plugin-dongxuelian-ai/lib/agent/skills/pool-service.js:34` 用 `^---\n...` 解析 Skill 元数据。

影响：CRLF 的 Skill 文件安装进 Skill Pool 时，元数据可能读不到，名称/描述/版本回退到目录名或空值。

更好修复方案：

- 改成 `^---\r?\n([\s\S]*?)\r?\n---`。
- 复用已有 `agent/skills.js` 或 `persona-schema.js` 的 frontmatter parser，避免再散落一套。
- 回归测试：CRLF `SKILL.*.md` 能正确读出 name/description/version。

### 21. `handlePostBotStart` 失败对前端不可见

证据：

- `packages/koishi-plugin-dashboard/lib/routes/bot.js:133-138` 异步执行 restart 命令，HTTP 永远返回 `{ ok: true }`。
- 失败只写日志。

影响：脚本不存在、平台不支持或启动失败时，用户界面仍显示“启动命令已发送”。

更好修复方案：

- 启动前检查脚本存在和平台能力。
- 短窗口内同步等待启动结果，或响应中明确要求用户跳日志页查看结果。
- 回归测试：脚本不存在时返回 400。

## P3：低优先级但真实存在

### 22. `loginFailMap` 可被大量独立 IP 堆积

证据：

- `packages/koishi-plugin-dashboard/lib/auth.js:12` 定义 `loginFailMap`。
- 删除只发生在同 IP 再次访问过期窗口时，或认证成功时：`auth.js:224-255`。

影响：大量一次性失败 IP 会长期占用 Map 项。风险低于权限 bug，但长跑服务仍应修。

更好修复方案：

- 增加定时清理过期失败记录。
- 增加硬上限，超限按最旧记录淘汰。
- 回归测试：注入大量 IP，推进时间后 size 回落。

### 23. `pet-bridge` 的 OneBot 参数也缺本地校验

证据：

- `packages/koishi-plugin-pet-bridge/lib/protocol.js:128` 对 `groupId` 直接 `Number(groupId)`。

影响：与 `send_file_to_user` 类似，错误会推迟到 OneBot 层。

更好修复方案：

- 与主插件共用 OneBot 参数校验 helper。
- 失败时在调用前返回明确错误。
