# 优化建议复核版

复核日期：2026-05-21

本文只保留仍需要追踪的优化项。原文中已经修复、已经有明确代码实现或已有测试防线的条目，已从待办正文删除，不再作为后续任务列出。

## 标签说明

- **[可疑]**：我认可这个风险方向，建议作为可疑点继续追踪；但不能仅凭感觉认定线上一定有 bug。
- **[待优化]**：已有实现或已有部分测试，还需要补强边界、文档或验证层。
- **[未做]**：当前基本没有独立落点，需要先补方向、入口或契约。
- **[已坐实]**：本轮代码实扫已经找到明确链路，可以按真实 bug 或真实边界缺口处理。

已确认修复的原条目已从本文删除，不再作为待办保留。

## 一、测试体系

### [可疑][未做] 独立 `test:regression`

认可原因：原文“追真实事故样本，不追覆盖率”的方向是对的。当前 `test:quick` 里已经混入了一些回归断言，但没有独立的 `test:regression` 入口，真实事故样本和静态防线仍混在一起。

完善方向：

- 新增 `npm run test:regression`，只放已经确认过的 bug 最小复现。
- `npm test` 改为包含 `quick + scenario + plugins + regression`。
- 每条 regression 用事故说明命名，例如 `image-cache exact message id`、`agent fallback non-empty reply`。
- 每条 regression 附四问：真实失败输入、断言的失败现象、mock 依赖、未覆盖真实链路。

### [可疑][待优化] 现有 quick 测试承担了太多职责

建议：

- 把“导出/常量/脚本/静态防线”继续留在 `test:quick`。
- 把图片、Agent、Dashboard 鉴权、TTS 这些真实 bug 防回归逐步迁到 `test:regression`。
- 保留少量重复静态检查可以接受，但不要让 quick 变成所有历史事故的堆叠桶。

### [可疑][未做] Linux regression 层

认可原因：服务器长期运行的失败点和开发环境不一样，应该单独有轻量检查。

完善方向：

- 新增 `npm run test:linux-regression`，只在 Linux 环境跑。
- 第一批检查：Node 能力、`/proc/meminfo` 读取失败降级、Chromium 缺失提示、`@satorijs/core@3.7.0`、运行数据目录是否为绝对路径。
- 所有示例路径用 `<YOUR_DATA_DIR>`，不要写真实服务器路径。

## 二、数据一致性

### [可疑][未做] 数据 key 契约文档

认可原因：当前代码里有 `channelKey`、`conversationKey`、`userId`、`messageId`、文件安全 key 多套粒度；虽然图片链路已修复，但后续功能仍容易再写错粒度。

完善方向：

- 新增 `docs/data-key-contract.md` 或放入现有测试说明文档。
- 明确每类数据的 key 粒度、落盘目录、是否允许跨用户共享。
- 新增功能前先回答：这是群级、用户级、群用户级，还是消息级数据。

建议表：

| 数据 | 推荐 key 粒度 | 说明 |
|------|---------------|------|
| 会话历史 | `channelKey::userId` | 用户私有上下文 |
| 群共享上下文 | `channelKey` | 只放群内短期话题 |
| 图片历史 | `channelKey + messageId` | 必须能反查发送者和会话 |
| 图片缓存 | `channelKey/messageId.ext` | 文件名必须精确匹配 |
| 用户记忆 | `channelKey + userId` | 不把模型推测直接当事实 |
| Agent 结果 | `channel + channelKey + userId` | 避免 Dashboard 和 QQ 混写 |

### [可疑][待优化] 文件安全 key 仍有多处分散实现

建议：

- 增加统一的 `safeRuntimeKey()` 和 `safeFileKey()`。
- 运行时 Map key 和落盘文件名不要共用同一个清洗函数。
- 禁止新代码继续手写 `String(key).replace(...)`。
- 第一阶段只收口新代码和高风险目录，不做全仓一次性大改。

### [可疑][待优化] 图片分析状态还不够细

当前图片历史能记录 `analyzed` 和 `analysis`，但视觉模型不支持、下载失败、模型空回复等情况还容易表现成“没有分析结果”。

建议：

- 增加 `analysisStatus`：`pending`、`done`、`download_failed`、`skipped_no_vision_model`、`model_empty`。
- 用户追问图片时，根据状态明确说“没下载到 / 当前模型不支持视觉 / 分析还没完成”。
- 不要只依赖替换会话文本，图片历史也应能作为独立上下文注入。

## 三、服务器运行态

### [可疑][待优化] data-dir 漂移防线还可以更硬

当前启动入口和脚本已经显式设置数据目录，也有 `scripts/seal-data-dir.sh`。剩余风险是：异常启动方式仍可能绕过脚本。

建议：

- 启动时打印 `DATA_DIR`，但不要把真实服务器地址写进可提交文档。
- 如果运行时数据目录指向包内 `packages/.../data`，服务器模式下直接 error 或强 warning。
- 健康检查里加入“当前进程真实环境变量”和“包内 data 是否为软链接/空目录”的只读检查。

### [可疑][未做] 只读服务器健康检查脚本

认可原因：运行态只看进程存在不够，必须能快速判断是否真的连上 QQ、Dashboard、数据目录和依赖版本。

完善方向：

- 新增只读脚本，例如 `scripts/healthcheck-server.sh`。
- 检查项：Koishi 端口、Dashboard 端口、日志关键字、`@satorijs/core` 版本、`DATA_DIR`、关键文件权限。
- 脚本只读，不执行部署、重启、清理或写文件。
- 文档示例统一使用 `<YOUR_SERVER_HOST>`、`<YOUR_DATA_DIR>`。

### [可疑][未做] 运行态版本可追踪

完善方向：

- 启动日志输出 package version、插件版本、Node version、Koishi version、`@satorijs/core` version。
- 能取到 git commit 时输出短 SHA；取不到时输出 `unknown`。
- Dashboard 状态页同步展示这些只读信息。

## 四、Agent 系统

### [可疑][待优化] 工具结果合约还不统一

当前工具执行层已有 `{ ok, text, error, fallbackTool }` 基础结构，但原文建议的机器可读结果、警告、降级标记还没有形成统一契约。

建议统一为：

```js
{
  ok: true,
  text: "给模型看的摘要",
  data: {},
  warnings: [],
  source: "tool_name",
  degraded: false
}
```

落地方向：

- 先让 registry 兼容旧字符串返回。
- 新工具强制返回统一对象。
- 搜索、浏览器、文件、TTS、图片工具优先补 `source/degraded/warnings`。
- Agent 回复生成时明确区分“工具事实”“工具失败”“模型推测”。

### [可疑][待优化] 空回复兜底已有，但缺独立 regression

当前 Agent 引擎已有 `(Agent 未获取到有效回复)` 兜底，QQ 链路也有一些非空断言。仍建议把“工具失败 / reasoning-only / 空模型回复”单独放进 regression。

建议：

- 模拟模型只返回 reasoning。
- 模拟工具成功但模型二轮空回复。
- 模拟工具失败后模型试图编造。
- 断言最终 QQ 回复非空、无内部日志、无 system prompt、无工具 JSON 泄露。

### [可疑][待优化] 危险工具权限可视化还可继续细分

Dashboard 已经能显示危险工具、外部网络工具、默认渠道和开关。后续建议继续补：

- 只读工具、外部网络工具、文件写工具、shell/browser/javascript 高风险工具分组。
- QQ 默认可用和 Dashboard 默认可用分列展示。
- 确认后执行时记录 pendingId、toolName、channel、userId，但不要记录敏感参数原文。

### [可疑][待优化] Agent 记忆需要证据边界

当前自动记忆已有 Dashboard / QQ 区隔和失败不写入测试，但“证据来源”和“置信度”还不够明确。

建议：

- 自动记忆只写用户明确表达、重复出现或人工确认的信息。
- 每条记忆增加 `source`、`sourceMessageId`、`confidence`、`createdBy`。
- 搜索结果、网页摘要、模型推测不能直接进入用户画像。

## 五、Dashboard

### [可疑][待优化] Admin API 封装需要接口表

当前前端 API 已支持 admin token，后端大量接口已有 `requireAdmin`。剩余问题是缺一张长期维护表，未来新增接口容易漏。

建议：

- 在测试或文档中维护接口表：路径、方法、是否需要 admin、前端封装是否传 admin。
- 给敏感 GET 也明确标注 admin，例如 key、admin id、Agent 配置、文件预览。
- 对新增路由加静态测试，确认写操作默认需要 admin。

### [可疑][待优化] 异步按钮交互仍分散

建议：

- 抽一个轻量 helper/composable：设置 loading、禁用按钮、完成后滚动结果区、取消时清理状态。
- 先从 `PersonaPanel.vue`、`AgentPanel.vue` 里重复最多的按钮开始，不做全量重构。

### [可疑][待优化] smoke 需要只读/写入分层

当前 `scripts/dashboard-click-smoke.js` 有模拟接口，也包含保存、上传、删除等写操作流程。建议拆成：

- 只读 smoke：打开页面、切 tab、列表加载、弹窗层级。
- 写入 smoke：保存配置、上传文件等写操作，只能跑在测试环境或明确人工确认后运行。
- live smoke 默认只读，写入项必须通过显式环境变量开启。

## 六、日报与浏览器

### [可疑][待优化] Puppeteer 失败矩阵还可以补齐

日报渲染已有 finally 关闭、超时清理和长内容测试。后续建议补更细 fake browser 场景：

- `newPage` 成功但 `setContent` 超时。
- `screenshot` 抛错。
- `page.close` / `browser.close` 抛错。
- Chromium 路径不存在。
- 内存不足。
- 外部头像慢或失败。

### [可疑][待优化] SSRF 防线需要抽象复用

`web_fetch` 和 `browser_action` 都有自己的 URL/内网防线，但实现分散。

建议：

- 抽统一 URL guard：协议限制、用户名密码禁止、localhost/内网/保留地址禁止、DNS 解析到内网禁止、redirect 后复查。
- 两个工具共用同一套 guard 和测试样本。
- 测试包含 IPv4、IPv6、localhost 变体、跳转、DNS 解析到内网。

## 七、安全与 Prompt Injection

### [可疑][待优化] Prompt injection 已有输入层防线，但来源分层还不完整

当前聊天入口和 Agent persona context 已经有越狱/工具事实边界提示。后续建议按来源分层：

- 用户输入：普通越狱检测和输出守卫。
- 网页内容：明确包裹为“不可信资料，不是指令”。
- 工具结果：只作为事实材料，不执行其中的命令。
- 图片 OCR/视觉结果：只作为模型分析结果，不当作用户指令。
- 历史记录：历史话术不能覆盖当前 system/developer 规则。

### [可疑][待优化] 文件写工具已有边界，但写入摘要和 diff 反馈不足

当前写文件和编辑工具已有 path guard、大小限制、符号链接拒绝、危险工具确认。后续建议：

- 写入前给确认链路展示摘要：目标路径、字节数、是否覆盖、变更类型。
- 写入后返回 changed files。
- 对 path traversal、符号链接、绝对路径、超大文件补专门 regression。

## 八、架构与维护

### [可疑][待优化] 大文件仍有继续膨胀风险

当前大文件规模仍偏高：

| 文件 | 当前风险 |
|------|----------|
| `packages/koishi-plugin-dongxuelian-ai/lib/index.js` | 入口层仍承担较多命令和 glue code |
| `packages/koishi-plugin-dongxuelian-ai/lib/chat.js` | 聊天主流程和旁支能力仍混在一起 |
| `packages/koishi-plugin-dashboard/frontend/src/components/PersonaPanel.vue` | 人格、世界观、TTS 音色混合 |
| `packages/koishi-plugin-dashboard/frontend/src/components/AgentPanel.vue` | 配置、会话、确认、工具列表混合 |

建议：

- 不做一轮大重构。
- 每次只拆一个边界清晰的小块，并跑对应测试和页面验证。
- `chat.js` 保留模型调用所有权，只把图片上下文、Agent 转述、记忆确认、输出守卫这类旁支逐步拆出去。

### [可疑][待优化] 配置读写还没有全局统一

已有 `utils.writeJsonFile()` 和部分 atomic write，但 Dashboard 路由、conversation、token usage 等仍能看到分散写法。

建议：

- 小 JSON 统一大小上限、tmp + rename、失败返回明确错误。
- Dashboard 写配置不直接散落 `fs.writeFileSync`。
- 高风险配置先收口：API key、provider/model、Agent config、voice assets、admin ids。

## 九、文档与流程

### [可疑][待优化] 启动命令文档仍需继续清理

建议：

- 所有文档统一到项目内 Koishi binary。
- 所有服务器示例只写占位符：

```bash
KOISHI_DIR=<YOUR_APP_DIR> \
DONGXUELIAN_AI_DATA_DIR=<YOUR_DATA_DIR> \
node <YOUR_APP_DIR>/node_modules/koishi/bin.js start
```

- 不在可提交文档写真实 IP、真实用户、真实路径组合。

### [可疑][未做] 事故卡片制度化

认可原因：单靠 commit message 很难长期追踪“这个测试守的是哪次事故”。

完善方向：

- 在本地或可提交的安全文档中建立模板；可提交版本只能用脱敏输入和占位符。
- 每个确认 bug 修完后记录：真实失败输入、失败现象、根因、修复、回归测试、未覆盖风险。
- 真实服务器信息、真实 token、真实日志 URL 不进入事故卡片。

## 十、本轮隐藏 bug 扫描新增发现

扫描范围：日报生成、Dashboard 路由与前端 API 封装、Agent 浏览器/文件工具、语音 ASR 下载、运行脚本默认值、运行时 JSON 写入。以下是本轮扫描后认为值得继续追踪的隐藏风险。

### [可疑][待优化] 日报失败会提前污染 cooldown

扫描发现：日报命令在发送“正在生成”提示后立刻写入 cooldown，后续 AI 分析、HTML 渲染、截图或图片发送失败时，用户仍会被冷却限制拦住。

建议：

- cooldown 只在日报图片成功发送后写入。
- 如果需要防止失败重试刷屏，单独加短失败 backoff，不复用成功 cooldown。
- 增加 regression：模拟 `analyzeWithAI` 失败、`renderReportImage` 失败、`session.send(image)` 失败，断言失败后可以立即重试或只触发短 backoff。

### [可疑][待优化] Dashboard 部分只读/写入接口鉴权边界需要重新确认

扫描发现：Dashboard 已有大量 `requireAdmin`，但仍存在几类边界不一致风险：部分敏感只读接口未显式 admin，图集上传/删除/样式修改接口也没有在路由层看到统一 admin 校验。

建议：

- 为所有 Dashboard API 建一张接口矩阵：路径、方法、是否写入、是否敏感、后端是否 `requireAdmin`、前端封装是否传 admin。
- 图集如果设计为公开能力，需要在文档里写清楚公开原因、文件大小/格式/频率限制和误删恢复方式。
- 如果图集只应管理员操作，上传、删除、样式修改都应补 admin，并加 403 触发 AdminDialog 的页面回归。
- 敏感只读接口，例如 key 用量、fallback、日志配置、限流配置，需要明确是否允许未登录读取。

### [可疑][待优化] 语音 ASR 下载链路缺少统一 URL guard

扫描发现：语音转写会从消息里的 record URL 下载音频，目前主要限制协议前缀、超时和大小，没有复用网页工具已有的 localhost、内网、保留地址、DNS 解析和跳转防线。

建议：

- 明确 record URL 的信任边界：只信任适配器生成的本地安全 URL，还是允许用户文本里传入任意 URL。
- 如果允许任意 URL，复用统一 URL guard，并覆盖 localhost、内网地址、重定向、超大文件、慢响应测试。
- 如果只信任适配器 URL，文本里解析到的 URL 不应直接进入下载链路，或者必须走更严格校验。

### [可疑][待优化] 浏览器工具 redirect 后的最终目标防线还需补强

扫描发现：浏览器工具打开 URL 前会做协议、账号密码、内网地址和 DNS 检查，也在请求完成后观察远端地址；但跳转后的最终 URL 和请求发起前拦截还需要更明确的统一策略。

建议：

- URL guard 抽成共享模块，导航前、redirect 后、每次 request 前都能复查。
- `openUrl`、搜索入口、新标签打开入口使用同一套 guard。
- regression 覆盖：公网 URL 302 到 localhost、DNS 解析到内网、IPv6 localhost、带用户名密码 URL、点击后跳转到内网。

### [可疑][待优化] 运行时 JSON 写入仍存在半写入和 silent failure 风险

扫描发现：会话、图片历史、Agent 文件工具、用户时区、部分配置和音色资产仍有直接 `writeFile` / `writeFileSync` 或 catch 后静默返回的写法。部分写法已有 tmp + rename，但失败回退仍可能删除旧文件后再 rename。

建议：

- 建一个统一的运行时 JSON 写入 helper：大小上限、tmp 写入、fsync 可选、rename、失败保留旧文件、错误返回给调用方。
- conversation、image-history、agent-user-timezones、voice-assets、Dashboard 配置先接入。
- 对 Agent 写文件工具，至少给危险写入链路补“写入前摘要 + 写入后 changed files + 失败原因”。
- regression 覆盖：写入中断、rename 失败、JSON 文件被截断、权限不足、旧文件不应丢失。

### [可疑][待优化] Agent 发送文件工具的 OneBot endpoint 仍是固定默认

扫描发现：Agent `send_file_to_user` 工具直接连接本机 OneBot WebSocket。默认使用本机地址是合理方向，但端口和 endpoint 还需要支持环境变量或配置覆盖。

建议：

- 增加 `ONEBOT_WS_URL` 或专用 Dashboard/Agent 配置项，默认仍可指向本机。
- 不允许配置成公网地址，除非显式通过 URL guard 或本机白名单。
- 连接失败时在工具结果里返回“可手动发送的文件路径”和当前 endpoint 来源，但不输出 token。

## 十一、第二轮隐藏 bug 扫描新增发现

扫描范围：Dashboard 请求体上限、图片下载、日志展示、Agent shell 执行环境、Dashboard Agent 前端历史缓存。以下是第二轮补扫后新增的可疑点。

### [可疑][待优化] 上传标称大小和全局请求体上限可能不一致

扫描发现：Dashboard 全局 `collectBody` 默认请求体上限小于等于 10MB，而图集标称图片上限是 8MB。图片上传走 base64 + JSON 后会膨胀，实际请求体可能超过全局上限，导致用户看到“支持 8MB”但实际接近上限的图片先被 413 拦截。

建议：

- 上传类接口不要只看文件二进制上限，也要计算 base64 和 JSON 包装后的请求体上限。
- 图集、TTS 克隆音频、cookie 上传分别维护“文件上限”和“请求体上限”的对应关系。
- 前端上传前按同一算法预估请求体大小，错误提示区分“文件过大”和“请求体过大”。
- regression 覆盖：7.5MB、8MB、8MB+1 byte 图片上传；TTS 克隆音频接近上限；缺少 `content-length` 的流式请求。

### [可疑][待优化] 图片分析下载链路还没有复用统一 URL guard

扫描发现：图片分析和 Agent 历史图片分析会调用图片 URL 下载函数；当前函数有协议、状态码、类型、大小和超时限制，但没有看到 localhost/内网/保留地址、DNS 解析、跳转目标复查等完整防线。

建议：

- 把图片下载、语音 ASR 下载、`web_fetch`、`browser_action` 的 URL 校验统一成共享 guard。
- 图片 URL 如果来自 OneBot 适配器，应明确标记为可信来源；如果来自用户文本或历史记录，必须走完整 URL guard。
- regression 覆盖：图片 URL 指向 localhost、内网 IP、IPv6 localhost、302 到内网、内容类型伪装、超大响应无 `content-length`。

### [可疑][待优化] 运行日志返回前缺少统一脱敏层

扫描发现：日志中心会返回原始 Koishi 日志文本。即使入口只开放给 Dashboard 已登录用户，日志里仍可能包含 token、cookie、代理地址、密钥前缀或第三方错误返回。

建议：

- Dashboard 所有“运行日志返回给前端”的路径先经过统一 redactor。
- redactor 覆盖：API key 形态、管理员令牌形态、NapCat 令牌形态、浏览器凭据、认证头、代理账号密码、私有 URL。
- 保留调试价值：只显示类型、长度、末尾 4 位或 hash，不显示原文。
- regression 用假 token、假 cookie、假私有 URL 写入日志，断言 API 返回中无原文。

### [可疑][待优化] Agent shell 工具继承完整环境变量

扫描发现：Agent shell 工具执行时把 `process.env` 整体传给子进程。虽然 shell guard 会阻止读取 `/proc/*/environ` 等明显危险命令，但普通命令、第三方工具或报错输出仍可能间接暴露环境变量。

建议：

- shell 工具默认使用白名单 env，只传 `PATH`、必要 locale、项目运行所需最小变量。
- 对确实需要的变量显式加入 allowlist，不传 API key、token、cookie 等敏感项。
- stdout/stderr 返回前同样经过 redactor。
- regression 覆盖：命令输出环境变量、子进程报错带 env、超时输出、不同系统 shell。

### [可疑][待优化] Dashboard Agent 聊天历史保存在 localStorage

扫描发现：Dashboard Agent 前端会把最近聊天历史保存到 `localStorage`。这能提升体验，但如果用户让 Agent 读取日志、配置或粘贴敏感内容，浏览器本地会残留这些文本。

建议：

- Agent 历史默认只保存在内存，或提供“记住本机历史”的显式开关。
- 保存前做长度限制和敏感词脱敏；退出登录、切换人格、管理员 token 失效时清理。
- UI 上提供一键清空，并提示历史只保存在本机浏览器。
- regression 覆盖：发送含 token 形态文本后刷新页面，确认 localStorage 不保留原文。

## 十二、最后一轮代码实扫新增发现

扫描范围：Dashboard 路由注册与前端 API admin 标记、用户消息图片/语音 URL 提取链路、日志脱敏覆盖。以下条目是最后一轮扫描后新增，或从“可疑”推进到“已坐实”的问题。

### [可疑][待优化][已坐实] 图集写接口普通登录即可上传、删除和改样式

扫描发现：`router.js` 对 Dashboard API 只先做普通 `authMiddleware`，图集路由里的 `POST /dashboard/api/gallery`、`DELETE /dashboard/api/gallery`、`PUT /dashboard/api/gallery/style` 处理函数没有调用 `requireAdmin`。前端封装也把 `uploadGalleryImage`、`deleteGalleryImage`、`updateGalleryImageStyle` 的 admin 参数设为 `false`。

这已经不是单纯“看起来可疑”：只要拿到普通 Dashboard 登录 token，就能进入图集写接口。除非图集被明确设计成普通登录用户可写，否则应按权限边界 bug 处理。

建议：

- 先定级：图集只读可以普通登录，上传、删除、样式修改默认应走 admin。
- 后端在三个写 handler 入口补 `requireAdmin`；前端对应 API 封装改为 admin 调用，让 403 触发 AdminDialog。
- regression 覆盖：普通 token 上传/删除/改样式返回 403；admin token 成功；图集图片读取接口仍按既定策略可读。
- 如果最终决定图集写入允许普通登录，必须补频率限制、误删恢复、审计日志和公开原因说明。

### [可疑][待优化][已坐实] 用户消息里的图片/语音 URL 可进入下载链路但缺少统一 URL guard

扫描发现：`extractImageUrls()` 会从 `[CQ:image ... url=...]`、`<img src="...">`、`<image|img|file url="...">` 提取 http(s) URL；`prepareVisionRequest()`、`appendVisionMessage()` 和图片分析队列会把这些 URL 交给 `downloadImageAsBase64()`。语音链路里 `extractVoiceUrls()` 会从 `[CQ:record ... url=...]` 和 `<record url="...">` 提取 URL，随后 `downloadVoiceFile()` 下载。

下载函数已有协议、状态码、类型、大小和超时限制，但没有看到 localhost、内网、保留地址、DNS 解析到内网、跳转最终目标复查这一类统一防线。也就是说，用户消息文本可以把外部 URL 带入图片识别或语音转写下载链路。

建议：

- 抽一个共享 `mediaUrlGuard`：协议限制、禁止用户名密码、禁止 localhost/内网/链路本地/保留地址、DNS 解析复查、redirect 后最终目标复查。
- 区分来源：适配器生成的 file/id 和用户文本里显式给出的 URL 不要混用同一信任级别。
- 图片下载、语音下载、Agent 图片分析、网页抓取和浏览器工具尽量复用同一套 guard，不再各写各的半套规则。
- regression 覆盖：用户消息携带 localhost、内网 IP、IPv6 localhost、DNS 解析到内网、302 跳转到内网、超大响应和慢响应。

### [可疑][待优化] 普通登录可读配置、统计和日志边界需要重新定级

扫描发现：部分 GET 接口在后端没有 `requireAdmin`，前端也用普通调用读取，例如 `GET /dashboard/api/config`、`GET /dashboard/api/providers`、`GET /dashboard/api/personas?name=...`、`GET /dashboard/api/logging`、`GET /dashboard/api/throttle`、`GET /dashboard/api/keys/usage`、`GET /dashboard/api/fallback`、`GET /dashboard/api/bot/activity`。其中有些可能是设计为普通 Dashboard 登录可见，但现在缺少一张明确的权限矩阵。

这条还不能整体直接定性为漏洞，因为要看产品预期：普通登录是否等同运维可见。如果普通登录只是低权限访问，这些接口就可能泄露模型配置、provider 地址、人格正文、日志开关、用量统计和运行日志内容。

建议：

- 建 Dashboard API 权限矩阵：路径、方法、返回敏感度、是否写入、是否需要 admin、前端封装是否带 admin。
- 把“普通登录可读”的接口显式列入白名单，并写明允许原因；其余敏感 GET 补 `requireAdmin`。
- regression 自动遍历矩阵：普通 token/admin token 分别请求，断言状态码和前端 admin flag 一致。
- 对返回内容分级脱敏：即使普通登录可读，也不返回完整 base URL、token 形态字符串、日志原文或人格私密段落。

### [可疑][待优化][已坐实] 日志脱敏覆盖不一致已坐实为实现差异

扫描发现：Agent `query_logs` 工具有 redactor，但规则主要覆盖 `api_key/token/authorization/password/secret` 这类 key-value 形态；Dashboard 日志中心的 `GET /dashboard/api/bot/activity` 会返回 `entries` 和 `lines`，没有看到同一层统一 redactor，而且前端 `fetchLogs()` 也是普通登录调用。

建议：

- 抽统一 redactor，Dashboard 日志、Agent 日志工具、shell stdout/stderr、工具错误返回都复用。
- 覆盖 standalone key 形态、Bearer 头、cookie、代理凭据、私有 URL、管理员令牌形态。
- regression 用假密钥、假 cookie、假私有 URL 写入测试日志，断言 Dashboard API 和 Agent 工具输出都没有原文。

## 十三、优先级

| P0 | Agent 空回复 / reasoning-only regression | [可疑][待优化] | 直接影响 QQ 用户体验 |

| P0 | 用户消息媒体 URL guard | [可疑][待优化][已坐实] | 用户文本可把图片/语音 URL 送入下载函数，缺内网、DNS 和跳转防线 |
| P0 | 日志/工具输出统一脱敏 | [可疑][待优化][已坐实] | Dashboard 日志内容和 Agent 工具输出都可能把敏感内容展示或缓存到前端 |

| P1 | data-dir 启动强校验 | [可疑][待优化] | 服务器长期运行最怕读错数据目录 |
| P1 | 只读健康检查脚本 | [可疑][未做] | 运行中需要快速判断真实连接、数据目录和依赖版本 |
| P1 | 工具结果统一合约 | [可疑][待优化] | 降低工具失败、警告、事实材料混淆 |
| P1 | Dashboard API 鉴权矩阵 | [可疑][待优化] | 防止敏感只读接口或写接口漏 admin，尤其是普通登录可读接口 |

## 建议下一步

1. 先补图集写接口权限定级和 regression：普通 token 403，admin token 200。
2. 再补用户消息图片/语音 URL guard regression，覆盖 localhost、内网、DNS 到内网和跳转到内网。
3. 新增独立 `test:regression`，把已经修复的图片链路断言、Agent 空回复、日报失败 cooldown、TTS voiceclone 模型选择迁进去。
4. 写 Dashboard API 鉴权矩阵，把普通登录可读接口逐个定级。
5. 写一份数据 key 契约，先覆盖会话、图片、记忆、Agent 结果。
6. 增加只读运行态健康检查脚本，只报告状态，不启动、重启、清理或写文件。
7. 补日志/工具输出 redactor，并把 Dashboard Agent localStorage 历史改成可控策略。
8. 后续再做上传请求体上限一致性、Dashboard smoke 分层和大文件拆分。
