# 表达学习候选池详细设计

## 模块契约（落地时遵循）

```
MODULE: 表达学习候选池（暂缓启用）
职责: 离线扫描已落盘的群聊缓存，抽出 situation×style 骨架候选，
      经审核后供 chat-prompt-builder 在合适人格/场景下注入参考。
边界: 只读 today-cache 与 daily-stats，不监听 session、不拦 middleware、
      不写人格文件、不直接修改 chat 主链路 messages。
状态: data/expression-pool/<channelKey>.json + 内存 lastUsedAt 索引。
```

## 状态

- v1 已落地：[expression-learner.js](../packages/koishi-plugin-dongxuelian-ai/lib/expression-learner.js) 上线**学习侧硬过滤纯函数**。给一段 today-cache 风格的消息列表，返回过滤后的 `kept` 与按原因聚合的 `skipped` 计数。
- v2.1 已落地：[expression-pool-store.js](../packages/koishi-plugin-dongxuelian-ai/lib/expression-pool-store.js) 提供候选池落盘、相似度合并、按贡献者归档、文件大小保护与 channel 隔离。
- v2.2 已落地：[expression-abstractor.js](../packages/koishi-plugin-dongxuelian-ai/lib/expression-abstractor.js) + [index.js](../packages/koishi-plugin-dongxuelian-ai/lib/index.js) 每日 23:55 旁路收割。当前实现读取 `today-cache-<channelKey>.json`，经过 v1 硬过滤后调用轻量模型抽象 situation/style，再写入 v2.1 候选池。**daily-stats 6 天冷启动尚未接入**，后续如果需要再单独补。
- v2.3 已收口：[expression-shadow-router.js](../packages/koishi-plugin-dongxuelian-ai/lib/expression-shadow-router.js) + [chat.js](../packages/koishi-plugin-dongxuelian-ai/lib/chat.js) 在模型调用前生成**影子注入诊断日志**。它只读取池子、计算如果 v2.4 启用会挑哪些候选，然后 `logDebug(ctx, 'expression-pool', ...)` 记录；**不改 messages、不写 prompt、不写 lastUsedAt、不改变用户可见回复**。

## 核心目标

让 Bot 听起来像在群里待过一段时间，但不学坏、不串人格、不让群友觉得"它在偷我的话"。

候选池里存的不是原话，是**句式骨架（style） + 这骨架适用的场景（situation）**。回复时偶尔挑一条骨架，作为参考材料注入主 prompt，主模型仍按人格说话，骨架是借来的语言模具，不是替换。

## 数据源：复用现有磁盘资产

不另起观察队列。学习器是纯离线扫描器，数据全部来自已有文件：

- `data/today-cache-<channelKey>.json` —— `saveSharedChannelTurn` 落盘的当日群消息，已含 `userId / ts / content / messageId / mentionUserIds`，content 已经过 `normalizeText`
- `data/daily-stats-*.json` —— 保留 6 天的历史，计划中可作为冷启动原料；当前 v2.2 暂未读取它，避免第一版 harvest 面太大

**可学群范围**：与 `summary-whitelist.json` 一致。`today-cache` 只对白名单群落盘，学习器自动继承这层授权，不需要再加开关。

## 候选数据结构（精简版）

```js
{
  id,
  situation,        // ≤20字，"什么场合"，不含具体话题词
  style,            // ≤20字，句式骨架，内容词换占位
  count,            // 相似度合并次数（≥0.75 视为同一条）
  contributors,     // [userId]，去重，用于"原作者在场降权"
  channelKey,       // 跨群隔离
  status,           // 'candidate' | 'reviewed' | 'archived'
  createdAt,
  lastUsedAt        // 单条冷却用
}
```

早期版本的 `allowedPersonas / blockedPersonas / moodTags / riskTags / styleStrength / scope / examples / meaning / expiresAt / positiveFeedback / negativeFeedback` 全部砍掉。OOC 防护放在人格端单点开关，不在每条候选上打标签。

## 人格表达策略（精简版）

每个人格在 plan 里声明一项：

```js
{ expressionPolicy: { injectionMode: 'on' | 'abstract' | 'off' } }
```

- 椿、东雪莲：`on`（注入具体骨架）
- 爱弥斯：`abstract`（只给"借鉴一种调侃句式"的抽象提示，不给原骨架）
- 长离、特蕾西娅：`off`（**不查池**，整条流水线对它们不存在）

## 学习侧硬过滤（按从源头到入池顺序）

学习器扫 `today-cache` 时逐条过：

1. **跳过 SELF**：bot 自己发的不学
2. **跳过含 `[图片]/[表情包]/at bot 昵称` 的消息**
3. **跳过敏感词命中**：复用 `SENSITIVE_KEYWORDS_RE`（与 [repeat.js](../packages/koishi-plugin-dongxuelian-ai/lib/repeat.js) 入口同源）
4. **跳过复读窗口**：与 [repeat.js:146](../packages/koishi-plugin-dongxuelian-ai/lib/repeat.js#L146) `checkGroupRepeat` 对齐——120 秒内同一 normalized text 被 ≥2 个不同 userId 说过，则该 key 在窗口内的所有消息全部跳过
5. **跳过敏感话题窗口**：5 分钟内出现"住院/去世/分手/抑郁"等关键词，整窗口学习暂停
6. **AI 自审**：小模型抽 situation/style 时，4 项硬要求——匹配场合 / 口语化 / 泛用性 / 不含具体人名

## 抽象与合并

抽够阈值（同 channel ≥ 10 条剩余消息）调一次小模型，让它产出：
- situation：≤20 字概括"什么场合"，不要原话
- style：≤20 字骨架，把内容词换成占位符（如 `按 X 发工资` / `典中典 X 现场`）

写入候选池前与池中已有条目做相似度对比，≥0.75 视为同一条，`count++`，`contributors` 并集，不创建新条目。

只有 `count ≥ 2` 的候选才算"够格备用"——确保是群体共识，不是某人口癖。

## 使用侧硬过滤

bot 准备回复时，按顺序过：

1. `injectionMode === 'off'` → 不查池
2. 当前会话上方处于敏感话题窗口 → 注入整体跳过
3. 该 channel 候选总数 < 10 → 跳过（冷启动门槛）
4. 调小模型从 `count ≥ 2` 的候选里挑 0–3 条，问"当前消息是什么场合，哪些 situation 匹配"
5. 挑出来的候选再过：
   - `now - lastUsedAt < 10 分钟` → 跳过（单条冷却）
   - `contributors` 中任一 userId 在过去 5 分钟发过言 → 跳过（**原作者在场降权**）
   - `now - createdAt < 24 小时` → 跳过（新表达延迟，给审核留窗）
6. 剩下的塞进 prompt 给主模型："本轮可参考以下骨架，但要换内容、契合人格"
7. 主模型回复后更新该条 `lastUsedAt`

## 注入路径

不新建跟 chat 平行的回复路径。在 [chat-prompt-builder.js](../packages/koishi-plugin-dongxuelian-ai/lib/chat-prompt-builder.js) 出 messages 的过程中，多插一个 system message 节点："本轮表达学习参考骨架："+候选若干。

人格 prompt、lore 注入、记忆注入全部不变，候选池注入是可选追加项。

## 运维通道

- **管理员擦除**：`expr.wipe <channelKey>` 清掉某群的全部 candidate / reviewed
- **"别学我说话"识别**：消息命中 `别学我说话 / 不要学我 / stop learning me` 关键词 → 把发话者最近 30 天 `contributors` 含其 userId 的条目全部 `archived`
- **审核通道**：Dashboard 提供 candidate → reviewed / archived 的人工 review 列表

## 明确不做

- 不自动改人格文件
- 不把用户口癖默认变 Bot 口癖
- 不跨群污染（A 群 reviewed 不进 B 群）
- 不学命令、token、日志、工具输出
- 不学越狱模板、攻击性表达、隐私信息、真实身份猜测
- 未 reviewed 不进 prompt
- 不监听 session（学习器纯离线）

## v1 已落地：怎么做的

### 选定的最小施工面

把"学习侧硬过滤"切成一个独立的纯函数模块，理由：

- 这层在整条流水线里风险最低、最可独立测——它**不需要小模型、不需要写盘、不需要改 chat 主链路**，错了顶多是少筛了几条/多筛了几条候选，不会让 bot 漏话或乱说话。
- 这层落地后，未来上抽象/合并/注入步骤时，输入数据已经是"安全清洗过的列表"，链路上游可以集中精力在"如何抽象 / 如何挑骨架 / 如何注入"，而不是反复复查"会不会把脏话/at bot/复读句子学进去"。
- 符合《AI协作规则》第二节关于模块大小、独立模块、不冲击主链路的硬约束。

明确**不做**的：候选池落盘、situation/style 抽象（小模型抽取）、相似度合并、`lastUsedAt` 冷却、注入 chat-prompt-builder、`expr.wipe`/Dashboard 审核、人格 `expressionPolicy` 字段。这些是 v2/v3 的事。

### 模块边界（与本设计契约对齐）

```
MODULE: 表达学习候选池 v1（学习侧硬过滤）
职责: 接收一段 today-cache 风格的群消息列表，按硬过滤规则筛掉不该被学习的条目，
      返回保留消息和按原因聚合的丢弃统计。
边界: 纯函数；不读写文件、不访问模型、不发送消息、不持有模块级状态、不修改传入数组。
状态: 无。
```

### 函数契约

入口：

```js
const { filterExpressionLearningMessages } = require('./expression-learner')
const { kept, skipped, total } = filterExpressionLearningMessages(messages, options)
```

`messages`：与 `today-cache-<channelKey>.json` 里 `messages[]` 同形——`{ userId, content, ts, messageId, mentionUserIds, role? }`。
`options`：`{ selfUserIds, botUserIds, botName, repeatWindowMs?, repeatMinUsers?, sensitiveTopicWindowMs? }`，全部可省。
返回：`{ kept: 过滤后消息[], skipped: { 原因 -> 被跳过条数 }, total: 输入条数 }`。

`skipped` 的原因 key 全部从 `EXPRESSION_LEARNER_SKIP_REASONS` 导出，不写魔法字符串。当前覆盖：

| 原因 | 触发条件 |
| --- | --- |
| `selfBot` | `role === 'assistant'` 或 `userId` 命中 `selfUserIds`/`bot` 等 token |
| `emptyText` | `normalize` 后空串 |
| `hasImageOrEmoji` | 命中 `[图片]/[表情包]/<image>/<face>/[CQ:image…]` 等 |
| `mentionsBot` | `mentionUserIds` 命中 `botUserIds`，或文本里出现 `@<botName>` |
| `sensitiveKeyword` | 命中 [constants.js:132](../packages/koishi-plugin-dongxuelian-ai/lib/constants.js#L132) 的 `SENSITIVE_KEYWORDS_RE` |
| `repeatWindow` | 与 [repeat.js:146](../packages/koishi-plugin-dongxuelian-ai/lib/repeat.js#L146) 对齐：默认 120 秒、≥2 个不同 `userId` 说同一 normalized text，整个窗口内的同文本消息都跳过 |
| `sensitiveTopicWindow` | 5 分钟窗内出现 `住院/去世/过世/死了/分手/离婚/抑郁/自杀/癌症/重病/葬礼` 任一关键词，整窗口跳过 |

### 复用了哪些既有零件

- `SENSITIVE_KEYWORDS_RE` 直接从 `constants.js` 引入，不复制不重写——保持与 chat-prompt-builder 政治敏感判定**同源**。
- 对内部所有文本统一走 `String(value).replace(/\s+/g, ' ').trim()`，与 [message-reader.js:63](../packages/koishi-plugin-dongxuelian-ai/lib/message-reader.js#L63) 的 `normalizeText` 行为一致。
- 复读窗口阈值与 [repeat.js](../packages/koishi-plugin-dongxuelian-ai/lib/repeat.js) 的 `REPEAT_MATCH_WINDOW_MS = 120000` / "≥2 个不同 userId" 严格一致——**学习侧不再额外发明阈值**，避免日后维护时两边阈值漂移。

### 为什么没有 cascade scenario 测试

`测试文件维护指南` 要求"行为变更优先加 scenario"。v1 不改任何用户可见行为（不发送消息、不改 prompt、不写池），所以走单元断言更直接。在 [cascade-test.js](../packages/koishi-plugin-dongxuelian-ai/test/cascade-test.js) 的 modPaths / expectedExports / syntaxFiles / duplicateScanFiles 四处登记，并在 affect-router 单元断言段后加了 9 条断言：

- 6 类硬过滤触发各 ≥1 条
- `kept` 必须包含跨窗口的中性聊天
- `kept` 必须不泄漏复读句和敏感话题窗口内的内容
- 空数组输入时 `total/kept/skipped.*` 全部归零

进入 v2（写池/抽象）时，再补 scenario。

### v2 起步怎么接上的

另一个 AI 已经把 v2 接到了"旁路可观测"阶段：候选池落盘前先调 `filterExpressionLearningMessages` 喂今日 `today-cache` 消息列表，把 `kept` 交给抽象阶段，把抽象出的 `{ situation, style }` 写入候选池。当前版本为了稳，没有同时接 `daily-stats` 6 天历史；这个冷启动扩展可以等 v2.3 日志质量稳定后再补。

## v2 计划：旁路诊断（v2.1–v2.3）

### 总体策略：纯旁路，先看日志再决定要不要真注入

v2.1–v2.3 上线之后，bot 对外行为**完全不变**——

- v2.1（候选池落盘）：写一份 `data/expression-pool/<channelKey>.json`，没人读，只是保留下来给后面用。
- v2.2（抽象 + 调度）：每日 23:55（CST）跑一次小模型抽 situation/style，把结果写进 v2.1 的池子。**不改主链路、不发消息、不阻塞 chat。**
- v2.3（旁路注入）：bot 准备回复时，按使用侧硬过滤挑出 0–3 条候选骨架，**只打日志，不进真 prompt**。这样能完整看到"如果当时真的注入了，会注入什么、被哪些规则筛掉了"。

整条 v2 都不会改用户可见行为；真正接进 prompt（也就是设计文档里"使用侧硬过滤 第 6 步"）放到 v2.4，等读完几天 v2.3 的日志、确认骨架质量稳定再说。

### v2.1：候选池落盘层（expression-pool-store.js）

**模块边界**

```
MODULE: 表达学习候选池 v2.1（落盘层）
职责: 提供 channel 隔离的候选池读写——load / append / merge / archive。
      存原始候选（每条 = situation + style + contributors + count + lastUsedAt 等）。
边界: 纯存储；不调模型、不读 today-cache、不发送消息、不被 chat 主链路 require。
状态: data/expression-pool/<safeChannelKey>.json，原子写。内存侧只有写队列，无长寿命缓存。
```

**导出 API**

```js
const {
  EXPRESSION_POOL_STORE_VERSION,
  loadExpressionPool,           // (channelKey) -> { entries: [], updatedAt }
  appendExpressionCandidate,    // (channelKey, candidate) -> { mode: 'created'|'merged'|'rejected', entry }
  archiveByContributor,         // (channelKey, userId) -> { archived: number }
  computeSituationStyleSimilarity, // (a, b) -> number 0..1
  EXPRESSION_POOL_SIMILARITY_MERGE_THRESHOLD, // 0.75
  EXPRESSION_POOL_MAX_ENTRIES_PER_CHANNEL,    // 500（防文件膨胀）
  EXPRESSION_POOL_MIN_USE_COUNT,              // 2（≥2 才算"够格"）
} = require('./expression-pool-store')
```

**候选条目 schema（精简版，与设计文档"候选数据结构"一致）**

```js
{
  id,                  // sha256(channelKey + situation + style).slice(0,16)
  channelKey,          // 跨群隔离写在 entry 上，校验用
  situation,           // ≤20 字
  style,               // ≤20 字
  count: 1,            // 合并次数
  contributors: [],    // userId 数组，去重，最多 50
  status: 'candidate', // candidate | reviewed | archived
  createdAt,
  lastUsedAt: 0,
  lastMergedAt: 0,
}
```

**合并规则**：调 `appendExpressionCandidate` 时，对 `entries` 里 `status !== 'archived'` 的条目逐条算相似度（situation 0.6 权 + style 0.4 权，按"分词后字符 jaccard"算），≥0.75 视为同一条 → `count++`、`contributors` 并集（截 50）、`lastMergedAt = now`、不新增。否则插入新条目；若条目数超 500，按 `count asc, lastMergedAt asc` 淘汰最弱的一条。

**文件路径与原子写**：

- 目录：`data/expression-pool/`，启动时 `fs.mkdirSync(..., { recursive: true })`。
- safeChannelKey = `String(key).replace(/[^a-zA-Z0-9._-]/g, '_')`（沿用 `safeChannelKey` 的同款规则）。
- 单文件大小上限：`EXPRESSION_POOL_MAX_FILE_BYTES = 1MB`，超阈用 `readJsonFileIfSmallSync({ unlinkOversize: true })` 直接清掉，与 user-profile 处理一致。
- 写入用 `writeJsonFile`（已有的 atomic rename）。

**风险护栏**：

- 模块**不被 chat.js / index.js 的 ready 钩子直接 require**，只被 v2.2 的 abstractor 调用——这样 v2.1 单独上线时确实"零运行时副作用"。
- 内存里不缓存 entries；每次 load/append 都直接读盘。落盘量小（每文件 ≤500 条）、写频低（每日定时一次），不需要长寿命缓存。

**cascade 接线**：

- modPaths / expectedExports（导出 7 个）/ syntaxFiles / duplicateScanFiles 四处登记。
- 单元断言：load 空文件返回空池；append 同一组 situation/style 触发 merge 而非新建；append 不同 situation 创建第二条；archiveByContributor 把命中的条目 status 标 archived 且 contributors 不再包含该 userId；safeChannelKey 把 `':'` `'/'` 替换掉，防止跨目录写。

### v2.2：抽象 + 每日定时收割（expression-abstractor.js + index.js scheduler）

**模块边界**

```
MODULE: 表达学习抽象 v2.2
职责: 喂"今日 today-cache"消息列表 → 经 v1 硬过滤 →
      调小模型抽 situation/style → 调 v2.1 store 写池。提供独立的 runHarvestForChannel 入口。
边界: 不改 chat 主链路，不监听 session；只在 ready 钩子里被定时器调用。
      小模型失败 / 无 key 全部静默吞错。
状态: 模块级只有 `lastHarvestAt: Map<channelKey, number>`，给观测用。
```

**调度位置**：放在 `index.js` 的 `ctx.on('ready')` 钩子里，紧跟在 `scheduleDailyStatsCleanup(ctx)` 后面新建 `scheduleExpressionHarvest(ctx)`，结构与 daily cleanup 一比一对照——

```js
function scheduleExpressionHarvest(ctx) {
  const run = async () => {
    try {
      const result = await runExpressionHarvestForAllChannels(ctx)
      logDebug(ctx, 'expression-pool', `harvest channels=${result.channels} kept=${result.totalKept} merged=${result.merged} created=${result.created}`)
    } catch (error) {
      ctx.logger('dongxuelian-ai').warn(`expression harvest failed: ${error.message}`)
    } finally {
      expressionHarvestTimer = setTimeout(run, getNextShanghaiMidnightDelayMs(Date.now() - 5 * 60 * 1000))
      if (expressionHarvestTimer && typeof expressionHarvestTimer.unref === 'function') expressionHarvestTimer.unref()
    }
  }
  expressionHarvestTimer = setTimeout(run, getNextShanghaiMidnightDelayMs(Date.now() - 5 * 60 * 1000))
  if (expressionHarvestTimer && typeof expressionHarvestTimer.unref === 'function') expressionHarvestTimer.unref()
}
```

**为什么 23:55 跑而不是 0:00**：`cleanupDailyStatsFiles` 在每日 0:00 触发，会按 `STATS_FILE_RETENTION_DAYS = 6` 把超龄 today-cache 删掉。把 harvest 提前 5 分钟，能保证当日数据还在盘上、刚刚新一天的 cleanup 不会把它带走。`getNextShanghaiMidnightDelayMs(now - 5min)` 复用现成函数，不自己造时区数学。

**遍历群范围**：扫 `DATA_DIR` 下 `today-cache-*.json` 文件名 → safeKey → 反查 summary-whitelist 是否仍授权。当前只读已落盘 today-cache；如果某群当天没落盘或不足 5 条通过硬过滤的消息，当天不会调用抽象模型。

**小模型选择**：复用 `analyzeChannelSensitive` 的 fallback 链——

```js
const harvestModels = [
  { provider: 'glm', model: 'glm-4.6v-flash', keyFile: GLM_KEY_FILE },
  { provider: 'dashscope', model: 'qwen-turbo', keyFile: DASHSCOPE_KEY_FILE },
  { provider: 'opencode', model: 'deepseek-v4-flash', keyFile: null },
]
```

带 `_fallbackSet: 'lightweight'`、`max_tokens: 200`、`try{}catch{}` 静默。

**抽象 prompt 硬要求**（作为 4 项 AI 自审，与设计正文一致）：

1. 给定一段 5–15 条群聊原文（已经过 v1 硬过滤），返回 JSON 数组（最多 5 条），每条含 `{ situation, style }`。
2. situation ≤20 字，描述"什么场合"，禁止包含具体话题词、人名、时间。
3. style ≤20 字，把内容词换占位（X / 某 / 这）。
4. 不能出现真名；如果原句无明显规律就返回空数组。

**JSON 解析失败 / 长度超限**：直接丢弃这一批，记 debug 日志，不写池。**不重试、不报警、不阻塞**。

**写池**：每条抽象结果调一次 `appendExpressionCandidate`。返回的 `mode = created/merged/rejected` 计入诊断日志聚合。

**风险护栏**：

- 整个 harvest 是 `try/catch` 包死的，模块级错误不传出 `run` 闭包。
- `runHarvestForChannel` 单次 `Promise.race(timeout=15s)` 兜底，避免某个 channel 阻塞别人。
- 不记原话到日志（只记 `kept=`/`created=` 数字），避免敏感语料漂到运维通道。

**cascade 接线**：modPaths（abstractor）/ expectedExports / syntaxFiles / duplicateScanFiles 四处登记 + 单元断言（不真调模型，注入 mock client，验证：硬过滤 0 条时直接返回 `{ channels:1, totalKept:0 }`；JSON 解析失败时不写池；正常路径调用 `appendExpressionCandidate`）。

### v2.3：旁路诊断路由（expression-shadow-router.js + chat.js 接点）

**模块边界**

```
MODULE: 表达学习旁路路由 v2.3
职责: chat 准备回复前，按使用侧硬过滤挑 0–3 条骨架；返回诊断对象（plan + skipped reasons）。
      调用方拿到诊断对象后只打 logDebug('expression-pool', ...)，不写真 system message。
边界: 纯函数（除了读 expression-pool-store）；不调模型、不发消息、不修改 messages 数组。
状态: 无。
```

**入口签名**

```js
const {
  buildExpressionShadowPlan,    // (input) -> diagnostic
  formatExpressionShadowDiagnostic,
  EXPRESSION_SHADOW_VERSION,
  EXPRESSION_SHADOW_SKIP_REASONS, // injectionOff / poolEmpty / coldStart / lowCount / cooldownPerEntry / contributorActive / freshCandidate / sensitiveTopicWindow
} = require('./expression-shadow-router')
```

`input`：`{ channelKey, personaName, cleanInput, recentSpeakerIds, sensitiveTopicActive, now }`，其中 `recentSpeakerIds` 是过去 5 分钟在该 channel 发言的 userId 数组（chat.js 拿 channelSharedCache 派生）。

`diagnostic` 形状（参考 reply-timing 的诊断对象）：

```js
{
  version: 1,
  decision: 'shadow_inject' | 'silent',
  channelHash: '<sha256-12>',
  personaHash: '<sha256-12>',
  injectionMode: 'on' | 'abstract' | 'off',
  poolSize: number,
  candidatesConsidered: number,
  candidatesPicked: number,
  pickedHashes: ['<sha256-12>', ...],   // 命中的骨架 id 哈希；不暴露原文
  skipped: { injectionOff: 0, poolEmpty: 0, coldStart: 0, lowCount: 0, cooldownPerEntry: 0, contributorActive: 0, freshCandidate: 0, sensitiveTopicWindow: 0 },
  reasons: [],   // ['cold_start', 'persona_off' …]
}
```

**使用侧硬过滤**（与设计正文"使用侧硬过滤 1–6 步"对齐）：

1. `injectionMode === 'off'` → `silent` + `injectionOff++`。
2. `sensitiveTopicActive` → `silent` + `sensitiveTopicWindow++`（chat 这边用 v1 的 `EXPRESSION_LEARNER_SENSITIVE_TOPIC_KEYWORDS` 做最近 5 分钟扫描得出）。
3. `poolSize < 10` → `silent` + `coldStart++`。
4. 拿 `count >= 2` 的子集（其余 `lowCount++`）。
5. 逐条过：`now - lastUsedAt < 10min` → `cooldownPerEntry`；`contributors ∩ recentSpeakerIds ≠ ∅` → `contributorActive`；`now - createdAt < 24h` → `freshCandidate`。
6. 剩余里随机或按 `count desc` 取 0–3 条。

**诊断输出文本**（`formatExpressionShadowDiagnostic` 返回单行字符串，与 reply-timing/affect-router 风格一致，所有原文都不进日志，只用 sha256 短哈希）：

```
decision=shadow_inject channel=<hash> persona=<hash> mode=on pool=23 considered=6 picked=2 picked_hashes=ab12...,cd34... skipped=injectionOff:0,poolEmpty:0,coldStart:0,lowCount:1,cooldownPerEntry:1,contributorActive:1,freshCandidate:1,sensitiveTopicWindow:0 reasons=will_inject_if_v24
```

**chat.js 接点**：在 [chat.js](../packages/koishi-plugin-dongxuelian-ai/lib/chat.js) `callOpenAI` 之前（即 [chat.js:879](../packages/koishi-plugin-dongxuelian-ai/lib/chat.js#L879) 那行之前）插一段 try/catch：

```js
try {
  const expressionShadow = buildExpressionShadowPlan({
    channelKey,
    personaName,
    cleanInput,
    recentSpeakerIds: getRecentSpeakerIdsFromChannelCache(channelKey),
    sensitiveTopicActive: detectSensitiveTopicActive(channelKey),
    now: Date.now(),
  })
  logDebug(ctx, 'expression-pool', formatExpressionShadowDiagnostic(expressionShadow))
} catch (error) {
  logDebug(ctx, 'expression-pool', `shadow_failed ${error && error.message ? error.message : String(error)}`)
}
```

**严格不做的**：

- 不在这次 messages 里 push 任何 system message。
- 不更新 `lastUsedAt`（毕竟没真用）。
- 不让任何分支抛错传到主链路；任何 try/catch 里的失败只打 debug 日志。

**cascade 接线**：modPaths / expectedExports / syntaxFiles / duplicateScanFiles 四处登记 + 单元断言（注入空池 → coldStart；mode=off → injectionOff；正常分支挑出 1–3 条骨架；contributors 与 recentSpeakerIds 重合时该条被剔；diagnostic 字符串里不含原文 situation/style 字段）。

### 不做的事（明确划线）

- 不接 Dashboard / 不写 `expr.wipe` 命令——v2.3 还没"reviewed"概念，没必要先建审核 UI。

- 不动人格文件（`expressionPolicy` 字段以默认值兜底：东雪莲/椿/默认 = `on`，其他 = `off`，全部硬编码在 expression-shadow-router 里，不进 plan）。

### 如何读日志、出问题怎么排查

整条流水线的所有调试输出都走 `logDebug(ctx, 'expression-pool', ...)`，可在 `data/debug-log-config.json` 里把 `modules['expression-pool'] = true` 单独打开，**不影响 reply-timing/affect-router 等其他通道**。

**第一类日志：每日 harvest 摘要**（每天 23:55 一行）

```
[D] [expression-pool] harvest channels=3 totalKept=42 created=5 merged=2 rejected=0
```

排查："今天某群没产生候选" → 看汇总行：`totalKept=0` 多半是 v1 全过滤掉了或 today-cache 没落盘；`abstract_failed>0` 是小模型返回非 JSON/空数组；`created/merged` 全 0 说明没有写入可用候选。

**第二类日志：每次回复前的旁路决策**（每次发言决定要不要回复时一行）

```
[D] [expression-pool] decision=silent channel=ab12.. persona=cd34.. mode=on pool=23 considered=6 picked=0 skipped=...,coldStart:0,...,freshCandidate:3 reasons=cold_window_blocks_all
```

排查："为什么 v2.4 真接进 prompt 后还是不注入" → 提前看这行：picked=0 + freshCandidate=3 表示候选都太新（<24h），需要等老化。picked=2 但 contributorActive=1 表示原作者在线，按规矩剔了。

**第三类日志：异常 / 兜底**（出错才打）

```
[D] [expression-pool] shadow_failed pool file json parse error
[D] [expression-pool] harvest_failed channel=<hash> abstract_timeout
```

排查："chat 突然变慢/报错" → 不会，因为 v2.3 全 try/catch 静默，只看 debug 日志。

**直接读池子文件**：

- 路径 `data/expression-pool/<safeChannelKey>.json`，结构 `{ entries: [...], updatedAt }`。
- 想 wipe 某群：`rm data/expression-pool/<safeChannelKey>.json` 即可（v2.3 不缓存，下次 harvest 会重新生成）。
- 想看哪些骨架已经"够格备用"：`jq '.entries[] | select(.count >= 2)' <文件>`。

**v2.4（仍然待做，作为 v2.3 看够日志后的下一步）**：

- 先连续观察 2-3 天 `expression-pool` 日志，确认 shadow 决策里 `picked>0` 的骨架质量、人格 mode、冷启动/原作者在场/新候选窗口的跳过原因都符合预期。
- 把 v2.3 的 `expressionShadow.candidatesPicked` 真接进 chat-prompt-builder，新建 `createChatPromptExpressionSkeletonMessage(picks)`。
- 读后写回 `lastUsedAt`（这一步**必须配 channel/persona 白名单，灰度上线**）。
- 加 `expr.wipe <channelKey>`、`别学我说话` 触发 `archiveByContributor`。
- 接 Dashboard candidate → reviewed/archived 审核流程。
- 如日志显示候选不足，再补 v2.2 的 `daily-stats` 6 天冷启动读取；不要和真注入同一轮做，避免定位不清。
