## 已确认的真实问题

1. 回复分段过多是真实问题。线上日志多次出现 `parts=6/7/...`，源码在 `reply.js` 的 `sendReply()` 对回复调用 `splitSentences()` 后逐句发送；`conversation.js` 的 `saveConversationTurn()` 也按句拆 assistant 历史，可能强化碎片化。修复方向不能硬截断，应让模型学会 QQ 场景下自然少发，同时发送层只做防刷屏兜底。
2. 历史图片能力的设计存在，但线上没有形成可用图片历史。`index.js` 只在 image segment 有 http(s) URL 或正文可提取 http(s) 图片 URL 时调用 `storeImageUrl()`；`image-store.storeImageUrl()` 又要求 `url` 非空。QQ 本地/file-only 图片会被识别成 `hasVisual=true`，但不会入库，`enqueueAnalysis()` 随后找不到 entry 就退出。
3. `analyze_historical_image` 当前只返回“后台分析中”，不会等待分析结果用于当前轮回答；即使图片已入库，用户当下问“评价一下/看看图”也可能得不到图片内容。
4. 搜索/fetch 线上问题不能按本地改动解释。生产 HEAD 的 Agent 路由只覆盖显式搜索请求，`chat-tools` 里没有 `web_fetch`，搜索工具提示也较弱；本地未提交改动已做了部分优化，但没有部署，不代表线上已修。哈耶克案例日志显示走普通 chat，不是 Agent 搜索链路。
5. 上下文不是完全没保存，而是注入与过滤策略让模型容易接错目标。`getSharedContextNote()` 会过滤普通 assistant 消息，跨用户短追问看不到 bot 上一句；`<user>` 包装里昵称很醒目，裸“评价一下”容易把昵称当成评价对象。修复方向应是通用短句/指代解析与候选上下文排序，而不是硬编码“评价一下”。
6. ` ```html` 泄漏是真实问题。普通 chat 最终只 `sanitizeReply()` + `trimReply()`，没有统一过 `stripMarkdownForQQ()`；Agent 转述路径有去 Markdown，但 `stripMarkdownForQQ()` 本身也没有可靠移除 fenced code block 的逻辑。
7. “用户在质疑我 / 保持人设 / 我会调用 read_image_history 函数”等内部思考和工具计划泄漏是真实问题。现有 `isUnsafeThinkingReply()` 只覆盖部分“我应该回复/接话/吐槽”等模式，漏了“用户在质疑/用户现在是在/我需要解释/保持人设/我会调用 xxx 函数”等新型草稿。这个问题和逐句 `splitSentences()` 发送叠加后，会把内部草稿拆成多条发到群里。
